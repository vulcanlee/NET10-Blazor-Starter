# 系統例外紀錄

這一頁讓你**看系統自動收集的程式錯誤**，同一種錯誤會**合併成一列並累計次數**，方便找出最常發生、最新出現的問題，並**查看完整堆疊**。

> 這一頁只有管理員可以使用。

### 一分鐘看懂這一頁

- **解決什麼問題**：使用者回報「畫面出錯了」時，不必翻大量日誌，就能看到是哪一種錯誤、發生在哪一頁、已經發生幾次。
- **誰會用到**：系統管理員與負責維護程式的人員；一般使用者打開這一頁只會看到「你沒有權限存取此頁面」。
- **它在系統的哪個位置**：側邊選單「系統管理 › 統計與分析」底下，和日誌檢視、日誌等級設定是同一組排查工具。
- **開始前要準備**：大概知道出錯的時間、頁面或是哪位使用者遇到的，可以更快縮小範圍。
- **做完會得到**：每一種錯誤的最後發生時間、累計次數、發生頁面，以及可以交給開發人員的完整堆疊。
- **它不做什麼**：不是逐筆事件紀錄，不能用來數「今天發生了幾次錯誤」的明細；逐行的日誌請看日誌檢視，人員操作請看稽核紀錄。

## 一、功能摘要

- 依最後發生時間、來源、使用者帳號與關鍵字查詢例外。
- 按「查看」打開「例外明細」，看完整型別、日誌訊息樣板、首次發生時間與完整堆疊。
- 刪除單一列、清除 90 天未再發生的紀錄，或清空全部紀錄。
- 把目前查詢條件下的結果匯出成 CSV，最多 5,000 筆。

## 二、這個頁面在做什麼

這一頁是**聚合**的清單，不是逐筆事件：同一種錯誤再次發生時，不會新增一列，而是把那一列的「次數」加 1、更新「最後發生」時間。系統判斷「同一種錯誤」的依據是：例外類型、訊息、發生頁面與日誌訊息樣板四者都相同。所以同一個錯誤發生在兩個不同的頁面，會是兩列。

頁面上方的說明框寫著：「本頁收錄的是程式碼有記錄下來的例外，相同的例外會合併成一列並累加「次數」。少數刻意忽略的情況（例如使用者取消、正常關機）不會出現在這裡；完整的逐行日誌請由「日誌檢視」取得。」

錯誤是在背景寫入的，剛發生的錯誤可能要稍等片刻，再按「重新整理」才會出現。時間一律以伺服器本地時間記錄與顯示。

完整堆疊存在資料庫之外的檔案裡，只有在打開明細窗時才會讀取。清除或清空紀錄時，對應的堆疊檔案也會一起刪除。

## 三、畫面上有哪些按鈕、各自做什麼

### 查詢條件

| 條件 | 說明 |
|---|---|
| 「最後發生（起）」～「最後發生（迄）」 | 以每一列的最後發生時間篩選，可選到秒，只填一邊也可以 |
| 來源下拉（預設「來源：不限」） | 可選「畫面」「WebAPI」「系統啟動」「背景作業」「未知」 |
| 「使用者帳號」 | 輸入帳號的一部分即可 |
| 「關鍵字（類型／訊息／頁面／操作）」 | 比對例外類型、訊息、頁面與日誌訊息樣板 |

### 工具列按鈕

| 按鈕 | 做什麼 |
|---|---|
| 「查詢」 | 依上面的條件重新查詢，並回到第一頁 |
| 「重新整理」 | 用目前的條件重新查詢 |
| 「匯出目前查詢結果（CSV）」 | 把目前條件下的**全部**結果（不只當頁）下載成 CSV，最多 5,000 筆。查詢結果是 0 筆時按鈕會變灰 |
| 「清除 90 天未再發生的紀錄」 | 確認後刪除「最後發生」早於 90 天前的所有紀錄與其堆疊檔案，完成後顯示「已清除 N 筆紀錄。」或「沒有符合條件的紀錄。」 |
| 「清空全部紀錄」 | 確認後刪除所有紀錄與整個堆疊檔案目錄，完成後顯示「已清空全部例外紀錄」 |

CSV 的欄位依序是：最後發生、次數、例外類型、訊息、來源、頁面、操作、記錄器、使用者、首次發生。

### 清單欄位

| 欄位 | 意思 |
|---|---|
| 最後發生 | 這種錯誤最近一次發生的時間，預設最新的在最上面 |
| 次數 | **累計**發生幾次。10 次以上以橘色標示，100 次以上以紅色標示，可點標題依次數排序 |
| 類型 | 例外類型的簡短名稱，滑鼠移過去可看完整名稱 |
| 訊息 | 錯誤訊息 |
| 頁面 | 發生時所在的頁面或網址；沒有時顯示「—」 |
| 使用者 | 遇到錯誤的帳號；沒有時顯示「—」 |
| 操作 | 「查看」與「刪除」兩個按鈕 |

### 每一列的操作

| 按鈕 | 做什麼 |
|---|---|
| 「查看」 | 打開「例外明細」，列出例外類型、訊息、來源、頁面、操作（日誌訊息樣板）、記錄器、使用者、累計次數、首次發生、最後發生，下方是「完整堆疊」 |
| 「刪除」 | 跳出「刪除例外紀錄」確認窗：「確定要刪除這一列嗎？相同的例外若再次發生，會重新出現並從 1 次開始計算。」按「刪除」後顯示「刪除成功」 |

堆疊讀取中會顯示「讀取中…」。若顯示「堆疊檔案不存在（可能已被清除，或當初寫檔失敗）。完整日誌請改由「日誌檢視」查詢。」，代表只剩摘要資訊，請改到日誌檢視依時間查詢。

> **提醒**：明細窗裡的「操作（日誌訊息樣板）」**不是使用者按了什麼**，而是程式寫日誌時用的訊息樣板，裡面的大括號是還沒填入的參數，例如 `Name={CategoryName}`，而不是實際的名稱。刻意存樣板，是為了讓「同一種錯誤、不同參數值」合併成同一列。

> **提醒**：一列代表的是很多次發生，但「使用者」「來源」與「記錄器」記的是**第一次發生**時的資訊。清單上只寫一個帳號，不代表只有這個人遇到過。

> **提醒**：這一頁的刪除、清除與清空**不會**寫入稽核紀錄。

## 四、建議這樣操作，會得到什麼

### 情境一：使用者回報某一頁出錯

1. 「使用者帳號」輸入對方的帳號，「最後發生」選對方說的時間前後。
2. 按「查詢」，找到頁面相符的那一列，按「查看」。
3. 把例外類型、訊息、日誌訊息樣板與完整堆疊複製給開發人員。

會得到：足以重現與修正問題的完整資訊，也知道這個錯誤是不是早就出現過（看「首次發生」與「累計次數」）。

### 情境二：每週巡檢，找出最該優先處理的錯誤

1. 不設任何條件按「查詢」，點「次數」欄標題改成依次數排序。
2. 對次數特別多或顯示為紅色的列按「查看」，判斷是真正的問題還是可忽略的雜訊。

會得到：一份依影響程度排好的待處理清單。

### 情境三：修正上線後確認問題是否消失

1. 記下那一列的「累計次數」，或乾脆按「刪除」把它移除。
2. 過一段時間再查詢同樣條件。

會得到：若次數不再增加、或刪除後沒有重新出現，就代表修正有效；若重新出現，會從 1 次開始計算，「首次發生」就是修正之後第一次再犯的時間。

## 五、名詞解釋

| 名詞 | 白話解釋 |
|---|---|
| 例外 | 程式執行時遇到的錯誤狀況，例如資料庫連不上、找不到資料 |
| 聚合 | 相同的錯誤合併成一列並累計次數，而不是每發生一次就記一列 |
| 次數 | 這一列合併了幾次發生；和日誌檢視逐筆數出來的數量對不起來是正常的 |
| 來源 | 錯誤從哪裡發生：畫面操作、Web API 呼叫、系統啟動、背景作業，或無法判斷 |
| 日誌訊息樣板 | 程式寫日誌時用的句型，參數位置保留大括號，不是使用者的操作 |
| 記錄器 | 寫出這筆錯誤的程式模組名稱，給開發人員定位用 |
| 堆疊 | 錯誤發生當下程式的呼叫路徑，是開發人員除錯最需要的資訊 |

## 七、常見問題

**為什麼這裡的次數和日誌檢視裡數到的錯誤筆數對不起來？**
這一頁是聚合的，一列代表同一種錯誤的累計次數；日誌檢視是逐行紀錄。另外，少數刻意忽略的情況（例如使用者取消、正常關機）不會出現在這一頁。

**清單上有一列類型是「(其他)」，訊息說已達列數上限，是怎麼回事？**
為了避免資料庫被塞爆，不同種類的錯誤最多只保留 5,000 列。達到上限後，新出現的錯誤一律併入這一列累計。請用「清除 90 天未再發生的紀錄」或刪除不再需要的列，騰出空間後再觀察。

**我刪除了一列，為什麼它又出現了？**
代表這個錯誤又發生了。刪除只是移除目前的紀錄，同樣的錯誤再次發生時會重新建立一列，次數從 1 開始計算。
