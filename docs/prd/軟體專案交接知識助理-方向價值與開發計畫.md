## 1. 一頁摘要

**題目一句話**
一套裝在企業自己機器上的「專案交接知識助理」。它讀取專案的 git 歷史、既有文件與會議紀錄，讓接手維護的人問一句就得到**附出處**的答案；並在原開發者離開前，主動找出交接資料的缺口、逐題問他補齊。

**給誰**
有自建或委外開發軟體系統、而且人員會輪調或離職的企業與軟體公司。

**解什麼痛**
專案交接只有原始碼加原開發者的記憶。接手的人踩坑之後只能回頭問原開發者，有時原開發者還得親自出手修。公司為同一件事付了兩次錢，原開發者永遠脫不了身；原開發者離職後，那個系統就變成沒人敢動的黑盒子。

**怎麼收費（假設）**
軟體授權（買斷加年度維護，或年授權），按專案數或席次計。AI 模型費用由客戶自己的 Azure OpenAI／OpenAI 金鑰承擔，不經開發者之手。

**為什麼現在**
- MAF 1.0 已於 2026/4/3 正式發布，工作流、多代理協作、人機協作暫停與續跑、檢查點都已是穩定 API，不再是實驗品。
- 腳手架已具備 AI 呼叫的全部周邊（計費、配額、對話紀錄、提示詞版本、安全渲染、排程、稽核、權限、操作說明），第一版可以把力氣全放在核心功能上。
- 開發者本人就是第一個使用者，手上有真實專案可以當首個案例。

## 2. 問題與對象

### 2.1 目標客戶

- 有自己開發或委外開發的業務系統，而且這些系統要長期維護的企業。
- 軟體公司或資訊部門，專案做完要移交給維護團隊。
- 人員會輪調、離職、或外包人員合約到期就走的團隊。

共通點：**系統比人活得久，但知識跟著人走。**

### 2.2 痛點敘事（來自開發者親身經驗）

1. 專案完成後要交接給別人維護。
2. 交接時能給的只有原始碼，加上原開發者回憶「當時做了什麼」。沒有足夠的、可以事後補充的資料。
3. 接手的人三個月後踩到坑，回頭來問原開發者。有時原開發者還得親自出手解決。
4. 公司付了兩次錢：接手者摸索的時間，加上原開發者被打斷的時間。
5. 原開發者離職後，沒人可問，系統變成黑盒子，沒人敢改。

### 2.3 接手者真正會問的三類問題

| 類型 | 例子 | 答案通常藏在哪裡 |
|---|---|---|
| 以前的決定是什麼 | 「訂單為什麼要先鎖庫存再扣款？」 | 會議紀錄、群組對話、issue 討論 |
| 這段程式為什麼這樣寫 | 「這個 retry 為什麼是 3 次、間隔 5 秒？」 | git 歷史、commit 訊息、當時的會議決定 |
| 怎麼部署、設定、跑起來 | 「正式機的設定檔在哪？排程要怎麼啟動？」 | README、設定檔、CI 腳本、原開發者的腦袋 |

這三類的共通點是：**答案早就存在，只是散在不同地方，而且沒有人把它們串起來。**
注意：接手者**不會問**「客戶當初要什麼」，所以第一版不處理需求層的知識。

## 3. 價值主張與投資效益

### 3.1 對三種角色的價值

**對接手者**
第一天問第一題就能得到有出處的答案，例如：「2026/3/12 的會議決定先鎖庫存，因為客戶反映超賣；對應 commit abc123」。不用翻信、翻群組、翻半天 git log。

**對原開發者**
離開前不用寫一份永遠寫不完的交接文件。系統先把 git、文件、會議全讀完，**只拿它答不出來的那十幾題來問他**。他回答完，系統把交接文件收尾。離開後被打擾的次數明顯下降。

**對老闆**
一個儀表板看得到：這個月系統幫接手者回答了幾題、幾題附了出處、原開發者少被打擾幾次、哪些專案只剩一個人懂（離職風險清單）。知識留在公司，不跟著人走。

### 3.2 可量化指標（第一版就要能自己算出來）

| 指標 | 意義 |
|---|---|
| 問答題數 | 系統被依賴的程度 |
| 附出處比例 | 答案可信度；目標是「無出處即拒答」 |
| 使用者確認「答案正確」的比例 | 品質 |
| 原開發者被 @ 的次數（手動登記或估算） | 省下的打擾 |
| 每個專案「懂的人」數量 | 離職風險，單人專案列紅色 |
| 交接盤點產出的缺口題數與補齊題數 | 交接完整度 |

### 3.3 五條「做了也白做」的條件，與對應的設計決定

這五條是開發者自己列出的失敗條件，每個功能都要過這五關。

| 失敗條件 | 設計決定 |
|---|---|
| 客戶不需要 | 第一版只解上面三類被親身驗證過的問題，不加想像出來的功能。 |
| 太貴 | 客戶自帶 Azure OpenAI／OpenAI 金鑰，開發者只收軟體授權，不承擔 token 費用。 |
| 看不到投資效益 | 效益儀表板內建，不是加購。每次問答、每個出處都是可統計的事件。 |
| 感受不到好處 | 匯入 git 之後第一題就要有附出處的答案。git 歷史本身就是資料，不需要等資料累積。 |
| 要改變日常作法 | 系統只讀已經存在的東西（git、既有文件、既有會議紀錄），不要求任何人多寫一個字。原開發者唯一要做的是回答系統問他的問題。 |

## 4. 產品範圍（第一版）

第一版兩面都做：**接手者問答**與**交接盤點流程**。兩者共用同一套知識來源與索引。

### 4.1 接手者問答

**知識來源（第一版）**
- git：本機 clone 的 repository（commit 訊息、diff、blame、tag、分支）。
- 文件：指定資料夾內的 Markdown、文字檔、PDF、Word。
- 會議紀錄：從開發者既有的會議紀錄系統匯出的檔案（格式由開發者自己定義，兩套系統同一腳手架，格式可控）。

**互動**
- 使用者選一個專案，用自然語言問問題。
- 回答固定格式：結論、依據（逐條列出出處：會議日期與段落、commit 編號與檔案、文件檔名與章節）、信心說明。
- 找不到出處時明確說「沒有找到依據」，不編答案。
- 使用者可以按「這答案正確」或「不對，應該是……」。確認過的問答沉澱成該專案的記憶，下次相同問題直接命中。

**第一天的體驗**
匯入 git 之後，不用等任何其他來源，就能回答「這段為什麼這樣寫」與「最近誰改了什麼」。

### 4.2 交接盤點流程

**觸發**：管理者或原開發者對某專案按「開始交接盤點」。

**步驟**
1. 系統讀完該專案所有來源。
2. 產出交接文件草稿（固定章節：系統概觀、架構與主要模組、部署與設定、重要決定與原因、已知問題與坑、未完成事項、聯絡人）。
3. 列出缺口清單：每一章裡「來源中找不到答案」的項目，轉成具體問題（例如「正式環境的排程啟動方式沒有任何文件記載，請描述」）。
4. 逐題問原開發者。原開發者可以今天答三題、下週再答五題，流程狀態會保存，不會因為重開機或關瀏覽器就消失。
5. 全部回答完（或原開發者按「其餘略過」）後，系統把答案併回文件，產出 Markdown 與 PDF。
6. 原開發者的回答同時進入知識庫，接手者之後問到同一件事會直接引用。

**第一版的限制**：一次只處理一個專案；問題由系統產生，不支援管理者手動加題（列入第二版）。

### 4.3 管理面

- 專案清單：每個專案的來源、索引狀態、最後更新時間、懂的人數。
- 索引作業：手動「立即重建」與定期排程。
- 效益儀表板：第 3.2 節的指標。
- AI 配額：沿用腳手架既有的每日／每月新台幣上限。

### 4.4 非目標（第一版明確不做）

- 把系統對外開成 MCP 伺服器、IDE 整合（VS Code、Copilot、Claude Code 內直接問）。這是第二版最有吸引力的延伸，先不做。
- GitHub、Azure DevOps、GitLab 線上整合（issue、PR、pipeline）。第一版只讀本機 clone。
- 待辦追蹤代理（見第 10 章）。
- 多模型供應商切換（第一版只有 Azure OpenAI 與 OpenAI）。
- 多租戶 SaaS。第一版就是單一企業自架。

## 5. MAF 在這裡的角色

### 5.1 四個亮點，各對應一個產品功能

| MAF 能力（皆為 1.0 穩定 API） | 產品功能 | 客戶看到的價值 |
|---|---|---|
| 工作流的 human-in-the-loop（`RequestInfoExecutor`）＋ superstep checkpoint | 交接盤點流程的「逐題問原開發者、可跨日暫停續跑」 | 原開發者不用寫文件，只回答系統問他的題 |
| 多代理 concurrent 協作（fan-out／fan-in） | 程式碼代理人、會議代理人、文件代理人同時找證據，協調者只採納有出處的答案 | 答案是「證據拼出來的」，不是「AI 覺得」 |
| context providers（可自訂記憶後端） | 每個專案一份記憶；確認過的問答、原開發者的回答自動沉澱 | 資料越用越厚，沒有人多寫一個字 |
| MCP 支援（第二版） | 系統開成 MCP 伺服器，接手者在 IDE 裡直接問 | 客戶原本想不到、看到會想要的需求 |

另有 OpenTelemetry 觀測：每次問答、每個出處、每個工作流步驟都是事件，效益儀表板由此產生，不用另外埋點。

### 5.2 「agent 還是 workflow」的劃分

MAF 官方原則：能用函式寫的就不要用 agent；開放式問答用 agent，步驟固定用 workflow。

| 功能 | 做法 | 理由 |
|---|---|---|
| 接手者問答 | 一個 agent，掛三個工具（搜 git、搜文件、搜會議）與專案記憶 context provider | 開放式對話，需要自主決定查哪裡 |
| 交接盤點 | 一個 `WorkflowBuilder` 圖形工作流：讀來源 → 三個代理人並行產出章節 → 合併 → 找缺口 → `RequestInfoExecutor` 問人 → 併回 → 產出 | 步驟固定、要可暫停、要可觀測 |
| 索引建置（切塊、embedding） | 純函式與排程作業，不用 agent | 沒有決策，只有流程 |
| 效益統計 | 純函式 | 同上 |

### 5.3 刻意不用的 MAF 元件

- `Microsoft.Agents.AI.Foundry`、AG-UI hosting、A2A：截至 2026/10 仍為 preview，第一版不採用。
- Harness agent（有檔案與 shell 存取的長任務代理）：功能強但風險高，等「自動驗證部署步驟」這類需求成熟再評估。
- 宣告式 YAML 工作流：第一版用程式碼定義，待客戶有客製需求再開放。

### 6.3 四個必建缺口與做法

**缺口 1：MAF 與既有計費管線的轉接層**
現況：腳手架的 AI 呼叫是手寫 HttpClient（`stream:false`、無 tool calling、無 embedding），沒有 `Microsoft.Extensions.AI`。MAF 建在 `IChatClient` 之上。
做法（二擇一，M0 決定）：
- A. 用 `Microsoft.Agents.AI.OpenAI` 的 `IChatClient`，加一層 MAF middleware，在每次呼叫前後呼叫既有的 `IAiQuotaService.CheckAsync`、`ITokenUsageRecorder`、`AiCallCapture.RecordSafelyAsync`。符合速查表 §6.7「每次呼叫都要記帳」的紅線。
- B. 寫一個 `IChatClient` 實作包住 `IAiChatCompletionClient`。缺點是既有客戶端不支援 tool calling 與 streaming，等於要先擴充它。
建議 A，並在 `TokenUsageCallKinds` 新增 `Agent`、`Embedding` 兩種呼叫類型。

**缺口 2：embedding 與檢索**
現況：無向量儲存、無 SQLite FTS5。
做法：
- 第一版：embedding 向量存 SQLite blob，查詢時在記憶體做餘弦相似度（單一企業、數十個專案的規模夠用）。同時啟用 FTS5 做關鍵字檢索，兩者混合排序。
- 量大再換 `sqlite-vec`。
- embedding 呼叫點必須照 §6.7 記帳，費率已在 `AiPricingSettings`。

**缺口 3：git 讀取**
現況：無 LibGit2Sharp，也沒有呼叫 `git` 的程式。
做法：引入 LibGit2Sharp 讀 commit、diff、blame、tag。索引單位：每個 commit 一塊（訊息＋變更檔案清單＋重要 diff 摘要），每個檔案的 blame 摘要一塊。以排程作業增量更新。

**缺口 4：文件擷取與切塊**
現況：只有附件上傳，無解析。
做法：Markdown 與文字直接切塊；PDF 與 Word 用現有套件（PDFsharp 不擅長擷取，需另評估）或先要求轉成 Markdown。切塊帶出處（檔名、章節、頁碼）。

### 6.4 資料表草案

| 資料表 | 用途 |
|---|---|
| `HandoverProject` | 專案（或直接重用既有 `Project`，加欄位），對應 repo 路徑、文件路徑、會議匯出路徑 |
| `KnowledgeSource` | 每個來源的種類、路徑、最後索引時間、狀態 |
| `KnowledgeChunk` | 切塊內容、出處（類型、檔案、commit、行號、章節）、embedding blob、FTS5 索引 |
| `ProjectMemory` | 確認過的問答、原開發者的回答，供 context provider 讀寫 |
| `HandoverSession` | 一次盤點流程的狀態、checkpoint 參照、負責人 |
| `HandoverQuestion` | 缺口題目、回答、狀態（待答／已答／略過） |
| `QaLog` | 每次問答、出處清單、使用者回饋，供儀表板統計 |

大內文（切塊原文、交接文件、checkpoint）依腳手架慣例存檔案系統，資料表只存路徑，比照 `AuditContentPath` 的作法。

### 6.5 安全

- 送出到模型前遮蔽密鑰樣式（連線字串、API key、token）；這是企業最在意的事，要做成可驗證的單元測試。
- 稽核、日誌、用量紀錄一律不寫 AI 內文（腳手架既有紅線）。
- 模型金鑰由客戶在設定檔提供；Azure OpenAI 可選區域、資料不用於訓練，作為合規說法。
- 專案資料走既有 `RecordTeamScope` 行級權控：只有該專案團隊成員能問。

### 6.6 必須遵守的腳手架慣例

- 新 AI 呼叫點：§6.7 四件事（`ITokenUsageRecorder`、新 Operation／CallKind 常數、`AiCallCapture.RecordSafelyAsync`、先 `IAiQuotaService.CheckAsync`）。
- 系統提示詞經 `IAiSystemPromptProvider`，新增 `PromptTemplateKeys` 並同步 Guardrails。
- AI 回答只能經 `AiMarkdownRenderer` 渲染。
- 背景工作做成 `IScheduledJob`，禁止新增 `BackgroundService + PeriodicTimer`，禁止 Blazor 事件內 `Task.Run`。
- 新檔案路徑加進 `ExternalFileSystem`，並同步 `ApiIntegrationTests.CreateSettings()`。
- 新頁面四處登記（`MagicObjectHelper`、`Menu.json`、`MenuPermissionMap`、`CheckAccessPage`）加 `MenuPermissionConsistencyTests.ViewToMenuId`，並補 `HelpTopics.json` 與 `Datas\Help\*.md`。
- 新設定類別用 `AddValidatedOptions`。
- 模型變更產生 migration（SQLite）。
- 每次異動版本號 Patch +1；文件 UTF-8 含 BOM；提交前跑 `scripts\Invoke-QualityGate.ps1`。
- 套件版本集中在 `src\MyProject\Directory.Packages.props`。

## 8. 商業模式與定價假設

以下全部是**假設**，要靠早期驗證修正。

- **形式**：自架軟體授權。買斷加年度維護，或年授權。不做 SaaS，避開企業程式碼出網的疑慮。
- **計價單位**：按專案數或席次。建議按專案數，因為價值直接對應「幾個系統的知識被留下來」。
- **AI 費用**：客戶自帶 Azure OpenAI／OpenAI 金鑰，用量上限由腳手架既有配額功能控制。開發者不承擔 token 成本，也不需要為客戶代管金鑰。
- **合規說法**：Azure OpenAI 的資料不用於訓練、區域可選、可走私網，對企業資訊部門是熟悉的語言。
- **被動收入的來源**：年度維護或年授權續約。前提是安裝與升級要簡單到不需要開發者親自到場，這是 M5 的重點。
- **早期驗證**：
  1. 先用開發者自己的專案跑 M1 到 M3，產出真實的交接文件當作案例。
  2. 找 2 到 3 家願意試用的對象（自己任職的公司、熟人的公司），免費或低價試用，換取使用數據與推薦。
  3. 以儀表板數字（回答題數、附出處比例、原開發者少被打擾次數）作為定價依據。

## 9. 風險與因應

| 風險 | 因應 |
|---|---|
| 答案品質不穩，客戶一次被騙就不信任 | 出處強制；無出處即拒答；回饋按鈕；提示詞版本化可回滾 |
| 企業不准程式碼送到外部模型 | 首選 Azure OpenAI（區域、私網、不訓練）；MAF 原生支援 Ollama，可作為全本地備案，但第一版不做 |
| 冷啟動：新客戶沒有會議紀錄與文件 | git 歷史本身就是資料，M1 只靠 git 就能回答第二類問題；盤點流程會把原開發者的回答變成第一批文件 |
| 原開發者不配合回答缺口題 | 題數控制在十幾題；可略過；每答一題立即看到交接文件變完整；站內通知提醒 |
| MAF 版本變動 | 只用 1.0 穩定 API；preview 元件不碰；套件版本集中管理 |
| 密鑰外洩到模型 | 送出前遮蔽；單元測試守門 |
| 開發者時間有限 | 里程碑可獨立暫停；M1 完成即有可用價值 |
| 做出來沒人買 | 第 8 章的早期驗證先於 M4、M5；如果 2 到 3 家試用對象都不願付費，停在 M3，至少自己用 |
