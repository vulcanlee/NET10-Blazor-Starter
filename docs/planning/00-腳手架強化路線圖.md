## 一、為什麼有這份文件

本專案已是相當成熟的 .NET 10 Blazor Server 腳手架：7 個專案、**673 個測試**（2026/09/21 實跑，0 警告）、
**16 個「慣例守門測試」**、
RBAC 四方一致性驗證、例外自動收錄管線、LLM 費用逐列快照。核心資產不是功能數量，
而是「**把踩過的坑用測試釘死**」這套文化 ——
[`開發慣例與限制速查`](../architecture/開發慣例與限制速查.md) 691 行幾乎每一條都附著事故沿革。

但 2026/09/21 的全面盤點發現三個**結構性**問題，它們不會出現在任何單一功能的 PRD 裡：

1. **品質關卡全滅。** commit `05cca70` 刪除了 `.github/workflows/dotnet-ci.yml`（79 行、8 道關卡）。
   那 673 個測試、`dotnet format`、文件編碼檢查、弱點掃描**目前沒有任何自動執行**，
   而 6 份文件仍在描述它。一個「靠守門測試維持慣例」的專案失去執行守門測試的機制，
   是最危險的狀態 —— **腐化會靜默發生**。
2. **多租戶擴充點的時間窗正在關閉。** 已確認未來要長成「一租戶一 SQLite 檔」的 SaaS 底座。
   關鍵改動（`IDbContextFactory` Singleton→Scoped）**今天成本近乎零、驗證條件恰好成立**，
   但這個條件會隨任何一個新的 HostedService 而失效。見第 2 期。
3. **資料正確性地基缺席。** 無樂觀並行（兩人同時編輯＝後者無聲覆蓋）、無軟刪除、
   三個業務模組 CRUD **完全不寫稽核**。尚未交付任何正式系統，是動這些地基的唯一低成本時機。

## 三、資料切分決定（多租戶的前提，已拍板）

SQLite 沒有跨檔 FK，EF Core 的 LINQ 也無法跨 `DbContext` 組查詢
（`ATTACH DATABASE` 會破壞連線池語意與 migration 模型，**不可走**）。
因此切分原則是「**不製造跨庫 FK**」：

| 庫 | 內容 |
|---|---|
| **主庫 `master.db`**（日後才建） | `Tenant(Id, Slug, DisplayName, Status, CreatedAt, SchemaVersion)`、`TenantUserDirectory(LoginKey → TenantId)`。⚠️ **不含任何憑證**（無密碼雜湊、無 TOTP secret）。 |
| **租戶庫 `tenants/{id}/BackendDB.db`** | 現有 13 張表**原封不動**，所有 FK 維持有效。 |

**達成的效果**：一個帳號仍找得到它的租戶（登入頁輸入帳號 → 查目錄 → 導向對應租戶），
但 `UserTeam(MyUserId, TeamId)`、`AuditLog.ActorUserId`、`RolePermissionMap` 全部留在同一個檔案內，
FK 完整性不受影響，且保住 per-tenant 模式最大的賣點 —— **刪除租戶 ＝ 刪一個目錄**。

**要付的代價**：目錄映射表需要與租戶庫的 `MyUser` 同步（新增／刪除帳號時雙寫）。
這是可以用一個守門測試釘住的單點。

**目錄式優於檔名式**：用 `tenants/{id}/BackendDB.db` 而非 `{id}.db`，
因為 SQLite 的 `-wal`／`-shm` 伴生檔、以及該租戶的上傳檔都能收在同一個目錄底下。
不要在第一步就放棄「刪目錄＝刪租戶」這個性質。

### 兩個平台級例外（日後歸主庫）

- **`ExceptionLog`** —— 這是**程式碼缺陷**的紀錄，不是租戶資料。關鍵證據：`Signature` 有 `IsUnique()` 索引，
  設計意圖是「同一個 bug 只留一列、重複發生就合併」；分租戶會把同一個 bug 切成 N 列，**合併機制直接失效**。
  且 `ExceptionLogWriter` 是 `BackgroundService`，其 scope 沒有 circuit 也沒有 HttpContext ⇒ **沒有租戶** ——
  架構本身就在說這張表屬於平台。日後需加 `LastTenantId` 與 `AffectedTenantCount` 兩欄，
  並在入列時（`ExceptionLogEntry`）就把當下租戶抓起來帶著走。
- **`TokenUsageLog`** —— 明細留租戶庫（租戶要能看自己的用量），
  日後在主庫加 `TenantUsageDaily(TenantId, Date, Tokens, Cost)` 彙總表供計費，由排程日結。
  ⚠️ **現在不要提早做彙總表**，等真的要出帳再加。

### 登入的雞生蛋問題

登入頁在知道帳號之前必須先知道租戶，才能開對的 `.db`。建議**子網域為主、目錄映射為輔**。

⚠️ Google OAuth 的 `CallbackPath = "/signin-google"` 是固定的，多子網域下每個子網域都要在
Google Console 註冊 redirect URI（有數量上限）→ 實務上要改成「單一回呼網域 + state 帶租戶再轉址」。
這是日後的事，但會影響子網域方案的可行性判斷，先記在這裡。

### 跨庫查詢的四條對策

1. **不跨。** 管理端跨租戶查詢一律「迴圈各租戶庫查詢 → 記憶體合併 → 分頁」。
   因此所有跨租戶查詢**必須**強制帶時間範圍上限與每租戶筆數上限 ——
   做成 API 簽章的必填參數，不是靠自律。N=500 時沒有上限會把主機吃掉。
2. **去正規化冗餘字串欄位。** 凡是跨庫要顯示的欄位，一律在**寫入當下**把字串複製進來，不靠 FK。
   專案在 `AuditLog`（`ActorAccount`）上已有這個文化，延續即可。
3. **平台級唯讀彙總表**放主庫，由背景排程從各租戶庫日結。只給儀表板用，不作為真相來源。
4. ⚠️ **`Id` 只在租戶內唯一。** 13 張表全用 `int` 自增，分庫後跨租戶撞號是
   **資料污染而非錯誤**，不會丟例外、不會進日誌。任何把 `Id` 當全域唯一的用法
   （寫進 URL 而不帶租戶、當快取鍵、傳給外部系統）都要禁止；跨租戶的鍵一律 `(TenantId, Id)`。

## 第 1 期：啟動流程與設定地基

### 1-1 `IDatabaseInitializer` 重構

`Program.cs` 約 100+ 行硬寫的 migration／seed 邏輯 → 抽成 `MyProject.Business/Startup/`：

```text
IDatabaseInitializer.InitializeAsync(tenantId, ct)
IDatabaseSeeder { Order, Name, ShouldRun(ctx), SeedAsync(db, ctx, ct) }
  ├ DefaultRoleViewSeeder   (Order 10)
  ├ SupportUserSeeder       (Order 20)
  └ RbacBackfillSeeder      (Order 30，包住既有 IRbacBackfillService)
```

順便修掉三個既有缺陷：

- ⚠️ **`EnsureCreated()` 是死碼且有害。** 已有 15 筆 migration，
  `GetMigrations().Any() ? Migrate() : EnsureCreated()` 的第二分支永遠走不到；
  一旦走到會建出沒有 `__EFMigrationsHistory` 的庫，之後**永遠無法 migrate**。直接刪除。
- ⚠️ **每次啟動覆寫 `RoleView.TabViewJson`。** 管理員在 UI 調過的預設角色權限，重啟就被蓋回去。
  應改成「不存在才建立；存在則只**補**新增的權限鍵，**不移除**既有勾選」。
  多租戶下這會變成「一次重啟蓋掉 N 個租戶的設定」。
- **零測試覆蓋。** 那 100 行是專案裡唯一完全沒有測試的關鍵路徑；
  搬進 Business 後可單元測試，且愈晚拆愈難分辨「這是 bug 還是刻意的」。

**影響檔案**：`MyProject.Web/Program.cs`（100 行 → 1 行）、新增 `MyProject.Business/Startup/`

### 1-2 Migration 環境分流 + 跨行程鎖

新增 `Database:MigrationMode` 設定（`Automatic` / `VerifyOnly` / `None`）：

- **Development／Testing → `Automatic`**（腳手架要開箱即跑，不能退讓）
- **Production 預設 → `VerifyOnly`**：只查 `GetPendingMigrations()`，有待套用就**拒絕啟動並明確報錯**，
  同時讓 `/health/ready` 回 Unhealthy。migration 由部署腳本／一次性 job 負責。
- `Automatic` 一律用**檔案鎖**保護（對 db 檔旁的 `.migration.lock` 做獨佔 `FileStream`）——
  named `Mutex` 不跨 Docker 容器，檔案鎖是同時支援 IIS 與容器的最小公分母，共享 volume 上也成立。

- **為什麼**：目前 `if (!IsDevelopment())` 被註解掉，**所有環境都無條件 `Migrate()`**。
  IIS 多工作者行程或 Docker 多副本同時跑 migration → SQLite `database is locked` 或更糟的半套用狀態。
- **影響檔案**：`MyProject.Web/Health/DatabaseHealthCheck.cs`、1-1 的 initializer

### 1-3 設定驗證全覆蓋

目前 `ValidateDataAnnotations().ValidateOnStart()` **只覆蓋 `JwtSettings` 與 `CookieSettings`**；
另外 8 個 Options（`SystemSettings`／`Security`／`Cors`／`Swagger`／`CacheSettings`／`RateLimit`／
`AiSettings`／`AiPricingSettings`）只做 `Configure` 綁定，完全無驗證。

- **價值**：設定打錯目前要到執行期才炸，而且可能是在使用者面前炸。
  已有手寫的 `StartupSafetyValidator.cs` 做 Production 守門，這一項是把它系統化。
- **作法**：對複雜規則用 `IValidateOptions`（目前專案零實作）。

## 第 2 期：多租戶擴充點（現在就留，但不啟用）

> ⏳ **2-2 是整份路線圖唯一有時效性的項目。**
> 驗證結果：`IDbContextFactory<BackendDBContext>` 的 12 個引用點中，
> **沒有任何單例／HostedService 直接注入它**（`ExceptionLogWriter` 走 `IServiceScopeFactory.CreateScope()`），
> 所以今天把它改成 Scoped 是安全的。只要日後有人加一個注入工廠的 HostedService（很自然的需求），
> 這就變成無法分批的大改。

### 2-1 `ITenantContext`（Scoped）

放 `MyProject.Share/Tenancy/`：`TenantConstants`（`DefaultTenantId = "default"`）、
`ITenantContext`、`internal ITenantContextSetter`（只能成功 `Pin()` 一次）、
單租戶實作 `SingleTenantContext`。合計 40 行以內。

**三條必須寫進 XML 註解的不變量：**

- ⚠️ **租戶解析不得依賴 Path。** Blazor Server 的 circuit 內導覽（`NavigationManager`）**不產生新的 HTTP 請求**：
  使用者從 `/t/acme/...` 點到 `/t/globex/...`，路徑變了、DI scope 沒變、已開啟的 SQLite 連線也沒變。
  路徑派生的租戶會在 circuit 中途「變心」而資料層還連著舊的 `.db` ——
  **這是最安靜也最致命的跨租戶外洩型態**。路徑式租戶**只准用於 Web API**（每請求一個 scope，本來就正確）。
- ⚠️ **用 Scoped，不用 `AsyncLocal` 單例**（不同於 `ExceptionContextAccessor`）。
  `ExceptionLogWriter` 這種背景 scope 沒有 circuit 也沒有 HttpContext，
  AsyncLocal 會拿到前一次互動的殘留值；Scoped 則是「沒 Pin 就是沒 Pin」，會明確炸掉。
- ⚠️ **`Id` 只在租戶內唯一**（理由見第三節第 4 條）。同步寫進
  [`資料模型與資料庫`](../architecture/資料模型與資料庫.md)。

日後的租戶固定機制沿用專案既有模式：`ApplicationCircuitHandler` 已在做
「`OnCircuitOpenedAsync` 解析身分 + `CreateInboundActivityHandler` 每次互動前重設」。
⚠️ 租戶要**新開一個 `TenantCircuitHandler`**，不要塞進既有那個 ——
既有那個全程 `try/catch`「失敗不影響使用者」，而**租戶解析失敗必須中止**，語意相反。

### 2-2 DbContext 工廠包裝（★ 時效性項目）

```text
ITenantConnectionStringProvider (Singleton)
    ← MagicObjectHelper.GetSQLiteConnectionString 的唯一呼叫點
ITenantDbContextFactory (Singleton)
    ← ConcurrentDictionary 快取 per-tenant DbContextOptions
ScopedTenantDbContextFactory : IDbContextFactory<BackendDBContext> (Scoped)
    ← 讀 ITenantContext 委派給上者
DesignTimeDbContextFactory
    ← 必須同批，否則 dotnet ef migrations add 會壞
```

- **為什麼非得包一層**：框架的 `AddDbContextFactory` 把工廠與 `DbContextOptions` 都註冊成 **Singleton**，
  options 在**啟動時**由 lambda 建構一次 —— 單例工廠**在架構上不可能**讀到 scoped 的租戶。
- ⚠️ **必須快取 options**：每個**不同的** `DbContextOptions` 實例會讓 EF Core 建立自己的
  internal service provider。不快取會在建到第 20 個時噴 `TooManyDbContextOptionsWarning`，
  之後每次都是數十毫秒的冷啟。
- ⚠️ **`OnModelCreating` 絕不可依租戶分支。** EF 預設的 `IModelCacheKeyFactory` 只以 context 型別為鍵，
  所有租戶共用同一份編譯後的 model —— 這正是我們要的。若日後真需要 per-tenant schema
  就得自訂 `IModelCacheKeyFactory`，代價是記憶體中 N 份 model。**明確建議永遠不要走這條。**
- **影響面幾乎為零**：8 個 DataAccess 服務、5 個 Repository、`DataAccessServiceLifetimeTests`、
  `DatabaseHealthCheck`、`RecordAccessScopeProvider` **一行都不用改** ——
  注入型別 `IDbContextFactory<BackendDBContext>` 與 `BackendDBContext` 完全不變。這是選這個作法的主因。
- **順手標準化 SQLite 連線參數**（provider 是唯一適合的地方）：
  `Foreign Keys=True`、`PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`。
  WAL 對「一寫多讀」的 Blazor 情境幫助很大；`busy_timeout` 是 IIS 多工作者行程下
  避免 `database is locked` 的低成本保險。
- ⚠️ **`DesignTimeDbContextFactory` 必須同批做**：拿掉 `AddDbContextFactory` 後
  `dotnet ef migrations add` 會找不到 context，下一次加 migration 直接卡住。
- **影響檔案**：`MyProject.Web/Extensions/ServiceCollectionExtensions.cs`（`AddConfiguredDatabase`，約 8 行）、
  新增 `MyProject.Business/Data/`、`MyProject.AccessDatas/DesignTimeDbContextFactory.cs`

### 2-3 `ITenantPathResolver`（Scoped）

把租戶目錄組合收斂成一處。呼叫點只有 4 個：
`ProjectService.cs`（⚠️ 目前把路徑快取在建構子欄位，需改成每次解析）、
`ExceptionStackFileStore.cs`、`TokenUsageRawStore.cs`、`ApplicationBuilderExtensions.cs`。

| `ExternalFileSystem` 路徑 | 日後分租戶？ |
|---|---|
| `UploadPath` | ✅ |
| `DownloadPath` | ✅（見 2-5） |
| `ProjectFilePath` | ✅ |
| `TokenUsagePath` | ✅ |
| `ExceptionPath` | ❌ 共用（跟著 `ExceptionLog` 走平台庫） |
| `DataProtectionKeyPath` | ❌❌ **絕對不可** |

#### ⚠️⚠️ DataProtection 金鑰絕對不能分租戶 —— 四個理由

1. **時序上不可能。** `AddConfiguredDataProtection` 作用在 `IServiceCollection` 層級，
   金鑰環在**容器建立時**就綁定到一個實體目錄；租戶是請求／circuit 期才知道的。
   這不是「難做」，是**先後順序反了**。
2. **雞生蛋。** 登入 Cookie 的解密發生在 `UseAuthentication()`，而租戶 claim 就寫在那個 Cookie 裡面 ——
   要解密才知道租戶，要知道租戶才能挑金鑰。死結。
3. **共用消費者不只有 Cookie。** 同一個 `IDataProtectionProvider` 還被 Antiforgery token、
   Blazor circuit 狀態保護、以及 OAuth 的 correlation／state cookie 使用。
   OAuth 回呼特別致命：correlation cookie 在 A 網域寫入、在回呼網域讀取，
   分租戶金鑰會讓**第三方登入永久失敗**。
4. `MagicObjectHelper.DataProtectionApplicationName` 的既有註解已說了一半：
   判別子一變，全站 Cookie 立刻失效。分租戶等於把爆炸半徑乘以租戶數。

**正解是隔離 payload 而非隔離金鑰**：金鑰環保持全域單一，
需要租戶隔離的加密改用 purpose 字串帶租戶 —— `provider.CreateProtector("MyProject.Tenant", tenantId)`。
成本近乎零，且 A 租戶的密文在 B 租戶的 protector 下必定解不開。

> 補充（與租戶無關但同屬「全域單一」）：Docker／多副本部署下 `PersistKeysToFileSystem`
> **必須掛在共享 volume**，否則每個副本一組金鑰 —— 與 IIS 回收那個老問題同源。

### 2-4 四個守門測試

沿用專案既有手法（原始碼掃描 + `FindSourceRoot()` + 排除 `obj`／`bin`／`artifacts`／`MyProject.Tests`，
見 `MyProject.Tests/LoggingConventionTests.cs`）：

1. **`TenantDbContextConventionTests`** —— 對 `ServiceCollection` 跑 `AddConfiguredDatabase()`，
   斷言 `IDbContextFactory<BackendDBContext>` 的 `Lifetime == Scoped` 且實作型別正確
   （**釘死「不准退回框架預設的單例工廠」，最核心的一條**）；
   `new BackendDBContext(` 只准出現在兩個工廠檔；
   沒有任何型別的建構子參數是 `DbContextOptions<BackendDBContext>`。
2. **`TenantConnectionStringConventionTests`** —— `GetSQLiteConnectionString(` 與 `.UseSqlite(`
   的呼叫點白名單；原始碼中 `Data Source=` 字面值零出現。
   防的是「有人為了寫小工具，順手在別處自己 `new DbContextOptionsBuilder().UseSqlite(...)`」——
   那條路徑會永遠連著 default 租戶。
3. **`TenantPathConventionTests`** —— 正向釘住 4 個路徑的讀取點只准在 resolver 實作內；
   **反向**釘住 `DataProtectionKeyPath` **不得**進入 resolver。
   ⚠️ 反向這條是刻意的：「金鑰不分租戶」是一個**看起來像是漏掉、所以有人會好心補上**的決定。
   斷言訊息裡要寫清楚上面四個理由 —— 讓踩到的人當場讀到原因，而不是去翻文件。
   與既有 `AdminOnlyPermissionTests`「防止有人把死權限補上架」的精神完全一致。
4. **`DatabaseInitializerConventionTests`** —— `Program.cs` 不得含
   `Database.Migrate()`／`EnsureCreated()`／`SaveChanges()`；`EnsureCreated()` 全 `src`（測試除外）零出現；
   每個 `IDatabaseSeeder` 實作的 `Order` 唯一且**全部都在 DI 註冊表裡**
   （反射找出的實作集合 vs `ServiceCollection` 註冊集合逐一比對，手法同 `MenuPermissionConsistencyTests`）。

### 2-5 零程式碼的標記

## 第 3 期：資料正確性地基（未交付 ＝ 唯一低成本時機）

### 3-1 樂觀並行（RowVersion）

13 張表**完全沒有** `RowVersion` 或 concurrency token，也沒有任何 `DbUpdateConcurrencyException` 處理。

- **實際後果**：兩人同時開同一筆專案的編輯對話窗（那是 95vw／95vh 的大表單，停留時間長），
  後存檔者**無聲覆蓋**前者。不會報錯、不會有日誌、不會有稽核。
- **作法**：SQLite 無原生 `rowversion`，用 `byte[]` 或 `Guid` + `IsConcurrencyToken()` 自行維護；
  `FormModalFlow` 的失敗路徑接上「資料已被他人修改」提示（該樣板的 `return false` 路徑已備好）。
- **成本**：Entity + 一份 migration + Service 的 Update 路徑 + `New-CrudModule.ps1` 樣板。
- **建議範圍**：先只做有編輯 UI 的五張（`Project`／`Category`／`Team`／`MyUser`／`RoleView`），
  紀錄型三表（`AuditLog`／`ExceptionLog`／`TokenUsageLog`）不需要。

### 3-2 軟刪除

目前一律實體刪除，靠 `DeleteBehavior.Restrict`（`BackendDBContext.cs` 第 44–48 行）擋住有子資料的刪除。
誤刪無法救。

- **作法**：`ISoftDeletable` + `HasQueryFilter`（`OnModelCreatingPartial` 已預留擴充點）。
- ⚠️ **與既有唯一索引衝突**：`IX_Category_Name`、`IX_Team_Name`、`IX_Team_Code` 是**無條件**唯一索引，
  軟刪除後「已刪除的同名記錄」會擋住新建。必須改成 partial index（`WHERE IsDeleted = 0`）。
  這塊的完整脈絡見 [`開發慣例與限制速查` 第 4.2 節](../architecture/開發慣例與限制速查.md)，動之前必讀 ——
  那裡記載了「檢查時 Trim、寫入時不 Trim」造成兩筆看起來一模一樣的資料並存的事故。

### 3-3 業務 CRUD 稽核 + `AuditEvents` 常數類別

稽核目前有 15 個呼叫點（登入四種、使用者三種、角色三種、權限拒絕、附件下載、日誌等級、日誌匯出、稽核自清除），
但 **`Project` / `Category` / `Team` 的 CRUD 完全不寫**，登出也無稽核。
動作代碼是散落的字串字面值（`User.Create` 等），**沒有 `AuditEvents` 常數類別**。

- **價值**：合規上「誰改了哪筆業務資料」是第一個會被問的。目前答不出來。
- **作法**：建 `AuditEvents` 常數類別 + 守門測試（`WriteAsync` 的 action 參數只准來自常數）；
  在三個 Service 的 Add／Update／Delete 補寫入。
- **注意**：`AuditLogService.WriteAsync` 全程吞例外（刻意設計），補寫入不會有回歸風險。
- ⚠️ 待確認的落差：`MyProject.Tests/AuditEventsTests.cs` 提到 `AuditEvents` 型別，但主程式碼無該型別。

## 第 4 期：背景作業與保留期

### 4-1 週期性背景作業抽象

全專案唯一的 `BackgroundService` 是 `ExceptionLogWriter`（事件驅動，非排程）。**無任何排程框架**。

- **建議**：先用 `PeriodicTimer` + `IScheduledJob` 介面的最小實作（約 100 行），
  **不要一開始就上 Hangfire** —— 它需要自己的資料表且對 SQLite 支援不佳；
  等真的需要「可視化佇列／重試／一次性任務」再評估。
- **解鎖的需求**：保留期自動清理、租戶庫暖機、日結彙總、排程報表寄送、備份。

### 4-2 保留期自動清理

三張紀錄表的清理**全靠管理員手按**，門檻值還是程式常數：
`AuditLogView.razor.cs` 的 `PurgeDays = 365`、`ExceptionLogView` 的 `PurgeDays = 90`、
`TokenUsageLog` 依日期手選。

- **作法**：門檻設定化（`Retention:AuditLogDays` 等）+ 掛上 4-1 的排程。
- ⚠️ 清理必須連帶處理檔案 —— `ExceptionStackFileStore` 與 `TokenUsageRawStore` 的生命週期紅線
  （[速查表第 6.6、6.7 節](../architecture/開發慣例與限制速查.md)）規定**所有刪除路徑都必須經過它們**，
  否則會重蹈專案附件「資料列刪了、實體檔還在」的覆轍。

### 4-3 SQLite 線上備份

目前無任何備份機制。SQLite 的 `VACUUM INTO` 可在不中斷服務下做一致性快照。

- **價值**：per-tenant 模式下這會變成「備份 N 個檔」，
  先把單一庫的作法與排程建立起來，日後只是迴圈。
