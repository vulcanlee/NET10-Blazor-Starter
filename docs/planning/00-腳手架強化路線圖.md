## 一、目的與選題判準

這個腳手架的目的，是把**大部分系統都會用到**的功能與架構先做好。日後用它開發個人或企業系統時，
不必再重做這些功能，以縮短開發時間、提高品質與效率。

**選題判準（2026/10/03 確認）：**

> 只放「**大部分系統都會用到**」的功能。只有少數系統才需要的（例如 AD／LDAP／Entra ID 登入），
> 等複製出新專案後，在那個專案裡再做。

判準背後的理由：腳手架裡的每一項功能，所有衍生專案都要一起背負維護成本（升級、測試、文件、說明頁）。
只有少數專案用得到的功能，放進腳手架是讓多數專案替少數專案付費。

| 項目 | 決定 |

> **A-3a 實作結果與規劃的差異**（經過見 [changelog](../changelog/2026-10-03-資料庫初始化重構.md)）：
> - 預設角色的規則比原規劃更精確：「只補新增的權限鍵」若以「角色缺少的鍵」判斷，管理員刪掉的鍵也算缺少、一樣會被補回；
>   改為「**權限目錄（`Permission` 表）裡從未出現過的頁面鍵**才算新頁面」，並在同一次 SaveChanges 補上目錄列。
> - **沒有加 `busy_timeout`**：實測 Microsoft.Data.Sqlite 遇到 SQLITE_BUSY 會自己重試到命令逾時（預設 30 秒），由 `SqliteBehaviorTests` 釘住。
>   Foreign Keys 實測原本就已開啟，仍在連線字串明確寫出。
> - 鎖檔為 `BackendDB.db.migration.lock`，等待上限 60 秒（IIS 啟動時限預設 120 秒）。EF Core 9 起 `Migrate()` 自己有鎖，這把鎖實際保護的是 seed。
> - 限制：IIS 重疊回收時舊行程不會重跑初始化，migration 在重疊期間必須向下相容。
> - ⚠️ **後續項目（未排期）**：「預設角色」可以被改名或刪除；之後 seeder 會重新建立一個擁有全部頁面的「預設角色」，
>   而 Google 自動建立的帳號以名稱（`GoogleOAuthSettings:DefaultRoleName`）對應它。建議禁止改名與刪除這個角色。
>
> 以下為規劃時的原文（A-3b 仍依「Options 驗證全覆蓋」與「注意點」兩段執行）。

- **目的**：`MyProject.Web/Program.cs` 約 100 行硬寫的 migration 與 seed 邏輯，是專案裡唯一完全沒有測試的關鍵路徑，且帶著三個既有缺陷。
- **範圍**：
  - 抽成 `MyProject.Business/Startup/`：`IDatabaseInitializer.InitializeAsync(ct)` 與
    `IDatabaseSeeder { Order, Name, SeedAsync(...) }`（預設角色、support 帳號、RBAC 回填各一個 seeder）。
  - 修三個缺陷：
    1. ⚠️ **刪除 `EnsureCreated()` 死碼**：已有多筆 migration，那個分支永遠走不到；一旦走到會建出沒有 `__EFMigrationsHistory` 的庫，之後永遠無法 migrate。
    2. ⚠️ **不再每次啟動覆寫 `RoleView.TabViewJson`**：管理員在 UI 調過的預設角色權限，重啟就被蓋回去。改成「不存在才建立；存在則只**補**新增的權限鍵，不移除既有勾選」。
    3. 為初始化流程補上單元測試。
  - **migration 檔案鎖**：對 db 檔旁的 `.migration.lock` 做獨佔 `FileStream`。IIS 回收應用程式集區時，新舊工作者行程會短暫重疊，同時 `Migrate()` 會造成 `database is locked` 或半套用狀態。
  - **SQLite 連線參數標準化**：`Foreign Keys=True`、`PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`。WAL 對「一寫多讀」的 Blazor 情境幫助很大。
  - **Options 驗證全覆蓋**：對尚未驗證的設定區段補上 `ValidateDataAnnotations().ValidateOnStart()`，複雜規則用 `IValidateOptions`。
- **注意點**：`StartupSafetyValidator.cs` 已在做 Production 守門，Options 驗證是把它系統化，兩者分工要在設計時寫清楚。
- **驗收**：`Program.cs` 不再含 `Database.Migrate()`／`EnsureCreated()`；加一條守門測試釘住；兩個行程同時啟動不會壞庫。

  - 把既有兩個清理 worker 遷入；補上 `TokenUsageLog` 的保留期清理（目前不會自動清除）。
- **注意點**：
  - ⚠️ **IIS 重疊回收會雙跑**：新舊工作者行程短暫並存，兩邊都會觸發同一個作業。要用 DB 租約或檔案鎖保證同一時間只有一個行程執行。
  - ⚠️ 清理必須連帶處理檔案：`ExceptionStackFileStore`、`TokenUsageRawStore` 的生命週期紅線規定所有刪除路徑都要經過它們
    （[速查表 §6.6、§6.7](../architecture/開發慣例與限制速查.md)）。
  - 先評估 `Cronos`（只解析 cron 運算式）這類輕量套件；**不要一開始就上 Hangfire**（需要自己的資料表，對 SQLite 支援不佳）。
  - IIS 閒置逾時會讓應用程式集區停止，排程跟著停 —— 部署文件要寫明「AlwaysRunning + 停用閒置逾時」。
- **驗收**：兩個既有清理作業改由框架執行且行為不變；管理頁可手動觸發並看到紀錄；模擬兩個行程同時觸發，只執行一次。

### B-6 系統參數設定 UI

- **目的**：保留天數、鎖定次數、密碼原則、公司名稱這類值，目前要改 `appsettings.json` 再重啟。
- **範圍**：DB key/value 表（具型別、預設值、說明、分類）+ 快取 + 管理頁；每次修改寫稽核（舊值 → 新值）。
- **注意點**：
  - **只放非機密、執行期可以改的項目。** 金鑰、密碼、連線字串仍留在 `appsettings` 或環境變數。
  - 要定出「appsettings 與系統參數各管什麼」的清楚規則，避免同一個值兩邊都有，寫進速查表。
  - 讀取端要有型別安全的存取方式，不要散落字串鍵；用守門測試釘住鍵的唯一來源。
- **驗收**：修改參數後不重啟即生效；稽核看得到舊值與新值；參數鍵只有一個定義來源。

### B-7 SQLite 自動備份 + 還原

- **目的**：目前沒有任何備份機制，只有[《腳手架開發指引》§13](../guides/腳手架開發指引.md) 的手動清單。
- **範圍**：
  - 以 `VACUUM INTO` 在不中斷服務的情況下做一致性快照，連同附件、例外堆疊檔、Token 原始檔與 DataProtection 金鑰打包。
  - 掛 B-5 排程（預設每日），保留份數或天數取自 B-6。
  - 管理頁：手動備份、列出備份、下載。
  - **還原**採「停站 + 腳本」，寫進維運文件；不提供線上還原（執行中替換 db 檔不安全）。
- **注意點**：備份檔含所有資料與金鑰，存放位置與存取權限要在文件寫清楚；下載要寫稽核。
- **驗收**：排程備份產生可開啟的 db；依文件步驟還原後系統正常登入與運作；過期備份會被清除。

### B-8 站內通知 + 公告

- **目的**：目前只有 AntDesign 的暫時性 toast，不保存。各業務模組沒有辦法「通知某人某件事」。
- **範圍**：
  - `Notification` 表 + `INotificationService`（發給使用者、角色或部門）。
  - 右上角鈴鐺：未讀數、清單、標記已讀。
  - 公告：管理員發布，有起訖時間，登入後顯示。
  - 可選擇同時寄信（沿用既有 `IEmailQueue`）。
- **注意點**：Blazor Server 可以用單例事件匯流排把新通知推到各使用者的 circuit，**不需要自訂 SignalR Hub**；
  要處理 circuit 斷線與重連時的訂閱清理，避免記憶體洩漏。
- **驗收**：A 使用者觸發通知後，B 使用者不重新整理就看到鈴鐺數字變化；公告在起訖時間外不顯示。

## C 帳號安全

### C-9 可設定的密碼與鎖定原則 + 管理者解鎖

- **目的**：密碼原則目前只有「至少 6 字元、不可為預設值」，鎖定是 `MyUserServiceLogin.cs` 裡寫死的「5 次失敗鎖 15 分鐘」。企業資安稽核常會問這些。
- **範圍**：
  - `IPasswordPolicy`：長度、複雜度、歷史（不可重複最近 N 組）、到期天數。重用目前沒有被呼叫的 `MyProject.Business/Helpers/PasswordHelper.cs`。
  - 所有設密碼的路徑（變更密碼、重設密碼、管理員建立與修改使用者）一律經過它。
  - 鎖定次數與分鐘數改由 B-6 設定；使用者管理頁加「解鎖」按鈕（寫稽核）。
- **注意點**：密碼歷史需要新表，存雜湊而非明文；到期提醒可搭配 B-8 通知。
- **驗收**：調整原則後立即生效；每條設密碼路徑都套用同一套原則（加守門測試）；管理員可解鎖並留下稽核。

### C-10 個人資料頁

- **目的**：使用者目前只能改自己的密碼。
- **範圍**：修改姓名、Email、頭像；查看自己最近的登入紀錄（來自 `AuditLog`）。
- **注意點**：Email 變更是否要驗證，在設計時決定；頭像檔案沿用上傳的副檔名白名單與大小限制。
- **驗收**：修改後即時反映在右上角；登入紀錄只看得到自己的。

### C-11 工作階段管理（強制登出）

- **目的**：重設密碼、停用帳號後，其他裝置上的登入仍然有效。
- **範圍**：
  - `MyUser.SecurityStamp`：重設密碼、停用帳號、管理員按「強制登出」時更換。
  - Cookie：`OnValidatePrincipal` 定期比對 stamp（例如每 5 分鐘），不符即登出。
  - JWT：refresh 時比對 stamp，不符回 401。
- **注意點**：⚠️ 這是對 2026/07/09「Refresh Token 不可撤銷」決定的**部分翻案**：
  不落庫每顆 token，只做到「讓某位使用者的所有工作階段失效」。單顆 token 撤銷與裝置管理仍不做。
  Cookie 比對間隔要在「即時性」與「每次請求查 DB」之間取捨。
- **驗收**：重設密碼後，另一個瀏覽器在比對間隔內被登出；JWT refresh 被拒。

### C-12 MFA 兩步驟驗證（TOTP）

- **目的**：企業內部系統常被要求兩步驟驗證。
- **範圍**：
  - 重用既有骨架：`ITotpService`／`TotpService`、`MyUser.TwoFactorEnabled`／`TwoFactorSecret`、migration `AddTwoFactor`、`TotpServiceTests`。
  - 補上：QR 綁定頁、登入第二步、備用碼（雜湊儲存，用過即失效）、管理員重設使用者的 MFA。
  - 依角色強制啟用（設定來自 B-6）。
- **注意點**：
  - ⚠️ 這是對 2026/07/09「MFA 強制不實作」決定的**翻案**。
  - Google 登入是否也要第二步，在設計時決定。
  - API 的 JWT 登入路徑也要一併處理，不能留後門。
  - 產生 QR Code 需要套件，例如 QRCoder。
- **驗收**：啟用 MFA 的帳號沒有驗證碼就無法登入（UI 與 API 兩條路徑都要測）；備用碼只能用一次。

## D 組織呈現

### D-13 部門樹（Team 加 ParentId）

- **目的**：團隊目前是平面清單，主管看不到下屬部門的資料。
- **範圍**：
  - `Team.ParentId`（自我參照），存檔時防止循環。
  - `EffectiveTeamResolver` 展開為「自己的部門 + 所有下屬部門」；資料可見範圍隨之擴大。
  - 團隊清單改為樹狀管理 UI。
  - **順便補上既有缺口**：Web API 目前**不做**列級（團隊）過濾，只有 Blazor 端有。
- **注意點**：
  - 「沒有團隊的資料人人可看」這條既有規則維持不變。
  - 展開下屬的結果要快取，並在部門樹異動時失效。
  - 動之前讀 [`開發慣例與限制速查` §4.1](../architecture/開發慣例與限制速查.md)（紀錄分類／團隊標籤與團隊權控）。
- **驗收**：上層部門的使用者看得到下屬部門的資料，同層與上層的看不到；API 與 UI 的過濾結果一致（加整合測試）。

### D-14 首頁儀表板框架

- **目的**：登入後首頁 `/App` 目前是靜態介紹頁。各系統都需要一個放 KPI、圖表、待辦的首頁。
- **範圍**：`IDashboardWidget`（標題、權限鍵、排序、元件型別）註冊機制；首頁依權限顯示可見的 widget；腳手架附 2～3 個範例 widget（例如我的通知、專案狀態統計）。
- **注意點**：**先用固定排序，不做使用者自訂拖拉排版**（YAGNI）。widget 載入失敗不可拖垮整個首頁。
- **驗收**：無權限的 widget 不顯示也不查資料；新增一個 widget 只需新增一個類別並註冊。

### D-15 暗色模式

- **目的**：使用者可切換淺色或深色。
- **範圍**：在 `wwwroot/theme.css` 的 `:root` 加上暗色 token 覆寫；AntDesign 浮層同步調整（`OverlayStyles.razor`）；
  右上角切換，偏好存在使用者端。
- **注意點**：色票唯一來源是 `theme.css` 的 `:root`；樣式寫在哪裡的判準是 DOM 位置
  （[速查表 §6.9](../architecture/開發慣例與限制速查.md)、[`介面視覺設計規範`](../architecture/介面視覺設計規範.md)）。
  `ThemeConventionTests` 要擴充為兩套色票都檢查。
- **驗收**：切換後全站（含浮層、表格、登入頁）沒有殘留淺色區塊；重新整理後保留偏好。

## F AI

### F-17 Prompt 範本管理

- **目的**：prompt 目前寫在程式碼裡（`MyProject.Web/Ai/AiPromptDefaults.cs`、`AiExceptionPromptDefaults.cs`），改一個字就要重新部署。
- **範圍**：`PromptTemplate` 表（名稱、版本、內容、模型、參數）+ 管理 UI；保留歷史版本並可切回；既有日誌分析與例外分析的 prompt 遷入。
- **注意點**：資料庫沒有資料時要退回程式內建的預設值，確保全新安裝也能運作；修改 prompt 寫稽核。
- **驗收**：在 UI 修改 prompt 後，下一次 AI 呼叫即使用新版本；可切回舊版本。

### F-18 AI 用量配額與上限

- **目的**：目前只有「記帳」（`TokenUsageLog` 與費用快照），沒有「管制」，任何人都可以無上限地呼叫。
- **範圍**：依使用者或角色設定每日、每月的 token 或金額上限；呼叫前檢查，超過就擋下並顯示原因；達 80% 時發 B-8 通知。
- **注意點**：配額檢查與記帳之間有時間差（並行呼叫可能超出一點），設計時決定可接受的誤差；系統內部呼叫（例如健康檢查）是否計入要明確定義。
- **驗收**：超過上限的使用者呼叫被擋下；管理員調整上限後立即生效。

### F-19 AI 聊天元件（串流）

- **目的**：讓各系統只換 system prompt 就能有一個對話功能。
- **範圍**：可重用的 Blazor 對話元件：逐字串流輸出、Markdown 呈現（沿用 `AiMarkdownRenderer`）、停止、重新產生；
  對話與訊息存 DB；每次呼叫照常寫 `TokenUsageLog` 與 `AiCallLog`；呼叫前經過 F-18 配額檢查；system prompt 來自 F-17。
- **注意點**：目前的 `AiChatCompletionClient` 不是串流呼叫，需要擴充串流路徑，並確認串流模式下用量數字仍能正確取得與計費。
  Blazor Server 串流時要節流 UI 更新頻率。
- **驗收**：回應逐字出現；按停止後立即中斷且已產生的部分有記帳；對話重新開啟後歷史還在。

### F-20 文件知識庫（RAG）

- **目的**：AI 應用類系統最常見的需求：上傳公司文件，針對內容問答。
- **範圍**：上傳 PDF、Word、Excel → 解析文字 → 切分 → embedding → 向量儲存 → 問答時檢索相關片段並附上引用來源；
  文件依部門控管可見範圍（沿用 D-13）。
- **注意點**：
  - ⚠️ **向量儲存方式要在本項設計時決定**：sqlite-vec 原生擴充（要確認在 IIS 上的部署與 x64 原生檔載入），
    或向量存成 BLOB、查詢時在記憶體計算 cosine（文件量小時最簡單）。
  - embedding 的計費已在 `AiPricingSettings` 中。
  - 刪除文件時要連帶刪除片段與向量。
- **驗收**：上傳文件後可問答，回答附有可點開的來源片段；沒有權限的文件不會被檢索到。

### G-22 衍生專案升級（升級筆記 + patch 腳本）

- **目的**：已複製出去的專案不會知道腳手架修了什麼漏洞、加了什麼功能，目前完全沒有連結兩者的機制。
- **範圍**：
  - `New-StarterProject.ps1` 在衍生專案記錄來源腳手架版本（例如 `ScaffoldVersion`，與專案自己的 `SystemVersion` 分開）。
  - 腳手架每版在 changelog 標註「建議所有衍生專案跟進」的項目（安全修補、守門測試）。
  - 新腳本：取腳手架兩個版本之間的 git diff，套用與 `New-StarterProject.ps1` 相同的改名規則後產生 patch，讓衍生專案以 `git apply --3way` 套用。
- **注意點**：改名規則要抽成兩支腳本共用，避免兩邊不一致；migration 檔不適合直接套 patch（衍生專案已重建 Init migration），要在升級筆記中說明處理方式。
- **驗收**：用實際衍生出的測試專案，從舊版升級到新版，套用 patch 後 build、test 全綠。

| 簽核流程引擎 | 同上 |

| Refresh Token 落庫、單顆撤銷、裝置管理 | 維持 2026/07/09 決定；只做 C-11 的「整位使用者失效」 |

### 附錄：多租戶的分析摘要（供日後翻案參考）

v1.2 曾完整分析過「一租戶一 SQLite 檔」的做法，關鍵結論如下。完整內容見 v1.2（`git show 7734079:docs/planning/00-腳手架強化路線圖.md` 的第三節與第 2 期）。

- 資料切分原則是「不製造跨庫 FK」：主庫只放租戶與帳號目錄映射（不含任何憑證），現有資料表原封不動放在每個租戶的庫。
- 租戶解析**不得依賴 URL 路徑**：Blazor Server 的 circuit 內導覽不產生新的 HTTP 請求，路徑派生的租戶會在 circuit 中途改變，而資料層仍連著舊的 db。
- 框架的 `AddDbContextFactory` 是單例，讀不到 scoped 的租戶，需要自己包一層工廠，且必須快取每個租戶的 `DbContextOptions`。
- ⚠️ **DataProtection 金鑰絕對不能分租戶**（時序不可能、Cookie 解密的雞生蛋問題、OAuth correlation cookie 會永久失敗）；要隔離的是 payload（`CreateProtector("…", tenantId)`），不是金鑰。
- 各表的 `int` 自增 `Id` 只在租戶內唯一，跨租戶的鍵一律要用 `(TenantId, Id)`。
