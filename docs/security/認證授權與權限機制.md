# 認證授權與權限機制

- 文件版本：1.24
- 文件狀態：已實作
- 現行系統版本：0.10.5
- 首次實作版本：0.1.61
- 最後核對日期：2026/11/11

## 目的
本文件說明腳手架目前同時支援 Blazor UI Cookie 登入與 Web API JWT Bearer 認證。UI 與 API 使用不同 authentication scheme，避免互相干擾。

## Cookie 認證
Blazor UI 既有登入流程維持 Cookie authentication：
- scheme 使用 `MagicObjectHelper.CookieScheme`。
- Login path 為 `/Auths/Login`。
- Logout path 為 `/Auths/Logout`。
- Access denied path 為 `/Auths/Login`。

此機制主要服務 Razor/Blazor 頁面與既有後台使用者體驗。

效期與金鑰（0.9.39 起）：

- 票證效期由 `appsettings.json` 的 `CookieSettings` 決定：沒勾「記住我」**8 小時**
  （`ExpireMinutes`）、勾了 **30 天**（`RememberMeDays`，登入時以
  `AuthenticationProperties.ExpiresUtc` 明寫覆蓋，因為 `ExpireTimeSpan` 是整個 scheme 共用的）。
  `SlidingExpiration` 預設 `true`。⚠️ 0.9.39 之前三者都沒有設定，吃框架隱藏預設 14 天。
- 🔴 **Cookie 由 Data Protection 金鑰加密，金鑰換一批就全站登出。** 金鑰環固定寫到
  `SystemSettings:ExternalFileSystem:DataProtectionKeyPath`，並以
  `MagicObjectHelper.DataProtectionApplicationName` 固定判別子（不固定的話換部署路徑也會失效）。
  IIS 與多機部署的注意事項見[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)。
- ⚠️ **「未認證」導向登入頁，不是登出頁**（0.9.39 起）。`/Auths/Logout` 會無條件
  `SignOutAsync` 刪掉 Cookie，而「未認證」同時涵蓋「Cookie 一時讀不出來」——
  導到登出頁會把使用者原本還有效的「記住我」永久毀掉。其餘五個分支
  （`Sid` 無效／查無使用者／帳號停用／缺 `RoleView`／例外）維持導向登出，各有測試釘住。

### Google OAuth2 第三方登入
網頁登入除了帳號密碼外，亦可選用 Google 單一登入（SSO）。Google 驗證完成後同樣以 `MagicObjectHelper.CookieScheme` 完成登入，並串接既有權控（`RoleView`）。首次登入會自動建立停用中的帳號，待管理者啟用；Google 帳號只用於網頁登入，不支援 API（0.9.63 起）。完整設定與流程請見「Google OAuth2 第三方登入」一文。

## 頁面層授權（0.9.41 起）
0.9.41 之前 Blazor 頁面一律不標 `[Authorize]`，只靠下一節的 `AuthenticationStateHelper.Check(...)`。那個檢查要等元件先渲染一次才會導走，未登入者直接輸入 `/App` 等網址會**瞬間看到系統畫面**。現在：

- **HTTP 閘門**：`Components/Pages/_Imports.razor` 對整個 `Pages/` 標 `[Authorize]`。未登入的整頁請求在授權中介軟體就被 Cookie challenge 302 到 `/Auths/Login?ReturnUrl=…`，瀏覽器收不到任何頁面內容。
- **匿名白名單**：`Home`（`/`）、`Error`、`NotFound`、`Login`、`Logout`、`Pending`、`ForgotPassword`、`ResetPassword`（0.9.60 起）、`RefreshSession`（0.9.103 起）、`TwoFactor`（0.9.104 起）各自標 `[AllowAnonymous]`，由 `PageAuthorizationTests` 釘住；新增匿名頁面必須同步更新白名單。`NotFound` 必須匿名，否則 API 的 401／404 經狀態碼頁重跑後會被換成 302。
- **circuit 內**：`Routes.razor` 改用 `AuthorizeRouteView`，未授權時不渲染並導向登入頁。
- **檢查完成前不渲染**：`MainLayout` 在 `Check` 成功前不渲染側邊欄、頁首與頁面；各檢視在權限判定完成前不渲染（`isAccessChecked`）。已登入但沒有權限的人只會看到「你沒有權限存取此頁面」，不會先閃出工具列與表格框架。
- **ReturnUrl 防護**：登入後導回原頁面，但 `ReturnUrl` 一律經 `ReturnUrlGuard.Sanitize` 只接受站內路徑，其餘回 `/App`。0.9.41 之前會把外站網址原樣塞進 `RedirectUri`（open redirect）。

細節與新增頁面的規則見 [開發慣例與限制速查 §5.1](../architecture/開發慣例與限制速查.md)。

## UI 登入後檢查
Blazor 元件進入受保護頁面時，會透過 `AuthenticationStateHelper.Check(...)` 做 Cookie 認證後的二次檢查，並回傳 `AuthenticationCheckResult` 讓 Layout、NavMenu 或 Page 判斷是否繼續載入。

目前檢查項目：
- 未登入或 Cookie 無效時，導向 `/Auths/Login`（0.9.39 起，理由見上方 Cookie 認證一節），回傳 `Unauthenticated`。0.9.41 起整頁請求已先被 HTTP 閘門擋下，這個分支只剩 circuit 內的情況會走到。
- `ClaimTypes.Sid` 缺失、格式錯誤或不是有效使用者 Id 時，導向 `/Auths/Logout`，回傳 `InvalidUser`。
- 使用者不存在、帳號停用、缺少 `RoleView` 或角色權限 JSON 無法初始化時，導向 `/Auths/Logout`，回傳 `InvalidUser`。
- 使用者仍使用需要強制更換的預設密碼時，導向 `/ChangePassword`，回傳 `RequiresPasswordChange`。
- 工作階段版本不符時（0.9.103 起，見「工作階段失效」），導向 `/Auths/Logout?reason=session`，回傳 `SessionRevoked`。
- 必須使用兩步驟驗證卻還沒設定時（0.9.104 起，見「兩步驟驗證」），導向 `/TwoFactorSetup`，回傳 `RequiresTwoFactorSetup`。
- 檢查成功時，會把使用者與角色權限寫入 `CurrentUserService.CurrentUser`，回傳 `Succeeded`。

`/ChangePassword` 是強制改密碼流程允許進入的例外頁面；使用者在該頁完成密碼更新後，才會回到一般系統頁面。

## JWT Bearer 認證
Web API 使用 JWT Bearer：
- JWT 設定來源為 `appsettings.json` 的 `JwtSettings`。
- `JwtSettings` 會綁定到強型別 `MyProject.Web.Auth.JwtSettings`。
- Access token（JWT）用於 API 呼叫授權。
- Refresh token 0.10.0 起是**存在伺服器端的不透明字串**（`RefreshSession` 資料表，只存 SHA-256），每次使用就輪替，可撤銷；見下方「刷新 Token（0.10.0 起落庫、輪替與撤銷）」。
- 以 access token 呼叫 API 時，`ApiActorMiddleware`（0.10.0 起）每個請求從資料庫載入目前使用者並填入 `CurrentUserService`，規則與網頁的 `AuthenticationStateHelper.Check` 共用 `ICurrentUserLoader`：帳號不存在、停用或工作階段版本已換一律回 401 `ApiResult`。Business 服務因此在 API 路徑上也知道「誰在操作」（稽核、團隊範圍、自我保護）。

`JwtSettings` 欄位：
- `Issuer`
- `Audience`
- `SigningKey`
- `AccessTokenMinutes`
- `RefreshTokenDays`
- `ClockSkewMinutes`

## Auth API
`/api/Auth/*` 與 `/api/v1/Auth/*` 兩組路由相同。這組 API 是 WASM 前端與日後 App 共用的登入入口（0.10.0 起，見 [WASM 遷移計畫](../migration/WASM遷移計畫.md)）：
- `POST login`：使用帳號密碼登入，成功回傳 access token 與 refresh token（`isPersistent=true`）。0.9.104 起帳號已啟用兩步驟驗證時要另帶 `twoFactorCode`（見「兩步驟驗證」）。
- `POST refresh`：用 refresh token 換一組新的 access token 與 refresh token（舊的 refresh token 隨即失效）。失敗一律回 401「Refresh Token 無效或已過期。」。
- `POST logout`（0.10.0 起）：撤銷這個 refresh token 所屬的整串；不論 token 認不認得都回成功（避免被拿來試探）。已發出的 access token 仍可用到到期，用戶端應同時丟棄。
- `POST bridge`（0.10.0 起，WASM 遷移過渡期）：已用網頁 Cookie 登入的使用者打開 WASM 頁面時，用 Cookie 換一組 token。
  - ⚠️ 必須帶自訂標頭 `X-MyProject-Client`（值不拘），沒帶回 400：跨站請求要帶自訂標頭就得先通過 CORS 預檢，而 CORS 預設不允許任何來源，別的網站因此無法利用使用者的 Cookie 替他換出 token（CSRF 防護）。
  - 回應的 `isPersistent` 沿用 Cookie 的「記住我」：true 時前端存 localStorage，false 時存 sessionStorage；換出的整串 token 不會比 Cookie 活得久（見下方「整串上限」）。
  - ⚠️ 除了 Cookie 驗證器（比對快取），bridge 還會以資料庫再比一次 Cookie 上的工作階段版本，不符回 401。否則別的行程換了版本、快取還沒看到時，剛被撤銷的 Cookie 能換出一串帶新版本、躲過撤銷的 token（M1 獨立審查發現）。
  - 換出的 refresh token 記下 Cookie 的 `login_session` claim；從網頁登出（`/Auths/Logout`）時一併撤銷。0.10.0 之前發出的 Cookie 沒有這個 claim，bridge 會補上並以原本的屬性重新簽發 Cookie。
  - 純 token 登入上線（遷移 M9）後移除。
- `GET me`：0.10.0 起回傳 `SessionInfoDto`（原本 `CurrentUserDto` 的超集），每次從資料庫讀：身分、有效權限鍵、有效團隊、`mustChangePassword`、`requiresTwoFactorSetup`、`twoFactorEnabled`。權限只供畫面顯示用，真正的授權仍由每個 API 判斷。

## API 授權規範
- Project/Category/Team CRUD API 預設全部需要 Bearer token；0.10.4 起的使用者、角色、稽核紀錄、寄信紀錄 API，0.10.5 起的系統例外、日誌、日誌等級、AI 對話紀錄、Token 用量、AI 提示詞 API 也是（且只限管理員，見下方「只限管理員的 API」）。
- 登入、refresh、logout、bridge 允許匿名（bridge 自己驗證 Cookie）；0.10.3 起以一次性下載票證下載檔案的 `GET api/v1/downloads/{ticket}` 也允許匿名（票證本身就是憑證，見下方「一次性下載票證」）。
- **強制改密碼／強制設定兩步驟驗證期間擋下 API**（0.10.0 起，`ApiSessionGateFilter`，全域）：以 access token 呼叫時，使用者被要求先改密碼或先設定兩步驟驗證，業務 API 一律回 403 `ApiResult`，`errorCode` 為 `PASSWORD_CHANGE_REQUIRED` 或 `TWO_FACTOR_SETUP_REQUIRED`（`ApiErrorCodes`）；只有標 `[AllowDuringForcedSetup]` 的 `me`、`logout`、`bridge` 放行。網頁版靠換頁導到設定頁做到這件事，API 以前只要拿到 token 就能繞過。
- 0.10.0 起帳號已刪除的 access token 回 **401**（工作階段失效），以前要到權限檢查才擋下、回 403。
- API 未授權與禁止存取回應也會包成 `ApiResult`。
- 0.9.105 起專案、分類 API 與畫面套用同一套**團隊列級過濾**（`RecordTeamScope`，含團隊樹的下屬團隊）：範圍外的紀錄不在搜尋結果裡，單筆、修改、刪除回 404，指派範圍外的團隊回 400。
  JWT 身分的使用者 Id 由 `RequestActorResolver` 取出（NameIdentifier）；已登入卻取不到 Id 一律什麼都看不到。見 [紀錄分類與團隊權控 PRD](../prd/紀錄分類與團隊權控-prd.md)。

### 功能級／動作級授權（關閉 API 越權缺口）
- 除 `[Authorize]`（驗證 token）外，CRUD 控制器**每個動作方法**以 `[HasPermission(頁面, 動作)]`（`MyProject.Web/Filters/HasPermissionAttribute.cs`）強制授權；缺權限回傳 `ApiResult` 403。
- 動作對應：GET/`search`→`view`、POST→`create`、PUT→`edit`、DELETE→`delete`（動作常數見 `MyProject.Share/Helpers/PermissionKeys.cs`）。頁面鍵取自 `MagicObjectHelper`（Project→`專案項目`、Category→`分類清單`、Team→`團隊清單`）。
- **權限鍵兩型**：裸頁面鍵（如 `專案項目`）＝ 舊制＝該頁全部動作（向後相容）；動作鍵（如 `專案項目:edit`）＝ 特定動作。判定時「擁有動作鍵」或「擁有該頁裸鍵」即通過，故既有角色**零破壞**；「唯讀角色」只給 `專案項目:view`。
- 權限判定由 `IPermissionChecker`（`MyProject.Business/Services/Other/PermissionChecker.cs`）負責：管理員一律通過，否則比對使用者的有效權限鍵。此舉修正先前「API 只驗 token、任何登入者可呼叫任意 CRUD」的越權問題。
- **權限來源已切換為 RBAC 關聯表**：`UserRole → RolePermissionMap → Permission`（0.9.95 起另經 `RoleView` Join，已軟刪除的角色不給權限；關聯本身保留，角色還原後恢復），多角色取聯集（容錯併入 legacy `RoleViewId`）。角色/使用者編輯時由 `IRbacWriteService` 雙寫保持即時一致（0.9.136 起與主表同一個交易，寫入失敗時整筆回復）。
- ⚠️ **`CheckAccessPage(頁面鍵)` 的通過條件為「管理員 ∨ 裸頁面鍵 ∨ `頁面鍵:view`」（0.9.37 起）**。第三項不可省略：角色矩陣只勾「檢視」時產生的是動作鍵而**不含裸鍵**，少了它，唯讀角色會連頁面都打不開、選單也不顯示，動作級授權就只剩 API 端生效。這是 `CheckAccessAction`「動作鍵不中則退回裸鍵」的鏡像，由 `AuthenticationStateHelperTests` 兩條測試釘住上下界（`:view` 通過、`:create` 不通過）。完整教學見 [腳手架開發指引 §6（白話導讀）與 §7（技術細節）](../guides/腳手架開發指引.md)。
- ⚠️ **動作只有四個：`view`／`create`／`edit`／`delete`**。`export` 曾經存在於角色矩陣，但全系統沒有任何檢查點，屬「勾了等於沒勾」的死權限，已於 0.9.37 下架（`AdminOnlyPermissionTests` 守門）。要重新上架必須**先**有會檢查它的程式。
- **UI 選單顯示與 `AuthenticationStateHelper.CheckAccessPage`／`CheckAccessAction` 已改用 RBAC 權威來源**：登入態初始化（`Check`）時以 `IPermissionChecker.GetEffectivePermissionKeysAsync(userId)` 一次載入有效權限鍵（含多角色聯集）覆寫 `CurrentUser.RoleList`，UI 判定維持同步比對記憶體集合。`CheckAccessPage` 亦補上管理員短路（`GetEffectivePermissionKeysAsync` 不含 admin 隱含全通過）。至此 UI 與 API 共用單一 RBAC 來源、多角色 UI 生效，`TabViewJson` 退居角色編輯畫面回填用的相容欄位。

### 畫面上的按鈕：`<RequirePermission>`（0.9.110 起）
- 頁面能不能進由 `CheckAccessPage` 判斷（WASM 頁面是 `Permissions.CanAccessPage`，見下節）；頁面裡的新增、修改、刪除、還原等按鈕則用 `RequirePermission.razor`（0.10.2 起在 `MyProject.Web.Client/Commons/`，Server 與 WASM 共用，命名空間不變）包起來：
  `<RequirePermission Page="@MagicObjectHelper.角色_分類清單" Action="@PermissionActions.Edit">…</RequirePermission>`，有權限才渲染 `ChildContent`。
- 判斷規則與 `CheckAccessAction` 是**同一個純函式** `PermissionRules.CanAccessAction`（0.10.2 起檔案在 `MyProject.Models/Others/PermissionRules.cs`，讓 WASM 前端共用；命名空間仍是 `MyProject.Business.Helpers`）：管理員一律通過；擁有 `頁面:動作` 或裸頁面鍵即通過。`CheckAccessAction` 仍保留給程式碼內判斷，Razor 檢視一律改用元件（取代 `@if (AuthenticationStateHelper.CheckAccessAction(...))`）。目前用在專案、分類、團隊三個檢視。
- **`Fallback`（0.9.120 起）**：沒有權限時改渲染 `Fallback`；不給就什麼都不渲染。用途是「有權限可點、沒權限只能看」的內容，例如分類、團隊清單的狀態標籤：有 `edit` 時是可點的 `StatusPill`（點一下切換啟用／停用），沒有時顯示不可點的同一個標籤。
- ⚠️ 元件只管畫面顯示：伺服器端仍以 `[HasPermission]`／`IPermissionChecker` 為準，按鈕藏起來不等於動作被擋下。由 `RequirePermissionTests`（bUnit）釘住有／無權限與 `Fallback` 的行為。

### 畫面上的權限判斷：`PagePermissions`（0.10.2 起，WASM 遷移 M3）
- `RequirePermission`、`AuditHistoryButton` 與 WASM 頁面都經抽象類別 `PagePermissions`（`MyProject.Web.Client/Auth/PagePermissions.cs`）判斷：`IsAdmin`、`CanAccessPage(頁面鍵)`、`CanAccessAction(頁面鍵, 動作)`，規則一律是 `PermissionRules`（0.10.2 起新增 `CanAccessPage`，條件與 `CheckAccessPage` 相同：管理員 ∨ 裸頁面鍵 ∨ `頁面鍵:view`）。
- 兩種頁面只差「目前使用者」從哪裡來：Server 頁面是電路的 `CurrentUserService`（`MyProject.Web/Auth/ServerPagePermissions.cs`），WASM 頁面是 `/api/v1/Auth/me` 的回應（`ClientPagePermissions`，權限鍵已含角色展開後的結果）。
- 錯誤通知按「複製」能否附上完整例外（`MayCopyErrorDetail`）：管理員可以；Server 版另外在開發環境或 `Security:ReturnExceptionDetails=true` 時也可以（`ExceptionDetailPolicy`）。
- WASM 頁面開頁時寫 `Permissions.CanAccessPage(MagicObjectHelper.X)`，管理員專屬頁寫 `Permissions.IsAdmin`。沒有權限時「沒有權限開頁」的稽核（`Permission.Denied`，detail `via=WASM`）由伺服器在 `POST /api/v1/shell/page-view` 依選單的權限鍵寫（`SidebarMenuService.FindPagePermissionAsync`），頁面不自己寫。
- ⚠️ 和 `RequirePermission` 一樣只管畫面：WASM 頁面呼叫的每個 API 仍由 `[HasPermission]`（管理頁是 `[AdminOnly]`）判斷；某些參數要更高權限時（例如「顯示已刪除」與匯出已刪除要刪除權限）由 Controller 的 `ForbidUnless` 回 403。

### 每個 API action 都要標註授權意圖（0.10.4 起，WASM 遷移 M5）
- 只有 `[Authorize]` 的端點，任何登入的人都能呼叫；新增端點時忘了加權限是最常見的越權漏洞。0.10.4 起每個 `[ApiController]` 的 public action（含繼承自基底 controller 的）都必須標下列其中之一（標在類別上等於每個 action），由 `ApiAuthorizationConventionTests` 守門，漏標就失敗；除了 `[AllowAnonymous]`，controller 或 action 上也一定要有 `[Authorize]`：
  | 標註 | 意思 |
  |---|---|
  | `[HasPermission(頁面, 動作)]` | 依角色矩陣的頁面／動作權限 |
  | `[AdminOnly]` | 只有管理員（權限鍵不在角色矩陣的管理頁）|
  | `[SignedInUser]` | 登入即可、刻意不檢查頁面權限（每個人只處理自己的資料：個人資料、WASM 外框、通知、公告、`Auth/me`）|
  | `[AllowAnonymous]` | 不需登入 |
- 兩個新屬性在 `MyProject.Web/Filters/AdminOnlyAttribute.cs`。`[SignedInUser]` 本身沒有行為，只是讓「本來就不需要頁面權限」與「忘了標」分得出來。

### 只限管理員的 API：`[AdminOnly]`（0.10.4 起）
- 用在使用者（`api/v1/users`）、角色（`api/v1/roles`）、稽核紀錄（`api/v1/audit-logs`，含 0.10.2 起的異動歷程）、寄信紀錄（`api/v1/email-logs`），0.10.5 起再加系統例外紀錄（`api/v1/exception-logs`）、日誌檢視（`api/v1/logs`）、日誌等級（`api/v1/log-level`）、AI 對話紀錄（`api/v1/ai-call-logs`）、Token 用量（`api/v1/token-usage`）、AI 提示詞（`api/v1/prompt-templates`）。這些頁的權限鍵刻意不放進角色矩陣（見下方「權限模型與指派」），所以不能用 `[HasPermission]`。
- 是 `IAsyncAuthorizationFilter`：沒登入回 401；不是管理員回 403 `ApiResult`（「只有管理員可以使用這個功能。」），並寫一筆 `Permission.Denied`（目標 `ApiEndpoint`／請求路徑，detail「需要管理員」）。稽核寫入失敗不影響拒絕。
- 管理員身分看 `ApiActorMiddleware` 依 access token 從資料庫載入的目前使用者（`CurrentUserService`），所以剛被取消管理員的人**下一個請求**就被擋，不必等 token 到期。
- ⚠️ 只對 JWT Bearer 請求有效：以 Cookie 驗證的請求不經 `ApiActorMiddleware`，讀不到目前使用者。目前唯一的 Cookie 端點 `BackupController.Download` 暫時標 `[SignedInUser]`、在方法內查資料庫確認管理員（程式註解寫明它是管理員專屬、不可拿掉這個檢查），M7 改成下載票證時改用 `[AdminOnly]`。

### 自我保護也在 API 擋（0.10.4 起）
- 「不可強制登出自己」「不可重設自己的兩步驟驗證」在 Server 版只是畫面不給按，0.10.4 起 `UsersController` 也擋，回 400：「不可強制登出自己的帳號，請使用右上角的登出。」「不可重設自己的兩步驟驗證，請到「兩步驟驗證」頁停用或重新設定。」。
- 停用自己、刪除自己，以及對 support 的停用、刪除、當複製範本，本來就在服務層（`MyUserService`）擋，畫面與 API 一致。
- **support 不可改帳號**（0.10.4 起，服務層）：「「support」是系統預設的開發帳號，不可修改帳號。」。上面的保護都比對帳號，以前先把 support 改名就能繞過「不可停用、不可刪除」（改寫前就有的問題）。
- **角色 API 只採納權限目錄**（0.10.4 起）：`RolesController` 把送來的矩陣套到 `RolePermissionService.InitializePermissionSetting()` 的範本上，目錄裡沒有的群組、頁面、動作一律忽略，所以 API 呼叫端無法把管理員專屬鍵（例如「稽核紀錄」）授予角色。

## 權限模型與指派（RBAC）

- **資料表**：`Permission`（權限鍵目錄）、`RolePermissionMap`（角色↔權限）、`UserRole`（使用者↔角色，含主要角色與額外角色）、`UserTeam`（使用者↔團隊）。角色主檔沿用 `RoleView`。
  `Permission` 由啟動時的 `RbacBackfillSeeder` 依 `RolePermissionService.CreatePermissionCatalog()` 補齊裸頁面鍵；動作鍵在角色存檔時由 `IRbacWriteService` 視需要補建。
- **分界**：權限鍵在程式裡宣告（`MagicObjectHelper` 常數、`Menu.json` 的 `id` 與 `SidebarMenuService.MenuPermissionMap`）；角色↔權限、使用者↔角色／團隊全由資料決定，在後台管理。換客戶只改資料，新增功能才要改程式。
- **角色×動作矩陣**（角色管理 `RoleViewView`）：每個權限節點有「（全部）」與「檢視／新增／編輯／刪除」。勾「全部」存成裸頁面鍵、四個動作勾選框變為停用；只勾動作則存成 `頁面:動作` 鍵（`RolePermissionService.GetPermissionInput`／`SetPermissionInput` 產出與回填）。
- **使用者指派**（使用者管理 `MyUserView`）：主要角色（`MyUser.RoleViewId`）＋「額外角色（多角色，權限取聯集）」＋「團隊（直接綁定此使用者）」；存檔由 `MyUserService.SyncAssignmentsAsync` 經 `IRbacWriteService` 寫入 `UserRole`／`UserTeam`，編輯時以 `GetUserAssignmentsAsync` 回填（已刪除的角色不帶回）。
- **有效團隊**：`EffectiveTeamResolver` ＝ `UserTeam` ∪ 各角色（`UserRole` ∪ legacy `RoleViewId`）的 `RoleView.DefaultTeamsJson`，再展開團隊樹的下屬團隊；`RecordAccessScopeProvider` 以此建立列級過濾範圍（`RecordTeamScope`）。同一個角色的人可以有不同的資料範圍。
- **管理員專屬頁面**：「系統管理」群組（帳號與權限、監控與診斷、AI 管理、系統設定與維運、管理助理五個子群組）的權限鍵刻意不列入 `RolePermissionService.GetRoleListPermissionAllName()`，不會種出 `Permission`、角色矩陣不顯示、任何角色都無法被授予，只有管理員能進。由 `AdminOnlyPermissionTests` 守門。
- **沒有使用 ASP.NET Core policy-based authorization**：API 以 `HasPermissionAttribute`（`IAsyncAuthorizationFilter`）判斷，UI 以 `CheckAccessPage`／`PagePermissions`／`<RequirePermission>` 判斷，兩邊都讀 `IPermissionChecker` 的結果；`MyUser.IsAdmin` 一律短路通過。
  Agent 工具（0.9.142 起）也經 `IPermissionChecker` 判權：每個工具執行前由 `IAiToolPermissionGuard` 以目前使用者檢查工具宣告的頁面鍵與動作，沒有權限不執行，見 [MAF AI 呼叫架構 §6.2](../architecture/MAF-AI呼叫架構.md)。

## 帳號鎖定（防暴力破解）

`MyUserServiceLogin.LoginAsync` 內建連續失敗鎖定：

- 每次密碼錯誤累加 `MyUser.AccessFailedCount`；達 `LockoutSettings:MaxFailedAttempts`（預設 **5 次**，系統參數可調，最少 1）即設定 `MyUser.LockoutEndUtc = UtcNow + LockoutMinutes`（預設 15 分鐘），鎖定期間即使密碼正確也拒絕登入。
- 0.9.101 起：帳號不存在、密碼錯、鎖定中**同一則訊息**（「帳號或密碼不正確，或帳號已被暫時鎖定。」），登入頁固定顯示鎖定規則；鎖定時通知全體管理員並寄信；稽核 `Login.LockedOut` 只記造成鎖定的那一次。
- 成功登入後 `AccessFailedCount` 歸零。⚠️ 鎖定**到期時先歸零再驗證**（0.9.100 之前次數留在門檻上，到期後錯一次就立刻再鎖）。
- 管理員可在使用者清單「解鎖」（`MyUserService.UnlockAsync`，稽核 `User.Unlock`，不換版本號）；設定新密碼（管理員、本人、忘記密碼）也會解除鎖定。
- Google 登入也受鎖定限制（`ExternalLoginResult.Evaluate`，回登入頁 `?sso=locked`）。
- 0.9.104 起兩步驟驗證碼輸錯也累加同一個次數（稽核 `Login.TwoFactorFailed`）；⚠️ 密碼對了但還沒過第二步時**不**歸零，否則可以靠重輸密碼把次數洗掉、無限猜驗證碼。
- 相關欄位由 migration `AddAccountLockout` 建立（SQLite）。
- 0.9.60 起「忘記密碼」重設成功時會一併把 `AccessFailedCount` 歸零、`LockoutEndUtc` 清除 —— 被鎖住的人重設後可立即登入。

## 忘記密碼（0.9.60 起）

需要啟用寄信（`EmailSettings:Provider` 不是 `None`）。流程與欄位見 [登入與帳號流程 PRD](../prd/登入與帳號流程-prd.md)，
紅線見 [開發慣例與限制速查 §6.13](../architecture/開發慣例與限制速查.md)。安全相關的設計：

- **防列舉**：送出後畫面一律相同；信走背景佇列，回應時間不因「有寄信」而變長；原因只寫稽核。
  唯一例外是輸入內建帳號名稱 `support`：名稱公開，畫面明說「不提供忘記密碼服務」（0.9.85 起）。
- **token**：32 bytes 亂數，資料庫只存 SHA-256；效期 30 分（`PasswordResetSettings:TokenLifetimeMinutes`）；
  單次使用（交易內搶占），新申請與重設成功都作廢該帳號其餘 token。
- **排除對象**：`support`（每次啟動會被重設）、停用帳號、沒有本地密碼的 Google 帳號、Email 無效。
- **防濫用**：同帳號 60 秒冷卻（`RequestCooldownSeconds`）＋ 4 碼驗證碼（只是減速帶）。**沒有依 IP 限流**。
- **連結**：以 `EmailSettings:PublicBaseUrl` 組網址，不採用請求的 Host header（防 password reset poisoning）；
  重設頁回應 `Referrer-Policy: no-referrer`、`Cache-Control: no-store`。
- **已知限制**：重設後其他裝置的 Cookie／JWT 仍然有效（沒有 security stamp，理由同下方「Refresh Token 限制」）。
  0.9.103 起已解除：重設密碼會更換 `MyUser.SecurityStamp`，其他裝置的登入與 refresh 一併失效；0.9.136 起已發出的 access token 也一併失效（見「工作階段失效」）。

## 兩步驟驗證（TOTP，0.9.104 起）

使用者自己在 `/TwoFactorSetup` 以驗證器 App 掃 QR 開啟；管理員可依角色或系統參數強制。完整需求見 [兩步驟驗證 PRD](../prd/兩步驟驗證-prd.md)。
2026/07/09 原決定不做綁定 UI 與登入第二步，2026/10/03 翻案（[翻案紀錄](../changelog/2026-10-03-腳手架路線圖v2-前提修訂與翻案.md)）。

| 項目 | 做法 |
|---|---|
| 演算法 | `ITotpService`（RFC 6238：HMAC-SHA1、30 秒、6 碼，允許前後各一步誤差），`FindMatchingStep` 回傳符合的時間步 |
| 密鑰 | `MyUser.TwoFactorSecret` 以 Data Protection 加密（`ITwoFactorSecretProtector`，purpose `MyProject.TwoFactorSecret.v1`）；確認驗證碼之前只在頁面記憶體 |
| 防重放 | `MyUser.TwoFactorLastStep`；接受條件為條件式 `UPDATE … WHERE TwoFactorLastStep IS NULL OR < step` 影響 1 列 —— 同一組碼只能用一次，並行請求只有一個成功 |
| 備用碼 | 10 組（`XXXXX-XXXXX`），`TwoFactorBackupCode` 只存 HMAC-SHA256（金鑰含使用者 Id）；輸入不分大小寫、可省略橫線與空白；`UsedAtUtc IS NULL` 條件式標記，每組一次 |
| 登入第二步 | 密碼（或 Google）通過 → 5 分鐘的加密 Cookie `.MyProject.TwoFactorPending`（使用者 Id、工作階段版本、記住我、返回網址）→ `/Auths/TwoFactor`；送出時重查版本與狀態，錯誤計入鎖定次數 |
| 記住裝置 | `.MyProject.TwoFactorDevice`（使用者 Id＋工作階段版本，`TwoFactorSettings:RememberDeviceDays`，預設 30 天，0＝不提供）；⚠️ 版本換掉（改密碼、強制登出、重設）就失效 |
| Google 登入 | 帳號已啟用時同樣走第二步（Google 會連結同 Email 的既有帳號，不問就能繞過）；Google 建立、沒有本機密碼的帳號不能也不需要開啟 |
| Web API | `POST /api/Auth/login` 的 `twoFactorCode`：已啟用而未帶 → 401「需要兩步驟驗證碼。」（不計失敗）；帶錯 → 計失敗；必須使用卻還沒設定 → 401「請先在網頁完成兩步驟驗證設定。」 |
| 強制 | 任一有效角色（主要或額外，排除已刪除）勾 `RoleView.RequireTwoFactor`，或管理員且 `TwoFactorSettings:RequireForAdmins`；support 與沒有本機密碼的帳號豁免。`AuthenticationStateHelper.Check` 在「必須變更密碼」之後判斷，導向 `/TwoFactorSetup`（兩頁互不導向） |
| 停用與重設 | 本人停用要驗證碼（必須使用的人不能停用）；管理員「重設兩步驟驗證」清掉密鑰與備用碼。啟用、停用、重設都換工作階段版本，本人經 `/Auths/RefreshSession` 保持這台登入 |
| 稽核 | `User.TwoFactorEnable`／`TwoFactorDisable`／`TwoFactorBackupCodesRegenerate`／`TwoFactorReset`、`Login.TwoFactorFailed`；成功登入的 detail 帶 `mfa=totp|backup|device` |

- ⚠️ **金鑰環遺失或換掉**（`ExternalFileSystem:DataProtectionKeyPath`）時所有人的密鑰都解不開、驗證碼一律不正確：由管理員逐一重設。support 帳號不受強制，是這種情況下的救援入口。
- ⚠️ 系統備份同時包含資料庫與金鑰環 —— 備份檔外流仍等於密鑰外流（見[備份與還原操作手冊](../operations/備份與還原操作手冊.md)）。

## 帳號停用的檢查點（0.4.34 起）

`MyUser.Status = false` 的帳號，**在發證之前**就會被 `MyUserServiceLogin.LoginAsync` 擋下
（回「帳號已停用，請聯絡系統管理員。」並寫入 `Login.Disabled` 稽核）。
`Refresh` 換發時另以資料庫現況再確認一次（0.10.0 起在 `RefreshTokenStore.RotateAsync`：查無此人、已刪除或停用一律撤銷整串）。

> 沿革：0.4.34 之前 `LoginAsync` **完全沒有檢查 `Status`**。UI 路徑靠
> `AuthenticationStateHelper.Check` 在後續每次頁面載入時擋下，但 `/api/Auth/login`
> 會直接發出 JWT，而 `PermissionChecker` 與 `HasPermissionAttribute` 也都不看 `Status` ——
> 等於停用帳號仍可正常呼叫 API。

## 刷新 Token（0.10.0 起落庫、輪替與撤銷）

0.10.0（WASM 遷移 M1）起 refresh token 不再是 JWT，而是存在伺服器端的不透明字串（32 bytes 亂數），由 `IRefreshTokenStore`（`MyProject.Business/Services/Other/RefreshTokenStore.cs`）管理，資料表 `RefreshSession`：

| 規則 | 做法 |
|---|---|
| 只存雜湊 | 資料庫只有 SHA-256（`TokenHash`，唯一索引）；token 原值只回給用戶端一次，不進日誌與稽核 |
| 每次使用就輪替 | `refresh` 以條件式更新「搶下」舊的那一筆（`RevokedAtUtc` 與 `ReplacedById` 都是空才更新得到），再發一筆同一串（`FamilyId`）的新 token；有效期從這次起重算 `JwtSettings.RefreshTokenDays` 天 |
| 重用偵測 | 已被換掉的 token 在換掉 **30 秒後**又被拿來用（`ReplacedById` 有值），代表可能外洩：整串撤銷，稽核 `Token.ReuseDetected` |
| 寬限期 | 30 秒內（`RefreshTokenStore.ReuseGracePeriod`）又被用，多半是兩個分頁同時刷新、或刷新回應遺失後重送：回 401 但**不撤銷**，另一邊換到的新 token 照常可用（稽核 `Token.RefreshFailed reason=Superseded`）。代價是攻擊者若在 30 秒內搶先使用不會觸發撤銷 |
| 整串上限 | `AbsoluteExpiresAtUtc`：bridge 換出的 token 取 Cookie 的到期時間，每次輪替的到期時間都不超過它 —— Cookie 閒置逾時或「記住我」期限一到，WASM 端也不能靠刷新延長登入；API 登入不設上限 |
| 工作階段版本 | 紀錄記下發出當時的 `SecurityStamp`，刷新時與資料庫比對，不符就撤銷整串（稽核 `Token.RefreshFailed reason=SessionRevoked`）；改密碼、停用、改角色、強制登出等不必另外撤銷 |
| 帳號狀態 | 查無此人、已刪除或停用：撤銷整串（`reason=UserInactive`） |
| 登出 | `POST logout` 撤銷整串；從網頁登出時依 Cookie 的 `login_session` 撤銷 bridge 換出的 token |
| 清理 | 排程「登入 Token 清理」（`RefreshSessionRetentionJob`，每天 03:00）刪除已到期的紀錄；撤銷但未到期的要保留，重用偵測需要 |
| 用戶端資訊 | `ClientKind`（`api`／`web-bridge`）、`IsPersistent`、`DeviceLabel`（User-Agent 截斷）——裝置欄位預留給日後的「我的登入裝置」清單 |

**被限流（429）不是登入失效**（0.10.5 起，WASM 遷移 M6 實機發現）：WASM 前端以 Cookie 換 Token、刷新 Token 或讀 `/me` 時被伺服器限流，`ClientSession` 設 `IsThrottled`、**不清 Token、不回登入頁**，
外框顯示「請求過於頻繁，請稍後再試。」（`ClientSession.ThrottledMessage`，與伺服器 429 的訊息相同）與「重新整理」按鈕；刷新被 429 擋下時刷新 Token 沒有被用掉，也不改用 Cookie 重換（同樣會被擋）。
一般 API 或串流呼叫在刷新時被限流，`ApiClient` 回 429 的失敗結果，畫面照一般錯誤顯示。0.10.1～0.10.4 會一路試到「重新登入」，短時間內快速換頁的人被丟回登入頁。

> 沿革：0.4.34 起換發時回查資料庫（停用、降權即時生效）；2026/07/09 曾決定「refresh token 落庫不納入範圍」，0.9.103 以 `SecurityStamp` 做到「整位使用者失效」；
> 0.10.0 因 WASM 前端與日後 App 改用純 token 登入，「可靠登出、單顆撤銷、重用偵測」成為必要，改為落庫。
> ⚠️ 契約變更：refresh token 不再是 JWT，曾經解析 refresh token 內容的用戶端要改為只當不透明字串保存。

## 一次性下載票證（0.10.3 起，WASM 遷移 M4）

瀏覽器原生下載（`<a download>`）帶不了 `Authorization` 標頭，大檔也不能先讀進 WASM 記憶體再存檔；0.10.3 起專案附件改用一次性下載票證，取代以 Cookie 驗證的 `ProjectFileController`（已刪除）。

| 項目 | 做法 |
|---|---|
| 申請 | `POST api/v1/Project/files/{fileId}/ticket`：一般的 Bearer API，要 `專案項目:view`，而且要看得到這個附件（專案未刪除、在團隊範圍內、實體檔存在），否則 404 |
| 票證 | `DownloadTicketService`（`MyProject.Web/Downloads/`，singleton）：32 個隨機位元組（URL-safe Base64），記下種類、目標 Id、使用者 Id 與當下的安全戳記（`SecurityStamp` claim）；60 秒內有效 |
| 兌換 | 匿名的 `GET api/v1/downloads/{ticket}`（`DownloadsController`，`[AllowAnonymous]`）：兌換時就從記憶體移除，**只能用一次**，重放回 404；過期沒用的在下次發票證時清掉 |
| 兌換時重新檢查 | 以使用者 Id 與發票證時的安全戳記經 `ICurrentUserLoader` 重新載入使用者：帳號停用或刪除、改了密碼、被強制登出、角色變動（都會換安全戳記）一律拒絕；被要求先改密碼或先設定兩步驟驗證時也拒絕。再確認仍有 `專案項目:view`，最後 `ProjectService.GetFileDownloadAsync` 再查一次團隊範圍、專案是否已刪除、實體檔是否存在 |
| 失敗回應 | 不論哪一種原因，都回同一個 404 `ApiResult`「下載連結無效或已過期，請回到頁面重新下載。」；原因只寫日誌，不讓外部從回應分辨票證是否存在或使用者狀態 |
| 稽核 | 成功下載寫 `Project.FileDownload`（目標 `ProjectFile`、`file=原始檔名`），操作者是申請票證的人 |
| 續傳 | 不支援（票證只能用一次）；下載中斷要回頁面重新點檔名 |

- ⚠️ 票證存在**單一行程的記憶體**：IIS 應用程式集區要維持一個背景工作處理序（預設值），集區回收只會讓還沒用的票證失效。多台主機或多個處理序時要改成共享的儲存（目前沒有這個需求）。
- 票證會出現在網址上：用過或過期就失效，事後從代理伺服器或瀏覽器的記錄裡拿到也沒用；但票證還沒用、60 秒還沒到時，拿到網址的人可以先下載一次（兌換仍以**申請者**的身分與權限判斷，所以只會是申請者本來就能下載的那個檔案）。
- 已知限制：下載管理員或瀏覽器擴充功能若先預先抓取一次網址，會把票證用掉，真正的下載得到 404；使用者再點一次檔名即可。
- M7 的系統備份下載會沿用同一套機制（`BackupController` 目前仍走 Cookie）。

## 工作階段失效（0.9.103 起）

`MyUser.SecurityStamp` 是這位使用者的工作階段版本。登入 Cookie 與 access token 都帶著它（claim `security_stamp`），refresh token 紀錄也記著發出當時的版本；版本一換，舊的工作階段全部失效。

**快取立即失效（0.10.0 起）**：版本的查詢有快取（見下表），以前改版本的地方都直接寫資料庫、沒有清快取，被強制登出、停用或改密碼的人最多還能再用 `ValidationIntervalMinutes`（預設 5 分鐘）。
0.10.0 起 `SecurityStampInvalidationInterceptor`（掛在 DbContext 選項上）攔到任何「改 `MyUser.SecurityStamp` 的 UPDATE」或「刪除 `MyUser`」就清掉 `SecurityStampCache`（交易中則提交後再清一次），同一個行程內**下一個請求就失效**。
快取另有世代計數：查詢開始後才被清掉的話，這次讀到的舊版本不寫回快取（否則查詢與清除同時發生時，舊版本又會被快取最多 5 分鐘）。追蹤實體存檔與 `ExecuteUpdate` 都攔得到，日後新增的改版本路徑也不必記得手動清。別的行程（IIS 重疊回收）仍最晚在快取存活時間後看到。

| 什麼時候換 | 在哪裡 |
|---|---|
| 設定新密碼（管理員、本人、忘記密碼重設） | `IPasswordPolicy.ApplyAsync`（登入時的舊雜湊升級不換） |
| 設定檔換了 support 的密碼 | `SupportUserSeeder` |
| 停用、管理員身分變更、角色變更（主要或額外） | `MyUserService.UpdateAsync`（只改姓名、Email 不換） |
| 清單點狀態標籤啟用／停用（0.9.120 起） | `MyUserService.SetStatusAsync`（同時換 `ConcurrencyStamp`；support 與自己不可停用） |
| 刪除 | `MyUserService.DeleteAsync` |
| 管理員按「強制登出」 | `MyUserService.ForceLogoutAsync`（稽核 `User.ForceLogout`，不換 `ConcurrencyStamp`） |

| 檢查點 | 時機 |
|---|---|
| 已開著的頁面 | `AuthenticationStateHelper.Check` 每次換頁比對（沿用 5 秒內的查詢結果），不符 → `/Auths/Logout?reason=session`，稽核 `Login.SessionExpired` |
| HTTP 請求（新開頁、重新整理、檔案下載） | `SecurityStampCookieEvents.OnValidatePrincipal`，資料庫查詢快取 `CookieSettings:ValidationIntervalMinutes`（預設 5 分鐘）；⚠️ 快取不符時再查一次資料庫才判定失效（避免剛換過版本後重新登入被誤判） |
| 下載票證（0.10.3 起） | 兌換時以發票證時記下的使用者 Id 與版本經 `ICurrentUserLoader` 重新載入：版本不符、帳號停用或刪除，一律回同一個 404 |
| API | refresh 時比對紀錄上的版本：不符撤銷整串、回 401、稽核 `Token.RefreshFailed reason=SessionRevoked`。0.9.136 起每個 Bearer 請求也在 `OnTokenValidated` 比對（`ISecurityStampService.IsValidAsync`，快取同上），0.10.0 起 `ApiActorMiddleware` 再以 `ICurrentUserLoader` 確認（5 秒快取）；不符或帳號停用／刪除就回 401 `ApiResult` |

- ⚠️ Bearer 驗證只接受 access token（`OnTokenValidated` 檢查 `token_type`）。0.9.102 之前 refresh token 也能直接當 Bearer 用，等於 access token 的效期形同虛設。
- **這台裝置保持登入**：自己在 `/ChangePassword` 改密碼、管理員在使用者管理改了自己的角色或密碼之後，頁面取得一張 2 分鐘、一次性的 ticket 整頁導到 `/Auths/RefreshSession` 換發新 Cookie；
  使用者管理 0.10.4 起是 WASM 頁：`PUT api/v1/users/{id}` 改到自己而且版本換掉時，回傳 `SessionRefreshUrl`（`/Auths/RefreshSession?ticket=…&returnUrl=%2Fmyusers`，同一套 ticket，由伺服器發），WASM 頁整頁導過去；換發後頁面重新以新的 Cookie 換 Token。其他裝置維持登出。改別人時不回這個網址，對方下一個請求就被登出（API 401、刷新被拒）；
  ⚠️ 必須帶著原本的 Cookie（同一個使用者、舊版本相符）而且 ticket 的新版本等於資料庫目前的版本才換發 —— 否則別人可以把自己的 ticket 連結寄給你，讓你登入成他。沿用原本 Cookie 的記住我與到期時間。
- 資料庫預設值是空字串：IIS 重疊回收時舊版程式新增的帳號沒有版本，登入時補上；比對時空字串一律不符。升級前簽發的 Cookie 與 token 沒有這個 claim，**升級後每個人要重新登入一次**。
