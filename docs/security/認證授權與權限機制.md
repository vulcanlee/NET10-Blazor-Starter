# 認證授權與權限機制

- 文件版本：1.29
- 文件狀態：已實作
- 現行系統版本：0.10.10
- 首次實作版本：0.1.61
- 最後核對日期：2026/11/13

## 目的
本文件說明腳手架的登入（認證）與權限（授權）機制。0.10.8（WASM 遷移 M9）起**網頁與 Web API 都只用 Token 登入**：存取 Token 是 JWT Bearer，刷新 Token 是存在伺服器的不透明字串；**不再發登入 Cookie**。
整個系統只剩一個 Cookie：Google 登入過程中暫存 Google 身分的外部 Cookie（`MagicObjectHelper.ExternalCookieScheme`，5 分鐘，回呼處理完就清掉），它不是登入憑證。

> 沿革：0.1.61～0.10.7 網頁用 Cookie 登入（`MagicObjectHelper.CookieScheme`，名稱 `.MyProject.Auth`）、API 用 JWT，兩個 scheme 並存；0.10.0～0.10.7 的 WASM 頁面以 `POST bridge` 用 Cookie 換 Token。
> 0.10.8 移除登入 Cookie 的 scheme、`bridge`、`/Auths/RefreshSession`（換發 Cookie）、`SecurityStampCookieEvents`、`CookieClaims`、待驗與記住裝置兩個 Cookie；預設驗證機制改為 JWT，系統健康監控的「身分驗證」改檢查「JWT 是預設驗證機制且設定完整」。

## 網頁登入（0.10.8 起純 Token）
登入相關頁面（`/Auths/Login`、`/Auths/TwoFactor`、`/Auths/ForgotPassword`、`/Auths/ResetPassword`、`/Auths/Pending`、`/Auths/Logout`）都在 WASM，資料經 `api/v1/Auth/...`（見下方「Auth API」）。

- 登入頁呼叫 `POST api/v1/Auth/login/web`：帳號密碼對了就發一組**網頁發出管道**（`RefreshClientKinds.Web`，`web`）的 Token；帳號已啟用兩步驟驗證時，記住過的裝置直接完成，否則回**待驗票證**、前端帶到 `/Auths/TwoFactor`。失敗訊息與鎖定規則同下方「帳號鎖定」。
- 前端（`ClientSession`、`TokenStore`、`wwwroot/js/client-auth.js`）把 Token 存在瀏覽器：勾「記住我」存 **localStorage**（關掉瀏覽器仍維持登入），沒勾存 **sessionStorage**（關掉分頁就登出）；同一個鍵，一次只存一邊。
- 存取 Token 快到期或 API 回 401 時，前端以刷新 Token 換新：多個分頁以 Web Locks 排隊，拿到鎖先重讀 storage（別的分頁可能已經換好）；換不到才清掉 Token、帶 `returnUrl` 回登入頁。

效期由 `appsettings.json` 的 **`SessionSettings`**（0.10.8 起，取代 `CookieSettings`）決定，只管網頁管道；App 等以 `POST api/v1/Auth/login` 登入的仍看 `JwtSettings`：

| 設定 | 預設 | 意思 |
|---|---|---|
| `IdleTimeoutMinutes` | 480 | 沒勾「記住我」時，刷新 Token 多久沒用就失效（分鐘）；關掉分頁也會登出，兩者取先到 |
| `IdleTimeoutSliding` | `true` | 沒勾時是否滑動：`true` 每次刷新重新起算；`false` 從登入起最多 `IdleTimeoutMinutes` 分鐘（一直使用也會到期） |
| `RememberMeDays` | 30 | 勾了「記住我」時整次登入的上限（天，從登入那一刻算，不滑動） |
| `AccessTokenMinutes` | 15 | 網頁的存取 Token 效期（分鐘），到期前前端自動換新 |
| `ValidationIntervalMinutes` | 5 | 工作階段版本的快取時間：改密碼、停用、強制登出後，別台主機最晚幾分鐘看到；同一台立即 |

- ⚠️ 舊鍵相容：設定檔或環境變數裡還有 `CookieSettings:ExpireMinutes`／`RememberMeDays`／`ValidationIntervalMinutes`／`SlidingExpiration` 時，會蓋過新區段的值，啟動時記一筆警告（`SessionSettings.ApplyLegacyCookieSettings`）；升級不會悄悄改變登入效期。
  `SlidingExpiration=false` 對應 `IdleTimeoutSliding=false`（0.10.8 獨立審查補上，以前會被靜默忽略、變成永不到期）。
- 🔴 **Data Protection 金鑰環仍然重要**（`SystemSettings:ExternalFileSystem:DataProtectionKeyPath`，以 `MagicObjectHelper.DataProtectionApplicationName` 固定判別子）：登入 Token 不靠它（存取 Token 用 `JwtSettings:SigningKey` 簽章，刷新 Token 只存雜湊在資料庫），所以換金鑰環**不會**讓已登入的人登出；
  但待驗票證、記住裝置 Token、兩步驟驗證的設定票證、TOTP 密鑰、Google 登入的外部 Cookie 與 OAuth state 都以它加密 —— 金鑰環換掉，記住過的裝置要重新輸入驗證碼、已設定兩步驟驗證的人驗證碼一律不正確（要由管理員重設）。IIS 與多機部署的注意事項見[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)。

### 新分頁、跨分頁登出與「同一個瀏覽器只有一個身分」（0.10.8 起）
- **新分頁取得 Token**：沒勾「記住我」時 Token 在 sessionStorage，新開的分頁讀不到。新分頁以 BroadcastChannel 向已開的分頁要，對方在刷新鎖內以自己的刷新 Token 呼叫 `POST api/v1/Auth/session/fork` **開一串新的**交過來（沿用登入識別 `LoginSessionId`、「記住我」與整串上限；自己那一串不輪替）。**每個分頁各一串**，互相不會觸發重用偵測。1 秒（`ClientSession.OtherTabsTimeout`）沒人回應就帶 `returnUrl` 回登入頁。
  `session/fork` 只接受網頁管道、目前有效（沒被換掉、沒撤銷、沒過期）的刷新 Token；建立新串後再確認來源沒有剛好被登出，否則新串一併作廢（0.10.8 獨立審查）。
- **登出**：`/Auths/Logout` 呼叫 `POST api/v1/Auth/logout`，伺服器依 `LoginSessionId` 撤銷**這次登入的每一串**（每個分頁各一串）；前端清掉 Token、以 BroadcastChannel 通知其他分頁，其他分頁刷新失敗就回登入頁。別人的登出不受影響。
- **storage 事件**：記住我的 Token（localStorage）被別的分頁清掉 → 回登入頁；換成另一個人 → 整頁重新載入（畫面上的資料是原本那個人的）；同一人刷新了 → 沿用新的。
- **同一個瀏覽器只有一個身分**（與以前的 Cookie 相同，0.10.8 獨立審查）：登入成功（登入頁、兩步驟驗證頁、Google 兌換）時廣播「誰登入了」，顯示另一個人的分頁丟掉自己的 Token、重新載入改用新的登入。否則同一個瀏覽器兩個分頁登入不同人時，新分頁可能拿到另一個人的 Token。
- 開一個登入分頁**不會**把其他分頁登出（以前的 `auth-reset.js` 會清 storage，0.10.8 起移除）。

### Google OAuth2 第三方登入
網頁登入除了帳號密碼外，亦可選用 Google 單一登入（SSO），串接既有權控（`RoleView`）。首次登入會自動建立停用中的帳號，待管理者啟用；Google 帳號只用於網頁登入，不支援 API（0.9.63 起）。
0.10.8 起回呼不再發登入 Cookie，改產生**一次性代碼**導回 `/Auths/Login#code=…`，前端以 `POST api/v1/Auth/google/exchange` 換 Token：代碼只存雜湊、60 秒、只能兌換一次，並**綁定發起的瀏覽器**（前端產生驗證值，只把雜湊帶給伺服器，兌換時出示原值）；沒帶綁定值的請求（舊書籤、直接打網址）一律回登入頁、不建立也不連結帳號。Google 登入沒有「記住我」。完整設定與流程請見「Google OAuth2 第三方登入」一文。
0.10.10 起（WASM 遷移 M11）前端可以是獨立站台：登入頁的 Google 按鈕經 `ApiAddress.GoogleLogin` 整頁導到 **API 主機**的 `/Auths/Google/Login`，回呼（`/signin-google`）也在 API 主機；之後所有導回前端的網址（代碼、被拒絕的 `?sso=…`、待開通頁、錯誤頁）一律經 `ClientSettings.FrontendUrl` 組成——雙站台時接在 `ClientSettings:BaseUrl` 後面，同站台時是本站路徑。**只用設定值，不採用請求的 Host 或任何參數**，不可成為開放式重新導向（`returnUrl` 另經 `Url.IsLocalUrl` 檢查，只放進代碼、不拿來導向）。

### 雙站台的 CORS（0.10.10 起）
前端與 API 不同網址（`ClientSettings:BaseUrl` 有值）時，API 主機以 CORS 允許前端呼叫：允許的來源只有 `ClientSettings:BaseUrl` 的來源加上 `Cors:AllowedOrigins`（前端以外的其他網站）；只收 `Authorization`、`Content-Type` 兩個標頭與 GET／POST／PUT／DELETE，公開 `Content-Disposition`，**不允許憑證**（Token 在 `Authorization` 標頭，不用 Cookie）；預檢（OPTIONS）在驗證與限流之前回應，不會被 401／429 擋下。兩者都沒設定（同站台的預設）時不回任何 CORS 標頭。CORS 只是瀏覽器端的限制，不是授權——每個 API 照樣以 Token 授權。

## 頁面層授權
0.10.8 起**所有頁面都在 WASM**，0.10.9 起（WASM 遷移 M10）Server 渲染基礎已移除；0.10.10 起（M11）前端是獨立的靜態網站（入口頁 `MyProject.Web.Client/wwwroot/index.html`，取代 0.10.9 的主機頁 `Components/App.razor`），主機只剩 API（同站台時另提供前端的靜態檔）。頁面不在 HTTP 層擋，由外框把關：

- **頁面不可標 `[Authorize]`**：伺服器不發登入 Cookie，整頁請求時不知道誰在登入；預設驗證機制是 JWT，標了反而讓整頁請求拿到 401 JSON。由 `PageAuthorizationTests` 守門。
- **未登入的整頁請求只拿到靜態的 `index.html`**（0.10.10 起；同站台由主機、雙站台由靜態站回應，任何網址都一樣），沒有任何系統內容；0.10.9 以前是主機頁渲染的空 WASM 外殼（不預先渲染）。
- **外框閘門**：`ClientMainLayout` 在登入檢查（Token 與 `/api/v1/Auth/me`）通過前不渲染側邊欄、頁首與頁面；沒有 Token 也要不到（見上方「新分頁」）就帶 `returnUrl` 回登入頁。各檢視在權限判定完成前也不渲染，沒有權限的人只看到「你沒有權限存取此頁面」。
- **匿名白名單（9 頁）**：`/`（啟動頁）、`/Error`、`/not-found`、`/Auths/Login`、`/Auths/Logout`、`/Auths/Pending`、`/Auths/ForgotPassword`、`/Auths/ResetPassword`、`/Auths/TwoFactor`，由 `PageAuthorizationTests` 釘住；新增匿名頁面必須同步更新白名單，並確認頁面不含需要登入才能看的內容。匿名頁的 API 呼叫不帶 Token、收到 401 不導回登入頁；沒登入時瀏覽器錯誤只留在主控台、不回報伺服器。
- **ReturnUrl 防護**：登入後導回原頁面，但 `returnUrl` 一律經 `ReturnUrlGuard.Sanitize`（0.10.8 起在 `MyProject.Web.Client/Auth/`）只接受站內路徑，其餘回 `/App`；伺服器端（`login/web`、待驗票證、Google 代碼）也再過一次。
- 資料一律經 API，每個 API 各自以 Token 授權（見下方「API 授權規範」）——頁面的閘門只管畫面，不是安全界線。

> 沿革：0.9.41 之前頁面不標 `[Authorize]`、只靠元件內的檢查，未登入者會瞬間看到系統畫面；0.9.41～0.10.7 以 `Components/Pages/_Imports.razor` 對 Server 頁面標 `[Authorize]`，未登入的整頁請求被 Cookie challenge 302 到登入頁。

細節與新增頁面的規則見 [開發慣例與限制速查 §5.1](../architecture/開發慣例與限制速查.md)。

## 登入後檢查
WASM 外框啟動時由 `ClientSession.InitializeAsync` 檢查：讀 storage 的 Token（沒有就向已開分頁要）→ 呼叫 `/api/v1/Auth/me`。伺服器端每個以存取 Token 呼叫的請求由 `ApiActorMiddleware` 經 `ICurrentUserLoader` 從資料庫載入目前使用者（與日後的 App 同一套規則）：

- 沒有 Token、Token 無效或換不到新的：清掉、帶 `returnUrl` 回登入頁。
- 帳號不存在、停用、已刪除或工作階段版本已換：API 回 401，前端刷新也被拒（稽核 `Login.SessionExpired`，見「工作階段失效」），回登入頁。
- 必須先變更密碼（`mustChangePassword`）：整頁導到 `/ChangePassword`；必須先設定兩步驟驗證（`requiresTwoFactorSetup`）：整頁導到 `/TwoFactorSetup`。⚠️ 已經在那一頁就不再導（兩頁 0.10.8 起也在 WASM，再導一次會無限重新載入）；兩頁互不導向。這兩頁照樣顯示完整外框，外框需要的 API 標 `[AllowDuringForcedSetup]`，業務 API 一律 403（見「API 授權規範」）。
- **沒有主要角色的帳號不能用網頁**：網頁管道的 Token 一律回 403 `NO_PRIMARY_ROLE`（`ApiActorMiddleware`），前端登出。App 以 API 登入的 Token 不受影響。（M7 起 `/App` 是 WASM 時這條其實有缺口，0.10.8 先寫測試證明後補上。）
- 檢查成功：`/me` 回身分、有效權限鍵、有效團隊，外框與 `PagePermissions` 據此顯示選單與按鈕。

伺服器回 429（被限流）不是登入失效：不清 Token、不回登入頁，見下方「刷新 Token」最後一段。

> 沿革：0.10.7 以前 Server 頁面由 `AuthenticationStateHelper.Check(...)`（`MyProject.Business/Services/Other/`）在換頁時檢查並導頁（`/Auths/Logout?reason=session`、`/ChangePassword`、`/TwoFactorSetup`）；0.10.8 起已沒有 Server 頁面，類別在 0.10.9（M10）隨 Server 渲染基礎一起刪除（`AuthenticationCheckResult` 同）。

## JWT Bearer 認證
網頁（WASM 前端）與 Web API 都用 JWT Bearer，0.10.8 起它是**預設驗證機制**：
- JWT 設定來源為 `appsettings.json` 的 `JwtSettings`，綁定到強型別 `MyProject.Web.Auth.JwtSettings`。
- Access token（JWT）用於 API 呼叫授權。效期：網頁管道看 `SessionSettings:AccessTokenMinutes`（預設 15 分鐘），API 登入看 `JwtSettings:AccessTokenMinutes`。
- 0.10.8 起存取 Token 另帶 `fid`（所屬的那一串刷新 Token）與 `client_kind`（發出管道 `web`／`api`）。每個請求檢查那一串是否已撤銷（`IRefreshTokenStore.IsFamilyActiveAsync`）：登出、重用撤銷之後，已發出的存取 Token 也立即失效 —— 同一台主機立即，多台主機最多 30 秒（`RefreshTokenStore.FamilyCheckWindow`）。0.10.8 以前發的存取 Token 沒有 `fid`，照舊只比工作階段版本，最晚到期就沒了。
- Refresh token 0.10.0 起是**存在伺服器端的不透明字串**（`RefreshSession` 資料表，只存 SHA-256），每次使用就輪替，可撤銷；見下方「刷新 Token（0.10.0 起落庫、輪替與撤銷）」。
- 以 access token 呼叫 API 時，`ApiActorMiddleware`（0.10.0 起）每個請求從資料庫載入目前使用者並填入 `CurrentUserService`（經 `ICurrentUserLoader`）：帳號不存在、停用或工作階段版本已換一律回 401 `ApiResult`；網頁管道的 Token 另擋沒有主要角色的帳號（403 `NO_PRIMARY_ROLE`）。Business 服務因此在 API 路徑上也知道「誰在操作」（稽核、團隊範圍、自我保護）。

`JwtSettings` 欄位：
- `Issuer`
- `Audience`
- `SigningKey`
- `AccessTokenMinutes`（API 登入）
- `RefreshTokenDays`（API 登入）
- `ClockSkewMinutes`

## Auth API
`/api/Auth/*` 與 `/api/v1/Auth/*` 兩組路由相同（0.10.8 新增的網頁端點只有 `api/v1`）。完整端點見 [Web API 端點目錄](../architecture/Web%20API%20端點目錄.md)。

**App 與網頁共用**：
- `POST login`：App 用。帳號密碼登入，成功回傳 access token 與 refresh token（發出管道 `api`，`isPersistent=true`）。0.9.104 起帳號已啟用兩步驟驗證時要在同一個請求另帶 `twoFactorCode`（見「兩步驟驗證」）。契約 0.10.8 不變。
- `POST refresh`：用 refresh token 換一組新的 access token 與 refresh token（舊的 refresh token 隨即失效）；新 Token 的效期依那一串的發出管道。失敗一律回 401「Refresh Token 無效或已過期。」。
- `POST logout`（0.10.0 起）：網頁管道（0.10.8 起）撤銷**這次登入的每一串**（依 `LoginSessionId`，每個分頁各一串），API 管道撤銷這一串；已發出的存取 Token 也立即失效（見上方 `fid`）。不論 token 認不認得都回成功（避免被拿來試探）。
- `GET me`：0.10.0 起回傳 `SessionInfoDto`，每次從資料庫讀：身分、有效權限鍵、有效團隊、`mustChangePassword`、`requiresTwoFactorSetup`、`twoFactorEnabled`。權限只供畫面顯示用，真正的授權仍由每個 API 判斷。

**網頁登入用（0.10.8 起，WASM 遷移 M9；全部只有 `api/v1`）**：
- `GET login-settings`（匿名）：登入頁、忘記／重設密碼頁、啟動頁要顯示的公開設定（系統名稱與說明、Google 與寄信是否啟用、鎖定次數與分鐘、記住裝置與記住我天數、密碼規則、重設連結有效分鐘）。不算登入配額。
- `POST login/web`（匿名）：見上方「網頁登入」。必須設定兩步驟驗證的帳號也照樣拿到 Token，由閘門擋業務 API、前端帶到設定頁。
- `POST two-factor`（匿名）：待驗票證＋驗證碼或備用碼＋「記住這台裝置」，回 Token（勾了另回記住裝置 Token）。等待期間改了密碼、被停用或強制登出，這次登入作廢（`TWO_FACTOR_TICKET_INVALID`，前端回登入頁）。
- `POST google/exchange`（匿名）：Google 一次性代碼＋瀏覽器驗證值換 Token；帳號已啟用兩步驟驗證時回待驗票證（記住過的裝置除外）。
- `POST session/fork`（匿名，以刷新 Token 為憑證）：新分頁取得 Token，見上方「新分頁」。
- `POST password/forgot`、`password/reset/check`、`password/reset`（匿名）：忘記與重設密碼，回應不快取、不帶 Referer。`GET`／`POST password/change`（登入、強制期間可用）：變更自己的密碼，回這台的新 Token。
- `GET two-factor/setup`、`POST two-factor/setup/start`、`enable`、`backup-codes`、`disable`（登入、強制期間可用）：自己的兩步驟驗證設定；`start` 由伺服器產生 QR Code（PNG data URI）與設定票證，金鑰確認前不進資料庫；`enable`、`disable` 回這台的新 Token。

> 已移除（0.10.8）：`POST bridge`（0.10.0～0.10.7 WASM 頁面以網頁 Cookie 換 Token 的過渡端點，必須帶 `X-MyProject-Client` 標頭防 CSRF、換出的 Token 不比 Cookie 活得久）。

## API 授權規範
- Project/Category/Team CRUD API 預設全部需要 Bearer token；0.10.4 起的使用者、角色、稽核紀錄、寄信紀錄 API，0.10.5 起的系統例外、日誌、日誌等級、AI 對話紀錄、Token 用量、AI 提示詞 API 也是（且只限管理員，見下方「只限管理員的 API」）；0.10.7 起的 Agent 測試台、系統管理助理、Agent 工作流程與通知推播串流也是（見下方「Agent 與通知推播的 API」）。
- 允許匿名：`login`、`refresh`、`logout`，0.10.8 起的 `login-settings`、`login/web`、`two-factor`、`google/exchange`、`session/fork`、`password/forgot`、`password/reset/check`、`password/reset`（各自以帳密、票證、代碼或刷新 Token 為憑證）；0.10.3 起以一次性下載票證下載檔案的 `GET api/v1/downloads/{ticket}` 也允許匿名（票證本身就是憑證，見下方「一次性下載票證」）。
- **強制改密碼／強制設定兩步驟驗證期間擋下 API**（0.10.0 起，`ApiSessionGateFilter`，全域）：以 access token 呼叫時，使用者被要求先改密碼或先設定兩步驟驗證，業務 API 一律回 403 `ApiResult`，`errorCode` 為 `PASSWORD_CHANGE_REQUIRED` 或 `TWO_FACTOR_SETUP_REQUIRED`（`ApiErrorCodes`）。
  只有標 `[AllowDuringForcedSetup]` 的端點放行：`me`、`logout`，0.10.8 起加上 `password/change`、`two-factor/setup/*`（兩個設定頁搬到 WASM），以及這兩頁外框要用的 `shell/*`、通知（含推播串流）、公告橫幅的讀取與關閉（都只涉及自己的資料）——所以強制頁照樣顯示完整外框。⚠️ 新增端點時不要隨手加這個屬性，否則強制改密碼的人可以直打 API 繞過。
- 0.10.0 起帳號已刪除的 access token 回 **401**（工作階段失效），以前要到權限檢查才擋下、回 403。
- API 未授權與禁止存取回應也會包成 `ApiResult`。
- **限流在驗證之後**（0.10.8 獨立審查）：`UseRateLimiter` 排在 `UseAuthentication` 之後，已登入的請求依**每人**分區、未登入依 IP。以前排在前面，全部都是匿名、全部依 IP 分區，同一個出口 IP（NAT、反向代理）的所有人共用一份配額。
  較嚴格的**登入配額**（`RateLimit:LoginRequestsPerMinute`，預設每 IP 每分鐘 10 次）0.10.8 起涵蓋 App 的 `login`、`two-factor`（含自己的設定：重新產生備用碼與停用時驗證碼錯了不計入鎖定，只靠這裡擋）、`google`、`password`、`session`；**網頁登入 `login/web` 與 `login-settings` 不算**（網頁登入照以前的畫面登入靠帳號鎖定防猜密碼，並受一般 API 每 IP 配額；算進去的話同一個出口 IP 的公司早上登入尖峰會被擋）。
- 0.9.105 起專案、分類 API 與畫面套用同一套**團隊列級過濾**（`RecordTeamScope`，含團隊樹的下屬團隊）：範圍外的紀錄不在搜尋結果裡，單筆、修改、刪除回 404，指派範圍外的團隊回 400。
  JWT 身分的使用者 Id 由 `RequestActorResolver` 取出（NameIdentifier）；已登入卻取不到 Id 一律什麼都看不到。見 [紀錄分類與團隊權控 PRD](../prd/紀錄分類與團隊權控-prd.md)。

### 功能級／動作級授權（關閉 API 越權缺口）
- 除 `[Authorize]`（驗證 token）外，CRUD 控制器**每個動作方法**以 `[HasPermission(頁面, 動作)]`（`MyProject.Web/Filters/HasPermissionAttribute.cs`）強制授權；缺權限回傳 `ApiResult` 403。
- 動作對應：GET/`search`→`view`、POST→`create`、PUT→`edit`、DELETE→`delete`（動作常數見 `MyProject.Share/Helpers/PermissionKeys.cs`）。頁面鍵取自 `MagicObjectHelper`（Project→`專案項目`、Category→`分類清單`、Team→`團隊清單`）。
- **權限鍵兩型**：裸頁面鍵（如 `專案項目`）＝ 舊制＝該頁全部動作（向後相容）；動作鍵（如 `專案項目:edit`）＝ 特定動作。判定時「擁有動作鍵」或「擁有該頁裸鍵」即通過，故既有角色**零破壞**；「唯讀角色」只給 `專案項目:view`。
- 權限判定由 `IPermissionChecker`（`MyProject.Business/Services/Other/PermissionChecker.cs`）負責：管理員一律通過，否則比對使用者的有效權限鍵。此舉修正先前「API 只驗 token、任何登入者可呼叫任意 CRUD」的越權問題。
- **權限來源已切換為 RBAC 關聯表**：`UserRole → RolePermissionMap → Permission`（0.9.95 起另經 `RoleView` Join，已軟刪除的角色不給權限；關聯本身保留，角色還原後恢復），多角色取聯集（容錯併入 legacy `RoleViewId`）。角色/使用者編輯時由 `IRbacWriteService` 雙寫保持即時一致（0.9.136 起與主表同一個交易，寫入失敗時整筆回復）。
- ⚠️ **頁面權限 `PermissionRules.CanAccessPage(使用者, 頁面鍵)`（0.10.8 以前另有 `AuthenticationStateHelper.CheckAccessPage`，規則相同）的通過條件為「管理員 ∨ 裸頁面鍵 ∨ `頁面鍵:view`」（0.9.37 起）**。第三項不可省略：角色矩陣只勾「檢視」時產生的是動作鍵而**不含裸鍵**，少了它，唯讀角色會連頁面都打不開、選單也不顯示，動作級授權就只剩 API 端生效。這是 `PermissionRules.CanAccessAction`「動作鍵不中則退回裸鍵」的鏡像，由 `CurrentUserLoaderTests` 兩條測試釘住上下界（`:view` 通過、`:create` 不通過；0.10.8 以前在 `AuthenticationStateHelperTests`）。完整教學見 [腳手架開發指引 §6（白話導讀）與 §7（技術細節）](../guides/腳手架開發指引.md)。
- ⚠️ **動作只有四個：`view`／`create`／`edit`／`delete`**。`export` 曾經存在於角色矩陣，但全系統沒有任何檢查點，屬「勾了等於沒勾」的死權限，已於 0.9.37 下架（`AdminOnlyPermissionTests` 守門）。要重新上架必須**先**有會檢查它的程式。
- **UI 選單顯示與頁面、按鈕的判斷都用 RBAC 權威來源**：`ICurrentUserLoader` 載入目前使用者時以 `IPermissionChecker.GetEffectivePermissionKeysAsync(userId)` 一次載入有效權限鍵（含多角色聯集）覆寫 `CurrentUser.RoleList`；選單由 `SidebarMenuService`（`GET api/v1/shell/menu`）以 `PermissionRules.CanAccessPage` 過濾，WASM 前端以 `/api/v1/Auth/me` 回的同一組鍵經 `PagePermissions` 判斷，都是同步比對記憶體集合。`PermissionRules` 含管理員短路（`GetEffectivePermissionKeysAsync` 不含 admin 隱含全通過）。0.10.8 以前 Server 頁面由 `AuthenticationStateHelper.Check` 載入、`CheckAccessPage`／`CheckAccessAction` 判斷（0.10.9 起已刪除）。至此 UI 與 API 共用單一 RBAC 來源、多角色 UI 生效，`TabViewJson` 退居角色編輯畫面回填用的相容欄位。

### 畫面上的按鈕：`<RequirePermission>`（0.9.110 起）
- 頁面能不能進由 `Permissions.CanAccessPage` 判斷（見下節）；頁面裡的新增、修改、刪除、還原等按鈕則用 `RequirePermission.razor`（0.10.2 起在 `MyProject.Web.Client/Commons/`，命名空間不變）包起來：
  `<RequirePermission Page="@MagicObjectHelper.角色_分類清單" Action="@PermissionActions.Edit">…</RequirePermission>`，有權限才渲染 `ChildContent`。
- 判斷規則是**純函式** `PermissionRules.CanAccessAction`（0.10.2 起檔案在 `MyProject.Models/Others/PermissionRules.cs`，讓 WASM 前端共用；命名空間仍是 `MyProject.Business.Helpers`）：管理員一律通過；擁有 `頁面:動作` 或裸頁面鍵即通過。程式碼內判斷用 `Permissions.CanAccessAction`，Razor 檢視一律用元件（0.10.8 以前 Server 頁面的 `AuthenticationStateHelper.CheckAccessAction` 規則相同，0.10.9 起已刪除）。目前用在專案、分類、團隊三個檢視。
- **`Fallback`（0.9.120 起）**：沒有權限時改渲染 `Fallback`；不給就什麼都不渲染。用途是「有權限可點、沒權限只能看」的內容，例如分類、團隊清單的狀態標籤：有 `edit` 時是可點的 `StatusPill`（點一下切換啟用／停用），沒有時顯示不可點的同一個標籤。
- ⚠️ 元件只管畫面顯示：伺服器端仍以 `[HasPermission]`／`IPermissionChecker` 為準，按鈕藏起來不等於動作被擋下。由 `RequirePermissionTests`（bUnit）釘住有／無權限與 `Fallback` 的行為。

### 畫面上的權限判斷：`PagePermissions`（0.10.2 起，WASM 遷移 M3）
- `RequirePermission`、`AuditHistoryButton` 與 WASM 頁面都經抽象類別 `PagePermissions`（`MyProject.Web.Client/Auth/PagePermissions.cs`）判斷：`IsAdmin`、`CanAccessPage(頁面鍵)`、`CanAccessAction(頁面鍵, 動作)`，規則一律是 `PermissionRules`（0.10.2 起新增 `CanAccessPage`，條件與 `CheckAccessPage` 相同：管理員 ∨ 裸頁面鍵 ∨ `頁面鍵:view`）。
- 「目前使用者」來自 `/api/v1/Auth/me` 的回應（`ClientPagePermissions`，權限鍵已含角色展開後的結果）。0.10.7 以前的 Server 頁面用電路的 `CurrentUserService`（`MyProject.Web/Auth/ServerPagePermissions.cs`，0.10.9 起已刪除）；0.10.8 起已沒有 Server 頁面。
- 錯誤通知按「複製」能否附上完整例外（`MayCopyErrorDetail`）：只有管理員可以。0.10.7 以前 Server 頁面另外在開發環境或 `Security:ReturnExceptionDetails=true` 時也可以（`ServerPagePermissions` 依 `ExceptionDetailPolicy`；0.10.8 起頁面全部在 WASM 即只認管理員，0.10.9 起 `ServerPagePermissions` 已刪除）。`ExceptionDetailPolicy` 現在只決定 API 500 回應是否帶例外細節。
- WASM 頁面開頁時寫 `Permissions.CanAccessPage(MagicObjectHelper.X)`，管理員專屬頁寫 `Permissions.IsAdmin`。沒有權限時「沒有權限開頁」的稽核（`Permission.Denied`，detail `via=WASM`）由伺服器在 `POST /api/v1/shell/page-view` 依選單的權限鍵寫（`SidebarMenuService.FindPagePermissionAsync`），頁面不自己寫。
- ⚠️ 和 `RequirePermission` 一樣只管畫面：WASM 頁面呼叫的每個 API 仍由 `[HasPermission]`（管理頁是 `[AdminOnly]`）判斷；某些參數要更高權限時（例如「顯示已刪除」與匯出已刪除要刪除權限）由 Controller 的 `ForbidUnless` 回 403。

### 每個 API action 都要標註授權意圖（0.10.4 起，WASM 遷移 M5）
- 只有 `[Authorize]` 的端點，任何登入的人都能呼叫；新增端點時忘了加權限是最常見的越權漏洞。0.10.4 起每個 `[ApiController]` 的 public action（含繼承自基底 controller 的）都必須標下列其中之一（標在類別上等於每個 action），由 `ApiAuthorizationConventionTests` 守門，漏標就失敗；除了 `[AllowAnonymous]`，controller 或 action 上也一定要有 `[Authorize]`：
  | 標註 | 意思 |
  |---|---|
  | `[HasPermission(頁面, 動作)]` | 依角色矩陣的頁面／動作權限 |
  | `[AdminOnly]` | 只有管理員（權限鍵不在角色矩陣的管理頁）|
  | `[SignedInUser]` | 登入即可、刻意不檢查頁面權限（每個人只處理自己的資料：個人資料、WASM 外框、通知〔0.10.7 起含推播串流〕、公告、`Auth/me`）|
  | `[AllowAnonymous]` | 不需登入 |
- 兩個新屬性在 `MyProject.Web/Filters/AdminOnlyAttribute.cs`。`[SignedInUser]` 本身沒有行為，只是讓「本來就不需要頁面權限」與「忘了標」分得出來。

### 只限管理員的 API：`[AdminOnly]`（0.10.4 起）
- 用在使用者（`api/v1/users`）、角色（`api/v1/roles`）、稽核紀錄（`api/v1/audit-logs`，含 0.10.2 起的異動歷程）、寄信紀錄（`api/v1/email-logs`），0.10.5 起再加系統例外紀錄（`api/v1/exception-logs`）、日誌檢視（`api/v1/logs`）、日誌等級（`api/v1/log-level`）、AI 對話紀錄（`api/v1/ai-call-logs`）、Token 用量（`api/v1/token-usage`）、AI 提示詞（`api/v1/prompt-templates`），0.10.6 起再加排程作業（`api/v1/scheduled-jobs`）、系統健康監控（`api/v1/system-health`）、系統備份（`api/v1/backups`）、資料保留與清理（`api/v1/data-retention`）、資料庫用量（`api/v1/database-usage`）、系統參數（`api/v1/system-parameters`）、公告管理（`api/v1/announcements` 的清單、新增、修改、刪除）與首頁的排程作業小工具（`GET api/v1/dashboard/scheduled-jobs`），0.10.7 起再加系統管理助理（`api/v1/admin-assistant`，含巡檢報告）。這些頁的權限鍵刻意不放進角色矩陣（見下方「權限模型與指派」），所以不能用 `[HasPermission]`。
- 是 `IAsyncAuthorizationFilter`：沒登入回 401；不是管理員回 403 `ApiResult`（「只有管理員可以使用這個功能。」），並寫一筆 `Permission.Denied`（目標 `ApiEndpoint`／請求路徑，detail「需要管理員」）。稽核寫入失敗不影響拒絕。
- 管理員身分看 `ApiActorMiddleware` 依 access token 從資料庫載入的目前使用者（`CurrentUserService`），所以剛被取消管理員的人**下一個請求**就被擋，不必等 token 到期。
- ⚠️ 只對 JWT Bearer 請求有效（靠 `ApiActorMiddleware` 載入的目前使用者）。0.10.6 起已沒有以 Cookie 驗證的 API：原本唯一的 Cookie 端點 `BackupController.Download`（0.10.4～0.10.5 暫時標 `[SignedInUser]`、在方法內查資料庫確認管理員）已刪除，改成 `[AdminOnly]` 的 `POST api/v1/backups/{檔名}/ticket` 申請一次性下載票證（見下方「一次性下載票證」）；0.10.8 起整個系統也不再發登入 Cookie。

### Agent 與通知推播的 API（0.10.7 起，WASM 遷移 M8）
- **Agent 測試台**（`api/v1/agent-playground`）：每個 action `[HasPermission(角色_Agent測試台, View)]`；產生測試專案另要 `專案項目:create`、清除測試專案另要 `專案項目:delete`（同一個 action 疊兩個 `[HasPermission]`，兩個都要過）。
- **系統管理助理**（`api/v1/admin-assistant`，含巡檢報告）：每個 action `[AdminOnly]`（權限鍵不在角色矩陣，同 Server 版只有管理員）。
- **Agent 工作流程**（`api/v1/agent-workflows`）：類別上 `[HasPermission(角色_Agent工作流程)]`。執行跨好幾個請求，伺服器的執行登錄表只讓**擁有者**操作（別人的執行一律 404，不洩漏是否存在）；每次回覆以那個請求重新載入的目前使用者更新執行 scope 的身分，權限被改了下一步就照新的算。
- 三組的對話與紀錄一律只限本人（`AiAgentConversationService` 以目前使用者過濾）；工具仍由工具外殼以目前使用者的權限在執行前檢查（§「權限模型與指派」的 Agent 工具）。核准不可復原的動作要輸入「確認」，伺服器也擋（400）。
- **通知推播串流**（`POST api/v1/notifications/stream`）：`[SignedInUser]`，只訂閱**自己**的通知與全體公告的變動，串流不帶內容（外框收到後自己以一般 API 重查）。長連線只在請求開始時檢查一次身分，所以伺服器在**存取 Token 到期前 1 分鐘**主動結束串流（最後一筆 `renew`，前端刷新 Token 後重連），連線滿 30 分鐘也結束（`reconnect`）——帳號停用、強制登出、改密碼最慢在下一次重連時生效（期間外框的其他 API 照常被擋）。**每位使用者最多 3 條**推播連線（第 4 條起 429）。`NotificationSettings:PushEnabled=false` 時端點回 404。

### 自我保護也在 API 擋（0.10.4 起）
- 「不可強制登出自己」「不可重設自己的兩步驟驗證」在 Server 版只是畫面不給按，0.10.4 起 `UsersController` 也擋，回 400：「不可強制登出自己的帳號，請使用右上角的登出。」「不可重設自己的兩步驟驗證，請到「兩步驟驗證」頁停用或重新設定。」。
- 停用自己、刪除自己，以及對 support 的停用、刪除、當複製範本，本來就在服務層（`MyUserService`）擋，畫面與 API 一致。
- **support 不可改帳號**（0.10.4 起，服務層）：「「support」是系統預設的開發帳號，不可修改帳號。」。上面的保護都比對帳號，以前先把 support 改名就能繞過「不可停用、不可刪除」（改寫前就有的問題）。
- **角色 API 只採納權限目錄**（0.10.4 起）：`RolesController` 把送來的矩陣套到 `RolePermissionService.InitializePermissionSetting()` 的範本上，目錄裡沒有的群組、頁面、動作一律忽略，所以 API 呼叫端無法把管理員專屬鍵（例如「稽核紀錄」）授予角色。

## 權限模型與指派（RBAC）

- **資料表**：`Permission`（權限鍵目錄）、`RolePermissionMap`（角色↔權限）、`UserRole`（使用者↔角色，含主要角色與額外角色）、`UserTeam`（使用者↔團隊）。角色主檔沿用 `RoleView`。
  `Permission` 由啟動時的 `RbacBackfillSeeder` 依 `RolePermissionService.CreatePermissionCatalog()` 補齊裸頁面鍵；動作鍵在角色存檔時由 `IRbacWriteService` 視需要補建。
- **分界**：權限鍵在程式裡宣告（`MagicObjectHelper` 常數、`Menu.json` 的 `id` 與 `SidebarMenuService.MenuPermissionMap`）；角色↔權限、使用者↔角色／團隊全由資料決定，在後台管理。換客戶只改資料，新增功能才要改程式。
- **角色×動作矩陣**（角色管理 `RoleViewView`）：每個權限節點有「（全部）」與「檢視／新增／編輯／刪除」。勾「全部」存成裸頁面鍵、四個動作勾選框變為停用；只勾動作則存成 `頁面:動作` 鍵（`RolePermissionService.GetPermissionInput`／`SetPermissionInput` 產出與回填）。
- **使用者指派**（使用者管理 `MyUserView`）：主要角色（`MyUser.RoleViewId`）＋「額外角色（多角色，權限取聯集）」＋「團隊（直接綁定此使用者）」；存檔由 `MyUserService.SyncAssignmentsAsync` 經 `IRbacWriteService` 寫入 `UserRole`／`UserTeam`，編輯時以 `GetUserAssignmentsAsync` 回填（已刪除的角色不帶回）。
- **有效團隊**：`EffectiveTeamResolver` ＝ `UserTeam` ∪ 各角色（`UserRole` ∪ legacy `RoleViewId`）的 `RoleView.DefaultTeamsJson`，再展開團隊樹的下屬團隊；`RecordAccessScopeProvider` 以此建立列級過濾範圍（`RecordTeamScope`）。同一個角色的人可以有不同的資料範圍。
- **管理員專屬頁面**：「系統管理」群組（帳號與權限、監控與診斷、AI 管理、系統設定與維運、管理助理五個子群組）的權限鍵刻意不列入 `RolePermissionService.GetRoleListPermissionAllName()`，不會種出 `Permission`、角色矩陣不顯示、任何角色都無法被授予，只有管理員能進。由 `AdminOnlyPermissionTests` 守門。
- **沒有使用 ASP.NET Core policy-based authorization**：API 以 `HasPermissionAttribute`（`IAsyncAuthorizationFilter`）判斷，UI 以 `PagePermissions`／`<RequirePermission>`（規則 `PermissionRules`）判斷，兩邊都讀 `IPermissionChecker` 的結果；`MyUser.IsAdmin` 一律短路通過。
  Agent 工具（0.9.142 起）也經 `IPermissionChecker` 判權：每個工具執行前由 `IAiToolPermissionGuard` 以目前使用者檢查工具宣告的頁面鍵與動作，沒有權限不執行，見 [MAF AI 呼叫架構 §6.2](../architecture/MAF-AI呼叫架構.md)。

## 帳號鎖定（防暴力破解）

`MyUserServiceLogin.LoginAsync` 內建連續失敗鎖定：

- 每次密碼錯誤累加 `MyUser.AccessFailedCount`；達 `LockoutSettings:MaxFailedAttempts`（預設 **5 次**，系統參數可調，最少 1）即設定 `MyUser.LockoutEndUtc = UtcNow + LockoutMinutes`（預設 15 分鐘），鎖定期間即使密碼正確也拒絕登入。
- 0.9.101 起：帳號不存在、密碼錯、鎖定中**同一則訊息**（「帳號或密碼不正確，或帳號已被暫時鎖定。」），登入頁固定顯示鎖定規則；鎖定時通知全體管理員並寄信；稽核 `Login.LockedOut` 只記造成鎖定的那一次。
- 成功登入後 `AccessFailedCount` 歸零。⚠️ 鎖定**到期時先歸零再驗證**（0.9.100 之前次數留在門檻上，到期後錯一次就立刻再鎖）。
- 管理員可在使用者清單「解鎖」（`MyUserService.UnlockAsync`，稽核 `User.Unlock`，不換版本號）；設定新密碼（管理員、本人、忘記密碼）也會解除鎖定。
- Google 登入也受鎖定限制（`ExternalLoginResult.Evaluate`，回登入頁 `?sso=locked`）。
- 0.9.104 起兩步驟驗證碼輸錯也累加同一個次數（稽核 `Login.TwoFactorFailed`）；⚠️ 密碼對了但還沒過第二步時**不**歸零，否則可以靠重輸密碼把次數洗掉、無限猜驗證碼。
- 相關欄位由 migration `AddAccountLockout` 建立（SQLite）。
- 0.9.60 起「忘記密碼」重設成功時會一併把 `AccessFailedCount` 歸零、`LockoutEndUtc` 清除 —— 被鎖住的人重設後可立即登入。

## 忘記密碼（0.9.60 起）

需要啟用寄信（`EmailSettings:Provider` 不是 `None`）。流程與欄位見 [登入與帳號流程 PRD](../prd/登入與帳號流程-prd.md)，
紅線見 [開發慣例與限制速查 §6.13](../architecture/開發慣例與限制速查.md)。安全相關的設計：

- **防列舉**：送出後畫面一律相同；信走背景佇列，回應時間不因「有寄信」而變長；原因只寫稽核。
  唯一例外是輸入內建帳號名稱 `support`：名稱公開，畫面明說「不提供忘記密碼服務」（0.9.85 起）。
- **token**：32 bytes 亂數，資料庫只存 SHA-256；效期 30 分（`PasswordResetSettings:TokenLifetimeMinutes`）；
  單次使用（交易內搶占），新申請與重設成功都作廢該帳號其餘 token。
- **排除對象**：`support`（每次啟動會被重設）、停用帳號、沒有本地密碼的 Google 帳號、Email 無效。
- **防濫用**：同帳號 60 秒冷卻（`RequestCooldownSeconds`）＋ 4 碼驗證碼（只是減速帶）；0.10.8 起 `api/v1/Auth/password/*` 算進較嚴格的登入配額（每 IP 每分鐘 10 次，與其他登入端點共用一份，見「API 授權規範」）。0.10.7 以前沒有依 IP 限流。
- **連結**：以 `EmailSettings:PublicBaseUrl` 組網址（0.10.10 起雙站台時是 `ClientSettings:BaseUrl`，指向前端），不採用請求的 Host header（防 password reset poisoning）；
  重設頁的整頁回應（0.10.8 起頁面在 WASM，由主機對 `/Auths/ResetPassword` 加上；0.10.10 起雙站台由前端靜態站的 `web.config` 加上）與 `password/*` API 的回應都帶 `Referrer-Policy: no-referrer`、`Cache-Control: no-store`。
- **已知限制**：重設後其他裝置的 Cookie／JWT 仍然有效（沒有 security stamp，理由同下方「Refresh Token 限制」）。
  0.9.103 起已解除：重設密碼會更換 `MyUser.SecurityStamp`，其他裝置的登入與 refresh 一併失效；0.9.136 起已發出的 access token 也一併失效（見「工作階段失效」）。

## 兩步驟驗證（TOTP，0.9.104 起）

使用者自己在 `/TwoFactorSetup` 以驗證器 App 掃 QR 開啟；管理員可依角色或系統參數強制。完整需求見 [兩步驟驗證 PRD](../prd/兩步驟驗證-prd.md)。
2026/07/09 原決定不做綁定 UI 與登入第二步，2026/10/03 翻案（[翻案紀錄](../changelog/2026-10-03-腳手架路線圖v2-前提修訂與翻案.md)）。

| 項目 | 做法 |
|---|---|
| 演算法 | `ITotpService`（RFC 6238：HMAC-SHA1、30 秒、6 碼，允許前後各一步誤差），`FindMatchingStep` 回傳符合的時間步 |
| 密鑰 | `MyUser.TwoFactorSecret` 以 Data Protection 加密（`ITwoFactorSecretProtector`，purpose `MyProject.TwoFactorSecret.v1`）；確認驗證碼之前只在頁面記憶體 |
| 防重放 | `MyUser.TwoFactorLastStep`；接受條件為條件式 `UPDATE … WHERE TwoFactorLastStep IS NULL OR < step` 影響 1 列 —— 同一組碼只能用一次，並行請求只有一個成功 |
| 備用碼 | 10 組（`XXXXX-XXXXX`），`TwoFactorBackupCode` 只存 HMAC-SHA256（金鑰含使用者 Id）；輸入不分大小寫、可省略橫線與空白；`UsedAtUtc IS NULL` 條件式標記，每組一次 |
| 登入第二步 | 密碼（或 Google）通過 → `login/web`（或 `google/exchange`）回 5 分鐘的**待驗票證**（`TwoFactorLoginTickets`，Data Protection purpose `MyProject.TwoFactorTicket.v1`；內容是使用者 Id、工作階段版本、記住我、返回網址、登入方式，到期時間在加密內容裡），前端存在這個分頁的 sessionStorage → `/Auths/TwoFactor` 送 `POST two-factor`；送出時重查版本與狀態（換了就作廢、回登入頁），驗證碼錯了計入鎖定次數、票證仍可再用；成功一次就作廢（同一張票證兩個請求同時通過，只有先作廢的拿得到 Token）。0.10.7 以前是加密 Cookie `.MyProject.TwoFactorPending` |
| 記住裝置 | **記住裝置 Token**（Data Protection purpose `MyProject.TwoFactorDeviceToken.v1`；使用者 Id＋工作階段版本，`TwoFactorSettings:RememberDeviceDays`，預設 30 天，0＝不提供），前端存 localStorage，下次登入時帶給 `login/web`／`google/exchange`；⚠️ 版本換掉（改密碼、強制登出、重設）就失效。0.10.7 以前是 Cookie `.MyProject.TwoFactorDevice` |
| Google 登入 | 帳號已啟用時同樣走第二步（Google 會連結同 Email 的既有帳號，不問就能繞過）；Google 建立、沒有本機密碼的帳號不能也不需要開啟 |
| App 的 API 登入 | `POST /api/Auth/login` 的 `twoFactorCode`：已啟用而未帶 → 401「需要兩步驟驗證碼。」（不計失敗）；帶錯 → 計失敗；必須使用卻還沒設定 → 401「請先在網頁完成兩步驟驗證設定。」 |
| 設定 | `/TwoFactorSetup`（0.10.8 起在 WASM）經 `api/v1/Auth/two-factor/setup`：`start` 由伺服器產生金鑰與 QR Code（PNG data URI），金鑰在確認驗證碼前不進資料庫，改以 15 分鐘的**設定票證**（`TwoFactorSetupTickets`，purpose `MyProject.TwoFactorSetup.v1`，綁定使用者，成功啟用一次就作廢）交給前端，啟用時帶回來 |
| 強制 | 任一有效角色（主要或額外，排除已刪除）勾 `RoleView.RequireTwoFactor`，或管理員且 `TwoFactorSettings:RequireForAdmins`；support 與沒有本機密碼的帳號豁免。在「必須變更密碼」之後判斷（`/me` 的 `requiresTwoFactorSetup`），WASM 外框導向 `/TwoFactorSetup`（兩頁互不導向；已在該頁不再導）；業務 API 403 `TWO_FACTOR_SETUP_REQUIRED` |
| 停用與重設 | 本人停用要驗證碼（必須使用的人不能停用）；管理員「重設兩步驟驗證」清掉密鑰與備用碼。啟用、停用、重設都換工作階段版本；本人啟用或停用時 API 回這台的新 Token，前端存起來後整頁回 `/Profile`（0.10.7 以前經 `/Auths/RefreshSession` 換發 Cookie） |
| 稽核 | `User.TwoFactorEnable`／`TwoFactorDisable`／`TwoFactorBackupCodesRegenerate`／`TwoFactorReset`、`Login.TwoFactorFailed`；成功登入的 detail 帶 `mfa=totp|backup|device` |

- ⚠️ **金鑰環遺失或換掉**（`ExternalFileSystem:DataProtectionKeyPath`）時所有人的密鑰都解不開、驗證碼一律不正確：由管理員逐一重設。support 帳號不受強制，是這種情況下的救援入口。
- ⚠️ 系統備份同時包含資料庫與金鑰環 —— 備份檔外流仍等於密鑰外流（見[備份與還原操作手冊](../operations/備份與還原操作手冊.md)）。

## 刷新 Token（0.10.0 起落庫、輪替與撤銷）

0.10.0（WASM 遷移 M1）起 refresh token 不再是 JWT，而是存在伺服器端的不透明字串（32 bytes 亂數），由 `IRefreshTokenStore`（`MyProject.Business/Services/Other/RefreshTokenStore.cs`）管理，資料表 `RefreshSession`：

| 規則 | 做法 |
|---|---|
| 只存雜湊 | 資料庫只有 SHA-256（`TokenHash`，唯一索引）；token 原值只回給用戶端一次，不進日誌與稽核 |
| 每次使用就輪替 | `refresh` 以條件式更新「搶下」舊的那一筆（`RevokedAtUtc` 與 `ReplacedById` 都是空才更新得到），再發一筆同一串（`FamilyId`）的新 token；有效期從這次起依發出管道重算（`WebSessionTokens.Lifetime`）：API 管道 `JwtSettings.RefreshTokenDays` 天，網頁管道勾「記住我」`SessionSettings.RememberMeDays` 天、沒勾 `IdleTimeoutMinutes` 分鐘（所以沒勾時是閒置逾時） |
| 重用偵測 | 已被換掉的 token 在換掉 **30 秒後**又被拿來用（`ReplacedById` 有值），代表可能外洩：整串撤銷，稽核 `Token.ReuseDetected`。0.10.8 起網頁登入**同一次登入（`LoginSessionId`）的每一串一起撤銷**（獨立審查：否則偷到刷新 Token 的人先 `session/fork` 一串自己的，被偵測到時只撤銷被偵測的那一串，偷開的照常可用）；`session/fork` 也只接受目前有效的那一個，被換掉的舊 Token 不能拿來開新串 |
| 寬限期 | 30 秒內（`RefreshTokenStore.ReuseGracePeriod`）又被用，多半是兩個分頁同時刷新、或刷新回應遺失後重送：回 401 但**不撤銷**，另一邊換到的新 token 照常可用（稽核 `Token.RefreshFailed reason=Superseded`）。代價是攻擊者若在 30 秒內搶先使用不會觸發撤銷 |
| 整串上限 | `AbsoluteExpiresAtUtc`：網頁勾「記住我」是登入起 `RememberMeDays` 天；沒勾而且 `IdleTimeoutSliding=false` 是登入起 `IdleTimeoutMinutes` 分鐘；沒勾而且滑動（預設）不設上限。每次輪替、`session/fork`、換一串的到期時間都不超過它；API 登入不設上限。（0.10.0～0.10.7 bridge 換出的 token 取 Cookie 的到期時間） |
| 工作階段版本 | 紀錄記下發出當時的 `SecurityStamp`，刷新時與資料庫比對，不符就撤銷整串（稽核 `Token.RefreshFailed reason=SessionRevoked`）；改密碼、停用、改角色、強制登出等不必另外撤銷 |
| 帳號狀態 | 查無此人、已刪除或停用：撤銷整串（`reason=UserInactive`） |
| 登出 | `POST logout`：網頁管道依 `LoginSessionId` 撤銷這次登入的每一串（每個分頁各一串），API 管道撤銷這一串；已發出的存取 Token 經 `fid` 檢查也立即失效（同一台主機立即、多台最多 30 秒，`FamilyCheckWindow`） |
| 新分頁 | `session/fork`（0.10.8 起）：以一個分頁目前有效的刷新 Token 開一串新的（新 `FamilyId`，沿用 `LoginSessionId`、`IsPersistent`、整串上限，來源不輪替）；只限網頁管道。建立後再確認來源沒有剛好被登出，否則新串作廢 |
| 清理 | 排程「登入 Token 清理」（`RefreshSessionRetentionJob`，每天 03:00）刪除已到期的紀錄；撤銷但未到期的要保留，重用偵測需要 |
| 用戶端資訊 | `ClientKind`（`api`、0.10.8 起的 `web`；`web-bridge` 是 0.10.0～0.10.7 以 Cookie 換出的舊紀錄，常數留著辨識，到期後由排程清掉）、`IsPersistent`、`LoginSessionId`（同一次網頁登入）、`DeviceLabel`（User-Agent 截斷）——裝置欄位預留給日後的「我的登入裝置」清單 |

**被限流（429）不是登入失效**（0.10.5 起，WASM 遷移 M6 實機發現）：WASM 前端刷新 Token 或讀 `/me` 時被伺服器限流，`ClientSession` 設 `IsThrottled`、**不清 Token、不回登入頁**，
外框顯示「請求過於頻繁，請稍後再試。」（`ClientSession.ThrottledMessage`，與伺服器 429 的訊息相同）與「重新整理」按鈕；刷新被 429 擋下時刷新 Token 沒有被用掉。
一般 API 或串流呼叫在刷新時被限流，`ApiClient` 回 429 的失敗結果，畫面照一般錯誤顯示。0.10.1～0.10.4 會一路試到「重新登入」，短時間內快速換頁的人被丟回登入頁。

> 沿革：0.4.34 起換發時回查資料庫（停用、降權即時生效）；2026/07/09 曾決定「refresh token 落庫不納入範圍」，0.9.103 以 `SecurityStamp` 做到「整位使用者失效」；
> 0.10.0 因 WASM 前端與日後 App 改用純 token 登入，「可靠登出、單顆撤銷、重用偵測」成為必要，改為落庫；0.10.8 網頁也改成純 Token 登入（發出管道 `web`、新分頁 `session/fork`、存取 Token 帶 `fid` 可即時撤銷）。
> ⚠️ 契約變更：refresh token 不再是 JWT，曾經解析 refresh token 內容的用戶端要改為只當不透明字串保存。

## 一次性下載票證（0.10.3 起，WASM 遷移 M4）

瀏覽器原生下載（`<a download>`）帶不了 `Authorization` 標頭，大檔也不能先讀進 WASM 記憶體再存檔；0.10.3 起專案附件、0.10.6 起系統備份改用一次性下載票證，取代以 Cookie 驗證的 `ProjectFileController`、`BackupController`（都已刪除）。

| 項目 | 做法 |
|---|---|
| 申請 | 附件：`POST api/v1/Project/files/{fileId}/ticket`：一般的 Bearer API，要 `專案項目:view`，而且要看得到這個附件（專案未刪除、在團隊範圍內、實體檔存在），否則 404。備份（0.10.6 起）：`POST api/v1/backups/{檔名}/ticket`，`[AdminOnly]`，檔名經 `BackupStore.TryResolveFullPath` 且檔案存在，否則 404 |
| 票證 | `DownloadTicketService`（`MyProject.Web/Downloads/`，singleton）：32 個隨機位元組（URL-safe Base64），記下種類（`ProjectFile`／`Backup`）、目標（附件 Id 或備份檔名，0.10.6 起是字串）、使用者 Id 與當下的安全戳記（`SecurityStamp` claim）；60 秒內有效 |
| 兌換 | 匿名的 `GET api/v1/downloads/{ticket}`（`DownloadsController`，`[AllowAnonymous]`）：兌換時就從記憶體移除，**只能用一次**，重放回 404；過期沒用的在下次發票證時清掉 |
| 兌換時重新檢查 | 以使用者 Id 與發票證時的安全戳記經 `ICurrentUserLoader` 重新載入使用者：帳號停用或刪除、改了密碼、被強制登出、角色變動（都會換安全戳記）一律拒絕；被要求先改密碼或先設定兩步驟驗證時也拒絕。附件再確認仍有 `專案項目:view`，最後 `ProjectService.GetFileDownloadAsync` 再查一次團隊範圍、專案是否已刪除、實體檔是否存在；備份再從資料庫確認**仍是管理員**，檔名再經 `BackupStore.TryResolveFullPath`（只認備份根目錄下、檔名合格的 zip，擋路徑穿越）且檔案存在 |
| 失敗回應 | 不論哪一種原因，都回同一個 404 `ApiResult`「下載連結無效或已過期，請回到頁面重新下載。」；原因只寫日誌，不讓外部從回應分辨票證是否存在或使用者狀態 |
| 稽核 | 成功下載寫 `Project.FileDownload`（目標 `ProjectFile`、`file=原始檔名`）或 `Backup.Download`（目標 `Backup`、`file=檔名`），操作者是申請票證的人 |
| 續傳 | 不支援（票證只能用一次）；下載中斷要回頁面重新點（備份下載 0.10.6 起也一樣，Server 版的 Cookie 下載原本可以續傳）|

- ⚠️ 票證存在**單一行程的記憶體**：IIS 應用程式集區要維持一個背景工作處理序（預設值），集區回收只會讓還沒用的票證失效。多台主機或多個處理序時要改成共享的儲存（目前沒有這個需求）。
- 票證會出現在網址上：用過或過期就失效，事後從代理伺服器或瀏覽器的記錄裡拿到也沒用；但票證還沒用、60 秒還沒到時，拿到網址的人可以先下載一次（兌換仍以**申請者**的身分與權限判斷，所以只會是申請者本來就能下載的那個檔案）。
- 已知限制：下載管理員或瀏覽器擴充功能若先預先抓取一次網址，會把票證用掉，真正的下載得到 404；使用者再點一次檔名即可。
- 系統備份下載 0.10.6 起（WASM 遷移 M7）沿用同一套機制；備份含全部資料與金鑰環，所以兌換時多一道「仍是管理員」的檢查。

## 工作階段失效（0.9.103 起）

`MyUser.SecurityStamp` 是這位使用者的工作階段版本。access token 帶著它（claim `security_stamp`；0.10.7 以前登入 Cookie 也帶），refresh token 紀錄也記著發出當時的版本，待驗票證、記住裝置 Token 與 Google 一次性代碼也綁著它；版本一換，舊的工作階段全部失效。

**快取立即失效（0.10.0 起）**：版本的查詢有快取（見下表），以前改版本的地方都直接寫資料庫、沒有清快取，被強制登出、停用或改密碼的人最多還能再用 `ValidationIntervalMinutes`（預設 5 分鐘）。
0.10.0 起 `SecurityStampInvalidationInterceptor`（掛在 DbContext 選項上）攔到任何「改 `MyUser.SecurityStamp` 的 UPDATE」或「刪除 `MyUser`」就清掉 `SecurityStampCache`（交易中則提交後再清一次），同一個行程內**下一個請求就失效**。
快取另有世代計數：查詢開始後才被清掉的話，這次讀到的舊版本不寫回快取（否則查詢與清除同時發生時，舊版本又會被快取最多 5 分鐘）。追蹤實體存檔與 `ExecuteUpdate` 都攔得到，日後新增的改版本路徑也不必記得手動清。別的行程（IIS 重疊回收）仍最晚在快取存活時間後看到。

| 什麼時候換 | 在哪裡 |
|---|---|
| 設定新密碼（管理員、本人、忘記密碼重設） | `IPasswordPolicy.ApplyAsync`（登入時的舊雜湊升級不換） |
| 設定檔換了 support 的密碼 | `SupportUserSeeder` |
| 停用、管理員身分變更、角色變更（主要或額外） | `MyUserService.UpdateAsync`（只改姓名、Email 不換） |
| 清單點狀態標籤啟用／停用（0.9.120 起） | `MyUserService.SetStatusAsync`（同時換 `ConcurrencyStamp`；support 與自己不可停用） |
| 刪除 | `MyUserService.DeleteAsync` |
| 管理員按「強制登出」 | `MyUserService.ForceLogoutAsync`（稽核 `User.ForceLogout`，不換 `ConcurrencyStamp`） |

| 檢查點 | 時機 |
|---|---|
| 已開著的頁面（0.10.8 起都在 WASM） | 頁面的每個 API 請求照下方「API」一列檢查；被拒（401）時前端刷新，刷新也因版本不符被拒 → 清掉 Token、回登入頁，伺服器另記 `Login.SessionExpired`（0.10.8 獨立審查補上，個人資料頁的登入紀錄靠它）。0.10.7 以前由 `AuthenticationStateHelper.Check` 換頁時比對、導到 `/Auths/Logout?reason=session`，HTTP 請求另由 `SecurityStampCookieEvents` 比對 Cookie（0.10.8 已移除） |
| 下載票證（0.10.3 起） | 兌換時以發票證時記下的使用者 Id 與版本經 `ICurrentUserLoader` 重新載入：版本不符、帳號停用或刪除，一律回同一個 404 |
| API | refresh 時比對紀錄上的版本：不符撤銷整串、回 401、稽核 `Token.RefreshFailed reason=SessionRevoked`。0.9.136 起每個 Bearer 請求也在 `OnTokenValidated` 比對（`ISecurityStampService.IsValidAsync`，資料庫查詢快取 `SessionSettings:ValidationIntervalMinutes`，預設 5 分鐘；⚠️ 快取不符時再查一次資料庫才判定失效，避免剛換過版本後重新登入被誤判），0.10.0 起 `ApiActorMiddleware` 再以 `ICurrentUserLoader` 確認（5 秒快取）；不符或帳號停用／刪除就回 401 `ApiResult` |

- ⚠️ Bearer 驗證只接受 access token（`OnTokenValidated` 檢查 `token_type`）。0.9.102 之前 refresh token 也能直接當 Bearer 用，等於 access token 的效期形同虛設。
- **這台裝置保持登入**（0.10.8 起，`SelfSessionRenewal`，`MyProject.Web/Auth/WebSessionTokens.cs`）：自己改密碼（`POST api/v1/Auth/password/change`）、啟用或停用兩步驟驗證（`two-factor/setup/enable`、`disable`）、管理員在使用者管理改了自己的角色或密碼（`PUT api/v1/users/{id}` 改到自己而且版本換掉）之後，伺服器把**這次請求所屬的那一串**（存取 Token 的 `fid`）換成新的一串，直接在回應裡回這台的新 Token（`Tokens`；沿用登入識別、「記住我」與整串上限）。
  前端存起來後整頁重新載入：改密碼回 `/App`、兩步驟驗證回 `/Profile`、管理員改自己重新載入目前頁面，選單、權限與右上角換成新的身分。其他裝置與這台的舊 Token 都失效；改別人時不回 Token，對方下一個請求就被登出（API 401、刷新被拒）。
  新 Token 只回給發出請求的那個人，沒有可以轉寄的連結。存取 Token 沒有 `fid`（0.10.8 以前發的）或那一串已不存在時不回 Token，前端下一個請求就被要求重新登入。
  > 沿革：0.10.7 以前頁面取得一張 2 分鐘、一次性的 ticket 整頁導到 `/Auths/RefreshSession` 換發新 Cookie（WASM 的使用者管理由 API 回 `SessionRefreshUrl`）；換發必須帶著原本的 Cookie 而且 ticket 的新版本等於資料庫目前的版本，防止別人把自己的 ticket 連結寄給你。0.10.8 隨登入 Cookie 一起移除。
- 資料庫預設值是空字串：IIS 重疊回收時舊版程式新增的帳號沒有版本，登入時補上；比對時空字串一律不符。0.9.103 升級前簽發的 Cookie 與 token 沒有這個 claim，當時**升級後每個人要重新登入一次**。0.10.8 停發登入 Cookie 時也一樣：原本以 Cookie 登入的網頁使用者升級後要重新登入一次（App 的 Token 不受影響）。
