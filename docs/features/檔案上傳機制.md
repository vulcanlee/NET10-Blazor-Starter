# 檔案上傳機制

- 文件版本：1.8
- 文件狀態：已實作
- 現行系統版本：0.10.8
- 首次實作版本：0.1.61
- 最後核對日期：2026/11/11

## 文件目的

說明專案紀錄的附件如何上傳、儲存、刪除，以及實體檔案的目錄組織策略。

> 0.4.24 起「工作項目」與「會議記錄」已移除，其附件機制（`MyTasFile` / `MeetingFile`、`TaskFilePath` / `MeetingFilePath`）一併下架。新增其他領域模組時可比照本文件的 `Project` 樣板複刻。

---

## 1. 附件對照

| 主表 | 附件 Entity | 設定檔欄位（`SystemSettings.ExternalFileSystem`） |
|------|--------------|----------------------------------------------------|
| `Project` | `ProjectFile` | `ProjectFilePath` |

預設值（`appsettings.json`）：

```json
"ProjectFilePath":  "C:\\temp\\MyProject\\ProjectFile"
```

啟動時 `Program.cs` 的 `#region 系統使用的目錄準備` 會呼叫 `EnsureDirectoryExists(...)` 自動建立缺少的目錄。

---

## 2. 目錄組織策略

每筆紀錄的附件依「主表的建立時間」決定目錄分層：

```
{各模組根目錄}/
└── {年}/                ← 主表 CreatedAt.Year
    └── {月}/             ← 主表 CreatedAt.Month（補零兩碼）
        ├── {GUID}.pdf
        ├── {GUID}.xlsx
        └── ...
```

例：2026 年 5 月新增的專案，其檔案會落在 `C:\temp\MyProject\ProjectFile\2026\05\` 下。

- 實體檔名一律改為「`GUID`（`N` 格式）＋原副檔名」，不沿用使用者給的檔名（`ProjectService.SavePhysicalFileAsync`）。
- `ProjectFile` 記錄 `OriginalFileName`（原始檔名，下載時還原）、`StoredFileName`、`RelativePath`（`年/月/GUID.副檔名`，一律以 `/` 分隔）、`ContentType`、`FileSize`。

## 3. 上傳行為

- 一筆紀錄可上傳多個檔案（`InputFile multiple`）。
- 單檔最大 1GB（`ProjectService.MaxUploadFileSize`）：前端選檔時超過上限即提示並略過該檔，後端前置檢查再驗一次（API 回 400「檔案 X 超過 1GB 限制」）。
- 0.10.3 起 WASM 頁面在選檔時也依 `GET api/v1/Project/options` 的 `AllowedExtensions` 檢查副檔名，不在清單的提示「檔案 X 的類型不在允許清單中。」並略過（不加進待上傳清單）；伺服器存檔前一樣再檢查。
- **0.10.3 起專案項目頁以 WebAssembly 執行，檔案內容不經過 WASM 記憶體**：選檔時瀏覽器的 `File` 物件留在 `MyProject.Web.Client/wwwroot/js/browser-files.js`，.NET 端（`Commons/BrowserFiles.cs`）只拿到 id、檔名、大小；按「儲存」時由 JS 組 `FormData`、帶 Bearer 直接送到 `POST`／`PUT api/v1/Project`（multipart：`data` 是專案 JSON、`files` 是附件、`removedFileIds` 是要移除的附件 Id），由 `ApiClient.SendFormAsync` 處理 401 刷新後重送一次與連線失敗。實測 200 MB 上傳＋存檔 5.2 秒，頁面 JS 記憶體 8 MB。
- **請求大小上限**：multipart 的 action 一次請求最多 4 GB（`ProjectController.MaxRequestBytes`），IIS 端由 `MyProject.Web/web.config` 的 `<requestLimits maxAllowedContentLength="4294967295" />` 放寬（IIS 預設約 28.6 MB，超過會直接回 404.13、程式收不到；發佈時 SDK 會把 aspNetCore 處理常式合併進這份檔案，`WebConfigTests` 守門）。其他端點仍是 ASP.NET Core 預設的約 30 MB。
- **副檔名白名單**（0.4.35 起，`MyProject.Business/Helpers/UploadFileTypePolicy.cs`）：
  預設涵蓋文件、試算表、簡報、圖片與封存格式，刻意**不含**
  `.html/.htm/.svg/.xhtml/.js/.exe/.bat/.cmd/.ps1/.sh`。
  各案可於 `SystemSettings:Upload:AllowedExtensions` 覆寫；留空採用內建預設。
- **ContentType 一律依副檔名決定**，不採用呼叫端提供的值 ——
  攻擊者可以上傳 `.txt` 卻宣稱是 `text/html`；配合 `nosniff` 標頭，避免同源 stored XSS。
- 在「新增模式」下，使用者選的檔案會先暫留在瀏覽器；按下「儲存」後才送到伺服器，Service 將實體檔案落地到對應年月目錄，並與資料庫紀錄在同一次存檔寫入。副檔名不在白名單時回 400「檔案 X 的類型不在允許清單中。」，整筆都不存。
- 在「修改模式」下：
  - 既有檔案會列在清單中，可手動移除（標記為待刪除）。
  - 可繼續加入新檔案，落地行為同新增模式。
  - 按下「儲存」後：先寫入新檔案，再移除被標記為待刪除的檔案 —— 0.9.97 起**先刪 `ProjectFile` 資料列並存檔、成功後才刪實體檔**（0.10.3 起是交易提交後才刪）（經 `ProjectFileStore`，路徑跑出附件根目錄即拒絕，刪不掉只記警告）；0.9.96 之前是先刪實體檔再刪資料列。
- **資料與附件在同一個資料庫交易裡**（0.10.3 起，`ProjectService.AddAsync`／`UpdateAsync`）：主表、附件資料列與移除的附件資料列一起提交。任何一步失敗（例如實體檔寫入失敗）就整筆回滾——新增的專案不會建立、修改回到修改前、版本號不變（使用者照原本的視窗再按「儲存」即可），這次寫出的實體檔逐一刪除，被標記移除的實體檔留著；回「專案附件儲存失敗」。
  0.10.2 之前主表先存檔，附件失敗時專案已存進去、附件沒有，而且沒有稽核紀錄。
- 待上傳／待刪除的檔案也算「未儲存變更」：只加了檔案、沒動欄位，按取消一樣會先詢問（`ProjectViewView.UploadStateFingerprint`）。

## 4. 刪除行為

0.9.94 起刪除專案改為**軟刪除**：

1. `ProjectService.DeleteAsync` 只把主表標記為已刪除（`SoftDeleteHelper.MarkDeleted`），資料列與附件實體檔都保留，可在「顯示已刪除」中還原（`RestoreAsync`）。
   軟刪除期間附件無法下載（`GetFileDownloadAsync` 回查無 → 404）。
2. 永久刪除（`PurgeAsync`，只能對已刪除的專案執行）：**先移除主表並 `SaveChanges`**（附件資料列由 `DeleteBehavior.Cascade` 一併刪除，見 `BackendDBContext.OnModelCreating`），
   **成功後才刪附件實體檔**（經 `ProjectFileStore`，刪不掉只記警告，留下孤兒檔不影響資料正確性）。
3. 刪除超過 `SoftDeleteSettings:PurgeAfterDays`（預設 90 天）的專案由排程作業 `SoftDeletePurge` 自動永久刪除（0.9.97 起），附件檔一併刪除。

> 沿革：0.9.93 之前 `DeleteAsync` 是直接硬刪 —— 先逐一刪實體檔、再移除主表；刪檔失敗時主表不刪，但已刪掉的實體檔不會復原。

## 5. 稽核（0.9.78 起）

附件的異動與下載都會寫進稽核紀錄（`/audit-logs`），動作代碼定義在 `MyProject.Business/Helpers/AuditActions.cs`：

| 事件 | 動作代碼 | 寫入點 | 內容 |
|------|----------|--------|------|
| 新增／修改專案時上傳附件 | `Project.FileUpload` | `ProjectService.AddAsync`／`UpdateAsync` | `count=上傳筆數`；這次沒有上傳就不寫 |
| 修改專案時移除既有附件 | `Project.FileDelete` | `ProjectService.UpdateAsync` | `count=移除筆數`；沒有移除就不寫 |
| 下載附件（0.4.31 起）| `Project.FileDownload` | `DownloadsController`（0.10.3 起，兌換下載票證時；之前是 `ProjectFileController`）| 目標為 `ProjectFile`、`file=原始檔名` |

- 只在整筆儲存成功後才寫；操作者取自目前登入者。
- 刪除整筆專案只寫一筆 `Project.Delete`（軟刪除，內容 `title=`）；永久刪除寫 `Project.Purge`（內容含 `files=附件數`），排程自動清除寫彙總的 `Project.AutoPurge`；都不另寫 `Project.FileDelete`。
- 專案本身的新增、修改、刪除另有 `Project.Create`／`Update`／`Delete`，見 [專案項目 PRD](../prd/專案項目-prd.md)。

## 6. 對應 DTO 與設定強型別

`SystemSettings.ExternalFileSystem` 透過 `IOptions<SystemSettings>` 注入到 Service：

```csharp
public class FooService(IOptions<SystemSettings> options, ILogger<FooService> logger)
{
    private readonly ExternalFileSystem fileSystem = options.Value.ExternalFileSystem;
    // ...
}
```

於 Service 內統一使用 `fileSystem.ProjectFilePath` 等屬性，**禁止**直接從 `IConfiguration` 讀字串。

## 7. `/UploadFiles` 靜態資源對應（0.10.8 起移除）

0.4.35～0.10.7 由 `Program.cs` 的 `#region 綁定靜態資源` 呼叫 `ApplicationBuilderExtensions.UseConfiguredDownloadStaticFiles`，
把 `DownloadPath` 掛成 `/UploadFiles`，並以「必須已驗證身分」的閘門擋未登入（只認登入 Cookie）。
0.10.8 起網頁不再發登入 Cookie，這個路徑沒有任何人能通過、也沒有任何地方連到它，已整個移除；`DownloadPath` 只在啟動時建立。

> 沿革：0.4.35 之前它掛在驗證中介軟體**之前**，而 `UseStaticFiles` 本身不看授權，
> 等於整個 `DownloadPath` 目錄匿名可讀。

- 要讓使用者下載檔案，一律走一次性下載票證（見下一點）；衍生專案若在 `DownloadPath` 放過要給人下載的檔案，改成票證下載。
- 附件目錄（`ProjectFilePath`）從來不直接對應 `/UploadFiles`；0.10.3 起下載附件要先以 Bearer 呼叫 `POST api/v1/Project/files/{fileId}/ticket`（需 `專案項目:view`）取得一次性下載票證網址，再由瀏覽器以暫時的 `<a download>` 原生下載 `GET api/v1/downloads/{ticket}`（匿名、60 秒、只能用一次、不支援續傳）。兌換時重新載入使用者、重查權限，再由 `ProjectService.GetFileDownloadAsync` 做團隊可見範圍與路徑逃脫檢查後回傳檔案串流（任何失敗一律回同一個 404）。細節見《[Web API 端點目錄](../architecture/Web%20API%20端點目錄.md)》第三節。
  0.4.31～0.10.2 用的 `ProjectFileController`（`GET /api/project-files/{id}/download`，只收 Cookie 驗證、支援續傳）0.10.3 起已刪除。

## 8. 實作檢查清單

新增「附件功能」時請確認：

- [ ] Entity 已新增 `XxxFile` 子表，並在 `BackendDBContext.OnModelCreating` 設定 `Cascade`。
- [ ] `appsettings.json` 已新增對應根目錄欄位，並在 `SystemSettings.ExternalFileSystem` 模型中對映；同步加進 `ApiIntegrationTests.CreateSettings()`（漏改會讓整合測試把檔案寫進開發者的真實目錄，見[速查表 §6.6](../architecture/開發慣例與限制速查.md)）。
- [ ] 附件要長期保存：確認新目錄有沒有納入系統備份（`SystemBackupService.SelectFolders` 只備份列出的目錄，新目錄要在那裡加一行並同步 `scripts/Restore-Backup.ps1`，見[備份與還原操作手冊](../operations/備份與還原操作手冊.md)與速查表 §6.16）。
- [ ] `Program.cs` 的 `#region 系統使用的目錄準備` 已呼叫 `EnsureDirectoryExists` 包含新目錄。
- [ ] Service 對外提供 `Add` / `Update` / `Delete` 時皆同步處理實體檔案。
- [ ] 對外下載端點需做角色檢查與檔名清洗，避免路徑跳脫攻擊；WASM 頁面的下載沿用一次性下載票證（`DownloadTicketService`，加一種 `Kind` 並在 `DownloadsController` 分派），不要用 `location.assign` 觸發下載。
- [ ] WASM 頁面上傳不要把檔案讀進 WASM 記憶體，沿用 `BrowserFiles`＋`ApiClient.SendFormAsync`；API 在同一個網址以 `[Consumes]` 分 JSON 與 multipart 兩個 action，multipart 的請求上限與 `web.config` 一致。
- [ ] 上傳、刪除、下載附件都寫稽核；動作代碼加在 `AuditActions`，呼叫點引用常數（`AuditConventionTests` 守門）。
