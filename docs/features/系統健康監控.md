# 系統健康監控

- 文件版本：1.3
- 文件狀態：已實作
- 現行系統版本：0.9.59
- 首次實作版本：0.1.68
- 最後核對日期：2026/09/24

## 文件目的

說明本專案的健康檢查端點與人工巡檢頁面，讓維運人員可以快速判斷網站、API、資料庫、日誌、身分驗證、檔案系統、主機資源與安全設定是否正常。

---

## 1. 部署探針

系統保留 ASP.NET Core Health Checks 端點：

| 路徑 | 用途 | 說明 |
|------|------|------|
| `/health/live` | Liveness | 檢查應用程式處理程序是否仍存活。 |
| `/health/ready` | Readiness | 檢查資料庫連線是否可用，供部署平台判斷是否可接流量。 |

這兩個端點只提供簡短狀態，適合部署平台、反向代理或外部監控系統輪詢，不提供詳細診斷資料。

---

## 2. 人工巡檢頁

管理員可直接開啟：

```text
/system-health
```

此頁自 0.9.22 起列於左側選單「系統管理 → 統計與分析 → 系統健康監控」（`Menu.json` id 65，圖示 `monitor_heart`）。
必須先以 Cookie 登入，且目前使用者必須是管理員（`IsAdmin=true`）才可查看 —— 選單只是入口，
把關的仍是頁面 `OnInitializedAsync` 內的 `CheckIsAdmin()`；非管理員不會看到這個選單項。

頁面內容包含：

- 整體健康百分比。
- 整體紅 / 黃 / 綠燈號。
- 每個檢查項目的紅 / 黃 / 綠燈號、權重、狀態、證據與失敗訊息。
- 「寄信測試」區塊（0.9.59 起）：輸入收件者、按「寄出測試信」同步寄一封測試信，當場顯示成敗；
  寄信未啟用（`Provider=None`）時停用。每次寄送都寫一筆稽核 `Email.Test`（不含收件者）。
- 頁尾顯示目前 NLog 今日日誌檔案的最後 100 筆原始紀錄。

## 3. 燈號與分數

整體健康分數採加權計算：

| 狀態 | 單項得分 | 燈號 |
|------|----------|------|
| Healthy | 取得完整權重 | 綠燈 |
| Degraded | 取得一半權重 | 黃燈 |
| Unhealthy | 不得分 | 紅燈 |

整體燈號門檻：

| 分數 | 燈號 | 說明 |
|------|------|------|
| `>= 90` | 綠燈 | 系統健康。 |
| `70-89` | 黃燈 | 系統可運作，但有項目需要關注。 |
| `< 70` | 紅燈 | 系統健康程度不足，應立即檢查失敗項目與日誌。 |

## 4. 檢查項目

權重合計 **135**（0.9.24 起由 100 增為 125；0.9.59 加入「寄信服務」增為 135）。分數是「得分／總權重」，
總權重由項目自行加總，不是固定 100 —— 新增項目會等比稀釋既有項目的佔比。

| 項目 | 權重 | 主要證據 |
|------|------|----------|
| 網站 / 應用程式 | 10 | 環境、版本、啟動時間、運作時間。 |
| API | 10 | Controller action 數量、Swagger 啟用狀態。 |
| 資料庫 | 25 | Provider（固定 SQLite）、連線狀態、待套用 migration 數量。 |
| 日誌 | 15 | NLog 目錄、今日 log 檔、最後 100 筆讀取狀態。 |
| 身分驗證 | 15 | Cookie scheme、JWT bearer、Issuer/Audience 是否設定、SigningKey 長度。 |
| 檔案系統 | 10 | Database、Download、Upload、ProjectFile 目錄存在與可寫入。 |
| 主機資源 | 5 | Process working set、目前磁碟可用空間。 |
| 安全設定 | 10 | Swagger in Production、CORS origins、`Security.ReturnExceptionDetails`。 |
| LLM API | 10 | 端點主機、模型名稱、往返耗時。**每次載入都會真的呼叫一次**（見下方警告）。 |
| 快取服務 | 10 | Provider、InstanceName、Redis 連線字串是否設定、寫入後讀回的往返耗時。 |
| AI 計費表 | 5 | 目前模型、計費表筆數、命中的價格鍵、匯率。 |
| 寄信服務 | 10 | Provider；Smtp 時另有主機、埠號、加密方式、帳號／寄件者是否設定、連線＋登入耗時。None／Pickup 黃燈，Smtp 實測（上限 5 秒、**不寄信**）。 |

### 4.1 ⚠️ LLM API 檢測會產生費用

這是唯一一項**每次開啟頁面都會對外發出付費 API 呼叫**的檢查（送一句 `hello`）。

- 每次約 27 個 token、費用約 **NT$0.005**，並會依專案慣例記入「Token 用量」，
  作業名稱為「**系統健康檢測**」，可在該頁用作業篩選器單獨檢視。
- 頁面載入會因此多等 **1～3 秒**。
- 逾時固定 **30 秒**（`AiHealthProbe.ProbeTimeout`），**刻意不沿用** `AiSettings.TimeoutSeconds`
  —— 後者預設 600 秒，沿用會讓端點失聯時整個管理頁卡住十分鐘。
- AI 未設定時**不會發出任何請求**，該項顯示黃燈並註明「AI 未設定（選配功能）」。
  這是刻意的：沒接 AI 的部署不該因此變成紅燈。
- 三項新檢查都各自 try/catch 並自帶逾時 —— 既有 8 項裡有 7 項沒有防護，
  單一項目拋例外會炸掉整份報告。新增外部相依的檢查時務必照做。

## 5. 日誌顯示注意事項

`/system-health` 頁尾會顯示最後 100 筆原始日誌紀錄，不會額外遮罩內容。此設計是為了讓管理員快速追查失敗項目，但也代表頁面可能顯示路徑、帳號或例外訊息。

部署時請確認：

- 只有可信任管理員可以登入此頁。
- NLog 不應寫入密碼、token、完整連線字串等 secret。
- 正式環境的日誌保存期限與存取權限符合組織政策。
