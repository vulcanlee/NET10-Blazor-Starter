## 1. 分層與依賴方向 ⚠️

依賴方向一律向上，**不得反向相依**：

```
MyProject.Web ──► MyProject.Business ──► MyProject.AccessDatas
       │                  │
       └──► MyProject.Dtos / MyProject.Models / MyProject.Share
```

- `MyProject.Share`、`MyProject.Models`、`MyProject.Dtos`：不得相依其他專案。
- UI（Razor）**不得直接 `using` `BackendDBContext`**，只能呼叫 Service / Repository。
- 細節見 [架構總覽](架構總覽.md)。

## 2. 模型變更要產生 Migration ⚠️

本專案**只支援 SQLite**（0.4.24 起移除 SQL Server 支援），migration 一律放在單一組件：

- SQLite：`src/MyProject/MyProject.AccessDatas/Migrations/`

**任何 Entity／欄位變更都要產一次 migration**，否則程式碼與資料庫 schema 會不一致。指令見 [EFCore 指令備忘](../guides/EFCore.md)。

> 資料庫連線一律由 `ServiceCollectionExtensions.AddConfiguredDatabase` 以 `UseSqlite` 註冊，連線字串由 `MagicObjectHelper.GetSQLiteConnectionString` 結合 `SystemSettings.ExternalFileSystem.DatabasePath` 產生；`appsettings.json` 已無 `DatabaseProvider` 設定。

## 3. EF 追蹤與編輯隔離 ⚠️

- 表格列被編輯前要先 `Clone()` 隔離，避免雙向綁定污染來源資料。
- **Blazor 路徑的資料服務一律注入 `IDbContextFactory<BackendDBContext>`**（`Services/DataAccess/*`），
  每個方法開頭 `await using var context = await contextFactory.CreateDbContextAsync();`，用完即棄。
  私有輔助方法若參與同一個工作單元，請把 `context` 當參數傳進去，**不要自行 CreateDbContext**。
- ⚠️ **不要改回注入 scoped `BackendDBContext`**：在 Blazor Server，DI scope ＝ SignalR circuit，
  存活時間等同使用者整個連線（數分鐘到數小時），不是一次 HTTP 請求。scoped 會造成追蹤實體只增不減
  （記憶體成長、讀到過期資料），兩個元件事件重疊時還會拋
  「A second operation was started on this context」。由 `DataAccessServiceLifetimeTests` 守門。
- 沿革：0.4.36 之前用 scoped context，因而長出 `CleanTrackingHelper` 這條慣例（全專案 47 處呼叫，
  每個新模組都得記得照抄）。改用工廠後該慣例整條退場，`CleanTrackingHelper` 已移除。
  API 路徑的 Repository 仍用 scoped context —— 那裡 scope ＝ 單次 HTTP 請求，本來就正確。
- 附件「資料表紀錄」由 EF Core Cascade 處理，但**實體檔案**仍須由 Service 層在刪除前後手動移除。見 [檔案上傳機制](../features/檔案上傳機制.md)。

## 3.1 分頁查詢一律先排序 ⚠️（0.4.46 起）

**`Skip`／`Take` 之前必定要有 `OrderBy`。** 沒有 `ORDER BY` 時 SQLite 不保證回傳順序，
分頁會出現「同一筆在第 1、2 頁都看到」或「某筆翻遍所有頁都看不到」；EF Core 會記下
`RowLimitingOperationWithoutOrderByWarning` 警告。

- **Blazor 路徑**（`Services/DataAccess/*Service.GetAsync(DataRequest)`）：排序結果收在
  `IOrderedQueryable<T>? sorted`，分支未命中就留 `null`，最後在 `Skip` 之前收斂：

  ```csharp
  dataSource = sorted ?? dataSource.OrderByDescending(x => x.UpdatedAt).ThenByDescending(x => x.Id);
  ```

  這樣「欄位空白」「欄位不認得」「`SortDescending` 為 null」三種落空輸入都會退回預設排序。
  **不要**寫成 `: dataSource`（原樣回傳）—— 那正是 0.4.46 之前警告的來源。
- **API 路徑**（`Repositories/*Repository.GetPagedAsync`）：`switch` 運算式一定要留 `_ =>` 預設分支。
- 排序鍵要能唯一決定順序，因此一律 `ThenBy(x => x.Id)` 收尾，否則同值列在頁與頁之間仍會漂移。
- 守門：`MyProject.Tests/TestDbContextFactory.cs` 以
  `ConfigureWarnings(w => w.Throw(CoreEventId.RowLimitingOperationWithoutOrderByWarning))`
  把這個警告在測試中升級為例外，任何漏排序的分頁查詢只要被測試碰到就會失敗。
- 新模組請直接用 `scripts/New-CrudModule.ps1`，樣板已是正確寫法。

## 4. Web API 回應一律包信封 ⚠️

- 任何 Controller 一律回傳 `ApiResult<T>`；分頁則包 `PagedResult<T>`（定義於 `MyProject.Dtos`）。
- UI 用 Cookie 認證（`MagicObjectHelper.CookieScheme`）、API 用 JWT Bearer，兩套 scheme 互不干擾。
- CRUD API 預設需要 Bearer token；login / refresh 允許匿名。未授權／禁止存取的回應也包成 `ApiResult`。
- 除驗證身分外，受保護 CRUD **每個動作**另以 `[HasPermission("resource:action")]`（`HasPermissionAttribute` + `IPermissionChecker`）做**動作級授權**，無權限回 **403**（維持 `ApiResult`）；管理員短路。
- ⚠️ **claim 對應在 Cookie 與 JWT 兩套機制中是相反的**：Cookie 是 `Sid`=UserId、`NameIdentifier`=帳號、`Name`=**姓名（個資）**；JWT 是 `NameIdentifier`=UserId、`Name`=帳號。`HasPermissionAttribute.ResolveActor` 以「`NameIdentifier` 是不是數字」判斷來源，且只在 JWT 那一支取用 `ClaimTypes.Name`。新增從 claim 取身分的程式碼時照同樣方式處理，別假設只有一套對應。
- 平行路由：保留 `/api/...`，新用戶端優先用 `/api/v1/...`。
- 見 [Web API 設計慣例](Web%20API%20設計慣例.md)、[API Versioning 策略](API%20Versioning%20策略.md)、[認證授權與權限機制](../security/認證授權與權限機制.md)。

## 4.1 紀錄分類/團隊標籤與團隊權控 ⚠️

- Project 的 `Categories`/`Teams` 為**多值標籤**，以換行分隔字串儲存；務必透過 `TagStringHelper`（`ToStored`/`ToList`）轉換，AutoMapper 已以 `ForMember` 處理 List↔字串。
- **團隊行級權控**只在 **Blazor 服務層**：清單 `GetAsync` 對非管理員套 `BuildTeamAccessPredicate`，單筆 `GetAsync(id)`／檔案下載以 `IsTeamAccessible` 守門。非管理員僅見「無團隊（公開）或與其角色團隊交集」的紀錄。透過 `IRecordAccessScopeProvider` 取得範圍。
- 使用者**有效團隊**由 `IEffectiveTeamResolver` 計算＝直接綁使用者的 `UserTeam` ∪ 其角色 `RoleView.DefaultTeamsJson`（聯集去重）；登入時載入 `CurrentUser.TeamList`（見 `AuthenticationStateHelper.Check`），API/檔案下載走 `RecordAccessScopeProvider`。此設計讓「團隊綁使用者」與「團隊綁角色」並存，達成個別使用者差異化授權。
- ⚠️ **團隊欄位留空一律是合法值，不得改成 `[Required]` 硬擋**；要提醒就走軟性確認 `TeamBindingConfirm`（`Web/Components/Commons/`），目前涵蓋分類（`CategoryViewView`）、專案（`ProjectViewView`）與使用者（`MyUserView`，0.4.43 起）三處。呼叫端只負責提供「會有什麼影響」那句話，對話窗標題／按鈕文案一律由樣板決定，**不要各自寫 `ConfirmAsync`**。使用者維護那支另有兩項判斷：訊息依角色 `DefaultTeams` 有無而分兩種措辭，且勾選「管理員」時直接放行（管理員不受行級過濾，提醒只是雜訊）。
- **分類主檔本身也帶 `Teams` 標籤**（0.4.40 起）：`Category.Teams` 同樣是換行分隔字串，表示「哪些團隊可以使用這個分類」，未設定＝公用分類。過濾集中在 `CategoryService.ApplyTeamVisibility`，套用於清單 `GetAsync`、單筆 `GetAsync(id)` 與下拉用的 `GetAllEnabledNamesAsync`。
- ⚠️ **分類的空團隊規則與紀錄相反**：紀錄是「使用者沒有團隊 → 只看得到公開紀錄」；分類是「使用者沒有團隊 → 視為不受限，看得到全部分類」。分類可見性只是下拉清單的便利性過濾，安全邊界由 RBAC 負責，故採寬鬆規則。修改時勿「順手改成一致」，`CategoryServiceTeamVisibilityTests` 會擋。
- 分類的**名稱唯一性檢查不套團隊過濾**（全域比對），否則會出現「看不到卻建得出同名分類」。
- Web API（repository 路徑）目前**不**做行級過濾（與母專案一致）。⚠️ 但 `CategoryController.Update` 是整筆覆寫，`CategoryCreateUpdateDto` 必須帶 `teams` 欄位，否則每次 API 更新都會把團隊綁定清空。

### 4.2 分類／團隊的名稱唯一性 ⚠️（0.4.41 起）

- **寫入前一律正規化**：`Category.Name`、`Team.Name`、`Team.Code` 由 `NameNormalizer`（`Business/Helpers/`）處理，且**掛在 AutoMapper 的「→ Entity」映射上**，所以 Blazor 與 Web API 兩條路徑都涵蓋。新增這類欄位時請比照辦理。
  - ⚠️ 沿革：先前是「檢查時 Trim、寫入時不 Trim」，導致「技術文件 」原樣入庫後，「技術文件」再也比不到它（SQLite 的字串比較對尾隨空白敏感），兩筆看起來一模一樣的資料同時存在。**檢查與儲存必須比對同一個字串。**
  - `Team.Code` 用 `NormalizeOptional`，空白一律歸成 `null`。「未填」在資料庫中只能有一種表示法 —— SQLite 的唯一索引視 NULL 互不相等，但**空字串彼此相同**。
- **資料庫唯一索引**：`IX_Category_Name`、`IX_Team_Name`、`IX_Team_Code`（`BackendDBContext.OnModelCreating`）。前置檢查與寫入不在同一個交易裡（TOCTOU），索引是最後一道防線。索引採 SQLite 預設的 BINARY 定序（區分大小寫），服務層的不分大小寫判定更嚴格會先擋下；**刻意不改欄位 collation**，以免影響既有查詢。
- **UI 不得丟棄 `VerifyRecordResult`**：`AddAsync`／`UpdateAsync` 的回傳值必須檢查後才顯示成功。否則唯一索引擋下的寫入仍會顯示「新增成功」。
- **唯一索引違反須經 `UniqueConstraintHelper.TryGetFriendlyMessage` 轉譯**，否則會被服務層的泛用 `catch (Exception)` 變成看不懂的「新增失敗」。
- **UI 與 API 的判定語意必須一致**：`CategoryRepository.ExistsByNameAsync` 等 API 路徑的檢查也要走 `NameNormalizer` + 不分大小寫。曾經出現「UI 擋得下、API 塞得進去」。
- ⚠️ **加唯一索引的 migration 必須先清理既有資料**：`Program.cs` 啟動時無條件 `Database.Migrate()`，只要有一筆重複就會 migration 回滾、`__EFMigrationsHistory` 不寫入、**每次重啟都再失敗一次**。作法見 `20260826073047_AddCategoryTeamNameUniqueIndex`（去空白 → 空代號歸 NULL → 重複改名為「原名 (重複-Id)」→ 建索引），由 `CategoryTeamUniqueIndexMigrationTests` 以真正的 `MigrateAsync()` 守門（其餘測試 fixture 用 `EnsureCreatedAsync()`，測不到 migration）。
- 已知限制（非本次回歸，中文名稱不受影響）：SQLite 的 `lower()` 只折疊 ASCII，`ÉCOLE`／`école`、全形英數不視為重複；亦未做 Unicode 正規化。現有大小寫測試用 ASCII 剛好綠燈，**不要據此以為非 ASCII 也有保護**。
- 待辦：`MyUser.Account` 與 `RoleView.Name` 的唯一性檢查更弱（未 Trim、區分大小寫、無索引），影響登入與權限，另案處理。

## 5. 權限與選單對應（已改為宣告式，非位置索引）

側邊選單以**選單 Id → 權限鍵**的宣告式對應決定顯示，**重排 Menu.json 不會錯位**（已移除舊的位置索引耦合）：

- `src/MyProject/MyProject.Web/Datas/Menu.json` — Sidebar 結構（含各項 `id`）。
- `SidebarMenuService.MenuPermissionMap`（`src/MyProject/MyProject.Web/Components/Layout/SidebarMenuService.cs`）— `Id → 權限鍵` 對應，權限鍵取自 `MagicObjectHelper` 常數。
- `MagicObjectHelper`（`src/MyProject/MyProject.Share/Helpers/MagicObjectHelper.cs`）— 權限鍵常數。

新增受權限控管的頁面時：於 `MagicObjectHelper` 新增權限鍵常數、於 `Menu.json` 新增項目（給定唯一 `id`）、於 `MenuPermissionMap` 加入 `id → 權限鍵`。三者以 **`id` 對應**，不再依賴排列順序。

**⚠️ 還有第四方：頁面自己的權限檢查（0.4.33 起納管）**

檢視在 `OnInitializedAsync` 內呼叫的 `CheckAccessPage(權限鍵)`，**必須與該路由在 `MenuPermissionMap` 中的鍵一致**。

三方 id 對得上、第四方卻用錯鍵，症狀是「使用者看得到選單、點進去被踢出」——
0.4.33 之前 `ProjectViewView` 就是用**群組鍵**（`角色_專案管理`）而非葉節點鍵（`角色_專案項目`），
只被授予「專案項目」的角色會被擋在門外。

新增檢視時請一併於 `MyProject.Tests/MenuPermissionConsistencyTests.cs` 的 `ViewToMenuId` 登錄
（管理員專屬檢視則登錄到 `AdminOnlyViews`），測試會驗證四方一致。

**權限鍵常數不得帶前後空白**：權限鍵會被寫進 RBAC 資料表並以 **Ordinal** 比對，
空白會讓授權靜默對不上。同一個測試檔會擋下。

**管理員專屬頁面（權限鍵刻意不上架角色矩陣）**：

- 「統計與分析」群組：`/logs`、`/database-usage`、`/log-level-setting`
- 「系統管理」群組：`/myusers`、`/roleviews`（**0.4.33 起**）

這兩組的權限鍵都**不列入** `RolePermissionService.GetRoleListPermissionAllName()`，
因此不種 `Permission` 資料列、角色矩陣不顯示、任何角色都無法被授予，
只有頁面的 `CheckIsAdmin()` 能通過。由 `AdminOnlyPermissionTests` 守門，**請勿補上**。

> 沿革：0.4.33 之前「系統管理」群組有上架矩陣，但兩個頁面實際以 `CheckIsAdmin()` 守門，
> 形成「勾得到卻永遠無效」的死權限。

補充現況（RBAC 已落地）：
- **權限粒度到動作級**：`view/create/edit/delete/export`（見 `PermissionKeys.cs`），可做「可看不可改」；裸頁面鍵＝該頁全動作（向後相容）。
- **一使用者多角色**：`UserRole` 多對多，權限取**聯集**；團隊直綁使用者（`UserTeam`）。
- **UI 與 API 共用單一權威來源** `IPermissionChecker`（RBAC 關聯表）：登入時 `AuthenticationStateHelper.Check` 以 `GetEffectivePermissionKeysAsync` 一次載入有效權限鍵（含多角色聯集）到 `CurrentUser.RoleList`，供選單/`CheckAccessPage`/`CheckAccessAction` 同步比對；`TabViewJson` 退為角色編輯回填用的相容欄位。

> 權限判定的權威來源為 RBAC 關聯表（見 [認證授權與權限機制](../security/認證授權與權限機制.md)）；完整路線見 [權限授權現況評估與改善路線](../security/權限授權現況評估與改善路線.md)。

## 6.1 按鈕與圖示慣例

- 圖示函式庫是 **BlazorMaterialIcons**（`readme.md` 技術堆疊表已宣告）。**不要使用 emoji，也不要使用 AntDesign 的 `<Icon>`** —— 後者全專案零使用。
- 載入的是 **classic Material Icons** 字型（`App.razor` 的 Google Fonts），**不是 Material Symbols**。使用 Symbols 專有名稱（例如 `database`）會渲染成破圖方塊。同理，下載圖示要用 `file_download` 而非較新的 `download`。
- **按鈕圖示一律透過共用元件**，不要自己寫 `<Button>` 塞圖示：

  | 情境 | 元件 | 樣式 |
  |---|---|---|
  | 工具列（新增／重新整理／搜尋／清空／匯出）| `<ToolbarIconButton Title Icon OnClick [Disabled] />` | 36×36，一般 Default 外觀 |
  | 表格操作欄（修改／刪除／移除）| `<CrudActionButton Title Icon OnClick [Danger] [Disabled] />` | 28×28，透明無框 |

  兩者都自帶 `<Tooltip>` 與視覺隱藏的無障礙標籤，**外層不需再包 `<Tooltip>`**，也不需自訂 `*-icon-button` CSS。

- 常用對應：新增 `add`、重新整理 `refresh`、搜尋 `search`、清空 `close`、匯出 `file_download`、修改 `edit`、刪除 `delete`、移除 `close`。
- **表格排序解析一律用 `TableSortHelper`**（`Components/Commons/`）：它以 reflection 讀 AntDesign
  內部屬性，對套件升版脆弱，因此全專案只留一份。不要複製回檢視。
- **通知訊息一律用 `ViewNotification`**（`Components/Commons/`）。
  注意「新增成功／修改成功／刪除成功」沿用 `NotificationType.Warning`（既有外觀，非筆誤），
  因此刻意不提供 `Success` 多載。
- **新模組請用 `scripts/New-CrudModule.ps1` 產生**，不要複製既有檢視 ——
  0.4.27 的 emoji 回歸正是複製貼上造成的。改了慣例請一併更新產生器樣板。
- 選單圖示另受 `MyProject.Tests/MenuIconTests.cs` 的白名單管控（`Menu.json` 新增 icon 須同步加入）；按鈕圖示則由 `MyProject.Tests/ButtonIconConventionTests.cs` 擋下 emoji。

## 6.2 版面層級（z-index）約定 ⚠️（0.4.44 起）

⚠️ **帶 `z-index` 的定位元素會建立 stacking context —— 內層再高也翻不出去。** 這是本專案踩過的坑：
`.top-row` 是 `position: sticky` ＋ `z-index`，所以 `.user-menu-dropdown` 的 `z-index: 20`
**只在頂部列內部有效**；對整頁而言，整個頂部列是以 `.top-row` 自己的數值參與根層級堆疊。
要調整某個元素跟頁面內容的前後關係，**改的是它最外層那個 stacking context 的值，不是它自己的**。

現行根層級由低到高（`MainLayout.razor.css` 的 `@media (min-width: 641px)` 區塊）：

| 層 | 值 | 來源 |
|---|---|---|
| AntDesign 表格固定欄儲存格（`.ant-table-cell-fix-left/right`，另帶 `background: #fff`）| 2 | AntDesign 套件 |
| AntDesign 表格 sticky 標頭、選取欄 | 3 | AntDesign 套件 |
| AntDesign 表格容器邊框（`.ant-table-container::after`）| 4 | AntDesign 套件 |
| `.top-row`（頂部列，含使用者選單）| **20** | `MainLayout.razor.css` |
| `.page.sidebar-collapsed .sidebar`（含 `z-index: 40` 的飛出選單）| **30** | `MainLayout.razor.css` |
| AntDesign Modal／Notification／Tooltip | 1000+ | AntDesign 套件 |

- `.top-row` 必須 **> 4**，否則使用者選單的「關於」「登出」會被有固定「操作」欄的頁面蓋住
  （`MyUserView`、`RoleViewView`、`CategoryViewView`、`ProjectViewView`、`TeamViewView` 五處用
  `<ActionColumn Fixed="ColumnFixPlacement.Right">`）。
- `.sidebar` 必須 **> `.top-row`**，否則收合側邊欄的飛出選單會被頂部列蓋掉。
- **不要用「移除 `z-index`」來解**：`.top-row` 沒有 `z-index` 就不建立 stacking context，選單確實會浮上來，
  但 sticky 標頭反而會被表格固定欄穿透 —— 換一個 bug 而已。
- `.ant-table-resizing` 是 99，但本專案沒有任何表格開 `Resizable`；日後若要啟用，這張表要重算。
- 沿革：`Fixed` 自建立 `MyUserView` 起就有，`.top-row` 的 `z-index: 1` 自 `Init` 起就有，屬長期潛伏。
  0.4.24 新增「關於」讓選單面板多一項、變高，把「登出」推進表格範圍才變得明顯。
  **症狀會隨捲動位置與視窗高度飄移**，容易誤判成「有時好有時壞」的偶發問題。

## 7. 啟動時的 Seed 行為

`Program.cs` 於 `app.Build()` 後會：套用 migration 或 `EnsureCreated()`、Seed 預設角色（`MagicObjectHelper.預設角色`，覆寫 `TabViewJson`；RBAC 關聯表 `RolePermissionMap` 由啟動時的 `RbacBackfillService` 從 `TabViewJson` 回填）、Seed 預設帳號（`BootstrapSettings.SupportAccount`，密碼以 `SecurePasswordHasher.HashPassword`（**PBKDF2**）雜湊、`IsAdmin=true`；既有帳號密碼驗證失敗時自動升級為 PBKDF2）。此為冪等行為。預設帳號種子值來自 `BootstrapSettings`。見 [資料模型與資料庫](資料模型與資料庫.md)、[密碼種類與儲存機制](../security/密碼種類與儲存機制.md)。

## 7.1 建置設定一律走共用檔 ⚠️（0.4.32 起）

- **`TreatWarningsAsErrors` 已開啟**（`src/MyProject/Directory.Build.props`）。專案長期維持 0 warning，
  任何新警告都會直接讓建置與 CI 失敗。需要豁免時針對**單一規則碼**加 `NoWarn` 並註明原因與解除條件，
  **不要整包關閉**。
- **套件版本一律改 `src/MyProject/Directory.Packages.props`**（Central Package Management）。
  `.csproj` 只寫 `<PackageReference Include="..." />`，**不要寫回 `Version`**。
- **`Nullable` / `ImplicitUsings` 已收斂到 `Directory.Build.props`**，不要在 `.csproj` 重複宣告。
- **格式由 `.editorconfig` 管控**，CI 有 `dotnet format --verify-no-changes` 關卡。
  提交前可先跑 `dotnet format src/MyProject/MyProject.slnx`。
- SDK 版本由 repo 根目錄的 `global.json` 鎖定。

完整說明見 [CI-CD 與品質檢查 §2.1](../operations/CI-CD與品質檢查.md)。

## 8. 版本與文件 ⚠️

- **單一版本來源**：`appsettings.json` 的 `SystemSettings.SystemInformation.SystemVersion`，每次完成異動一律將**最後一碼（Patch）+1**（例：`0.4.0 → 0.4.1`，不進位、不分異動性質；顯示格式 `Major.Minor.Patch (YYYY/MM/DD)`），並於 commit message 說明。
- **文件編碼**：`docs/` 下所有 `.md` 一律 **UTF-8 含 BOM**，CI 以 [`scripts/Test-DocsEncoding.ps1`](../../scripts/Test-DocsEncoding.ps1) 遞迴強制；繁體中文不得有亂碼。
- 異動若影響既有功能／API／資料表／設定／UI，須同步更新對應文件並更新索引。對照表見 [維護規範](../operations/維護規範.md)。
- 引用程式碼請用「相對路徑」（必要時加行號），勿臆測。
