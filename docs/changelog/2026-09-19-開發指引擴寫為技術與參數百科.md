## 為什麼

0.9.34 交付的 `腳手架開發指引.md`（577 行）**太薄**：§3「技術棧」用 103 行涵蓋 12 項技術，
平均每項 8.6 行 —— 那是導覽，不是能拿來做教育訓練的教材。

而且它回答不了最實際的問題：「我想調 NLog，要動哪些參數？」
現有文件按**設定區段**組織，缺的是按**任務**組織的那一層。

## 做了什麼

`docs/guides/腳手架開發指引.md`：**577 → 2,182 行**，十二章。新增三章：

### §3 技術棧（103 → 1,092 行，16 項技術）

每項固定八段：**它在解決什麼問題 → 不用它會怎樣 → 為什麼選它 → 用在哪 →
可以調什麼 → 常見情境食譜 → 踩過的坑 → 何時該換掉／深入閱讀。**

⭐ 其中「**為什麼選它**」這一段全 repo 原本是**零覆蓋** ——
既有文件很擅長解釋「某個決定為什麼這樣做」，但從來沒有回答「為什麼選這個技術」。
每一項都附替代方案的取捨表（Blazor Server vs WASM vs MVC vs API+React、
SQLite vs SQL Server vs PostgreSQL、AutoMapper vs Mapperly、NLog vs Serilog…）。

**深度來自 §3 自己的內容，不是把別處抄過來。** 盤點後各技術的既有覆蓋差異極大：
AntDesign 樣式已有 780 行 L3 文件、Cookie/JWT/RBAC 有 978 行、AI 有約 1,300 行 ——
那些一律**連結**。真正從零寫的是覆蓋最薄的三項：
**Blazor 渲染模式與 circuit**（全 docs 原本只出現 2 次「渲染模式」）、
**AutoMapper**（全 repo 合計約 15 行）、**速率限制**（無專屬文件）。

### §4 設定檔完全指南（新，243 行）

依使用者決定，`appsettings.json` 的逐鍵說明**在指引裡也寫一份**。
補上 `日誌與設定檔說明.md` 原本**完全沒有**的 `JwtSettings`、`BootstrapSettings`、`AllowedHosts`；
標出兩個死設定、8 個「程式裡有但 JSON 裡沒有」的鍵、三個環境檔的差異、
`StartupSafetyValidator` 的五道檢查，以及「全案只有 `JwtSettings` 會在啟動時驗證」這件事。

### §5 沒有寫在設定檔裡的旋鈕（新，97 行）

**這一章別的文件完全沒有。** 會影響行為、但不在 `appsettings.json` 裡的常數，
依類別整理並附 `檔案:行號`。例如：

- **Blazor 畫面預設每頁 8 筆，Web API 預設 10 筆** —— 定義在兩個互不相依的組件裡
- **主要登入 Cookie 沒有設效期 → 吃框架預設的 14 天**（很多人不知道）
- 帳號鎖定 5 次／15 分、驗證碼 4 位、PBKDF2 十萬次
- 速率限制的**時間視窗固定 1 分鐘、佇列長度 0**，兩者都不可設定
- 上傳單檔 1GB（**三處要對齊**）、例外佇列 1000 滿載丟棄、健康權重總和 125

### §9 未來可以加什麼（新，184 行）

15 項，每項四段：解決什麼 → 何時需要 → **接在哪（本專案的具體位置）** → 成本。
刻意**不附安裝與註冊的程式碼片段** —— 那些沒人編譯、沒人測試，套件升版就過期，
而且看起來像官方建議。只寫「接在哪個檔案的哪一段」。

## 途中發現的缺陷

寫 §4／§5 需要逐項回程式碼查證，過程中發現六個問題。

### 🔴 D1：正式環境的預設密碼防線是空的（**未修，已決定只記錄**）

`StartupSafetyValidator.cs:24` 只比對字面字串 `"support"`，但：

- `appsettings.json:43` 出貨的是 **`1qaz@WSX`** → 不相等，**通過檢查**
- `appsettings.Production.json:15` 出貨的是**空字串** → 也不相等，**也通過檢查**

而 `Program.cs:343` 的 `HashPassword(...)` 沒有防呆，空字串會被雜湊 ——
**support 管理員帳號變成空密碼**，且因為 seed 每次啟動都比對，**每次重啟都重新套用**。

也就是說：**原封不動把腳手架部署到 Production，這道防線一次都不會觸發。**

使用者決定**不改程式、只寫進文件**。因此在三個地方明確寫出來：
指引 §2.3「地雷一」、§8 缺口清單第 13 項、§10.1 部署檢查的**第一項**，
並附上人工確認的指令。`日誌與設定檔說明.md` 新增的 §4.3.4 也完整說明。

### 🟠 D2：Production 的 `SigningKey` 出貨是空字串，服務會起不來

`JwtSettings` 是全案**唯一**有 `ValidateOnStart()` 的設定類別，`SigningKey` 帶
`[Required][MinLength(32)]`。`appsettings.Production.json:12` 出貨空字串 →
**不覆寫就直接啟動失敗**。這是刻意的 fail-fast，但原本零文件，
第一次部署的人只會覺得系統壞了。已寫進指引 §2.3 地雷二、§4.1 與新增的 §4.3.3。

### 🟠 D3：日誌 layout 與 `/logs` 解析器硬耦合（**已加守門測試**）

`LogQueryService.cs:22,24,27` 寫死 `TimestampLength=24`、`FieldCount=7`。
改 `nlog.config` 的 layout 之後，日誌檢視頁會**查不到任何東西，而且不會報錯** ——
看起來就像「最近沒有日誌」。

### 🟡 D4～D6：`日誌與設定檔說明.md` 的錯誤與缺漏（已修）

- §4.7 引用 `Program.cs:113-122`，實際是 `225-234`
- §5 說 Development 的 `Default` 是 `Information`，實際是 `Debug`；且該檔其實有三個鍵
- §4.1 說 `Logging` 區段「仍影響 Microsoft.* 的 Filter」，與同檔 L44「改它不會有任何效果」自相矛盾
  → 統一為「☠️ 死設定」
- AutoMapper 授權：原本寫「12+ 商業授權」，指引寫「16.x 起」，**兩個都是憑空宣稱**。
  改為引用**實跑時捕獲的實際警告訊息**，並標明目前版本是 16.1.1
- **完全沒有 `JwtSettings` 與 `BootstrapSettings` 兩節** —— 最安全敏感的兩組設定。已補上

## 兩道新的守門測試

`src/MyProject/MyProject.Tests/DocumentationConventionTests.cs`：

**`AppSettingsSections_ShouldBeDocumentedInBothGuides`**
—— `appsettings.json` 的每個頂層區段必須同時出現在兩份設定文件裡。
使用者選擇「逐鍵表複製一份」，代價是同一批說明存在兩處；這條讓分歧不再靜默。
比對「區段」而非「逐鍵」：`Provider`、`Model` 這種鍵名太通用會大量誤報。

**`NLogLayout_ShouldMatchLogQueryServiceFieldCount`**
—— 從 `nlog.config` 的 `file` target 數 layout 欄位數，與 `LogQueryService.FieldCount` 比對。
擋 D3。`FieldCount` 是 `private const`，測試以正規表示式從原始碼讀取，
**不為了一個測試放寬產品程式的可見範圍**。

兩條都**實際驗證過會紅**：故意刪掉 layout 的一個欄位、故意把指引裡的
`AiPricingSettings` 改名，兩條各自失敗並輸出精確訊息，還原後恢復綠燈。
