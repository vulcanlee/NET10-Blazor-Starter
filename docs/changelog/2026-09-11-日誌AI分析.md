## 需求

日誌檢視頁（`/logs`）原本只能讓管理員以時間區間、等級、關鍵字撈出 NLog 檔案內容，
再逐筆展開讀原始行。一次撈出上百筆時，人要自己在雜訊裡找出錯誤樣態與根因，很花時間。

這次在工具列加一個「AI 分析」按鈕，把目前查詢結果送到 Azure OpenAI 或 OpenAI 整理，
結果以唯讀對話窗呈現，可複製或匯出成 PDF 報告。供應商、端點、金鑰、模型與提示詞
都在 `appsettings.json` 設定。

## 關鍵取捨

| 決策 | 理由 |
|------|------|
| 唯讀對話窗，不追問、不串流 | 一次分析就是一份報告，追問與串流的複雜度換不到對應價值 |
| 用畫面現有結果，不重新查詢 | 行為完全可預測；對話窗會標明分析的區間、等級、關鍵字與筆數 |
| 純 `HttpClient`，不引入 AI SDK | 兩家的 Chat Completions 格式幾乎相同，差別只在 URL 與認證標頭 |
| named client 而非 typed client | typed client 會註冊成 Transient（與本專案「一律 Scoped」不一致），而且在 Blazor Server 會讓 `HttpClient` 活在整個 circuit 上，架空 `HandlerLifetime` 的輪替 |
| 不做自動重試 | 使用者主動觸發的單次動作，重試只會讓成本加倍並掩蓋設定錯誤 |
| 不做頻率限制 | 成本控管交給 Azure OpenAI 資源的配額層；事後追查看 `AuditLog` |
| PDFsharp-MigraDoc 而非 QuestPDF | 完全 MIT 授權，沒有營收門檻。這是會被別人拿去用的範本專案 |
| 手寫極小 Markdown→PDF 渲染器 | 只處理提示詞明確要求的語法，約 120 行，行為可預測，不多加依賴 |
| 只內嵌 Regular 一個字重 | Bold 會讓 repo 再肥約 7 MB，而 PDFsharp 沒有粗體模擬；層級改用字級與顏色表達 |
| 沿用管理員權限，不新增權限鍵 | 能進日誌檢視頁就能用，改動最小 |

## 踩到的坑

**`Web/Diagnostics/` 放不得。** `LoggingConventionTests` 會遞迴掃該資料夾每個 `.cs`，
缺 `ILogger<` 就紅燈。AI 的純函式檔直覺上該放那裡，但會讓九個檔案同時失敗。
因此另開 `Web/Ai/`。

**字型格式只有一種能用。** `notofonts/noto-cjk` 官方倉庫對繁中各字重只提供 `.otf`
（CFF/PostScript 輪廓），PDFsharp 明確不支援；Google Fonts 提供的是可變字型，
PDFsharp 不會套用字軸，所有字重會長得一模一樣。只能用靜態實例的 `.ttf`
（本專案由可變字型以 fontTools 實例化到 `wght=400`，方法記在 `Fonts/README.md`）。
另外**不可改用 Git LFS**：`actions/checkout` 預設不抓 LFS，CI 上只會拿到指標檔，
而 PDF 不會報錯，只會整片變成空白方框 —— 這正是
`AiReportPdfBuilderTests.Font_ShouldBeEmbeddedInWebAssembly` 斷言字型長度超過
一百萬位元組的原因。

**`GlobalFontSettings.FontResolver` 是 process 全域且 write-once。** 直接指派會在
`WebApplicationFactory` 第二次啟動 host 時丟例外，拖垮整組整合測試。
`EmbeddedFontResolver.EnsureRegistered()` 做成冪等，PDF 測試也標了 `[Collection]`。

**`StringBuilder.AppendLine` 用的是 `Environment.NewLine`。** 在 Windows 上是 CRLF，
會讓提示詞混用兩種行尾，也讓字元預算的計算與實際長度不符。改成全程用 LF，
預算才精確且跨平台一致。

**`Uri.ToString()` 會把路徑中的 `%20` 顯示成空白。** 那只是顯示慣例，實際送出的是
保留編碼的 `AbsoluteUri`。測試斷言要用後者。

**工具列圖示名稱沒有守門測試。** `ButtonIconConventionTests` 只擋 emoji，
`MenuIconTests` 只檢查 `Menu.json`。`ToolbarIconButton` 的 `Icon` 打錯只會渲染成破圖
方塊，CI 抓不到。本次用的 `insights`、`content_copy`、`picture_as_pdf` 都已比對過
classic Material Icons 的字元對照表，並在實跑時目視確認。

## 安全考量 ⚠️

日誌內容有一部分來自使用者輸入，所以模型的輸出是攻擊者可部分控制的，而結果會經
`MarkupString` 注入頁面。三道防線：提示詞明寫不得把日誌當指令、渲染時移除所有圖片
並對連結做 scheme 白名單、保留的連結加 `rel="noopener noreferrer nofollow"`。

⚠️ `DisableHtml()` 本身**不夠** —— 它完全不管連結的 URL scheme。詳見
[AI 日誌分析 §6](../features/AI日誌分析.md)。

金鑰只掛在單次請求上、錯誤訊息不回吐上游 body、稽核明細不寫日誌內容，
這三點都有測試守門。
