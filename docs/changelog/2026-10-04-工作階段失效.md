## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) C-11（第 2 批第一項）。改動前：改了密碼或停用帳號之後，其他裝置上的登入（Cookie 最長記住我 30 天、API refresh token 7 天）照樣有效；
管理員沒有辦法把某個人踢出去。2026/07/09「Refresh Token 不落庫、不可撤銷」的決定在這裡**部分翻案**：仍不落庫每顆 token，但能讓某位使用者的所有工作階段失效。

使用者決定：

- 改密碼（所有路徑）、停用或刪除、角色或管理員身分變更、管理員「強制登出」都讓所有工作階段失效。
- 已開著的頁面在下一次換頁失效、HTTP 請求最多 5 分鐘；API 只在 refresh 時檢查。
- 自己改密碼的這台裝置保持登入。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 一個使用者一個版本，不落庫每顆 token | 需求是「讓這個人全部登出」，不是管理每個裝置；不必新增 token 表與清理 |
| 已開著的頁面在換頁時檢查 | Blazor 連線不經過 Cookie 中介軟體，Cookie 驗證器看不到；換頁時的登入檢查本來就會查資料庫 |
| HTTP 請求的版本查詢快取 5 分鐘、不寫進票證 | 每個請求查一次資料庫太貴；把檢查時間寫進票證再續發會讓 Cookie 一直滑動，「不滑動」與記住我的期限都會失效 |
| API 只在 refresh 檢查 | 使用者決定；已發出的 access token 在 60 分鐘內仍可用 |
| 換發 Cookie 要求原本的 Cookie | 只憑 ticket 的話，別人可以把自己的 ticket 連結寄給你，讓你登入成他（登入 CSRF） |
| 只改姓名、Email 不換版本 | 不影響能做什麼或能不能登入，不該把人踢出去 |
| 換版本不動 `ConcurrencyStamp` | 強制登出不是編輯；別人開著這個人的編輯窗不應該衝突 |
| ⚠️ 快取裡的版本不符時再查一次資料庫才判定失效 | 實機發現：剛被停用又啟用（或改密碼後）立刻重新登入，快取還是舊版本，新的登入被踢回登入頁長達 5 分鐘。不符很少見，多查一次的代價可以忽略 |
| 空字串版本一律不符 | 重疊回收時舊版程式新增的帳號沒有版本；`'' == ''` 會讓沒有版本的 Cookie 永遠有效 |
