# 複刻腳本驗證與修正（0.9.177）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.177
- 首次實作版本：0.9.177
- 最後核對日期：2026/11/08

## 目的

0.9.173～0.9.176 加了稽核精確查詢、記錄開關、防竄改（新路徑 `AuditKeyPath`、新資料表與 migration）與 appsettings.json 的註解、標記與重新排序。
這次確認 `scripts/New-StarterProject.ps1` 用最新的倉庫複刻新專案仍然正常，產生的新專案也能開發與執行。做法是實際複刻一個 `Acme.Erp`（名稱含點號，涵蓋最多邊界情況），在新專案裡跑完整驗證。

稽核金鑰檔的重試是會隨網站發佈的程式碼，版本號 0.9.176 → 0.9.177。

## 找到並修正的問題

1. **新專案一建立就有 1 個測試失敗**：`AccountRoleUniqueIndexMigrationTests`（0.9.171 加入）寫死了腳手架的舊 migration 名稱，新專案重建成單一 `Init` 後必定失敗；它沒有登記到腳本的 `$starterMigrationTests`，所以沒被刪掉。已補上。
2. **稽核金鑰檔偶爾讀不到**：第一次驗證時新專案的 `AuditHashV1Tests.KeyStore_ConcurrentFirstUse_ShouldEndWithOneKey` 失敗一次（`IOException：檔案正被另一個處理序使用`）。剛建立的檔案可能被防毒軟體或另一個行程短暫鎖住；正式環境遇到時，那一筆稽核會因為取不到金鑰而寫不進去。`AuditIntegrityKeyStore` 的讀檔、寫暫存檔、搬移、刪除改成遇到 `IOException` 時稍等重試（最多 5 次）。修正後連跑 40 次通過；原本的失敗是偶發的，連跑通過不代表一定修好，只代表沒有變差。
3. **每次複刻都會印出一條警告**：《腳手架開發指引》§2.4 說明殘留掃描時直接寫出了 JWT 佔位金鑰的前綴，這一行本身就被掃到（文件寫著「正常複刻不會印出任何警告」）。改寫成 `DevelopmentOnly-…`。
4. **產生 Init migration 時在開發機建目錄**：腳本執行 `dotnet ef` 時，程式會依設定檔在 `C:\temp\<新名稱>\` 建 12 個資料目錄並寫日誌。改成比照 `New-CrudModule.ps1`，把所有外部路徑與 `NLog:BasePath` 導到暫存資料夾，結束後還原環境變數並刪除暫存資料夾。

## 新守門測試 `ScaffoldScriptConventionTests`

- `New-CrudModule.ps1` 與 `New-StarterProject.ps1` 的隔離清單都涵蓋 `ExternalFileSystem` 的每一個路徑（反射比對），並隔離日誌目錄。0.9.175 加 `AuditKeyPath` 時這兩份清單都要手動補、沒有測試守門。
- 測試檔出現 migration 名稱（`"yyyyMMddHHmmss_名稱"`）或 `IMigrator` 時，必須登記在 `$starterMigrationTests`（加測試前先確認會抓到漏登記的 `AccountRoleUniqueIndexMigrationTests`）。
- 除了腳本自己，任何文字檔都不可只寫 JWT 佔位金鑰的前綴，否則複刻時殘留掃描會固定印出警告。
