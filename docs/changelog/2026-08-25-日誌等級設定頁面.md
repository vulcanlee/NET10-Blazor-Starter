# 新增日誌等級設定頁面（0.4.29）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.29
- 最後核對日期：2026/08/26

## 目的

排查問題時常需要把日誌調到 Debug／Trace 看細節，查完再調回來。在此之前唯一的辦法是編輯 `nlog.config` 的 `<logger name="*"> minlevel` —— 那是一個會進版控、且可能被誤留在 Debug 的檔案異動。

這也讓先前的伏筆成立：日誌檢視頁（0.4.26）的等級篩選提供了完整六級，但 TRACE／DEBUG 一直等同「不限」，因為 `nlog.config` 只把 Info 以上寫進檔案。**本頁正是讓那兩個選項真正有意義的機制。**

## 變更範圍

### 一、新增 /log-level-setting 頁面

放進「統計與分析」子功能表（id 63，icon `tune`），緊接在「日誌檢視」下方 —— 調整等級之後通常就是要去看日誌，兩者相鄰。子功能表順序為 日誌檢視 → 日誌等級設定 → 資料庫用量。

兩張卡片（目前生效等級／系統預設等級）、行為說明橫幅、六級單選、套用與還原兩個動作。等級採 **NLog 命名**（TRACE／DEBUG／INFO／WARN／ERROR／FATAL），與日誌檔內實際字串及日誌檢視頁的篩選下拉一致。

調到 TRACE／DEBUG 時會先跳確認框（會大幅增加日誌量），其餘等級直接套用。變更寫入 `AuditLog`，能回答日後的「為什麼日誌突然變好多」。

這是專案首次使用 AntDesign 的 `RadioGroup`／`Radio`，也是「統計與分析」子功能表中第一個注入 `ModalService` 的頁面。

### 二、執行期狀態（專案首個可變單例）

新增 `MyProject.Web/Diagnostics/LogLevelRuntimeState.cs`（Singleton）。既有的 `SystemStartupState` 是不可變的，**沒有可變單例的先例可循**，因此鎖的責任完全在這裡：`LoggingRules` 是普通的 `IList`，改動發生在 Blazor circuit 執行緒上，而其他執行緒同時正在寫日誌。

於 `Program.cs`（`app.Build()` 之後）**啟動時**呼叫 `Initialize()`，不是等到有人開頁面才懶載入 —— 因為它同時負責下面那個 bug 的修復。

`LogManager.ReconfigExistingLoggers()` 是必要的：不呼叫的話，已建立的 Logger 會沿用快取的等級過濾器，設定等於沒生效，而執行中的應用程式每一個 Logger 都是已建立的。

### 三、順手修掉一個既有缺陷

`nlog.config` 設了 `autoReload="true"`，NLog 重載時會**整個換掉 `LogManager.Configuration`**，連帶清空 `Program.cs` 啟動時注入的 `BasePath`／`LogFilenamePrefix` 變數。

後果：只要有人在執行中編輯 `nlog.config`（存個檔就會觸發），`fileName="${var:BasePath}/${var:LogFilenamePrefix}-${shortdate}.log"` 的兩個變數就變成空字串，**日誌從此寫到磁碟根目錄**而非 `C:\temp\Logs\MyProject.Web\`。

這不是本次新增的問題，但本頁的說明文字正在告訴使用者可以去編輯 `nlog.config` —— 不修等於主動把人推進坑裡。`LogLevelRuntimeState` 訂閱 `ConfigurationChanged` 後依序：讀新的系統預設等級 → 補回變數 → 重新套用執行期覆寫。

因為最後一步的存在，**套用執行期設定後，直接改 `nlog.config` 的 minlevel 不會立即生效**（會被覆寫蓋過）。畫面上的說明橫幅已據此改寫，未沿用參考畫面的原文。

### 四、共用等級轉換（去掉即將形成的三重複製）

`ToRank(string)` 原本在 `LogViewerView.razor.cs` 與 `LogQueryService.cs` 各有一份（僅 fallback 不同）。本頁若再寫一份就是三重複製，因此提升為 `LogModels.cs` 的 `LogLevelRankHelper`，兩處既有呼叫改為委派並保留各自的 fallback 差異。

`LogLevelRank` 的序位 0-5 與 NLog `LogLevel.Ordinal` 完全一致，所以 `LogLevel.FromOrdinal((int)rank)` 是精確橋接，不需字串剖析。`Any`(-1) 與 `Unknown`(99) 不在範圍內，轉換前會擋掉。

## 實作中驗證出來的三件事

### 1. final 規則的實際行為與直覺不同

`final="true"` **只有在規則的等級範圍也吻合時才會攔截**。`<logger name="Microsoft.*" minlevel="Warn" final="true" />` 並不會攔掉 Microsoft 的 Debug 訊息 —— 那則訊息不符合 Warn 以上的範圍，會繼續往下比對，最後被萬用規則收走。

真正負責攔截的是 `nlog.config` 裡的「強制排除」規則，而它的三個條件**缺一不可**：涵蓋所有等級、`final="true"`、**且沒有 target**。第一版的測試就是漏掉「沒有 target」這項而誤判。

### 2. 對真實 nlog.config 驗證過的框架隔離性質

畫面上寫著「本設定只影響應用程式日誌」。這句話由 `LogLevelRuntimeStateTests.LoweringLevel_AgainstRealConfig_ShouldOnlyAffectApplicationLoggers` **直接載入專案真正的 nlog.config** 驗證，而非用合成設定 —— 合成設定重現不了 final 規則的實際行為。

套用 DEBUG 後實測：

| Logger | Debug 訊息 |
|---|---|
| `MyProject.Web.*` | 出現 |
| `Microsoft.EntityFrameworkCore.*` | 被攔截 |
| `Microsoft.*` | 被攔截 |

### 3. 未解除事件訂閱會造成跨測試污染

`LogLevelRuntimeState` 最初沒有解除 `ConfigurationChanged` 訂閱。正式環境中它是 Singleton、生命週期等同行程，看似無妨；但測試中前一個實例仍在監聽，會把它的覆寫套到後續測試建立的設定上 —— 症狀是**測試單獨跑會過、一起跑就失敗**。已實作 `IDisposable` 解除訂閱。

## 已知取捨

- **只改 `<logger name="*">` 規則**。調低只影響應用程式日誌（安全）；調高則**無法靜音** `Microsoft.Hosting.Lifetime`（Info）與 Microsoft／EF 的 Warn。這個不對稱是刻意保留的，畫面上有說明。
- **不寫回任何設定檔**，重新啟動就回到系統預設等級。刻意如此，避免有人把 Debug 誤留在版控裡。
- **未關閉 `autoReload`** —— 保留「改檔案不必重啟」這個既有便利性。
- **`appsettings.json` 的 `Logging:LogLevel` 是死設定**（`UseNLog()` 預設 `RemoveLoggerFactoryFilter: true`），本次未動它，但在 PRD 中記下這件事，因為它很容易誤導人。
