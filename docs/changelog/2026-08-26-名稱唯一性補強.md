# 分類／團隊名稱唯一性補強（0.4.41）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.41
- 最後核對日期：2026/08/26

## 目的

需求是「分類與團隊在增修時，名稱不可以重複」。稽核後確認**檢查本來就存在**
（`BeforeAddCheckAsync` / `BeforeUpdateCheckAsync`，會 Trim、不分大小寫），
但它擋不住幾種情況，重複資料仍然進得了資料庫。本次是把既有檢查補到真的擋得住。

屬預防性補強：提出需求時未實測到重複資料，開發資料庫當時也確認乾淨。

## 一、破口與修正

### 1. 檢查時 Trim，寫入時不 Trim（最主要的破口）

`BeforeAddCheckAsync` 會把輸入 `Trim()` 之後才比對，`AddAsync` 卻是 `Mapper.Map` 原值直接入庫。

於是：先建「技術文件 」（尾隨空白，原樣寫進 DB）→ 再建「技術文件」→
SQLite 的字串比較對尾隨空白敏感，`lower(Name) = '技術文件'` 比不到那一筆 →
**兩筆看起來一模一樣的資料同時存在**。全形空白 U+3000 與前導空白同理。

> 根因一句話：**檢查用的是 Trim 後的值，儲存用的是 Trim 前的值 —— 比對的不是同一個字串。**

**修正**：新增 `NameNormalizer`（`Business/Helpers/`），並把它掛在 AutoMapper
**所有「→ Entity」的映射**上（`CategoryAdapterModel`／`CategoryDto`／`CategoryCreateUpdateDto` → `Category`，
`TeamAdapterModel`／`TeamDto`／`TeamCreateUpdateDto` → `Team`）。
這是單一咽喉點：不論從 Blazor 或 Web API 進來，寫進資料庫的值一律已正規化。

### 2. 資料庫完全沒有唯一索引

`Category.Name`、`Team.Name`、`Team.Code` 都沒有唯一索引。
前置檢查與寫入各開一個 `DbContext`、不在同一個交易裡（TOCTOU），
兩個並發請求（或連按兩次 Enter）可以同時通過檢查、同時寫入。

**修正**：新增 `IX_Category_Name`、`IX_Team_Name`、`IX_Team_Code`。
索引採 SQLite 預設的 BINARY 定序（區分大小寫）＝ 純粹的最後防線；
服務層不分大小寫的判定更嚴格，會先擋下，兩者不衝突。
**刻意不改欄位 collation**，以免影響既有查詢與排序行為。

### 3. `Team.Code` 的空值形式不一致

`Code` 過去可能混雜 `NULL`、`""`、`"   "` 三種「未填」表示法。
SQLite 的唯一索引視 **NULL 互不相等**（多筆可共存），但**空字串彼此相同**（只能一筆）——
不先歸一化就建索引，第二個「沒填代號」的團隊會直接撞上約束。

**修正**：`NameNormalizer.NormalizeOptional` 把空白一律歸成 `null`；migration 一併清理既有資料。

### 4. API 路徑比 UI 路徑鬆

`CategoryRepository.ExistsByNameAsync` 是 `x.Name == name`，**不 Trim、區分大小寫**；
`TeamRepository` 的 `ExistsByNameAsync` / `ExistsByCodeAsync` 亦同。

結果是同一份資料 **UI 擋得下、API 塞得進去**：DB 已有「Report」時
`POST {"name":"report"}` 直接過關，「技術文件 」更是無條件過關（連順序條件都不需要）。

**修正**：三個方法改成與服務層相同語意（先正規化、再不分大小寫）。
這一層先前**完全沒有測試**，是這個不一致從未被發現的原因，本次補上。

### 5. UI 丟棄寫入結果

`CategoryViewView` / `TeamViewView` 忽略 `AddAsync` / `UpdateAsync` 回傳的 `VerifyRecordResult`，
無條件顯示「新增成功」。**不修的話，加了唯一索引後違反約束仍會顯示成功。**

**修正**：接住回傳值，失敗時顯示訊息並保持 Modal 開啟
（`ProjectViewView` 本來就是這樣寫，這次讓另外兩個檢視對齊）。

### 6. 唯一索引違反會被吞掉

全庫沒有任何 `DbUpdateException` 處理，違反約束會被服務層泛用的 `catch (Exception)`
轉成「新增分類失敗。」，使用者看不出問題在哪。

**修正**：新增 `UniqueConstraintHelper.TryGetFriendlyMessage`，
判別 `DbUpdateException` → `SqliteException.SqliteErrorCode == 19`，
再依訊息中的 `Category.Name` / `Team.Name` / `Team.Code` 轉成中文訊息。
（`Microsoft.Data.Sqlite` 由 `MyProject.AccessDatas` 傳遞相依而來，未新增套件參考。）

### 7. 順帶：0.4.40 留下的檢查順序問題

分類編輯頁的「團隊設定確認窗」被放在名稱重複檢查**之前**，
使用者要先回答對話窗、按下「仍要儲存」之後，才被告知「分類名稱已存在」。
本次改為 `驗證 → 名稱重複檢查 → 團隊確認 → 寫入 → 檢查結果`。

## 二、Migration 的資料清理（最需要留意的一段）

`Program.cs` 啟動時無條件呼叫 `Database.Migrate()`。既有資料庫只要有一筆重複名稱，
`CREATE UNIQUE INDEX` 就會失敗、migration 回滾、`__EFMigrationsHistory` 不寫入 ——
**每次重啟都再失敗一次，服務永遠起不來**。

因此 `20260826073047_AddCategoryTeamNameUniqueIndex` 在建立索引之前先跑資料清理：

1. `Team.Code` 空白歸一成 `NULL`（必須排在去重之前）
2. 去除 `Category.Name`、`Team.Name`、`Team.Code` 的前後空白
3. 不分大小寫去重：同名者中 **Id 最小的保留原名**，其餘改名為「原名 (重複-Id)」
4. 建立三個唯一索引

細節：

- SQLite 的 `trim(X)` 只移除半形空格，因此用 `trim(X, ' ' || char(9) || char(10) || char(13) || char(12288))`
  才能涵蓋 tab／換行／**全形空白 U+3000**，貼近 .NET `String.Trim()` 的語意。
- 尾碼用 **Id** 而非流水號：Id 唯一，改名結果保證不會再撞，也看得出是哪一筆。
- 去重刻意用**不分大小寫**（比索引的 BINARY 更嚴）。若只滿足索引，「Report」與「report」
  會同時留下，但服務層視為重複，管理員之後連編輯都會被擋 ——
  資料必須是「應用層也認為合法」的狀態。
- 被改名者**維持自己原本的大小寫**（`report` 不會被寫成 `Report`）：去重只判定重複，不竄改輸入字樣。
- 這段 SQL 不受 SQLite 逐列更新可見性的影響，因為「同名中 Id 最小的那筆永不改名」恆成立，
  其餘每一筆都一定找得到它。
- `Down()` 只移除索引；資料清理**不可逆**。

## 三、測試

新增 18 支測試（總數 268 → 286）：

- `CategoryServiceTests` / `TeamServiceTests`：寫入前正規化（含全形空白）、
  「先髒後乾淨」破口重現、空白代號歸 `null`、多筆未填代號共存、唯一索引兜底與訊息轉譯。
- **`CategoryTeamRepositoryUniquenessTests`（新檔）**：Repository 層先前零測試，
  補上 API 路徑的判定語意。
- **`CategoryTeamUniqueIndexMigrationTests`（新檔）**：本次最危險的部分必須有測試。
  其他 fixture 都用 `EnsureCreatedAsync()`（依 model 建表、跳過 migration），測不到這件事，
  因此這支刻意先 `MigrateAsync("…AddCategoryTeams")` 建到前一版、以原生 SQL 塞入
  重複／帶空白／空字串代號的資料，再 `MigrateAsync()` 到最新，驗證不拋例外、
  改名正確、索引建立。**專案內第一支走真正 migration 的測試。**

## 四、驗證

- 286 個測試全數通過；0 warning；`dotnet format` 無差異；文件編碼檢查通過。
- Migration 以**開發資料庫的兩份副本**實跑：
  - 乾淨副本 → 索引建立成功、資料未被改名。
  - 刻意塞入「技術文件」「技術文件 」「Report」「report」與兩筆 `Code = ''` 的髒副本 →
    migration 不失敗、重複者改名、空字串代號歸 `NULL`、三個索引都在。
  - 另驗證索引確實生效（插入重複名稱回 `UNIQUE constraint failed`）、多筆 `NULL` 代號可共存。
- 開發資料庫本身全程未被異動。

## 五、刻意不做

| 項目 | 理由 |
|------|------|
| `MyUser.Account` / `RoleView.Name` 的相同補強 | 它們的檢查更弱（未 Trim、區分大小寫、無索引），但影響登入與權限，風險高，另案處理 |
| Unicode 正規化（NFC/NFD）、全形英數折疊 | 現有行為即如此，非本次回歸；中文名稱不受影響 |
| 非 ASCII 大小寫折疊 | SQLite `lower()` 只折疊 ASCII，`ÉCOLE`／`école` 不視為重複。現有大小寫測試用 ASCII 剛好綠燈，是**假的安全感**，已在慣例文件標明 |
| Modal 連點兩次的 re-entrancy 防護 | 加上唯一索引與結果檢查後，重複送出只會得到明確錯誤訊息，資料不會壞 |
| Entity 層補 `[StringLength]` | 與唯一性無關 |
