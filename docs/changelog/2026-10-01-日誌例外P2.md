# 日誌與例外處理 P2：瀏覽器錯誤回報、慢操作記錄、日誌管線自我監控（0.9.79）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.79
- 首次實作版本：0.9.79
- 最後核對日期：2026/10/01

## 為什麼

[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) 的最後一批（P2，可觀測性強化）處理三個盲點：
- **瀏覽器端錯誤**：伺服器完全看不到使用者瀏覽器裡的 JavaScript 錯誤。
- **慢操作**：系統變慢時，日誌裡沒有「哪一步慢」的線索。
- **記錄機制本身**：記錄機制壞了，例如佇列滿、寫不進資料庫、告警寄不出去，沒有任何人會知道。

## 做了什麼

**LOG-20 瀏覽器錯誤回報**
- 新增 `wwwroot/js/client-error-reporter.js`，掛上 `error` 與 `unhandledrejection`，經 Blazor circuit 回報 `BrowserErrorReporter.Report`（`[JSInvokable]`，每個 circuit 一份）。
- 以 Error 記錄並帶 `BrowserScriptException`，進系統例外紀錄，新增來源「瀏覽器」。
- 只有登入後的 MainLayout 會註冊回報。
- 防濫用與防外洩：
  - 每個 circuit 每分鐘最多 10 筆，超過的丟棄並計數。
  - 訊息上限 1000 字、堆疊上限 4000 字。
  - 頁面只記路徑，去掉查詢字串與 `#` 之後的內容。
  - 過濾瀏覽器外掛的錯誤，以及 `ResizeObserver loop`、`Script error.` 等已知雜訊。
- 新增設定區段 `ClientErrorReporting`。

**LOG-21 慢操作記錄**
- 新增設定區段 `SlowOperationSettings`，超過門檻記 Warning：

| 類別 | 門檻 | 說明 |
|---|---|---|
| HTTP 請求 | 3 秒 | 排除 `/_blazor` 長連線 |
| 資料庫指令 | 1 秒 | 新增 `SlowDbCommandInterceptor`，只記指令類型，不記 SQL 與參數 |
| 寄信 | 10 秒 | |
| AI 呼叫與 AI 健康探測 | 60 秒 | |

- Google SSO 的往返是 HTTP 請求，由 HTTP 門檻涵蓋。

**LOG-22 日誌管線自我監控**
- 新增 `LoggingPipelineMonitor`，累計以下次數：
  - 例外寫入失敗
  - 前端回報因限流丟棄
  - 告警信入列失敗、寄送失敗
  - NLog 內部錯誤
- 系統健康監控新增「日誌管線」項目（權重 10，總權重 135 → 145），另外讀取：
  - 例外佇列長度與丟棄數
  - 日誌所在磁碟的可用空間

**文件**
- 新設定區段寫入兩份設定文件：操作文件 §4.13、§4.14 與開發指引。
- 健康監控的項目數（12 → 13）與權重（135 → 145）同步更新到所有文件與操作說明。

**測試與驗證**
- 新增 `BrowserErrorReporterTests`、`LoggingPipelineHealthTests`，以及 `ExceptionLogWriterTests` 的寫入失敗計數測試。
- `SystemHealthTests` 改為 13 項、總權重 145。
- 全部測試由 1,051 項增為 1,085 項，全數通過。
- 實機以 1 毫秒門檻啟動，確認以下行為：
  - 「Slow HTTP request」「Slow database command」兩種 Warning 都寫入日誌檔，資料庫那筆只記指令類型。
  - `/_blazor` 沒有被記成慢請求。
  - `client-error-reporter.js` 正常載入。
- `SystemVersion`：`0.9.78 → 0.9.79`。

## 刻意不做的事

- **不量「Blazor 單次互動」。** PRD 原規劃 3 秒門檻，但兩種情況都會被算成互動時間，每次都誤報：
  - AI 分析在按鈕事件裡等待數十秒。
  - 確認窗在等使用者按下按鈕。
- **管線監控不主動告警。** 告警本身失敗時無法再用告警通知；數字是本次啟動以來的累計，重啟歸零。
- **登入頁等靜態頁面不回報前端錯誤。** 那些頁面沒有 circuit，匿名者無從灌資料。
- **前端錯誤回報、健康監控頁的「日誌管線」卡片，尚未在瀏覽器內人工觸發驗收。**
