- 文件版本：1.0
- 文件狀態：已實作

- 最後核對日期：2026/11/08

## 目的

稽核紀錄是責任證據，但它就放在 SQLite 檔裡：拿得到資料庫檔的人（主機管理員、拿到備份的人、入侵者）可以直接改內容、刪掉幾筆、或塞入假紀錄，畫面上完全看不出來。

這次讓每筆新紀錄都帶簽章（HMAC-SHA256）並串成雜湊鏈，金鑰放在資料庫以外、而且**刻意不進備份**。只動了資料庫的竄改一定會被發現：稽核紀錄頁可以隨時按「驗證完整性」，每天 03:30 也會自動檢查，發現問題就通知全體管理員並寄信。

## 變更內容

### 1. 簽章與雜湊鏈

- **兩條鏈**：異動鏈（異動與安全事件）與瀏覽鏈（`Page.View`、`*.Search`、`*.View`）。兩類保留天數不同（365／90），放同一條鏈的話刪掉中間的瀏覽紀錄會讓鏈斷掉；分開後清除只從每條鏈**最舊的一端**刪，正常清除不會看起來像竄改。
- **每筆紀錄**有鏈內序號（從 1 連續遞增）、上一筆的雜湊、內容檔的 SHA-256、金鑰代號與簽章。簽章涵蓋全部欄位與內容檔雜湊，所以改了「修改差異」「查詢條件」這類內容檔也會被發現。
- **鏈頭** `AuditChainHead`：每條鏈一列，記「目前應該從第幾筆到第幾筆」、金鑰代號、開始保護時升級前紀錄的最大 Id，整列也有簽章。
- **寫入排隊**：每筆稽核寫入都在同一個 SQLite `BEGIN IMMEDIATE` 交易裡讀鏈頭、寫紀錄、更新鏈頭並重新簽章，外面再加一個靜態 semaphore，多人同時寫也不會缺號或重號。
- **清除**：每條鏈的保留起點＝門檻之後最早的那一筆，只刪序號比它小的；「資料保留與清理」頁的「下次會清掉幾筆」與實際清除用同一個保留起點（`AuditChainStore.ResolveExpiredAsync`）。
  - **刪之前先驗**：要刪的那一段必須從鏈頭起點連續、前後筆接得上、目前金鑰簽的都驗得過；有人把紀錄的時間改舊、想讓清除替他刪掉證據時，這條鏈停在那裡不刪（記 Error），每日檢查會回報那幾筆被改過。鏈頭不可信任時這條鏈也不刪。
  - **分批**：每批 5000 筆一個交易，鏈頭起點逐批往前推；批與批之間放開鎖，大量清除時登入等業務操作的稽核寫入不會被卡住。
- **清空全部**：序號接著編、不歸零，完整性驗證從下一筆紀錄重新起算；只刪被清掉的紀錄的內容檔（同時有寫入在等鎖時，它已寫好的內容檔不會被一起刪掉），鏈頭的 `LegacyMaxId` 歸零。升級前的紀錄被清光時 `LegacyMaxId` 也歸零，空出來的 `Id` 不能再冒充升級前的紀錄。
- **不把竄改洗成正常**：鏈頭簽章不對、金鑰代號被改（而金鑰其實沒換）、或終點被改小時，鏈頭標記為不可信任，之後的寫入照常進行（終點被改小時從實際最後一筆接續，不會撞號讓稽核停擺）但不替它重新簽章，直到「清空全部」。
- **金鑰真的換了才接受**：鏈頭的金鑰代號和目前不同時，只有「本行程剛產生新金鑰」或「資料庫以外的檢查點記的是另一把金鑰」才視為換了金鑰（兩條鏈的鏈頭一起改用新金鑰）；否則視為鏈頭被竄改。
- **寫入失敗改記 Error**：稽核寫不進去（例如鎖等超過 30 秒）會進系統例外紀錄，不再只是一行警告；業務操作照常完成。

### 2. 金鑰與新路徑 `AuditKeyPath`

- 新設定 `SystemSettings:ExternalFileSystem:AuditKeyPath`（預設 `C:\temp\MyProject\AuditKey`），是 `ExternalFileSystem` 的第 12 個目錄。
- 第一次寫稽核時自動產生 `audit-hmac.key`（32 個隨機位元組，base64）；同一個資料夾還有每日檢查寫的檢查點 `audit-chain-checkpoint.json`。
- ⚠️ **金鑰刻意不進系統備份**：金鑰和資料庫在同一份備份裡，拿到備份的人就能改紀錄再重算簽章。
- 啟動驗證擋下：沒填或不是絕對路徑；與任何其他資料目錄（`DatabasePath`、`DownloadPath`、`UploadPath`、`ProjectFilePath`、`ExceptionPath`、`TokenUsagePath`、`AiCallLogPath`、`AiAgentConversationPath`、`AuditContentPath`、`DataProtectionKeyPath`）或 `BackupPath` 重疊（相同、在其下或包含它）；放在網站目錄底下。
- 系統健康監控的「檔案系統」項目多檢查這個目錄（名稱 `AuditKey`）；`scripts/New-CrudModule.ps1` 產生 migration 時也把它隔離到暫存資料夾。

### 3. 稽核紀錄頁 `/audit-logs`

- 工具列新增「驗證完整性（檢查有沒有被改、被刪）」（圖示 `verified_user`），打開「稽核紀錄完整性驗證」視窗：
  - 綠色「全部正確」或紅色「發現問題」，加一句摘要，例如「檢查 12 筆，全部正確（5 筆升級前的紀錄未納入）。」
  - 有問題時列出問題清單（最多 50 個）。
  - 下方說明：這裡只比對、不更新檢查點；每天 03:30 的排程發現問題時會通知全體管理員並寄信；「金鑰不同」不算問題。
  - 每按一次寫一筆 `Audit.Verify`（摘要 `result=ok|failed; signed=N; issues=M; legacy=L; keyMismatch=K; trigger=manual`）。
- 明細窗多一欄「簽章」：「已簽章，異動鏈 #6」或「升級前的紀錄，未納入完整性驗證」。
- 「清空全部」的確認文字改為「將刪除所有稽核紀錄。此動作無法復原，且本次清空會另外留下一筆稽核紀錄；完整性驗證會從下一筆紀錄重新起算。」

### 4. 排程作業「稽核紀錄完整性檢查」

- 名稱 `AuditIntegrityVerify`，預設 `30 3 * * *`（避開 02:00 的備份與 03:00 的各項清理）；排程作業頁的說明「重算每一筆稽核紀錄的簽章，檢查有沒有被改、被刪或繞過系統塞入；發現問題時作業結果為失敗，並通知全體管理員（含電子郵件）。」
- 發現問題時作業結果為失敗，由既有的「作業失敗」通知送給全體管理員並寄信（**不新增通知分類**）；訊息列出前 3 個問題，請管理員到稽核紀錄頁看完整清單。
- 每次執行都更新檢查點、寫一筆 `Audit.Verify`（`trigger=Schedule`／`CatchUp`／`Manual`）；問題另以 ERROR 寫進 NLog 日誌檔（在資料庫以外，就算有人刪了通知也還在）。
- 內建排程作業 12 → 13 個。

### 5. 抓得到的竄改

| 情況 | 怎麼發現 |
|---|---|
| 內容被改 | 內容和簽章不符 |
| 中間被刪 | 序號缺號 |
| 最新幾筆被刪 | 接不上鏈頭的終點；之後再寫新紀錄仍持續回報 |
| 最舊幾筆被偷刪（不是經由清除） | 鏈頭的起點沒有跟著推進，從起點到第一筆之間缺號 |
| 鏈頭被改（含只改金鑰代號） | 鏈頭的簽章或金鑰代號不對；之後的寫入不會替它重新簽章，直到「清空全部」 |
| 鏈頭的終點被改小 | 之後的寫入從實際最後一筆接續（稽核不會停擺），並標記鏈頭被改過 |
| 把紀錄的時間改舊，想讓排程清除替他刪掉 | 清除前先驗簽章，驗不過就不刪；每日檢查回報「內容和簽章不符」 |
| 移除唯一索引後塞入重複序號 | 序號重複 |
| 檢查點檔被改壞 | 檢查點讀不懂（這一次無法比對倒回），排程會重寫一份 |
| 鏈頭被刪 | 下一次寫入時自動重建，回報一次「鏈頭曾經不見…已重建」 |
| 繞過系統塞入未簽章的紀錄 | 沒有簽章、Id 又大於開始保護時升級前紀錄的最大 Id |
| 偽造金鑰代號 | 金鑰代號不對（偽造） |
| 內容檔被改或不見 | 內容檔的 SHA-256 在簽章裡 |
| 金鑰檔不見／被換 | 不見時用執行中的金鑰自動寫回並回報；被換時回報 |
| 金鑰變更 | 和上次檢查時不同（靠檢查點） |
| 資料庫被倒回舊版、或最新紀錄連同鏈頭被換回舊的 | 比上次檢查時舊（靠檢查點） |
| 整條鏈連同鏈頭被刪 | 上次檢查時還在（靠檢查點） |

- **一次性與持續性**：金鑰變更、鏈頭重建、資料庫倒回只由第一次看到它的每日檢查回報一次（之後檢查點的基準跟著移動）；被改、缺號、接不上、未簽章、內容檔不符每天都報，直到「清空全部」。
- **金鑰遺失或換主機沒帶金鑰**：自動產生新金鑰、照常寫入；之前的紀錄歸類為「金鑰不同」（警告、另外計數、不算問題：仍檢查序號連續，但無法驗證內容）。每日檢查對「金鑰變更」告警一次。

## ⚠️ 升級影響

1. ⚠️ **正式環境的 appsettings 必須設定 `AuditKeyPath`**，而且是獨立目錄：不可與其他資料目錄或 `BackupPath` 重疊、不可在網站目錄底下，否則網站啟動失敗。資料夾的 NTFS 權限只給應用程式集區帳號與 Administrators。
2. ⚠️ **金鑰不在系統備份裡**：第一次寫稽核產生 `audit-hmac.key` 之後，請另外離線保存一份，和備份分開放。換主機時把它複製到新主機相同的 `AuditKeyPath`；沒帶的話系統會產生新金鑰照常運作，但之前的紀錄只能顯示「金鑰不同」，並會告警一次。
3. **升級前的紀錄不會被驗證**：顯示「升級前的紀錄，未納入完整性驗證」，不會被當成問題。
4. **每筆稽核寫入都要排隊**並更新鏈頭；打開「記錄瀏覽類事件」時每次換頁都會拿一次寫鎖。以 20～100 人的內部系統評估可以接受。
5. 從備份還原資料庫後，第一次每日檢查會回報一次「資料庫被倒回」並通知管理員，屬預期（備份與還原操作手冊已註明）。
6. 稽核寫入失敗從 Warning 改記 Error，會出現在「系統例外紀錄」。

## 新紅線

寫進[速查表 §6.31](../architecture/開發慣例與限制速查.md)：

1. **只有 `AuditChainStore` 可以新增、修改、刪除 `AuditLog` 與 `AuditChainHead`**（`AuditIntegrityConventionTests` 守門）。
2. **簽章格式 V1 已凍結**（`AuditHashV1Tests` 的固定答案）：要改只能另加 V2。
3. **`AuditKeyPath` 不可進備份、不可與其他資料目錄重疊**；新增 `ExternalFileSystem` 路徑時，除了 `ApiIntegrationTests.CreateSettings()` 也要加進 `New-CrudModule.ps1` 的隔離。
4. **寫入端用 `BEGIN IMMEDIATE`＋靜態 semaphore，驗證端用 DEFERRED 快照**；清除只刪每條鏈最舊的一段（統計與清除共用 `ResolveExpiredAsync`）；`DeleteContentMonthsBeforeAsync` 的邊界保護不可拿掉。

## 已知限制

1. ⚠️ **同時拿到資料庫與金鑰檔的人無法被發現**：可以改完再重算簽章。
2. 檢查點一天只更新一次：「先存一份舊的鏈頭，之後刪掉最新幾筆再把舊鏈頭放回去」，最晚在下一次每日檢查才會發現。
3. 金鑰遺失時，之前的紀錄只能顯示「金鑰不同」，無法驗證內容。
4. 用備份正常還原資料庫，也會觸發一次「資料庫被倒回」告警（預期中）。
5. 每筆稽核寫入都要排隊。
6. 「被改、缺號」這類持續性的問題每天都會告警，目前只能等那幾筆過了保留天數被清掉，或「清空全部」才會停；沒有「調查完畢、保留紀錄、重新起算」的管理操作。
7. 每日檢查可以在排程作業頁停用，能改資料庫的人也能把它停掉；停掉之後不會再有告警（排程作業頁與系統健康監控看得到它停用或逾期）。
8. 升級前的紀錄還沒清光之前，指定一個比 `LegacyMaxId` 小、目前沒被用到的 `Id` 塞入的未簽章紀錄，會被當成升級前的紀錄。
