# 修正 CI 還原被 NU1900 中斷（0.4.47）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.47
- 首次實作版本：0.4.47
- 最後核對日期：2026/08/27

## 症狀

GitHub Actions 的 `.NET CI` 在 Restore 步驟失敗，exit code 1：

```
...\MyProject.Tests.csproj : error NU1900: Warning As Error:
Error occurred while getting package vulnerability data:
An error occurred while sending the request. [...MyProject.slnx]
...
Failed to restore ...MyProject.Web.csproj (in 1.51 min).
Error: Process completed with exit code 1.
```

失敗的是 `Web`／`Business`／`AccessDatas`／`Tests` 四個專案，各卡 1.51~1.52 分鐘；
沒有外部 `PackageReference` 的 `Dtos`／`Models`／`Share` 則在 194 毫秒內還原成功。
程式碼沒有任何異動也會失敗。

## 根因

四步串成的：

| # | 環節 | 說明 |
|---|---|---|
| ① | `Directory.Build.props` 的 `TreatWarningsAsErrors=true` | 這是 MSBuild 屬性，**不只影響編譯** —— NuGet restore 階段的 `NU****` 警告同樣被升級為 error |
| ② | .NET 10 SDK 預設開啟 NuGet Audit | `NuGetAuditMode` 未設定即為 `all`，restore 時會向 `https://api.nuget.org/v3/vulnerabilities/index.json` 抓弱點索引 |
| ③ | 該 HTTP 請求失敗（1.5 分鐘 ≈ 逾時） | 產生 `NU1900` **警告** |
| ④ | ①把③升級成 error | restore 非零退出；後續 Build／Format／Test 都帶 `--no-restore`／`--no-build`，整條 pipeline 連帶失敗 |

關鍵在於 **`NU1900` 的語意是「取不到弱點資料」，不是「發現弱點」**。
真正代表發現弱點的是 `NU1901`~`NU1904`。把前者當成建置失敗，
等於讓 nuget.org 的可用度決定 CI 成敗 —— 這是假失敗，重跑可能就過，與程式碼品質無關。

只有那四個專案失敗，正因為只有它們有外部套件、需要稽核；這個分布本身就是根因的佐證。

另有一處不對稱：`NUGET_HTTP_TIMEOUT_SECONDS: "180"` 原本只掛在最後的 Vulnerability scan 步驟，
**最需要它的 Restore 步驟反而沒有**。

## 修正

### 1. NU1900 降回警告（核心）

`src/MyProject/Directory.Build.props`：

```xml
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
<WarningsNotAsErrors>$(WarningsNotAsErrors);NU1900</WarningsNotAsErrors>
```

`TreatWarningsAsErrors` 維持開啟，只針對**單一規則碼**豁免 —— 比照檔內 `NuGetAuditSuppress` 的既有寫法。
用 `WarningsNotAsErrors` 而不是 `NoWarn`：警告仍會印在 log 上，
才看得出 CI 是否常態性連不到 nuget.org；`NoWarn` 會把它整個藏起來。

### 2. CI 逾時設定提升到 job 層級

`.github/workflows/dotnet-ci.yml` 把 `NUGET_HTTP_TIMEOUT_SECONDS: "180"` 從
Vulnerability scan 的步驟層級移到 `build-test` 的 job 層級，涵蓋 Restore／Build／Test／Vulnerability scan。

### 3. 加入 NuGet 套件快取

在 Setup .NET 與 Restore 之間插入 `actions/cache@v4`，快取 `~/.nuget/packages`，
key 取自 `Directory.Packages.props`（CPM 的版本單一來源）與各 `.csproj` 的 hash。

不用 `actions/setup-dotnet` 內建的 `cache: true`：它預設以 `**/packages.lock.json` 當 hash 依據，
本 repo 沒有 lock 檔會直接報 `unable to cache dependencies`。

> 快取只減少套件下載量與時間，**不會**避免弱點索引那個 HTTP 請求。
> 真正讓 CI 不再被打斷的是第 1 項，第 2、3 項是降低發生機率與縮短 restore 時間。

## 取捨與排除的作法

- **不關閉 NuGet Audit**（`NuGetAudit=false`）：那會連真正的弱點警告一起關掉，把關就沒了。
- **不用 `NoWarn` 隱藏 NU1900**：警告要留著，才看得出 nuget.org 連線是否常態性有問題。
- **不加 `NU1905`**：實測發現它只在使用自訂 `<auditSources>` 時才會出現，本專案用預設稽核來源，
  CI 上不會遇到。憑猜測擴大豁免清單等於偷偷放寬把關。
- **不加 `packages.lock.json`**：會引入 `NU1004` 版本鎖不同步的維護成本，與本問題無關。
- **不加 restore 重試迴圈**：先用「降級＋逾時＋快取」觀察，真的變成常態再談。
- **不在 repo 加 `NuGet.config` 固定套件來源**：本機使用者層級的 NuGet 設定雖有兩個
  內網 HTTP 來源（目前皆已停用），但它們不是這次 CI 失敗的成因（CI 上讀不到）。
  已知風險：那兩個來源一旦被啟用、或離開公司網路，本機 restore 會出現同樣的 NU1900 ——
  屆時第 1 項修正同樣涵蓋它。

## 驗收

`NU1900` 無法靠等待重現，改以「指向連不通的稽核來源」穩定製造（設定檔放在暫存目錄，未進 repo）：

```xml
<auditSources>
  <clear />
  <add key="dead-audit-source" value="https://127.0.0.1:9/v3/index.json" />
</auditSources>
```

```powershell
dotnet restore src/MyProject/MyProject.slnx --configfile <暫存目錄>/nu1900.config --force
```

| 檢查 | 結果 |
|---|---|
| 修正前重現 | `error NU1900`，四個專案失敗、三個成功、exit code 1 —— 與 CI log 完全同形 |
| 修正後 | 同一指令的 NU1900 降為 `warning`；在只有 NU1900 的情境下 restore **exit code 0** |
| 反向確認把關 | 暫時停用 `NuGetAuditSuppress` 後重跑，`NU1903` 仍為 **error**（不是 warning），確認真正的弱點警告未被放寬 |
| `dotnet build -c Release` | 0 錯誤 0 警告 |
| `dotnet format --verify-no-changes` | 無變更 |
| `dotnet test -c Release` | 291 個測例全數通過 |
| `pwsh scripts/Test-DocsEncoding.ps1` | 全數 BOM、無亂碼 |

註：以自訂稽核來源重現時會另外出現 `NU1905`（稽核來源未提供弱點資料），
它是這個重現手法的副產物，CI 使用預設稽核來源時不會發生，因此不列入豁免。
