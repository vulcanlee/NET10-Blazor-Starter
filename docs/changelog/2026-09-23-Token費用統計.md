## 為什麼

需求是「做一個 Token 費用統計頁，預設看得到最近 1／7／30 天的用量與費用，
並可自訂過濾條件」。

盤點後發現需求的大部分**已經存在**於 `/token-usage`：帳號／起訖日／作業／型別／模型
五個篩選器、篩選範圍合計橫幅（含 `CostUsd`／`CostTwd`／未定價筆數）、依使用者／作業／
模型／型別四個分組頁籤、明細表、CSV 與 PDF 匯出。真正缺的只有兩件事：
**「最近 N 天」的快捷視角**，以及**費用隨時間的走勢**。

因此**擴充現有頁面**，而不是在「統計與分析」下再開一頁。再開一頁要複製同一套篩選與分組
邏輯，兩頁的數字還會有對不起來的風險 —— 而「同一份用量有兩個互相矛盾的總計」比「少一個
選單項」嚴重得多。**沒有新增選單項、沒有新增權限鍵、沒有 migration。**

## 做了什麼

### 「最近 1／7／30 天」摘要卡

合計橫幅下方新增三張卡，各顯示該區間的 NT$／US$、呼叫次數與合計 token。

- **點卡片＝把該區間套進起訖日再重查**，其餘篩選維持不動；目前選中的區間會標示出來。
- 卡片**沿用目前的帳號／作業／型別／模型篩選，只把日期換成自己的窗**。
  選了某個模型之後，卡片回答的是「這個模型近 1／7／30 天花了多少」，
  而不是永遠的全站大盤 —— 後者用篩選器問不出來，前者可以。
- 卡片上方那行字會列出目前套用了哪些非日期條件，避免把「篩選後的小數字」誤讀成全站總額。

### 「每日趨勢」頁籤（純 CSS 長條，**沒有引入任何圖表函式庫**）

每一列是一天：日期、兩根長條（費用 NT$ 一根、合計 token 一根）、以及右側的金額與次數。

- 兩根長條**各自以區間內的最大值歸一化，彼此不可互相比較** —— 畫面上有一行字明講這件事。
  兩者的單位不同（錢 vs token），共用一個尺規只會誤導。
- 區間**跟隨篩選**；起訖日都沒填時退回近 30 天，否則資料放久了會一次畫出上百格。
- **沒有資料的日期會補零**。缺口不補的話，長條圖會把「那天沒花錢」畫成「那天不存在」，
  相鄰兩根柱子看起來就成了連續的兩天。

### 為什麼只多兩次資料庫往返

近 1／7／30 天彼此是**巢狀區間**，所以只查一次「近 30 天」的逐日資料，
三張卡全部從同一份日列切片加總（`CardOf`）。趨勢再查一次。

替代做法是三張卡各呼叫一次 `GetSummaryAsync`，而那支方法內部有 8 個
`SumAsync`／`CountAsync` 往返 —— 三張卡就是 24 次查詢，為了三個數字並不划算。

⚠️ 逐日加總再相加，與一次 SUM 全部資料列，在 `double` 的最末幾位可能不同。
顯示精度是台幣 `N2`／美金 `N4`，沒有實質差異，**不是 bug**。

### 「最近 N 天」＝含今天往前數 N 日

近 1 天就是今天；近 7 天是 `today-6` 到 `today`（含頭含尾）。這個定義**只寫在
`TokenUsageRanges` 一處**，卡片標題、卡片查詢與趨勢預設區間都走它。
兩邊各寫一次日期運算，遲早會出現「卡片說近 7 天、趨勢畫了 8 格」。

`TokenUsageRangesTests` 釘住的就是這件事，包括「傳 `DateTime.Now` 也要得到乾淨的日期」——
否則起訖日會帶著時分秒進篩選器。

### `GroupBy(x => x.OccurredAt.Date)` 在 SQLite 上譯得出 SQL

這是動工前唯一沒把握的地方，所以先寫測試確認：`GetDailyAsync_ShouldGroupByLocalDate`
放一筆 `23:59` 與一筆隔日 `00:01`，要求落在不同列。聚合確實在資料庫端完成，
譯不出來會在測試就炸，而不是等到畫面才發現。

## 三個刻意的取捨

1. **「每日趨勢」是第一個頁籤，也是預設頁籤**（原本預設是「依使用者」）。
   本次擴充的主題就是費用走勢。這是唯一改變既有行為的地方。
2. **趨勢區間上限 180 天**：純 CSS 清單沒有分頁，區間更長就只顯示最後 180 天並標註。
   不設限的話，一個很寬的篩選就能讓頁面長到不可用。
3. **摘要卡與趨勢沒有納入 CSV／PDF 匯出**，匯出的欄位與內容完全沒動。
