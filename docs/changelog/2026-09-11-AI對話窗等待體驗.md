# AI 分析對話窗的等待體驗、取消、字級與滿版（0.9.8）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.8
- 首次實作版本：0.9.8
- 最後核對日期：2026/09/11

## 起因

使用者的原話：

> 當按下 AI分析 按鈕之後，有看到 toast 小視窗出現，不過，因為 AI 處理要一段時間，
> 此時看畫面，一時無法看出系統現在正在處理甚麼事情，這樣的 UX 設計體驗不好，
> 可能會造成使用者因為 AI 尚未處理完成，就以為這個頁面沒在做事情，而切換到其他頁面，
> 失去看到結果。

這個問題在 0.9.7 之後變得更嚴重。0.9.7 把 `TimeoutSeconds` 從 120 拉到 **600 秒**，
因為推論模型對上百筆日誌想上好幾分鐘是常態 —— 而在那幾分鐘裡，畫面上只有一則會自動
消失的右下角通知，按鈕變灰，表格不動，對話窗要等 AI 回來才第一次出現。

實測數字就在手邊：0.9.7 的驗證裡讓樁伺服器睡 150 秒，日誌記的是 `ElapsedMs=152044`。
整整兩分半鐘，使用者沒有任何依據判斷系統到底有沒有在動。

一併處理的還有三件使用者同時提出的事：對話窗要接近滿版、要有一般／中／大三段字級、
結果到手時要有 toast（這則本來就有）。

## 改了什麼

### 一、按下按鈕就開窗，同一個窗換三種內容

對話窗不再是「結果的容器」，而是「這次分析的容器」：

| 狀態 | 標題 | 內容 |
|------|------|------|
| 分析中 | AI 日誌分析（進行中）| 轉圈圈、大字「AI 正在分析 N 筆日誌…」、每秒更新的「已等待 N 秒」、以及一句「關閉本視窗將放棄這次分析」 |
| 成功 | AI 日誌分析結果 | 字級按鈕、複製／PDF、meta 資訊表、Markdown 報告 |
| 失敗 | AI 日誌分析失敗 | 錯誤訊息留在窗內，使用者自己關 |

**「已等待 N 秒」不是裝飾。** 轉圈圈只證明瀏覽器還活著 —— 它在網路斷掉、circuit 死掉的
時候一樣會轉。跳動的秒數才證明**這次呼叫**還在進行中。在最長可以等 10 分鐘的情境下，
這是使用者願意繼續等下去的唯一依據。

實作用 `PeriodicTimer` 綁在本次分析的 `CancellationToken` 上，分析一結束就自己收工，
不必另外管計時器欄位。⚠️ 更新畫面必須走 `InvokeAsync(StateHasChanged)` ——
計時器回呼不在 renderer 的同步內容上。

### 二、等待中關窗 = 放棄，而且是真的取消

按 X 或 Esc 會 `Cancel` 掉 `CancellationTokenSource`，HTTP 請求真的中止，
不是留在背景跑完。等待畫面上先講清楚這件事，不讓人事後才知道。

⚠️ **這裡有一個非做不可的區分**：逾時與使用者取消在 .NET 上**都是**
`TaskCanceledException`，唯一的分辨依據是 `cancellationToken.IsCancellationRequested`。
0.9.7 的程式碼沒有這個分支，使用者取消會落到泛型 `catch`，被記成
`LogError`「failed unexpectedly」、回傳「AI 分析失敗：TaskCanceledException。」——
把使用者的主動決定寫成系統故障。

現在 `AiAnalysisFailureReason` 多了 `Canceled`，服務層有自己的 catch，記 **INFO**：

```
AI log analysis canceled by the caller. Entries=100, ElapsedMs=3159
```

其餘附帶決定：

- **仍然寫 `AuditLog`**（`success = false`、Detail 尾端「失敗原因 Canceled」）。
  請求已經送出去了，上游很可能照樣計費 —— 稽核是成本追查的唯一帳本，
  取消不留紀錄會出現「帳單有、稽核無」的黑洞。
- **元件實作 `IDisposable`**：使用者在等待中直接導航離開也會取消。
  此時 circuit 已經收掉、`DbContext` 被釋放，稽核寫不進去（會換來一筆
  `ObjectDisposedException` 警告），所以那條路徑用 `isDisposed` 旗標跳過稽核，
  只留應用程式日誌。
- **等待中遮罩點不關**（`MaskClosable="@(isAiRunning == false)"`）。
  誤點一次遮罩就白花一次 AI 費用，代價太高。看結果時點外面關掉維持既有行為。

另外補了一道閘門：取消在傳輸層可能先變成 `HttpRequestException` 而不是
`OperationCanceledException`，於是服務層回的是 `UpstreamError` 而非 `Canceled`。
少了這道閘門，使用者關掉的視窗會在一兩秒後自己跳回來 —— 看起來像鬧鬼。

### 三、失敗留在窗內

0.9.7 以前失敗是「不開窗，只發一則 toast」。但那些訊息常常是
「請將 AiSettings:Temperature 設為 null」這種**要照著做**的內容，而 toast 幾秒就消失，
來不及抄。

現在失敗停在窗內由使用者自己關閉，**同時照舊發 toast**，並在應用程式日誌留下
WARN（檢視層，確認使用者確實看到了失敗畫面）與 ERROR（服務層既有的上游四欄診斷）。

失敗態**不顯示**複製與 PDF 按鈕 —— 沒有結果可以複製，按下去只會拿到上一次的殘留。

### 四、字級三段：100% / 125% / 150%

「一般／中／大」，預設「一般」，作用於**整個窗內容**（頁首 meta 資訊表與報告內文都跟著變）。

做法是 CSS 自訂屬性：`--ai-font-scale` 寫在 `.log-ai-body` 的 inline style，
`LogViewerView.razor.css` 裡每一條字級都改成 `calc(Npx * var(--ai-font-scale, 1))`。
自訂屬性會沿 DOM 繼承，所以 `MarkupString` 注入、落在 scope 之外的報告 HTML 也吃得到。

⚠️ **刻意不用 `em`**：`em` 在巢狀清單與 `pre code` 上會**複合相乘**，
第三層縮排的文字會被放大兩次，1.5 倍變成 2.25 倍。乘上同一個比例則每條規則各算各的。

⚠️ 倍率字串以 `CultureInfo.InvariantCulture` 格式化。本站跑
`RequestLocalizationMiddleware`，若當下文化把小數點寫成逗號，產出的是無效的 CSS 值
`1,25`，字級**靜默失效** —— 這種 bug 在開發機上永遠看不到。

**字級選擇不做持久化**，關窗重開回到「一般」。全庫目前沒有任何 `localStorage` /
`ProtectedBrowserStorage`，為了一個字級旋鈕引進一套前端偏好保存機制不划算。

### 五、接近滿版

`FormModalHelper.razor` 的 `.log-ai-modal` 從 900px × 88vh 改成 **96vw × 96vh**
（`top: 2vh`，上下各留 2vh，視覺對稱）。同時把 `<Modal Width="900">` 拿掉 ——
它本來就被 `!important` 蓋掉，留著只會讓下一個人改錯地方。

## 測試

新增兩類：

- `AnalyzeAsync_ShouldReportCanceled_WhenCallerCancels` —— 傳入已取消的 token，
  斷言 `Reason` 是 `Canceled` 而**不是** `Timeout` 或 `Unexpected`。
  這支直接釘住上面說的 filter 分辨。
- `AiModalStyleConventionTests` —— 掃 `.log-ai-meta*` 與 `.log-ai-report*` 底下的每一條
  `font-size`，要求都乘上 `var(--ai-font-scale`；另一支擋下在 `<Modal>` 標籤上加 `Width`。
  漏掉一條字級規則的症狀是「按了放大只有這段沒變」，不會壞、不會紅、程式碼看起來也正常，
  只有實際去點那三顆按鈕才發現 —— 正是最需要守門的那種漂移。
  （已實際把一條規則改回硬編碼驗證這支測試真的會紅。）

等待畫面與失敗畫面用固定字級，不在守門範圍：那兩個狀態下三顆按鈕根本不存在。
