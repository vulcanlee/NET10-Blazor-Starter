## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) A-4 拆成兩項（使用者決定），本次是 **A-4a 樂觀並行**；軟刪除為 A-4b。

5 張有編輯畫面的表（Project、Category、Team、MyUser、RoleView）沒有任何並行控制，全 repo 也沒有任何 `DbUpdateConcurrencyException` 處理：
兩人同時編輯同一筆，後存檔者**無聲覆蓋**前者。盤點另外發現兩個相關缺陷，使用者決定一起修：

1. **使用者管理、角色管理的存檔不看結果**：失敗也顯示「修改成功」—— 不修的話衝突提示在這兩頁永遠不會出現。
2. **編輯使用者會清掉鎖定狀態**：整筆覆蓋，而畫面模型沒有登入失敗次數、鎖定到期、兩步驟驗證、Google 綁定 —— 管理員只改姓名，被鎖定的帳號就解鎖了。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 拆成 A-4a／A-4b（使用者決定） | 同一批資料表，但改的是不同程式路徑（更新 vs. 刪除與所有查詢），驗證方式與風險類型不同 |
| API 的 PUT **強制**帶版本號（使用者決定） | 尚未交付，現在改契約沒有對外影響；選填等於保護可以被繞過 |
| 版本號只在「使用者編輯存檔」時更換 | 登入失敗計數、改密碼、種子資料若也換版本號，管理員在某人登入期間編輯該帳號就會誤報衝突；這些路徑改用「只更新自己負責的欄位」避免互相覆蓋 |
| `Apply` 一定明確設定 OriginalValue | 「先載入再複製欄位」（Project、MyUser、API 的 `SetValues`）若不設，EF 拿剛載入的新值比對，**永遠偵測不到衝突**（見第三節的驗證） |
| 管理員設定新密碼時解除鎖定 | 操作說明教的解鎖方式是「請管理員改密碼」；這個效果以前是整筆覆蓋順帶造成的，修正後若不明確寫出就會失效。只改其他欄位時不動鎖定 |
| 衝突時表單維持開啟 | 使用者的輸入還在，可以先記下再重開；不自動重新載入（會丟掉輸入） |
| 刪除不檢查版本號 | 刪除前已有確認窗；軟刪除與刪除路徑整體在 A-4b 處理 |
| helper 命名 `ConcurrencyStampHelper`（計畫寫 `ConcurrencyStamp`） | 實體上已有同名屬性，服務程式裡讀起來容易混淆 |

## 三、驗證（2026/10/03 實跑）

**故意改壞：拿掉 `Apply` 裡設定 OriginalValue 那一行**

| 路徑 | 結果 |
|---|---|
| Project、MyUser（tracked 載入再複製） | 衝突測試**失敗**（偵測不到衝突） |
| 3 個 API PUT（`FindAsync` + `SetValues`） | 衝突測試**失敗** |
| Category、Team、RoleView（整筆覆蓋：attach + Modified） | 仍通過 —— 這種寫法的比對基準本來就是客戶端帶來的值 |

這正好證明了設計上的陷阱，也證明測試能抓到它。

**真實瀏覽器**（Playwright 驅動本機 Edge；所有外部路徑都指向暫存目錄）：兩個分頁同時開啟同一筆分類的編輯視窗 →
A 先存：「修改成功」、視窗關閉；B 後存：「這筆資料在你編輯期間已被其他人修改或刪除。請關閉視窗、重新開啟後再編輯。」、**視窗維持開啟、B 的輸入還在**；
資料庫保留 A 的內容，版本號已換新。

**品質關卡**：`Invoke-QualityGate.ps1` 完整通過（1188 個測試）。
