## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) D-13（第 2 批第三項）。改動前團隊是平面清單，主管看不到下屬部門的資料；另外兩個既有缺口一起處理：
Web API（`ProjectRepository`／`CategoryRepository`）完全沒有團隊過濾，非管理員持 JWT 可取得全部紀錄；團隊改名不會更新專案、分類與角色上記錄的名稱。

使用者決定：

- 改名時一併更新所有引用。
- 有下屬部門時不可刪除。
- 公告／通知的團隊對象與資料可見範圍同一定義（團隊本身加上它所有上層部門的成員）。
- Web API 補上團隊過濾，並修正修改時的範圍檢查。
- 非管理員只能指派自己範圍內的團隊。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 上層檢查與寫入在同一個交易內 | SQLite 的寫入交易排隊，兩個同時「互設對方為上層」的請求才不會都通過（測試以檔案資料庫實際並行） |
| 部門樹快取 60 秒＋寫入時失效 | 每個頁面的登入檢查都要展開有效團隊；IIS 重疊回收時另一個行程最晚 60 秒看到 |
| 名稱引用維持不變，改名時同步更新 | 改存團隊 Id 要遷移所有紀錄的資料結構；同步更新在同一個交易內、改動範圍小 |
| 不可改成已刪除團隊用過的名稱 | 那個團隊留下的紀錄會被這個部門的人看到 |
| 修改時「新加的」團隊才要在範圍內 | 紀錄原本就掛著範圍外團隊（例如別人加的）時，只改標題也會被擋，無法使用 |
| 已登入卻解析不到身分一律拒絕 | 退回「只看公開」時，分類的反向規則（沒有團隊看得到全部）會讓這種請求看到所有分類 |
| 新增專案預設帶範圍裡最上層的團隊 | 範圍含所有下屬，全部帶上會讓主管建的專案對所有下屬公開 |
| Migration 不用 EF 的整表重建 | 重建分成好幾個交易並暫時關閉外鍵，中途失敗會留下半套資料表 |
