# 選單順序調整與新增日誌檢視頁面（0.4.26）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.26
- 最後核對日期：2026/08/26

## 目的

1. 「資料定義」屬於日常作業性質，卻排在偏管理性質的「系統管理」之後，順序不符使用頻率。
2. 要查看系統日誌只能登入伺服器直接開檔案。`/system-health` 雖顯示最後 100 筆，但只讀「今天」的檔案，且是一整塊無法篩選的純文字，無法用於實際排查。

## 變更範圍

### 一、選單順序調整

`Datas/Menu.json` 由 `首頁 → 專案管理 → 系統管理 → 資料定義 → 登出`
改為 `首頁 → 專案管理 → 資料定義 → 統計與分析 → 系統管理 → 登出`。

各項目的 id 不隨位置改變（5 仍是資料定義、3 仍是系統管理、4 仍是登出），這正是 id 制設計的用意 —— 渲染順序取決於檔案順序，id 只用於權限查表，重排不會錯位。

新增「統計與分析」群組（id 6，icon `analytics`），其下有「日誌檢視」（id 61，icon `description`，url `/logs`）。

`MyProject.Tests/MenuIconTests.cs` 的 `AllowedIcons` 同步加入 `analytics` 與 `description` —— 該測試以硬編碼白名單遞迴檢查 Menu.json 的每個 icon，不加會使測試失敗。

### 二、新增日誌檢視頁面

新增 `/logs`，提供四項篩選：

| 條件 | 預設 | 說明 |
|---|---|---|
| 時間區段 | 最近 1 小時 | 上限 3 天，超過自動夾住起始時間並提示 |
| 筆數 | 100 | 取最新 N 筆，範圍 1～10000 |
| 最低等級 | 不限 | 完整六級 |
| 關鍵字 | 空 | 比對整筆原始文字，不分大小寫 |

條件變更不自動查詢，需按「查詢」按鈕，避免每改一個條件就重讀檔案。

結果以表格呈現（時間／等級／記錄器／訊息／TraceId），等級以顏色標籤區分，畫面倒序、每頁 20 筆；**每列可展開檢視未經處理的完整原始文字**，含多行例外堆疊追蹤。

### 三、日誌讀取服務

新增 `MyProject.Web/Diagnostics/`，比照既有 `Web/Health/` 的基礎設施服務慣例（讀檔案不讀資料庫，不進 Business 層）：

> 命名避開 `Logs/`：`.gitignore` 的 `[Ll]ogs/` 規則（用於排除執行期日誌輸出）會連同原始碼目錄一併忽略，導致程式在本機可正常建置卻永遠無法進版控。同理，檢視元件放在 `Components/Views/Analytics/`、頁面放在 `Components/Pages/Analytics/`。

- `NLogFilePathResolver` —— 依 `NLog:BasePath` 與 Program 命名空間推導日誌目錄、檔名與區間內實際存在的檔案。
  - 以 `{前綴}-{日期}*.log` 萬用字元列舉而非精確檔名：nlog 設了 `archiveAboveSize` 卻未指定 `archiveFileName`，同一天可能另存在編號封存檔，其命名格式隨 nlog 版本而異，不宜臆測。
  - 排序依 `LastWriteTimeUtc` 而非檔名 —— 封存序號 10 與 2 的字典序會錯。
- `LogQueryService` —— 依時間升冪逐檔前向串流讀取，邊讀邊解析邊篩選，通過者推入容量為 N 的佇列。時間 O(檔案大小)、記憶體 O(N)。

解析以「第 24 個字元是否為 `|` 且前 24 字元可解析為時間戳」判斷新紀錄開頭，不符者視為前一筆的續行；整筆湊齊後才套用篩選，因為關鍵字比對的是完整原始文字。

**順帶去重**：`Health/HealthLogReader.cs` 的路徑推導原本是 `Program.cs` 那份的第二份複本，改為委派給 `INLogFilePathResolver`，避免再生出第三份。`Program.cs` 那份保留不動 —— 它執行時機早於 DI 容器建立，且帶有建立目錄、設定 NLog 變數等副作用。

### 四、匯出下載（專案首個 JS interop）

新增 `wwwroot/js/file-download.js`，以 `DotNetStreamReference` 經 SignalR circuit 串流位元組給瀏覽器，組成 Blob 觸發下載。

匯出內容為**本次查詢結果的全部 N 筆**（不受目前翻到第幾頁影響），**依時間正序（舊→新）**排列，與真實 nlog 檔的閱讀習慣一致；編碼為 UTF-8 含 BOM，確保記事本／Excel 開啟時繁體中文不亂碼。

專案原本已有 `Components/Layout/ReconnectModal.razor.js`（Blazor 範本自帶），因此這是首個 **interop**、非首個 JS 檔。此處刻意用全域函式的一般 script 而非 colocated module：module 需在 `MapStaticAssets` 下處理 fingerprint 過的 URL 並管理 `IJSObjectReference` 生命週期，為一個 12 行函式不划算。

### 五、權限（管理員專屬）

`MagicObjectHelper` 新增 `角色_統計與分析`、`角色_日誌檢視` 並登記於 `SidebarMenuService.MenuPermissionMap`，但**刻意未列入** `RolePermissionService.GetRoleListPermissionAllName()`。

因此不會種出 `Permission` 資料列、角色矩陣不顯示、任何角色都無法被授予，只有管理員短路能通過。此決定在兩處程式碼都加了註解說明，避免日後被當成漏掉的步驟補上。

頁面本身以 `CheckIsAdmin()` 守衛，與既有 `/system-health` 一致。

## 已知取捨

- **欄位切分的邊界**：layout 未對 `${message}` 逸出 `|`，訊息與例外的分界只能取最後一個 `|`；例外文字本身含 `|` 時「訊息」欄可能不完整。這正是每列可展開檢視原始文字的原因，`Raw` 永遠逐字正確。
- **不預先實作反向讀檔**。反向讀能把預設查詢從掃 100MB 降到讀 64KB，但需處理 UTF-8 多位元組邊界、續行反序歸屬、以及「篩選後才算 N 筆」無法用行數收斂等問題，約 150-250 行高風險程式碼。以目前日誌量（單檔 54KB）不值得。介面不會因此改變，是可逆的決定；觸發點是查詢耗時記錄經常超過 1 秒。服務已從第一天就記錄耗時、掃描檔數與行數。
- **時間選擇器用兩個 `DatePicker` 而非 `RangePicker`**。`RangePicker` 在本專案零使用、泛型簽章未經驗證，而 `DatePicker`（含 `ShowTime`）已在 `ProjectViewView` 驗證可用。
- **無伺服器端路由守衛**，唯一防線是 `OnInitializedAsync` 內的 `CheckIsAdmin()`；可接受的理由是權限通過前不讀取任何日誌內容。
- **TRACE／DEBUG 選項目前等同「不限」**，因 `nlog.config` 只把 Info 以上寫入檔案。保留選項是為了日後調低門檻時畫面不必再改。
- 未使用 `PermissionActions.Export` —— 它存在於 RBAC 且角色矩陣有欄位，但全專案從未被強制執行過。本頁是管理員專屬，匯出沿用同一道管理員檢查。
