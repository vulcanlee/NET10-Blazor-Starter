# AI 分析的上限設定精簡（0.9.7）

- 文件版本：2.0
- 文件狀態：已實作
- 現行系統版本：0.9.7
- 首次實作版本：0.9.7
- 最後核對日期：2026/09/11

## 起因

使用者問「`MaxCharactersPerEntry`、`MaxTotalCharacters`、`MaxOutputTokens` 這三個設定
為什麼需要？不用會不會有問題？」

回答問題的過程中查到一件比問題本身更急的事（`MaxOutputTokens` 的預設值是陷阱）。
討論完第一輪之後，使用者又追問兩件事並做了決定：

> `MaxTotalCharacters` 可否移除，有多少字，就送多少字到 AI 內

> `MaxTotalCharacters` `MaxOutputTokens` `Temperature` 這三個參數可以從
> `appsettings.json` 內移除嗎？

> 只留 Provider、Endpoint、ApiKey、Model 四個，其餘走程式預設 ——
> 這些預設值是多少？記得要寫入到相關文件內

> 將這個 `TimeoutSeconds` 不要移除，並且修改為 600 秒

所以這一版涵蓋**兩輪移除**：先拿掉單筆截斷，再拿掉總量預算，最後把設定檔收斂到五個鍵。

## 三個設定原本的角色

| 設定 | 作用 | 拿掉會怎樣 |
|------|------|------------|
| `MaxCharactersPerEntry` | 單筆日誌的截斷點 | 一筆巨大的例外堆疊會吃掉較多總預算、擠掉較舊的日誌 |
| `MaxTotalCharacters` | 送出內容的總字元預算 | 提示詞大小只剩筆數這一道界線 |
| `MaxOutputTokens` | 回應長度上限 | 不送這個參數，改由模型自己決定 |

三個都拿掉程式仍然會跑，差別是失去保護 —— 而這次的結論是**那些保護的代價比它擋下的風險大**。

## `MaxOutputTokens` 預設 2000 是個陷阱 ⚠️

微軟文件對 `max_completion_tokens` 寫得很明確：

> Both limits cover reasoning tokens, visible output tokens, and formatting tokens.
>
> This condition can occur before the model produces any visible output.
> You pay for input and reasoning tokens but receive no answer.
>
> To avoid running out of room, reserve at least 25,000 tokens for reasoning and output.

這個額度**同時涵蓋推論模型的思考 token**。預設的 2000 遠低於微軟建議的 25000，
在推論模型（o 系列、gpt-5 家族）上很可能思考還沒結束額度就用完 ——
拿到空回應，而輸入與思考的費用照付。

這與 0.9.6 修掉的 `Temperature` 是**完全同一類問題**：為舊模型設的預設值，
在推論模型上會出事。

而且原本的錯誤訊息對這個情況沒幫助。空回應時只會說「AI 沒有回傳任何內容，請稍後再試」，
使用者完全看不出是額度太小 —— 只會一再重試、一再付錢。

## 改了什麼

### 一、`MaxOutputTokens` 預設改為 `null`（不送）

型別 `int` → `int?`，預設值拿掉。不送就由模型自己決定，能相容所有模型；
要控成本的人再自己填，而且值要抓在 25000 以上。非正數視同不送。

同時移除常數 `MinimumOutputTokens = 256`：在推論模型的脈絡下夾到 256 是沒有意義的保護。

### 二、移除所有字元上限

兩輪做完的結果是 `AiLogPromptBuilder.Build` 從**三步驟降為一步驟**：

| | 0.9.6 | 0.9.7 |
|---|---|---|
| 1 | 筆數上限：取最新 N 筆 | **唯一剩下的處理** |
| 2 | 單筆截斷到固定字元數 | **移除**（第一輪）|
| 3 | 總量上限：由新到舊累加，單筆超標時硬切 | **移除**（第二輪）|

兩輪的理由是同一個：字元上限會把例外堆疊切掉尾巴，而堆疊尾巴常常才是根因所在。
第一輪只移除單筆截斷、把硬切留著當最後防線；使用者看完之後選擇連總量一起拿掉。
**有多少字，就送多少字。**

跟著失去意義的東西一併清掉：常數 `TruncationMarker` 與 `MinimumTotalCharacters`，
以及 `AiPromptBuildResult` 的四個成員 `TruncatedEntryCount`、`DroppedByTotalLimit`、
`BodyCharacterCount`（原本只為了斷言預算而存在）與 `IsTruncated`。
現在唯一會少送資料的原因是 `DroppedByEntryLimit`。

⚠️ `AiAnalysisResult.IsTruncatedByLength` 是**不同的東西**（回應端被模型切斷），沒有動。

### 三、代價：撞到內容視窗時要講得出解法

沒有字元上限之後，**`context_length_exceeded` 變成主要的失敗模式**。
這個錯誤的上游回應沒有 `param` 欄位，原本會落到 `DescribeBadRequest` 的通用分支，
只回一句「AI 服務拒絕本次請求（代碼 `context_length_exceeded`）」，看不出要做什麼。

改成具名分支：

> 送出的日誌量超過模型的內容視窗上限。請在日誌檢視頁縮小時間區間或減少查詢筆數後再試。

這不是額外功能，而是拿掉護欄的直接對價 —— 護欄沒了，撞牆時的指示就得寫清楚。

### 四、`appsettings.json` 收斂到五個鍵

```json
"AiSettings": {
  "Provider": "AzureOpenAI",
  "Endpoint": "",
  "ApiKey": "",
  "Model": "",
  "TimeoutSeconds": 600
}
```

`SystemPrompt`、`MaxEntries`、`MaxOutputTokens`、`Temperature` 刻意不寫進範本、走程式預設，
與 `SystemSettings.Upload` 同一作法。設定檔因此只剩「非填不可」與「最可能現場調整」的項目。

`TimeoutSeconds` 留下來並從 120 拉到 **600 秒**：推論模型對上百筆日誌的思考時間本來就
可能好幾分鐘，120 秒偏緊；而「要等多久」是部署環境之間差異最大、最需要現場調整的一項。

⚠️ 已知取捨：等待期間按鈕停用且**沒有取消機制**，上游若卡住，使用者最久會被困滿 10 分鐘。
這一版不處理。

### 五、程式預設值寫進文件 ⚠️

設定檔不再列出四個鍵，代表**文件是唯一查得到它們預設值的地方**。這張表同時進到
[日誌與設定檔說明 §4.8.1](../operations/日誌與設定檔說明.md) 與
[AI 日誌分析 §2.1](../features/AI日誌分析.md)：

| 鍵 | 程式預設值 | 在 appsettings | 實際效果 |
|---|---|---|---|
| `Provider` | `"AzureOpenAI"` | ✅ | 走 Azure v1 路徑；填 `"OpenAI"` 改走官方 OpenAI |
| `Endpoint` | `""` | ✅ | Azure 必填；OpenAI 留空即用 `https://api.openai.com` |
| `ApiKey` | `""` | ✅ | **必填，也是功能的開關** —— 沒填就停用 |
| `Model` | `""` | ✅ | **必填**。Azure 填部署名稱，OpenAI 填模型 id |
| `TimeoutSeconds` | `600` | ✅ | HTTP 逾時 10 分鐘 |
| `SystemPrompt` | `""` | ❌ | 用 `AiPromptDefaults.SystemPrompt` 的內建提示詞 |
| `MaxEntries` | `100` | ❌ | 送出最新的 100 筆；**這是唯一的送出量防線** |
| `MaxOutputTokens` | `null` | ❌ | 不送 `max_completion_tokens` |
| `Temperature` | `null` | ❌ | 不送 `temperature` |

`AiSettingsTests.Defaults_ShouldMatchDocumentedValues` 逐一斷言這些值，
所以改了預設值卻忘了改文件時，測試會先紅。該測試的註解也補上了指回文件的位置。

### 六、長度截斷變得可診斷

- 空回應且 `finish_reason` 為 `length` → 訊息改成「回應在產出任何內容之前就達到長度上限。
  請調高 AiSettings:MaxOutputTokens 或將它設為 `null`（推論模型的思考 token 也算進這個額度）。」
  判斷順序是：內容過濾 → 長度上限 → 其他。
- **有內容但被切斷時**（`finish_reason` 為 `length` 且內容非空）照常顯示結果，
  但多發一則警告說結尾可能不完整。一份看起來完整、實際被切掉結論的分析報告，
  比明講更危險。`AiAnalysisResult` 為此新增 `IsTruncatedByLength`。

## 順手修掉的小瑕疵

第一輪新寫的硬切守門測試抓到一個既有的 off-by-N：硬切時只扣了分隔行的長度，
沒扣截斷標記本身，所以最終長度會剛好超出上限一個標記的量（實測 1010 對上限 1000）。
修好之後，第二輪把整段硬切邏輯移除了 —— 但這個發現仍值得記著：
那個錯誤存在於 0.9.5 到 0.9.6 之間，而當時的註解宣稱它是「可精確斷言的保證」。

## 剩下的界線只有筆數 ⚠️

`MaxEntries`（預設 100）現在是唯一夾住送出量的設定。日誌檢視會把續行併成同一筆，
`archiveAboveSize` 是 100 MB，所以理論上一筆失控的堆疊或一個被記進日誌的大型序列化字串
就可能有數 MB。

實務上的數字沒那麼可怕：Azure 上 gpt-5 家族的輸入上限是 272,000 token，
而 100 筆典型 nlog 行約 20–30 KB（不到 10,000 token）。原本的 120,000 字元上限只約
30,000 token，也才用掉可用額度的一成 —— 它只在例外很多的查詢上才真的生效，
而那恰恰是最需要完整內容的場合。

成本的行為因此改變了：**同一筆數的花費現在會隨日誌實際長度浮動**，
例外很多的查詢會明顯更貴。常撞到內容視窗上限的話，調低 `MaxEntries` 是最直接的辦法
（它不在 `appsettings.json` 裡，但仍可設定）。

## 對既有使用者的影響 ⚠️

`appsettings.json` 的預設值現在是安全的，但 **User Secrets 或環境變數裡的舊值仍會蓋過它**。
若之前設過這幾項，請一併清掉：

```powershell
dotnet user-secrets --project src/MyProject/MyProject.Web remove "AiSettings:MaxOutputTokens"
dotnet user-secrets --project src/MyProject/MyProject.Web remove "AiSettings:MaxCharactersPerEntry"
dotnet user-secrets --project src/MyProject/MyProject.Web remove "AiSettings:MaxTotalCharacters"
```

後兩個鍵已不存在於 POCO，留著不會報錯（組態繫結會靜默忽略未知的鍵），
但它們已經沒有任何作用，留著只會誤導下一個讀設定的人。
`MaxOutputTokens` 不一樣 —— 那個鍵還在，舊值（例如 2000）**會真的生效**並蓋掉新的安全預設。
