# 登出需二次確認（0.9.29）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.29
- 首次實作版本：0.9.29
- 最後核對日期：2026/09/18

## 為什麼改

按下「登出」會立刻登出，沒有任何確認。

查證後發現登出有**三個 UI 入口**，全部直接連到 `/Auths/Logout`，而那一頁在
`OnInitializedAsync` 就直接 `SignOutAsync`：

| 入口 | 0.9.28 的實作 |
|---|---|
| 右上角使用者選單 | `MainLayout.razor` 的 `<a href="/Auths/Logout">` |
| 側邊欄展開 | `SidebarMenuNode.razor` 的 `<MenuItem RouterLink="@Item.Url">` |
| 側邊欄收合 | `NavMenu.razor` 的 `<a href="@item.Url">`（只有圖示） |

只改使用者選單的話，從側邊欄登出仍然會無聲登出。

## 改了什麼

三個入口都改走 `Components/Commons/LogoutConfirm.cs`：跳確認窗
「確認登出／確定要登出嗎？」，選「登出」才導向登出頁，選「取消」留在原頁。

- 使用者選單：`<a href>` → `<button @onclick>`（與同一選單的「變更密碼」一致）。
- 側邊欄展開：拿掉 `RouterLink`，改用 `<MenuItem OnClick>`。
- 側邊欄收合：`<a href>` → `<button @onclick>`，沿用原本的 class 讓外觀不變。

調性走**非破壞性的粉梅調**（`ConfirmDialog.AskAsync`）—— 登出不會毀掉任何資料，
重新登入就回來了；把每個提醒都染紅，紅色就不再代表任何事。

判斷「這個選單項是不是登出」用 `LogoutConfirm.IsLogoutUrl`，內部比對
`MagicObjectHelper.SignoutUrl`（`= "/auths/logout"`）—— 那個常數先前**定義了卻沒人用**，
正好拿來當三個入口共同的依據，不必各自硬寫網址字串。

## ⚠️ 系統的強制登出刻意不確認

`MyProject.Business/Services/Other/AuthenticationStateHelper.cs` 有**六處**
`NavigateTo("/Auths/Logout", true, true)`（未驗證、無效 Sid、查無使用者、帳號停用、
無角色、`RoleJson` 解析失敗）—— 那是系統行為不是使用者意圖。
對一個 session 已經失效的人跳出「確定要登出嗎？」只會讓他卡在一個毫無意義的問題上。

這兩條路徑在**分層上就是分開的**：`LogoutConfirm` 在 Web 層，`AuthenticationStateHelper`
在 Business 層，後者依依賴方向根本參照不到前者，構造上不可能誤走確認流程。

直接在網址列輸入 `/Auths/Logout` 也維持立即登出，刻意不擋 —— 刻意輸入網址不是誤觸。

## 為什麼不用單一導航攔截點

`NavigationManager.RegisterLocationChangingHandler` 看起來很誘人（一處攔截、所有入口自動涵蓋），
查證 ASP.NET Core 原始碼後確認**技術上可行**：互動式 Router 會攔截連結點擊並先跑
`notifyLocationChanging`，即使目標頁標了 `[ExcludeFromInteractiveRouting]`
（`Router.Refresh` 查不到路由 → 當外部 URL → 整頁載入）。

但它**不能用在這裡**：`RemoteNavigationManager.NavigateToCore` 在判斷 `ForceLoad`
**之前**就無條件呼叫 `NotifyLocationChangingAsync`，也就是說
`NavigateTo(uri, forceLoad: true)` **不會**略過 handler。那 6 處系統強制登出用的正是
`forceLoad: true`，會一起被攔下來跳確認窗 —— 比現況更糟；而 `AuthenticationStateHelper`
在 Business 層，也沒辦法設一個 bypass 旗標讓它跳過。

因此改用逐入口攔截：使用者主動點的三個 UI 元素走確認流程，強制登出在構造上就碰不到。

## 順手修掉一個會被引入的 bug

AntDesign 的 `Menu` 預設 `Selectable=true`，點下登出項會立刻把它標成選中。
取消登出不會產生 `LocationChanged`，`NavMenu.SyncMenuStateFromRoute()` 也就不會被觸發，
那個選中樣式會**一直留著**。因此 `LogoutConfirm.RequestAsync` 回傳是否已確認，
`SidebarMenuNode` 在取消時透過 `OnLogoutCancelled` 回報給 `NavMenu` 重設選中狀態。

## 已知取捨

使用者選單與收合側邊欄的登出從 `<a href>` 改成 `<button @onclick>`，
在**靜態 SSR 渲染的 MainLayout** 下會失效。這只發生在 `/Auths/<不存在的路徑>` 的 404 頁
（`App.razor.cs` 的 `RenderModeForPage()` 對 `/Auths` 開頭的路徑回傳 `null`），
而同一個選單裡的「變更密碼」「關於」在那個情境本來就已經是死的，
展開態的側邊欄（AntDesign `Menu`）同樣不會動。屬既有狀況的延伸，不另外處理。

## 守門

新增 `MyProject.Tests/LogoutConfirmationConventionTests.cs`（兩項）：

1. `Components/**/*.razor` 不得出現寫死的登出網址連結（`href` 或 `RouterLink`）。
2. 至少三處 code-behind 呼叫 `LogoutConfirm.RequestAsync` —— 三個入口都接上了。
