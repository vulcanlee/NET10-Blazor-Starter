## 目的

[路線圖 v2.0](../planning/00-腳手架強化路線圖.md) 的 A-3，使用者決定拆成兩項，本次是 **A-3a**（A-3b「Options 驗證全覆蓋」另一個版號）。

`Program.cs` 約 130 行硬寫的 migrate 與 seed，是專案裡唯一完全沒有測試的關鍵路徑，並帶著缺陷：

1. **預設角色的權限重啟後會長回來，而且是實際權限**：每次啟動把 `TabViewJson` 蓋回全部頁面，RBAC 回填再依它把 `RolePermissionMap` 補回。管理員對預設角色的限制，重啟就失效（操作說明甚至把它寫成「目前的設計」）。
2. `EnsureCreated()` 死碼：已有 18 筆 migration 走不到；一旦走到會建出無法 migrate 的資料庫。
3. 沒有跨行程保護：`RoleView.Name`、`MyUser.Account` 沒有唯一索引，兩個行程同時 seed 會建出重複列。
4. 連線字串只有 `Data Source=…`，沒有 WAL。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 拆成 A-3a／A-3b（使用者決定） | 初始化重構、鎖、連線參數都改同一段資料庫啟動程式，一起改、一起驗證；Options 驗證與資料庫無關、改動分散、風險類型不同（可能讓某環境啟動失敗），單獨一個版號方便定位與回復 |
| 預設角色**只自動加入新頁面**（使用者決定） | 「新頁面」= 程式碼有、但 `Permission` 目錄裡從未出現過的頁面鍵。路線圖原本寫的「只補角色缺少的鍵」不夠：管理員刪掉的鍵也算缺少，一樣會被補回 |
| 新頁面的 `Permission` 列在同一次 SaveChanges 寫入 | 偵測依據就是目錄；若交給之後的 RBAC 回填補目錄，seeder 先後順序一變，新頁面就永遠偵測不到 |
| 比對時 Trim | 0.4.32 之前的資料庫可能還有 `"登出 "` 這類鍵（正規化在 RBAC 回填才做），不 Trim 會誤判成新頁面 |
| 鎖等待上限 60 秒 | IIS in-process 的 `startupTimeLimit` 預設 120 秒；等太久會被 IIS 砍在 migration 中途 |
| 鎖只對「分享／鎖定衝突」重試 | 權限不足、路徑錯誤重試也不會好，立即失敗才不會變成兩分鐘的無聲等待 |
| 每個 seeder 之後 `ChangeTracker.Clear()` | seeder 共用同一個 DbContext；某個 seeder 失敗後殘留的變更，不能被下一個 seeder 的 SaveChanges 寫進去 |
| 不加 `busy_timeout` | 實測 Microsoft.Data.Sqlite 遇到 SQLITE_BUSY 會自己重試到命令逾時（預設 30 秒） |
| 明確寫出 `Foreign Keys=True` | 實測原本就已開啟（e_sqlite3 預設），但不能靠預設 —— 換原生程式庫時若預設變關閉，所有 FK 會靜默失效 |
| WAL 失敗只記警告 | 它是效能設定，不是正確性前提；設定存在檔案內，下次啟動會再試 |
| 例外情境（Startup）的設定留在同步的 `Main` | 情境存在 AsyncLocal，在非同步方法裡設定的值不會流回呼叫端 |
| 不做成 `IHostedService` | 明確呼叫才能保證資料庫就緒前不接請求；WebApplicationFactory 的行為也不變 |
| support 帳號的 seed 行為完全不變 | 本次是搬移與修缺陷，不改變既有的密碼救援行為 |

## 三、驗證（2026/10/03 實跑）

**SQLite 行為**（`SqliteBehaviorTests`，決定連線參數）：Foreign Keys 在連線字串沒寫時已為 1；`PRAGMA journal_mode=WAL` 回傳 `wal` 且重開連線後仍是 WAL；
持有寫入鎖的連線 500ms 後提交，另一條連線的寫入會等到它提交後成功；不放鎖時，命令逾時 1 秒的寫入約 1 秒後以 SQLITE_BUSY（5）失敗。

**故意改壞，測試必須失敗**（每項做完都已還原）：

| 改壞方式 | 失敗的測試 |
|---|---|
| 預設角色恢復「每次覆寫為全部頁面」 | `PageRemovedByAdmin_ShouldStayRemovedAfterRestart`、`LegacyKeyWithTrailingSpace_ShouldNotBeTreatedAsNewPage` |
| 比對時不 Trim | `LegacyKeyWithTrailingSpace_ShouldNotBeTreatedAsNewPage` |
| 拿掉跨行程鎖 | `LockHeldByAnotherProcess_ShouldTimeOut`、`TwoProcessesStartingTogether_ShouldNotDuplicateSeedData` |

> 踩到的坑：「兩個行程同時啟動」的測試一開始在**拿掉鎖之後仍然通過** —— EF 的 migration 鎖讓兩邊自然錯開，內建 seeder 又太快，競態重現不了，
> 這個測試其實沒有證明鎖的作用。改為加入一個測試專用的「先查、停 500ms、再寫」慢速 seeder 放大時間窗後，拿掉鎖就會穩定失敗。

**實際啟動網站**（資料庫指向暫存目錄，未動到本機開發資料庫）：

1. 全新資料庫啟動：日誌依序出現 migration、預設角色、support 帳號、RBAC 回填；資料庫為 WAL 模式，目錄出現 `-wal`、`-shm` 與 `BackendDB.db.migration.lock`；預設角色擁有全部 7 個頁面。
2. 停站，模擬管理員從預設角色移除「分類清單」（`TabViewJson` 與權限列都刪除，等同角色管理畫面的效果）。
3. 重新啟動：「分類清單」**沒有長回來**；support 密碼依設定重設，API 登入成功。

> 第一次以 support/support 從 API 登入回 401：開發環境會載入 User Secrets，其中的 `BootstrapSettings` 有另一組密碼，seeder 正確採用了它（與改版前相同）。
> 改以環境變數覆寫密碼後登入成功。

**品質關卡**：`Invoke-QualityGate.ps1` 完整通過（1134 個測試）。

## 已知限制與後續

- IIS 重疊回收時，舊的工作者行程不會重跑初始化，會以舊程式碼存取已升級的資料庫 —— migration 在重疊期間必須向下相容。
- 行程在 migration 中途被強制結束時，EF 的 `__EFMigrationsLock` **可能**殘留一列（未實測）；若下次啟動卡在套用 migration，停站後檢查並刪除。
- **後續項目（已記入路線圖，未排期）**：「預設角色」可以被改名或刪除，之後 seeder 會重新建立一個擁有全部頁面的「預設角色」，
  而 Google 自動建立的帳號以名稱對應它。建議日後禁止改名與刪除這個角色。
