# 帳號與角色名稱唯一性（0.9.171）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.171
- 首次實作版本：0.9.171
- 最後核對日期：2026/11/08

## 目的

速查表 §4.2 記著一項待辦：`MyUser.Account` 與 `RoleView.Name` 的唯一性檢查比分類、團隊弱。

- 比對沒有去頭尾空白，也分大小寫。
- 資料庫沒有唯一索引。
- 可能建出「Admin」和「admin」兩個帳號，影響登入與權限。

盤點時另外發現：Google 登入自動建立帳號時直接用 Email 當帳號，沒有先檢查是否已被別人使用。

## 使用者的決定（2026/11/08）

| 項目 | 決定 |
|---|---|
| 比對規則 | 帳號與角色名稱一律去頭尾空白、不分大小寫，不能重複 |
| 登入與忘記密碼 | 也不分大小寫（輸入「Admin」可以登入「admin」） |
| 既有重複帳號 | 保留最早建立的；其他改名為「原帳號 (重複-Id)」並停用，系統留下紀錄（審查後補一條：管理員優先保留，見「獨立審查」） |
| 既有重複角色 | 照分類的既有做法：後建的改名為「原名 (重複-Id)」 |

## 內容

- **寫入前正規化**：`AutoMapping` 的使用者帳號與角色名稱掛上 `NameNormalizer`；使用者的 `UpdateAsync` 是逐欄指定，另外正規化。
- **不分大小寫比對**：
  - 帳號：新增前、修改前、還原時的重複檢查；登入（Blazor 與 Web API 共用）；忘記密碼的帳號查詢；support 帳號種子。
  - 角色名稱：新增前、修改前、還原時的重複檢查。
  - 登入萬一還有多筆符合，優先取大小寫完全相同的那一筆。
- **Google 登入**：要自動建立新帳號，但 Email 已經是別的使用者的帳號名稱時（含已刪除的使用者），不建立也不合併（否則會登入到別人的帳號）。
  - 回登入頁顯示「這個 Email 已經是其他使用者的帳號名稱，無法自動建立帳號。如果那就是你的帳號，請系統管理員在帳號資料補上這個 Email，再用 Google 登入即可連結。」。
  - 兩個回呼同時建立同一個帳號時，撞到唯一索引的那一個也照這個結果處理，不回 500。
  - 稽核寫 `Login.Sso.Failed`，`reason=AccountTaken`。
- **資料庫唯一索引**：
  - migration `AddUserAccountRoleNameUniqueIndex` 新增部分唯一索引 `IX_MyUser_Account`、`IX_RoleView_Name`，只約束未刪除的資料，和分類一樣。
  - 照既有慣例用 BINARY 定序；不分大小寫由服務層先擋，索引是最後一道防線。
  - 違反時經 `UniqueConstraintHelper` 轉成「帳號已存在（不分大小寫），無法儲存。」與「角色名稱已存在（不分大小寫），無法儲存。」。
- **升級時的資料清理**：同一個 migration 在建立索引之前先處理。
  1. 帳號與角色名稱去頭尾空白，含全形空白。
  2. 未刪除的帳號裡不分大小寫重複的：保留管理員，其次 Id 最小的；其他的先寫稽核（時間為 UTC） `User.DuplicateAccountRenamed`（記原帳號與新帳號），再改名為「原帳號 (重複-Id)」、停用，並換 SecurityStamp，讓已登入的連線被登出。
  3. 未刪除的角色裡不分大小寫重複的：後建的改名為「原名 (重複-Id)」。
- **初始化鎖**：`DatabaseInitializationLock` 的說明更新。有了唯一索引後，鎖仍讓兩個同時啟動的行程依序 seed，第二個看到已存在就不再建立。

- **support 種子**：大小寫完全相同的優先；只差大小寫的那一筆不是管理員時，記 Critical 並讓啟動停下來，不會把別人提升成 support。
- **比對規則的實作**：程式端的小寫一律用新的 `NameNormalizer.ToLowerAscii`（同 SQLite 的 `lower()`，只折疊 A-Z）。

## 獨立審查

另派一個代理人只看程式差異，結果沒有高嚴重度問題。處理如下：

| 發現 | 處理 |
|---|---|
| 程式端用 C# 的 `ToLower()`，會折疊所有字母，SQLite 的 `lower()` 只折疊 A-Z：「Émile」這類帳號連大小寫完全照打都登不進去、忘記密碼也找不到，是回歸（中） | 新增 `NameNormalizer.ToLowerAscii`，所有比對改用它。新增測試 |
| support 種子不分大小寫比對，可能把只差大小寫的一般使用者提升成管理員並改掉他的密碼；migration 也可能把真正的 support 停用（中） | 種子大小寫完全相同的優先，只差大小寫的非管理員就拒絕啟動；migration 改成管理員優先保留。新增測試 |
| migration 寫入的稽核時間用了本地時間，稽核表存的是 UTC，畫面差 8 小時（中） | 改成 UTC。測試補時間斷言 |
| 資料庫索引只擋大小寫完全相同的重複，同時新增「Pat」「pat」兩邊都會過（低） | 不改：和分類一樣是已知的取捨，寫進速查表 |
| 去空白的範圍：C# 的 `Trim()` 比 migration 多去幾種罕見空白（低） | 不改：和分類的 migration 相同 |
| Google 登入：已刪除的使用者帳號就是這個 Email 時仍會新建；並行建立撞索引回 500；訊息可以提示怎麼連結（低） | 已刪除的也算占用；撞索引時照「已被使用」處理；訊息補上「請管理員補上 Email 後再用 Google 登入即可連結」。新增測試 |
| `PasswordResetService` 有一行註解還寫「帳號比對區分大小寫」（低） | 已更新 |

## 已知限制

- SQLite 的 `lower()` 只折疊 ASCII，全形英數與 `É` 這類字不視為重複（同分類）。
- 系統管理助理的帳號類工具維持原本的查法：先完全比對，再不分大小寫且唯一時才採用。
