- 文件版本：1.0

- 首次實作版本：0.4.38
- 最後核對日期：2026/08/26

## 目的

腳手架的核心賣點是「新增模組很快」，但實際上每個模組是**整份複製**既有檢視。
把實體名稱正規化後對照，`CategoryViewView.razor.cs` 與 `TeamViewView.razor.cs`
（各 397 行）只差約 25 行，連註解都一字不差。

**這不是理論風險，已經造成過實際缺陷**：`開發慣例與限制速查.md` §6.1 記載
「新頁面靠複製既有檢視時把 emoji 一路帶下去（六個檢視共 22 個按鈕）」，0.4.27 才補齊。

而既有的 `scripts/New-CrudModule.ps1` 救不了這件事 —— 它產出的是**空殼**：
Controller 的 `Search` 直接回空的 `PagedResult` 不接 Service、View 只有一個裸 `<Table>`、
測試是 `Assert.True(true)`、產出的 `Menu.{Name}.json` 用的還是早已廢除的 `permissionName` 欄位。
**產生器與真實樣板脫節，比沒有產生器更危險** —— 它給了「有工具」的錯覺，
於是大家繼續複製 `CategoryViewView`。

## 變更範圍

### 一、抽出兩個共用元件（檢視淨減 452 行）

| 元件 | 取代的重複 |
|------|-----------|
| `Components/Commons/TableSortHelper.cs` | 5 份 `GetCurrentSortModel` / `HasSortDirection` / `ResolveSortFieldName` |
| `Components/Commons/ViewNotification.cs` | 48 個結構相同的 `NotificationConfig` 區塊 |

`ResolveSortFieldName` 是**最該收斂的一段**：它以 reflection 讀 AntDesign 的內部屬性
（`Column.FieldName` → `Column.DataIndex`），對套件升版極為脆弱。
原本一旦 AntDesign 改了屬性名稱，五個地方要一起改；現在只有一個修改點。

> ⚠️ **刻意保留的既有行為**：專案的「新增成功／修改成功／刪除成功」等訊息
> 使用 `NotificationType.Warning`（非筆誤，是既有外觀）。
> 因此 `ViewNotification` **不提供 `Success` 多載**，避免有人順手改掉視覺表現。
> 「驗證失敗」則另有 `ValidationError`，含 `Duration = 5`（訊息較長，需要時間讀完）。

**未做的部分**：沒有把分頁／Modal 狀態欄位抽成 base class。
那需要重新命名 5 個 `.razor` 檔案中被標記引用的欄位，而專案**沒有任何 Blazor 元件測試**
（無 bUnit）可以接住回歸。以目前的測試涵蓋度，那筆交易不划算 ——
建議先補 bUnit，再談 base class。

### 二、重寫 `scripts/New-CrudModule.ps1`

產出 13 個檔案（Entity / 3 個 DTO / AdapterModel / Service / Repository / Controller /
Page / View 標記 / View code-behind / 測試 / README），全部對齊現行慣例：

- Service 注入 **`IDbContextFactory`**（0.4.36 起），不再有 `CleanTrackingHelper`
- Repository 維持 scoped `BackendDBContext`（API 路徑 scope ＝ 單次請求，本來就正確）
- Controller 回 `ApiResult<T>` / `PagedResult<T>`，以 `[HasPermission]` 做動作級授權，
  例外一律走 `this.ApiServerError`（遵守 `Security:ReturnExceptionDetails`）
- 檢視使用 `ToolbarIconButton` / `CrudActionButton` / `TableSortHelper` / `ViewNotification`，
  編輯前 `Clone()`，權限用 `CheckAccessPage` + `CheckAccessAction`
- `Skip`/`Take` 一律搭配 `OrderBy`；分頁在資料庫端執行
- 測試是**真的測試**（新增／重複名稱檢查／刪除），並使用 `TestDbContextFactory`
- README 列出四方權限一致性的完整註冊步驟，含
  `MenuPermissionConsistencyTests.ViewToMenuId` 的登錄

## 驗證

**產出的模組實際整合進方案並建置** —— 這是本次唯一有意義的驗收方式，
過程中抓到 5 個樣板 bug（舊產生器同樣有其中數個，代表它的產出從來沒編譯過）：

| 樣板 bug | 症狀 |
|---------|------|
| `$Name?` 在 PowerShell 被當成變數名 `Name?` | 產出 `Task<>`、` item = await ...`，無法編譯。改用 `${Name}?` |
| 缺 `using MyProject.Models.Systems` | 找不到 `VerifyRecordResult` / `DataRequest` / `DataRequestResult` |
| `DataRequest` 沒有 `Skip` 屬性 | 改用 `CurrentPage`/`PageSize`，與既有服務一致 |
| `<Column @bind-Field>` 在 AntDesign 1.6.0 已過時 | `TreatWarningsAsErrors` 下直接建置失敗。改用 `DataIndex="@nameof(...)"` |
| 檢視放在 `Views` 根命名空間 | Page 薄殼找不到元件。改放 `Views/{Name}s/` 並於 README 提示補 `_Imports.razor` |

最終結果：**`dotnet build -c Release` 0 warning、0 error**。

整合後執行測試會得到 EF Core 的 `PendingModelChangesWarning` ——
這正是 README 步驟二之三要求的「產生 migration」，**EF Core 自己會強制**，
開發者無法靜默略過。驗證完畢後已完整還原，工作目錄無殘留。

主線狀態：258 個測試全數通過、0 warning、`dotnet format` 0 error、文件編碼檢查通過。

## 影響與注意事項

- **新檢視請用 `TableSortHelper` 與 `ViewNotification`**，不要把樣板複製回檢視。
- **改了慣例請一併改產生器樣板**，否則它會再度淪為擺設。
- 產生器的檢視只到清單 + 刪除；**維護 Modal 仍需人工補上**（README 有標註參考來源）。
