# 「篩選範圍合計」改為儀表板卡片（0.9.53）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.53
- 首次實作版本：0.9.53
- 最後核對日期：2026/09/23

## 為什麼

`/token-usage` 的「篩選範圍合計」原本是一條單行橫幅，六個數字擠在一行用頓號分隔，
掃視困難。使用者要求改成與下方「近 1／7／30 天」一致的區塊卡片。

## 為什麼是四張卡，不是六張

橫幅上有六個數字，但其中兩個**不是對等項目**：

```
輸入（prompt）
 └─ 其中快取   ← 輸入的折扣子集，不另計入合計
輸出（completion）
 └─ 其中推理   ← 計入輸出，不另計入合計
合計 ＝ 輸入 ＋ 輸出
```

這條語意是整個功能被最多處強調的紅線（PRD §3.2、速查表 §6.7、`TokenUsageSummary`
的註解、`GetSummaryAsync` 的註解，以及
`GetSummaryAsync_ShouldNotDoubleCountCachedOrReasoning` 這支測試）。
橫幅時代靠「**其中**快取」「**其中**推理」兩個字撐住。

**做成六張長得一樣的卡，等於把這個層級拿掉** —— 讀的人會很自然地把六個數字當對等指標相加，
而那是錯的。所以改成四張，快取寫進【輸入】卡、推理寫進【輸出】卡，
**用版面層級表達從屬關係**，比只靠兩個字可靠。卡內另附一行淡字說明「不另計入合計」。

## 做了什麼

- 四張卡：輸入（送出／prompt）、輸出（接收／completion）、合計、花費。
- 花費卡主數字是 NT$，副行 US$；有未定價時掛上既有的橘色「⚠ 其中 N 筆未定價未計入」。
- 標題列比照下排寫成「篩選範圍合計　—　套用條件：…」。
- 下排標題列補上「（點卡片可套用該區間）」，讓「可點的是哪一排」一眼看得出來。

### 兩排的「套用條件」其實不一樣

⚠️ 上排是**完整篩選範圍，含起訖日**；下排的近 N 天卡會把日期換成自己的窗，**不含日期**。
兩排都寫「套用條件」卻指不同範圍會誤導，所以上排的字串會明確列出「日期 A ～ B」
（沒設時寫「不限」），下排維持原樣。

兩份字串共用 `BuildFilterText(bool includeDates)`，不會日後各自漂移。

### 樣式：兩排共用同一份基底

兩排要長得像，樣式就該同源，否則遲早漂移。抽出 `.token-usage-stat-card`
（框線、圓角、內距、flex 欄向）與 `.token-usage-stat-label/-value/-meta`，
兩排共用；`.token-usage-range-card` 只延伸出可點的部分（游標、hover、焦點框、選中狀態）。

⚠️ 上排用 `<article>` 而非 `<button>`：那排**沒有東西可套用**，
給了互動感只會讓人去點然後沒反應。

隨之移除只被舊橫幅使用的 `.token-usage-summary` 與 `.token-usage-summary strong`
（本次變更造成的孤兒）。

## 沒有做什麼

- **沒有新增「呼叫次數」卡** —— 原本橫幅沒有這個數字，加了是擅自擴大範圍。
- 沒有動資料查詢、服務或任何計算，`TokenUsageSummary` 一個欄位都沒改。
- 沒有動下排近 N 天卡的行為（仍可點擊套用區間），只有類別更名與標題列補一句提示。
- **沒有新增測試。** 這是純呈現層變更，沒有動任何計算；既有的
  `GetSummaryAsync_ShouldNotDoubleCountCachedOrReasoning` 仍守著「子集不重複計入」的**語意**，
  但**卡片版面有沒有正確傳達那個語意，只能靠目視**。
  `FilterScopeText` 是 Blazor 元件的私有屬性，專案沒有 bUnit，
  不引入新相依就無法直接斷言（既有的 `ActiveFilterText` 同樣沒有測試）。
