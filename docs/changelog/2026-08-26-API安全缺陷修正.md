# API 安全缺陷修正：例外外洩、停用帳號、預設拒絕（0.4.34）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.34
- 最後核對日期：2026/08/26

## 目的

修正四項 Web API 安全缺陷。其中兩項（一、二）是**文件宣稱與實作不符**，
第三項是實作第二項時才發現的既有漏洞。

## 變更範圍

### 一、Production 仍會外洩例外堆疊

`appsettings.Production.json` 設了 `Security:ReturnExceptionDetails: false`，
`ApiExceptionFilterAttribute` 也確實依此判斷 —— **但 Controller 的 catch 區塊完全繞過這個開關**：

```
Controllers/ControllerApiResponseExtensions.cs  →  ApiResult.ServerErrorResult(message, exception)
                                                →  ErrorDetail = exception.ToString()
                                                   Exception   = 含 StackTrace 的 ApiExceptionInfo
```

Controller 中共 **16 處**呼叫 `this.ApiServerError(...)`，全部無條件回傳完整堆疊，
與 `docs/architecture/Web API 設計慣例.md` 的宣稱直接相反。

**處置**：新增 `Configuration/ExceptionDetailPolicy` 作為**單一判斷來源**，
`ApiExceptionFilterAttribute` 與 `ApiServerError` 都改走它。
細節關閉時改用 `ApiResult` 既有的無例外多載，回應仍是完整的 `ApiResult` 信封。

### 二、Refresh Token 不查資料庫

`AuthController.Refresh` 只驗 JWT 簽章，接著**直接用 token claim 裡的 `IsAdmin`**
重建 `MyUser` 並簽發新 access token，全程沒有 DB 查驗。
帳號被停用、降權或刪除後，refresh token 在有效期內仍可持續換發帶 `is_admin=true` 的 token。

**處置**：換發時以新增的 `MyUserServiceLogin.GetActiveUserAsync(userId)` 回查資料庫，
查無此人或已停用一律回 401，`IsAdmin` 以資料庫現值重新取得。

> 這與 `docs/changelog/2026-07-09-三項待辦決定不實作.md` 決定不做的
> 「Refresh Token **落庫撤銷**」是兩件事：落庫撤銷讓「特定一顆 token」失效（仍不實作）；
> 回查資料庫讓「帳號被停用或降權」能即時生效。成本極低，不牴觸該決策。

### 三、停用帳號可以登入並取得 JWT（實作第二項時發現）

`MyUserServiceLogin.LoginAsync` **完全沒有檢查 `MyUser.Status`**。

- **UI 路徑**：靠 `AuthenticationStateHelper.Check:79` 在後續每次頁面載入時擋下 —— 尚可。
- **API 路徑**：`/api/Auth/login` 直接發出 JWT，而 `PermissionChecker` 與
  `HasPermissionAttribute` **也都不看 `Status`** —— 停用帳號可正常呼叫所有 API。

**處置**：在 `LoginAsync` 找到使用者之後、驗密碼之前檢查 `Status`，
回「帳號已停用，請聯絡系統管理員。」並寫入 `Login.Disabled` 稽核。
修在共用路徑上，UI 與 API 一起生效。

### 四、移除模板遺留 Controller，改為 Controller 端預設拒絕

`WeatherForecastController` 無任何授權標註、路由 `/[controller]` 不在 `/api` 之下
（連 `ApiExceptionFilterAttribute` 都不涵蓋，該 Filter 只處理 `/api` 前綴）、回傳裸物件不包 `ApiResult`。
資料本身無害，但它會被 `scripts/New-StarterProject.ps1` 複製到**每一個客戶專案**。
連同 `MyProject.Models/Others/WeatherForecast.cs` 一併移除。

同時於 `Program.cs` 加上 `app.MapControllers().RequireAuthorization()`，
讓「未標註 = 拒絕」；`ExternalAuthController`（Google OAuth 入口）補上明示的 `[AllowAnonymous]`。

> **刻意不用 `AuthorizationOptions.FallbackPolicy`**：原計畫是用它，但實際檢查後發現
> 它會把 Blazor 的 Razor Components 端點一起納入，而本專案的頁面**全部沒有 `[Authorize]`**
> （改在 `OnInitializedAsync` 內命令式檢查）—— 套上去會連 `/Auths/Login` 本身都鎖死。
> 改用只作用於 Controller 的 `RequireAuthorization()`，達到同樣的預設拒絕效果而不影響 UI。

### 五、分頁參數缺乏上下限

`SearchRequestBaseDto` 的 `PageIndex` / `PageSize` 沒有 `[Range]`：
`PageSize=int.MaxValue` 會把整張表撈進記憶體，`PageIndex=0` 會讓
`Skip((PageIndex - 1) * PageSize)` 變成 `Skip(-PageSize)` 而拋例外。

**處置**：`PageIndex` 下限 1、`PageSize` 限制 1～200（`MaxPageSize` 常數）。
違規由既有的 `ApiValidationFilter` 回 400。

## 驗證

新增測試（`dotnet test` 由 204 → **214 個全數通過**）：

| 測試 | 驗證 |
|------|------|
| `ApiExceptionDetailSuppressionTests`（Theory ×2）| 細節關閉時，**未攔截例外**與 **Controller catch** 兩條 500 路徑都不含例外資訊與堆疊 |
| `CaughtApiException_WithDetailsEnabled_ShouldIncludeExceptionInfo` | 細節開啟時仍照常回傳（未過度收斂）|
| `LoginAsync_WithDisabledAccount_ShouldFail` | 停用帳號登入失敗 |
| `GetActiveUserAsync_WithEnabledAccount_ShouldReturnUser` / `WithDisabledOrMissingAccount_ShouldReturnNull` | refresh 回查的判斷依據 |
| `WeatherForecastEndpoint_ShouldNotExist` | `/WeatherForecast` 回 404 |
| `Search_WithOutOfRangePaging_ShouldReturn400`（Theory ×3）| `PageIndex=0`、`PageSize=0`、`PageSize=int.MaxValue` 皆回 400 |

**變異測試**：把 `ApiServerError` 的判斷強制改回 `true`，
`ApiExceptionDetailSuppressionTests` 的 **caught 那條精準轉紅**、throw 那條仍綠
（後者走 filter，本來就是對的）—— 證實測試守在正確的位置。

其餘關卡：`dotnet build -c Release` 0 warning、`dotnet format --verify-no-changes` 0 error、
文件編碼檢查通過。

## 影響與注意事項

- **停用帳號的登入行為改變**：此前 UI 會先讓它登入、再於頁面載入時擋下；
  現在直接在登入頁顯示「帳號已停用」。API 則從「照常發 JWT」變為 401。
- **新增 Controller 時**，若需要匿名存取必須自己標 `[AllowAnonymous]`，否則會被預設拒絕擋下。
- **Controller catch 回 500 一律用 `this.ApiServerError(...)`**，
  不要自己組 `ApiResult.ServerErrorResult(message, exception)`（那個多載會無條件夾帶堆疊）。
- 分頁上限 200 定義於 `SearchRequestBaseDto.MaxPageSize`。
