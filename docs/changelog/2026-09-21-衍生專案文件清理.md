# 衍生新專案時自動清掉腳手架自身的歷史文件（0.9.46）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.46
- 首次實作版本：0.9.46
- 最後核對日期：2026/09/21

## 起因

使用者要拿這個腳手架開新系統，發現 `docs/` 有 **143 個檔、20,886 行**，其中很大一部分是
**腳手架自己的開發史**，對新系統沒有用處。三個痛點同時存在：

- 新專案的開發者打開 `docs/` 分不清哪些是「我的系統」、哪些是「腳手架的過去」
- AI 協作時這些文件會被搜到、佔 context，還可能依據過時的改版紀錄做出錯誤判斷
- 衍生專案可能交付給客戶，腳手架的「某某安全缺陷修正」不適合隨專案出去

上手指南 §8.2 步驟 8 原本就寫著「`docs/changelog/` 建議整個清空重來」，但**靠人記得做**，
腳本完全沒動它。

## 做了什麼

### 1. `New-StarterProject.ps1` 預設清理，`-KeepStarterHistory` 保留

分類的判準是「這份文件描述的是**你繼承到的東西**，還是**腳手架的過去**」：

| 目錄 | 檔數／行數 | 處置 | 理由 |
|------|-----------|------|------|
| `architecture` `security` `features` `operations` `guides` | 35 檔／9,673 行 | 留 | 描述你繼承到的程式 |
| `prd` | 17 檔／2,235 行 | 留 | 描述你繼承到的功能；保留文件中有 60 條連結指向它 |
| `changelog` | 77 檔／7,377 行 | **清空內容、保留 `README.md`** | 見下方 |
| `planning` | 8 檔／793 行 | 整個刪 | 01～06 是已封存快照，00 是腳手架自我改進路線圖 |
| `superpowers` | 5 檔／629 行 | 整個刪 | 已實作功能的設計稿 |

結果：143 份 → **54 份**。

### 2. `changelog/` 為什麼只清空、不刪目錄

`docs/operations/維護規範.md` 與 `docs/guides/腳手架開發指引.md` 的檢查清單都規定
「**每一次異動**要新增一篇 `docs/changelog/`」。新專案需要一個**空的** changelog
從自己的第一篇開始寫，而不是一個不存在的目錄。保留 `README.md` 還讓兩條指向
`../changelog/README.md` 的連結維持有效。

清完之後 `changelog/README.md` 的索引表會只剩表頭 —— 那正是一個新專案該有的樣子。

### 3. 斷連結採單一通則，不做逐段硬編的文字手術

清掉之後，保留文件裡會留下指向已刪檔案的連結。實作一條通則掃過 `docs/**/*.md` 與
`readme.md`，解析每個 Markdown 連結的目標：

- 整個目錄被刪 → 索引裡對應的**整節連標題一起移除**（`### planning — …`、`### 設計規格（superpowers）`）
- 整行只是一條索引項（`- [標題](目標)` 或表格列）→ **刪整行**
- 連結夾在敘述句中 → **降級為純文字**，句子仍然讀得通

實測結果：移除 168 行索引、降級 10 條連結，產出的專案中**指向被清理目錄的死連結為 0**。

⚠️ 這條通則**只處理指向被清理目錄的連結**。其他死連結（若原本就有）不在職責範圍內 ——
誤改反而難追。

反引號包住的檔名（例如「見 `` `changelog/2026-08-17-…md` ``」）不是 Markdown 連結，
會以純文字形式殘留，屬已知且可接受的殘留。

## 驗證

實跑腳本並比對兩種模式：

- 預設：`docs` 143 → 54 檔；`planning`／`superpowers` 不存在；`changelog` 只剩 `README.md`
- `-KeepStarterHistory`：`docs` 維持 143 檔，`planning` 完整保留
- 產出專案掃描全部 Markdown 連結：指向被清理目錄的死連結 0 條
- 產出專案 `Test-DocsEncoding.ps1` 通過、`dotnet build` 0 警告 0 錯誤
- `DocumentationConventionTests`（會實際讀取 `腳手架開發指引.md` 與 `日誌與設定檔說明.md`）通過

## 順帶查到、但**尚未修**的既有缺陷

`LoginRateLimitTests` 的兩個測試共用同一個 `IClassFixture` factory，登入配額是 2，
但 `GeneralApi_ShouldNotBeAffectedByLoginQuota` 會連打 **5 次**登入。若它先跑，
配額就被吃光，`Login_BeyondQuota_ShouldReturn429_WithApiResultEnvelope` 預期的前兩次 401
會直接變成 429。

xUnit 依測試案例 UniqueID 的雜湊排序，而 UniqueID **含組件名稱** —— 所以
**衍生專案叫什麼名字，決定了這兩個測試誰先跑**，也就決定了新專案第一天的測試是綠是紅。

控制組實驗：同樣命名為 `PruneApp`、但加上 `-KeepStarterHistory`（完全不清文件）產出的專案，
一樣失敗 → 與本次文件清理無關，是既有的測試順序相依缺陷。
