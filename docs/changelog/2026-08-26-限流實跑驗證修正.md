# 限流實跑驗證修正：政策被覆蓋與 429 信封（0.4.37）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.37
- 首次實作版本：0.4.37
- 最後核對日期：2026/08/26

## 目的

0.4.35 導入分割式限流後，**實際把應用程式跑起來驗證**時發現三個問題 ——
全部都是單靠單元／整合測試看不出來的。記錄於此，因為它們的成因都很容易再犯。

## 問題與修正

### 一、登入配額被端點慣例蓋掉，靜默失效

原本以 `[EnableRateLimiting("login")]` 屬性替登入端點指定較嚴格的配額。

**但 `MapControllers().RequireRateLimiting("api")` 這個端點慣例的套用時機晚於屬性**，
限流中介軟體取的是最後一筆 metadata —— `"login"` 被 `"api"` 蓋掉，登入配額等於沒設。

發現方式：連打 12 次登入，全部回 401，**一次 429 都沒有**。
（測試看不出來的原因：帳密錯誤本來就回 401，被限流也不會改變這個結果。）

**處置**：把登入的較嚴格配額**寫進同一個 `"api"` policy**，依請求路徑判斷，
不再依賴 metadata 的先後順序：

```csharp
options.AddPolicy("api", context =>
{
    var isLogin = IsLoginRequest(context);
    var permitLimit = isLogin ? settings.LoginRequestsPerMinute : settings.ApiRequestsPerMinute;
    var partitionKey = (isLogin ? "login:" : "api:") + ResolvePartitionKey(context);
    ...
});
```

前綴讓登入與一般 API 各自計數，不會互相消耗配額。

### 二、429 回應被錯誤頁重跑成 400 HTML

限流拒絕時只設狀態碼、不寫 body。空 body 的錯誤狀態會被
`UseStatusCodePagesWithReExecute("/not-found")` 攔下重跑 ——
它會拿**原始的 POST + `application/json`** 去執行 `/not-found`（Blazor 頁面），
被 antiforgery 擋下，最後回給呼叫端的是：

```
HTTP/1.1 400 Bad Request
Content-Type: text/html
The request has an incorrect Content-type.
```

呼叫端完全看不出真正發生了什麼事，也違反「Web API 回應一律包信封」的不變量。

**處置**：`OnRejected` 寫入 `ApiResult` JSON。有 body 之後就不會觸發重跑。

> 一併在 `Program.cs` 的 `UseStatusCodePagesWithReExecute` 上加註警語：
> **每一條 API 錯誤路徑都必須自己寫入 body**。
> 目前 JWT 的 401/403 事件、`ApiExceptionFilter`、`ApiValidationFilter`、
> `HasPermissionAttribute` 與限流的 `OnRejected` 都已如此。
>
> 註：曾嘗試以 `UseWhen` 把 `/api` 排除在錯誤頁重跑之外，但那會讓
> `/UploadFiles` 的 401 變成 404（該路徑不在 `/api` 下，卻仍受分支影響），
> 屬於得不償失的副作用，已回退。真正的修法是「錯誤路徑自己寫 body」。

### 三、設定在服務註冊時被急切讀取

`AddConfiguredRateLimiting(configuration)` 原本在**註冊時**就 `configuration.GetSection(...).Get<T>()`。

後果有二：
- 不支援設定重載。
- **`WebApplicationFactory` 的測試覆寫失效** —— 它套用組態的時機晚於服務註冊，
  導致新寫的限流測試怎麼調配額都不生效。

**處置**：改為在**請求時**由 `context.RequestServices` 取
`IOptionsMonitor<RateLimitSettings>.CurrentValue`。方法簽章不再需要 `IConfiguration`。

## 驗證

新增 `LoginRateLimitTests`（配額壓到 2 的測試工廠），`dotnet test` 由 256 → **258 個全數通過**：

| 測試 | 驗證 |
|------|------|
| `Login_BeyondQuota_ShouldReturn429_WithApiResultEnvelope` | 超額回 **429**、`Content-Type` 為 JSON、內容是 `ApiResult` 信封（不是 HTML） |
| `GeneralApi_ShouldNotBeAffectedByLoginQuota` | 打滿登入配額後，一般 API 仍回 401 而非 429（兩者分開計數） |

## 影響與注意事項

- **不要用 `[EnableRateLimiting]` 屬性覆寫端點慣例已指定的 policy** ——
  會被靜默蓋掉。需要差異化配額時，寫進 policy 內依路徑判斷。
- **API 的每一條錯誤路徑都要自己寫入 `ApiResult` body**，否則會被錯誤頁重跑機制毀掉。
- **設定請在請求時讀**（`IOptions`／`IOptionsMonitor`），不要在服務註冊時急切取值。
- 限流配額是「**每個呼叫端**」而非「每個帳號」：同一個 IP 打滿 10 次登入後，
  該 IP 上的合法登入也會被擋一分鐘。這是防「橫向猜測多個帳號」的設計，非缺陷。
