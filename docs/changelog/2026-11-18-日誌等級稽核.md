## 目的

使用者 2026/11/18 要求分析「哪些日誌需要以 Debug 或 Trace 寫入」，範圍是**前後端都檢視**。盤點後確認專案早有正式的分級規則（[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) §三、[日誌與設定檔說明](../operations/日誌與設定檔說明.md) §2），這次不另訂新規則，而是依它稽核並修正違規。
前端日誌過去只印在瀏覽器主控台，沒人檢查過等級；0.10.37 起有前端診斷記錄會把它送到伺服器，等級不對就會灌進日誌檔。

盤點時的數量：前端 Trace 0／Debug 66／Information 134／Warning 85／Error 78；後端（Web＋Business）Trace 0／Debug 60／Information 372／Warning 203／Error 131／Critical 3。後端大致合規（0.4.30 曾重新分類 50 處）。

## 調整的規則依據

- 純查詢按鈕（搜尋、重新整理、分頁、排序）、開關視窗、使用者或用戶端自己取消 → **Debug**（PRD §3.1、§3.4）。
- 畫面狀態的雜訊（選單選中項目、畫面初始化步驟）→ **Trace**。
- 欄位驗證失敗（使用者輸入的正常後果）→ **Information**；權限與身分驗證失敗 → Warning（不動）。
- **併發衝突、寫入時查無資料** → **Warning**（PRD §3.1、§3.2、§4.2：畫面過期或有人在探測，維運要看一眼）。
- 讀取查無資料（例如使用者打錯網址看到「找不到頁面」）→ Information。

### 沒有調整、刻意維持的

- `* view denied because the current user is not an administrator.`（Warning）：權限拒絕。
- `Delete * requested.`、`* submitted.`、`* completed.`、`* rejected.`、`* downloaded.`、`* exported.`、複製到剪貼簿（Information）：改變狀態或把資料帶走的操作。
- 前端「連不上伺服器」的每次呼叫 Warning：只在瀏覽器主控台；伺服器端的紀錄是 0.10.36 起一段中斷一筆。
- HTTP 請求完成、背景作業摘要等 PRD 明定的事件。
- 後端沒有一律改寫 Trace：PRD 規定 Trace 只用在逐筆迭代與外部呼叫的原始中繼資料，「不為填滿等級而寫」；前端的 Trace 是 0.10.37 起診斷模式用的操作軌跡（`API call completed.`、`Navigated.`）。

## 守門測試（`LoggingConventionTests`）

- `PureQueryAndUiEvents_ShouldBeDebugOrLower`：訊息符合 `(search|refresh) triggered.`、`searched.`、`Opened (create|edit|copy) modal`、`table changed.`、`cancel(l)ed by (the) user／client` 的，只能是 Trace 或 Debug；同時要比對到至少 20 處，避免訊息改寫法後規則形同虛設。
- `ConcurrencyConflictsAndWritesOnMissingRecords_ShouldBeWarnings`：`rejected by concurrency conflict.`、`Pre-update validation failed because … was not found.`、`rejected because (deleted) record was not found.` 一律 Warning；**也檢查 CRUD 產生器樣板**；至少 20 處。
- 兩條都以「故意改回錯誤等級」驗證過會失敗並指出檔案與行號。
- 擋不了的仍靠人工審查：訊息是否有意義、新寫法的事件等級是否選對。
