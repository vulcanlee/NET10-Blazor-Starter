# 修正日誌查詢會跳過「正在寫入」的檔案（0.4.39）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.39
- 最後核對日期：2026/08/26

## 目的

0.4.38 推送後 CI 紅燈，1 個測試失敗：

```
LogQueryServiceTests.Query_EntriesAfterEndTime_ShouldBeExcluded [FAIL]
  Assert.Single() Failure: The collection was empty
```

追查後發現這**不是測試寫壞**，而是 `LogQueryService` 的一段優化在特定時刻會誤判。

## 根因

`LogQueryService.QueryAsync` 的逐檔迴圈開頭有：

```csharp
// 整個檔案都比查詢起點舊，直接跳過。
if (File.GetLastWriteTime(file) < start) { continue; }
```

測試在「現在」寫入一個內容標記為 09:00 的日誌檔，然後查詢當日 08:00～10:00：

| | 寫檔時刻（= mtime）| 查詢起點 | `mtime < start` | 結果 |
|---|---|---|---|---|
| 這次 CI（UTC 03:16）| 03:16 | 08:00 | **成立** | 整檔跳過 → 0 筆 → 失敗 |
| 前一次 CI（UTC 09:09）| 09:09 | 08:00 | 不成立 | 通過 |
| 本機（台北 10:xx）| 10:xx | 08:00 | 不成立 | 通過 |

**這是既有的時刻相依缺陷，不是 0.4.38 造成的** —— 只要 CI 跑在當地時間 08:00 之前就會紅，
前一次剛好跑在 09:09 才是綠的。同檔其他測試的查詢起點都在過去（當日午夜或更早），不受影響。

## 處置：移除該優化，而非只改測試

判斷依據應該是**檔案內容的時間戳**，不是檔案系統中繼資料。理由：

1. **效益幾乎為零**。`NLogFilePathResolver.GetExistingFilesInRange` 已依**檔名日期**過濾，
   區間外的檔案根本不會被回傳；這個檢查只在「起始日當天、且已停止寫入」的檔案才省下一次讀取。
   而日誌檢視頁預設的「最近 1 小時」查詢**完全享受不到** ——
   當天檔案的 mtime 就是現在，必定不跳過，仍會從檔頭完整串流。
2. **它把查詢結果綁在檔案系統中繼資料上**。`nlog.config` 設了 `keepFileOpen="true"`，
   NTFS 對持續開啟的檔案可能延遲更新目錄項的 last-write time。若落後於查詢起點，
   **正在寫入的當天日誌檔會被整個跳過**，畫面顯示「查無日誌紀錄」但檔案裡其實有資料。
3. 它已經實際造成一次 CI 紅燈。

保留的另一項提前結束（`ReadFileAsync` 的 `ReachedEnd`）依據的是解析出的時間戳，沒有同樣的問題。

> **關於第 2 點的誠實補充**：實測本機執行中的日誌檔，mtime 與最後一筆時間戳完全一致（落後 0.0 秒），
> **NTFS 延遲更新在此環境並未重現**（`openFileCacheTimeout="30"` 會定期關閉檔案並刷新中繼資料）。
> 因此第 2 點是「已知風險、不再依賴」，而非「正在發生的災情」。
> 真正經過證實的理由是第 1 點與第 3 點。

## 變更範圍

- `MyProject.Web/Diagnostics/LogQueryService.cs`：移除該跳過判斷與其 `try/catch (IOException)`，
  並在原處留下註解說明為何刻意不做，避免日後被「順手優化」回來。
- `MyProject.Tests/LogQueryServiceTests.cs`：
  - 新增 `Query_WhenFileTimestampIsStale_ShouldStillReadEntries`：
    以 `File.SetLastWriteTime` 把 mtime 直接設成早於查詢起點，再斷言仍讀得到資料。
    **與執行當下幾點鐘無關**，修正前必紅、修正後必綠。
  - `WriteLog` 改為回傳檔案路徑，供上述測試調整檔案中繼資料。
  - `Query_EntriesAfterEndTime_ShouldBeExcluded` 的斷言改為附帶
    `Message` / `ScannedFileCount` / 實際套用區間 —— 原本失敗只會說
    「collection was empty」，完全看不出是沒找到檔案、被篩掉還是解析失敗。

## 驗證

- **先紅後綠**：新測試在修正前執行失敗，訊息為
  `實際取得 0 筆。 Message=指定條件下查無日誌紀錄。, ScannedFiles=0` ——
  `ScannedFiles=0` 直接證明是整個檔案被跳過，而非解析或篩選問題。修正後通過。
- `dotnet test` **259 個測試全數通過**（0.4.38 為 258）。
- `dotnet build -c Release` 0 warning、0 error；`dotnet format --verify-no-changes` 0 error；
  文件編碼檢查通過。
- 實跑量測執行中的日誌檔 mtime 與最後一筆時間戳（結果見上方補充）。

## 影響與注意事項

- **不要用檔案的 mtime／大小等中繼資料決定要不要讀一個日誌檔**。
  需要提前結束時，請依解析出的內容時間戳判斷。
- 移除後常見路徑的效能沒有變化（預設查詢本來就不會觸發該跳過）；
  最壞情況多讀一個「起始日當天且已停止寫入」的檔案，而 `ReadFileAsync` 本來就是串流 + 提前結束。
- 撰寫與時間有關的測試時，**不要讓查詢區間落在執行時刻之後**；
  需要驗證與時間相關的行為時，直接操作檔案中繼資料或使用固定基準時間。
