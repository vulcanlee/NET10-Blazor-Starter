## 症狀

Token 用量 PDF 的「註：…」那一段文字**超出頁面寬度**（使用者回報並附截圖）。

實測更糟：那一段 97 個中文字、9pt，排出來是 **30.79cm**，可用寬只有 26.5cm；
文字起點在 1.6cm，所以結尾落在 **32.39cm —— 而 A4 橫式整張紙才 29.7cm**。
最後約 8 個字是**印不出來的**，不是只壓到邊界。`AddSummary` 無視匯出範圍一律執行，
所以**每一份 Token PDF 都中**。

## 根因：MigraDoc 沒有中文斷行，而且是硬限制

從 MigraDoc 6.2.4 原始碼確認，不是推測。`PdfFlattenVisitor` 把段落切成排版單位時，
斷行機會是一組**寫死且封閉**的字元：

```csharp
case ' ': case '\r': case '\n': case '\t':   // 空白
case '-':                                     // 減號（非數字正負號時）
case '\u200B': case '\u200C':                 // 零寬空格、零寬不連字
case '\u00AD':                                // 軟連字號
default: currentString.Append(ch);            // ← 其餘一律累積，包含所有中文
```

中文落在 `default`，整段沒有空格的中文因此變成**單一個不可分割的「字」**。
`ParagraphRenderer.HandleNonFittingLine()` 遇到比整行還寬的「字」時：

```csharp
if (_savedWordWidth > 0)
{
    _currentWordsWidth = _savedWordWidth;   // 行寬 := 整個字的寬度
    _currentLineWidth = _savedWordWidth;    // 也就是直接伸出邊界
}
```

MigraDoc **沒有任何** `WordWrap`／`BreakStrategy` 設定可調，也沒有 UAX #14 斷行。

## 不只是使用者看到的那一段

**AI 日誌分析報表其實更嚴重。** 它是 A4 直式、可用寬 17cm、內文 10.5pt ⇒ **一行只容 45 字**，
而 `AiPromptDefaults` 要求模型「用三到五句話說明」＝ 60–150 字，整段一次 `AddText`。
一段 100 字的總結會排成 **37cm 寬**，**約一半的句子直接消失**。
雪上加霜的是 soft break 被刻意丟棄（原意是避免多餘空格），而那正是模型提供的唯一斷行機會。

## 做法：切成多個元素，**不是**插入零寬空格

MigraDoc 把每一個 `Text` 元素當成一個「字」，相鄰兩個之間就能斷行。
所以新的 `CjkLineBreak.AddTo(elements, text)` 把文字依中文斷行規則**切段後逐段 `AddText`**。

實測（3000 字中文、A4 直式）：單次 `AddText` 排出 **1 頁**（一條衝出頁面的長線）；
逐段 `AddText` 正確排成 **2 頁**。

斷行規則含中文排版禁則：
- **行首禁則** —— 不在 `。、，；：！？）」』】` 等之前斷，避免句讀被推到下一行開頭。
- **行尾禁則** —— 不在 `（「『【` 等之後斷，避免開括號孤零零留在行尾。
- 全形空格（U+3000）**後面**要斷得開 —— 它不是 ASCII 空白，MigraDoc 不認。
- 兩邊都是西文時不插手，交回 MigraDoc 原本的空格斷行（免得英文單字被攔腰折斷）。

### ⚠️ 為什麼不用零寬空格（U+200B）——這是本次最大的坑

U+200B 就在 MigraDoc 的斷行機會清單裡，插進字串看起來更簡單，而且第一版就是那樣寫的。
**但本專案內嵌的 Noto Sans TC 沒有 U+200B 的字圖。**

查證過程與數據：
- 解析字型 cmap：U+200B 對到 **glyph 0（.notdef）**；而該字圖有 **5 條輪廓、寬度整整 1 個 em**。
- 用 PDFsharp 實際量測：10pt 字級下一個 U+200B 量到 **10.00pt**。
  13 個字的句子從 130pt 膨脹到 **250pt**。

也就是說，那個寫法會在**每兩個中文字之間印一個看得見的方框**，而且文字寬度翻倍。
更糟的是**測試看不出來** —— 方框一樣會撐寬、一樣造成換行，頁數測試照樣變綠。

切成多個元素則**完全不新增任何字元**：沒有寬度、沒有方框，
從 PDF 複製出來的文字也與原文一字不差。

順帶查證：**U+00A0（不斷行空格）有字圖**（對到 glyph 1，與一般空格同一個），所以下面那項是安全的。

## 順帶修好：合計行的標籤與數字不再分家

合計行原本只能在 `標籤 數字` 之間的 ASCII 空格斷行，於是「輸入(送出)」留在行尾、
「17.87K」被推到下一行。改用 **U+00A0** 把兩者黏住，群組之間的全形空格則取得斷行機會。

## 測試：先確認它們會變紅

新加的兩支頁數測試都經過「**把斷行停用後必須變紅**」的驗證，不是寫完看到綠燈就算數。

最重要的一條是 `Split_ShouldNotChangeTheText`：**切出來的段落接回去必須與原文一字不差**。
這條不變量就是「不新增任何字元」的保證 —— 有它在，就不會有人再走回插入 U+200B 那條路。

### ⚠️ 兩支既有測試看起來有覆蓋，其實沒有

- `Build_ShouldNotThrow_WhenMarkdownIsChineseOnly` 只餵 **24 字**，一行就放得下。
- `Build_ShouldGrowWithContent` 名字有「相當長」，但 `\n\n` 把它切成 **400 段 × 15 字**，每段都放得下。

修正之前，**沒有任何測試餵過一段超過 45 字的中文**。兩支都已加註說明它們不覆蓋換行，
免得下一個人又誤以為有覆蓋。

另外，新的 AI 報表頁數測試第一版也是**假的**：它斷言「頁數 > 1」，但報表光附錄就不只一頁，
恆為真。已改成**比較長短兩份的頁數**才真正驗到東西。

- 沒有引入 PDF 文字抽取套件；頁數用既有的 PDFsharp `PdfReader` 數。
- 沒有重做兩份報表的版面。
