# WASM 遷移 M4：專案、附件與下載票證（0.10.3）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.10.3
- 首次實作版本：0.10.3
- 最後核對日期：2026/11/11

## 目的

WASM 遷移的第四個里程碑（計畫見 [WASM 遷移計畫](../migration/WASM遷移計畫.md)）：「專案項目」（`/projects`）改在使用者的瀏覽器以 WebAssembly 執行，
專案的 Web API 改走與畫面相同的服務（專案中已沒有 Repository），附件的上傳改由瀏覽器直接送出、下載改用一次性下載票證，以 Cookie 驗證的附件下載端點退役。其他頁面維持原狀。
測試報告見 [M04-專案附件與下載票證](../migration/測試報告/M04-專案附件與下載票證.md)。

## 變更內容

### 1. 專案項目頁改用 WebAssembly

- 頁面與檢視搬到 `MyProject.Web.Client`（`Pages/ProjectPage.razor`、`Views/Projects/ProjectViewView.*`），Server 版已刪除。
  畫面、按鈕、對話窗與訊息和以前相同：與 Server 版截圖比對 5 個畫面，4 個完全相同，1 個最多 8/255 的色差（55 個像素）。
- 資料經 `Web.Client/Api/ProjectApi.cs` 呼叫 API；DTO 與畫面模型的對應在 `ProjectDtoMapper`，WASM 頁面與伺服器的 Controller 共用。

### 2. 專案的 API 改走服務

- `ProjectController`（`/api/Project`、`/api/v1/Project`）改呼叫 `ProjectService`，團隊範圍、標題規則、附件、並行衝突、軟刪除與稽核和畫面只有一份。
  `ProjectRepository`、`UpdateOutcome`、`CombinedSearchHelper`、`ReplaceExpressionVisitor` 已刪除，**專案中已沒有 Repository**。
- 網址、HTTP 狀態碼與欄位名稱沒變。以下經使用者確認改成與畫面一致：
  - 關鍵字比對標題、描述、狀態、優先級、負責人（以前只比對標題與描述）。
  - 狀態、優先級不在畫面的選項裡回 400；結束日期早於開始日期回 400。
  - 開始、結束日期可以不填（`ProjectCreateUpdateDto.StartDate`／`EndDate` 改成可為 null，拿掉 `[Required]`）。
  - 錯誤訊息就是畫面那一句。
  - 原有的 `Owner`、`Status`、`Priority`、`StartDateFrom`、`StartDateTo`、`CompletionPercentageMin`／`Max` 篩選保留（`ProjectListFilter`）；`SortBy` 不分大小寫，不認得的退回預設排序（更新時間新到舊）。
- 新增或改變的端點（都要 Bearer 與 `[HasPermission(專案項目, …)]`）：
  - `GET {id}`：多回傳附件清單 `Files`（`Id`、`OriginalFileName`、`ContentType`、`FileSize`、`CreatedAt`；伺服器上的存放路徑不回傳），並寫一筆查看稽核 `Project.View`；`includeRelatedData` 參數保留相容、已不作用。
  - `POST search`：多了 `Categories`、`Teams`（符合任一，與畫面的篩選相同；已刪除清單也套用，WASM 頁面在顯示已刪除時不送）、`Deleted`（顯示已刪除，要有刪除權限，否則 403）、`RecordSearch`（使用者按「搜尋」時寫一筆 `Project.Search`）。
  - `GET options`：表單選項（分類、團隊、`IsAdmin`、`MyTeams`、新增時預設帶入的團隊 `DefaultTeams`、允許的副檔名、單一附件上限 1 GB）。
  - `POST`、`PUT {id}` 各接受兩種內容：JSON（不帶附件；`application/json`、`text/json`、`application/*+json`，與以前相同）與 `multipart/form-data`（`data` 是同一個 DTO 的 JSON 字串、`files` 是附件、`PUT` 另有 `removedFileIds`）。multipart 的 action 設路由 `Order = 1`（沒帶 Content-Type 時由 JSON 版回 415，與以前相同，不會因為模稜兩可回 500），並且不列入 Swagger（同一個方法＋路徑不能有兩個 action），格式寫在 [Web API 端點目錄](../architecture/Web%20API%20端點目錄.md)。multipart 與 Server 版走同一條路：資料與附件同一個交易存檔（見第 4 節），稽核依序是 `Project.Create`／`Update`，再來 `Project.FileUpload count=N`、`Project.FileDelete count=N`。
    multipart 的請求上限 4 GB（`ProjectController.MaxRequestBytes` = `uint.MaxValue`，IIS 的最大值）；單一附件超過 1 GB 回 400「檔案 X 超過 1GB 限制」，副檔名不在白名單回 400「檔案 X 的類型不在允許清單中。」，整筆都不存。
  - `DELETE {id}`（軟刪除）、`POST {id}/restore`、`DELETE {id}/purge`（連附件的實體檔一起刪），都要刪除權限。
  - `POST export`：xlsx，超過 10000 筆回 400 並說明原因，已刪除清單的匯出要刪除權限，寫 `Project.Export`。
  - `POST files/{fileId}/ticket`：申請一次性下載票證（見第 4 節）；附件看不到（專案已刪除、團隊範圍外、實體檔不見）回 404。
- 團隊範圍外的資料一律 404；修改、刪除、還原先查範圍、再比對標題。

### 3. 專案標題不能重複（使用者決定）

- 新增時、或修改且標題真的有變時，與另一筆未刪除專案的標題相同（去頭尾空白、英文不分大小寫）就擋下：「專案名稱已存在，無法新增。」／「專案名稱已存在，無法修改。」（API 回 409）。
- 還原時已有未刪除的同名專案也擋下：「已有同名的專案「X」，無法還原。請先將現有的同名專案改名後再還原。」（API 回 409，與分類相同）。
- 0.10.3 之前畫面允許同名（API 原本就回 409）。以前留下的同名專案，只要不改標題仍可存檔。
- 存檔時標題以 `NameNormalizer.Normalize` 去掉前後的空白、Tab、全形空白（`AddAsync`／`UpdateAsync`），空白不能繞過檢查。
- 已知限制：唯一性只在程式檢查，資料庫沒有唯一索引，兩個同時送出的新增可能都通過；標題全系統唯一（不分團隊），所以 409 會透露看不到的團隊有這個標題的專案（全系統唯一的取捨，已接受）。
- 檢查在 `ProjectService.BeforeAddCheckAsync`／`BeforeUpdateCheckAsync`，所以直接呼叫 `AddAsync` 的 AI Agent 工具與「產生測試專案」不受影響。

### 4. 資料與附件同一個交易存檔

- `ProjectService.AddAsync`／`UpdateAsync` 把專案與附件資料列放在同一個資料庫交易：附件寫入失敗就整筆回滾（新增的專案不建立、修改回到修改前、版本號不變，使用者直接再按「儲存」即可），這次寫出的實體檔刪除，被標記移除的實體檔在提交之後才刪。訊息仍是「專案附件儲存失敗」。
- 0.10.2 之前失敗時專案本身已存進去、附件沒存，也沒有稽核紀錄。

### 5. 一次性下載票證

- `MyProject.Web/Downloads/DownloadTicketService.cs`（singleton，存在記憶體）：32 個隨機位元組（URL-safe Base64），60 秒內有效，兌換時就移除（只能用一次，重放回 404）；過期沒用的在下次發票證時清掉。
- 新的匿名端點 `GET api/v1/downloads/{ticket}`（`DownloadsController`，`[AllowAnonymous]`）：兌換票證後，以發票證時記下的使用者 Id 與安全戳記經 `ICurrentUserLoader` 重新載入使用者（帳號停用、改密碼、被強制登出、角色變動都回 404；被要求先改密碼或先設定兩步驟驗證時也回 404），確認仍有 `專案項目:view`，再由 `ProjectService.GetFileDownloadAsync` 重查團隊範圍、專案是否已刪除、實體檔是否存在；寫稽核 `Project.FileDownload`（目標 `ProjectFile`、`file=原始檔名`），回檔案（`Content-Disposition: attachment`）。
- 任何失敗都回同一個 404 `ApiResult`「下載連結無效或已過期，請回到頁面重新下載。」，原因只寫日誌。
- **不再支援續傳（Range）**：下載中斷要回頁面重新點檔名（使用者接受這個取捨）。
- 票證只存在單一行程的記憶體：IIS 應用程式集區要維持一個背景工作處理序（預設值）；集區回收只會讓還沒用的票證失效，使用者重按一次即可。M7 的備份下載會沿用這套機制。
- 已知限制：下載管理員或瀏覽器擴充功能若先預先抓取一次網址，會把票證用掉，真正的下載得到 404；再點一次檔名即可。

### 6. 以 Cookie 驗證的附件下載端點移除

- `ProjectFileController`（`/api/project-files/{id}/download`、`/api/v1/project-files/{id}/download`）已刪除，舊網址回 404。專案附件已沒有以 Cookie 驗證的 API（系統備份下載 `BackupController` 仍走 Cookie，到 M7 再改）。

### 7. WASM 的附件上傳與下載

- 檔案內容不經過 WASM 記憶體：`MyProject.Web.Client/wwwroot/js/browser-files.js` 保留瀏覽器的 `File` 物件，.NET 端（`Commons/BrowserFiles.cs`）只拿到 id、檔名、大小；存檔時由 JS 組 `FormData`、帶 Bearer `fetch`（`ApiClient.SendFormAsync`：401 先刷新 Token 再重送一次、強制設定的 403 整頁導走、連不上伺服器顯示「目前無法連線到伺服器，請稍後再試。」）。
- 超過 1 GB 的檔案在選檔時就擋下（「X 超過 1GB 限制」，與以前相同）；類型不在允許清單的也在選檔時擋下（「檔案 X 的類型不在允許清單中。」，依 `GET options` 的 `AllowedExtensions`；以前要按儲存才知道），不加進待上傳清單，伺服器存檔前仍再檢查一次。實測 200 MB 上傳＋存檔 5.2 秒，頁面 JS 記憶體 8 MB。
- 下載：WASM 先申請票證，再用暫時的 `<a download>` 連結觸發瀏覽器原生下載。**不用 `location.assign`**：它會開始一次頁面導覽，實機發現之後 AntDesign 表格出錯（切到「顯示已刪除」整頁空白）。

### 8. IIS 請求大小上限

- 新增 `src/MyProject/MyProject.Web/web.config`，設定 `<requestLimits maxAllowedContentLength="4294967295" />`（IIS 預設約 28.6 MB，較大的上傳會在程式收到之前就被 IIS 以 404.13 擋下）。發佈時 SDK 會把 aspNetCore 處理常式合併進這份檔案（已實測）。由 `WebConfigTests` 守門。其他端點維持 ASP.NET Core 預設的約 30 MB。

## 升版注意

- 版本號 0.10.2 → 0.10.3。
- 沒有資料庫異動。
- ⚠️ **部署後確認網站目錄的 `web.config` 有 `requestLimits` 那一段**；少了它，超過約 28.6 MB 的附件存不進去。IIS 應用程式集區維持一個背景工作處理序（預設值），否則下載票證可能被當成無效。見 [正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)。
- 有外部程式或書籤直接用 `/api/project-files/{id}/download` 下載附件的，要改成先 `POST api/v1/Project/files/{fileId}/ticket` 再下載回傳的網址。
- 有程式呼叫專案 API 的，留意：關鍵字比對的欄位變多、狀態／優先級／日期不合規則回 400、錯誤訊息改成與畫面相同；狀態碼的分類方式不變。
- 專案標題重複會被擋下（畫面也是），還原時撞名也會被擋；以前就同名的資料不受影響，除非要改標題。
