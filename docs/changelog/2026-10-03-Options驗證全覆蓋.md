# Options 驗證全覆蓋：所有設定在啟動時驗證，設定矛盾一律拒絕啟動（0.9.92）

- 文件版本：1.0

- 首次實作版本：0.9.92
- 最後核對日期：2026/10/03

## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) A-3 拆出的第二項（A-3b）。20 個設定類別中只有 9 個在啟動時驗證；
9 個只做 `services.Configure<T>` 完全沒有驗證，2 個只用 `.Get<T>()` 讀。設定寫錯時系統「帶著錯的值跑」：

- `RateLimit` 設 0 → 每個 API 請求丟 `ArgumentException`；`AiSettings:Endpoint` 少了 `https://` → 按下 AI 按鈕才丟 `UriFormatException`。
- `GoogleOAuthSettings:Enabled=true` 卻沒填 ClientId → 登入頁靜默沒有 Google 按鈕；`AiSettings:Provider` 拼錯 → AI 功能靜默關閉。
- 外部目錄路徑留空 → 資料庫建在工作目錄、例外堆疊與 Token 原始檔靜默不寫；`ForwardedHeaders` 寫錯 → 被靜默略過。
- `AiPricingSettings:UsdToTwd` ≤ 0 → 每筆呼叫靜默變成「未計價」。
- 而且 `ValidateOnStart` 要到 `app.Run()` 才執行 —— 已經跑完 migration 與 seed 之後。

**政策（使用者決定）：設定矛盾（開了功能卻沒填齊、拼錯、格式錯誤）在任何環境一律拒絕啟動。** 想關掉功能就明確關掉（`Enabled=false` 或留空）。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 每個類別一個 `IValidateOptions<T>`，一次回傳**全部**錯誤 | 部署時改一條、重啟、再看到下一條非常折磨；訊息以設定鍵開頭，讀的人才知道要改哪一行 |
| 規則以「會在執行時才爆、或靜默失效」的實際位置為依據 | 只擋真的會出問題的值，不為了驗證而驗證 |
| 外部目錄要求**完整路徑** | 相對路徑會隨工作目錄改變，IIS 的工作目錄不是網站目錄 |
| `AiSettings` 以「有沒有填 ApiKey」判斷是否要用 AI | 出貨預設不用 AI（ApiKey 空白）時只檢查值本身；填了就代表要用，缺少的設定一律擋下 |
| 沒有欄位規則的 `Security`、`Swagger` 也改 `ValidateOnStart` | 型別錯誤（bool 填了 `"yes"`）才會在啟動時失敗，而不是第一次讀取時 |
| 驗證提早到資料庫初始化之前 | 設定寫錯不該先動到資料庫；`app.Run()` 時框架會再驗一次，無害 |
| `StartupSafetyValidator` 不動，與它的重疊檢查保留 | 它管「只有 Production 才擋的上線政策」；Options 驗證管「值本身合不合理」，所有環境都套用。刪掉重疊會改到既有的錯誤訊息與測試，價值不高 |
| 既有 9 個類別的 DataAnnotations 不改寫 | surgical；只補缺口（PublicBaseUrl、告警收件人） |
| **拿掉**計畫中「上傳副檔名必須以 `.` 開頭」 | 實作時發現 `UploadFileTypePolicy` 本來就會 Trim 並自動補上點，`pdf` 是合法寫法，這條規則會誤擋 |
| 快取 provider 錯誤仍在 `AddConfiguredCache` 註冊時就丟出 | 既有行為；驗證器另外補上一致的訊息與到期分鐘數 |

## 三、驗證（2026/10/03 實跑）

**故意改壞，測試必須失敗**（每項做完都已還原）：

| 改壞方式 | 失敗的測試 |
|---|---|
| `Security` 改回 `services.Configure<T>` | `TypeMismatch_InClassWithoutRules_ShouldFailOnStart`、守門測試 `ConfigurationSections_ShouldNeverBeBoundWithoutStartupValidation` |
| 拿掉 `RateLimit` 的範圍規則 | `RateLimit_NonPositive_ShouldFail` |
| 拿掉 `EmailSettings:PublicBaseUrl` 的檢查 | `EmailPublicBaseUrl_WithoutScheme_ShouldFailOnStart` |

**實際啟動網站**（開發環境，資料庫指向暫存目錄）：

- 正常設定 → 正常啟動（**使用者本機的 User Secrets 也通過新規則**）。
- 分別注入三種錯誤設定，三次都在**建立資料庫之前**就拒絕啟動（暫存目錄沒有出現資料庫檔），訊息指出鍵名：
  - `RateLimit__ApiRequestsPerMinute=0` → 「RateLimit:ApiRequestsPerMinute 必須介於 1 到 100000 之間，目前是 0。」
  - `GoogleOAuthSettings__Enabled=true` 不給憑證 → 「GoogleOAuthSettings:ClientId 不可留空。」「GoogleOAuthSettings:ClientSecret 不可留空。」
  - `AiSettings__Provider=Gemini` → 「AiSettings:Provider 只接受 AzureOpenAI 或 OpenAI（留空等同 AzureOpenAI），目前是「Gemini」。」

> 驗證過程的副作用（已清除）：三次故意的啟動失敗讓 `Program.cs` 把 6 個補登檔寫進了開發機真正的 `C:\temp\MyProject\Exception\pending`
> （當時只覆寫了資料庫與日誌路徑，沒覆寫 `ExceptionPath`）。若留著，下次正常啟動會被匯入系統例外紀錄。
> 已逐一核對內容確定是這三次測試產生的，再刪除；之後實際啟動驗證一律覆寫所有外部路徑。
