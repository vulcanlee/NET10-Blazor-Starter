# AI 供應商設定修正：Azure 改走 v1 端點、設定項精簡（0.9.5）

- 文件版本：2.0
- 文件狀態：已實作
- 現行系統版本：0.9.5
- 首次實作版本：0.9.5
- 最後核對日期：2026/09/11

## 問題

0.9.4 實作 AI 分析時，Azure OpenAI 走的是傳統路徑：

```
POST {資源}/openai/deployments/{部署名}/chat/completions?api-version=2024-10-21
```

但 Azure 入口網站的「Azure OpenAI 端點」欄位現在給的是 **v1 路徑**的值：

```
https://kmengineopenai1.openai.azure.com/openai/v1
```

使用者把這個值貼進 `AiSettings:Endpoint`，程式會組出
`.../openai/v1/openai/deployments/{部署名}/chat/completions?api-version=…`，
路徑重複，必定失敗。

修完這條之後，檢視同一批設定又發現兩件事：

**`Enabled` 是多餘的。** 功能能不能用，`Validate` 已經靠 `ApiKey`、`Model`
（Azure 再加 `Endpoint`）判斷得出來；範本出貨時 `ApiKey` 是空字串，所以新 clone
本來就是關的。`Enabled` 只多了一個「金鑰都填好了按鈕卻還是灰的」的踩雷點。

**OpenAI 分支缺路徑正規化。** Azure 加了補齊後綴的處理，OpenAI 沒有，兩邊不對稱：

```
Endpoint = "https://api.openai.com/v1"
→ https://api.openai.com/v1/v1/chat/completions    ← 重複
```

而 `https://api.openai.com/v1` 正是 OpenAI 官方文件裡 `base_url` 的寫法。

## 改了什麼

### 一、Azure 改走 v1 API

Azure OpenAI 改為只支援 **v1 API**，並移除兩個設定項。

| | 0.9.4（傳統路徑）| 0.9.5（v1 路徑）|
|---|---|---|
| 網址 | `{Endpoint}/openai/deployments/{Deployment}/chat/completions` | `{Endpoint}/chat/completions` |
| `api-version` | 必填，少了回 404 | 不需要，採隱含版本 |
| 部署名稱放哪 | 網址路徑 | 請求 body 的 `model` 欄位 |
| 需要的設定項 | `Endpoint`、`Deployment`、`ApiVersion` | `Endpoint`、`Model` |

### 二、移除 `Enabled`，`Model` 改為必填

功能的開關就是**有沒有填 `ApiKey`**，不再需要另一個旗標。`Model` 也拿掉預設值：
預設供應商是 Azure，而任何模型名稱拿去當部署名稱送出去都只會換來 404，留空才能在
按下按鈕之前就用 Tooltip 說清楚少了什麼。

### 三、OpenAI 補上對稱的路徑正規化

原本只有 Azure 會補齊版本後綴。現在兩家共用同一個 `EnsureSuffix`，Azure 補
`/openai/v1`、OpenAI 補 `/v1`，下列寫法都能用：

| Provider | 可接受的 `Endpoint` |
|---|---|
| Azure | `https://xxx.openai.azure.com/openai/v1`、`https://xxx.openai.azure.com` |
| OpenAI | 留空、`https://api.openai.com`、`https://api.openai.com/v1` |

### 改完之後的設定

設定從八個必填候選降到四個（Azure）與三個（OpenAI）：

```json
"AiSettings": {
  "Provider": "AzureOpenAI",
  "Endpoint": "https://your-resource.openai.azure.com/openai/v1",
  "ApiKey": "",
  "Model": "<部署名稱>"
}
```

```json
"AiSettings": {
  "Provider": "OpenAI",
  "Endpoint": "",
  "ApiKey": "",
  "Model": "gpt-4o-mini"
}
```

Azure 的 `Endpoint` 直接貼入口網站「Azure OpenAI 端點」的值即可，`Model` 填部署名稱
（入口網站 Deployments 那一頁看到的名稱），不是模型名稱。

### 程式碼

- `AiSettings`：移除 `Deployment`、`ApiVersion` 與 `Enabled` 共三個屬性；
  `Model` 預設值改為空字串。
- `AiChatEndpoint`：兩個分支改成同一個形狀；移除 `ResolveModelField`
  （兩家現在都用 `Model`，這個轉換函式沒有存在意義）；把 Azure 專用的
  `NormalizeAzureBaseUrl` 換成兩家共用的私有 `EnsureSuffix`
  （改為私有是因為測試全部透過 `Create` 斷言，測真實路徑比測輔助函式好）。
- `AiChatRequestFactory`、`AiLogAnalysisService`：改用 `settings.Model`。
- `StartupSafetyValidator`：Production 檢查的 gate 從 `Enabled == true`
  改為 `ApiKey` 非空。
- `appsettings.json`：移除三個鍵，`Model` 改空字串；`SystemVersion` 0.9.4 → 0.9.5。

### 為什麼不保留傳統路徑

v1 已是 GA 且微軟建議使用。同時支援兩套只會讓設定檔多出兩個「可能用不到」的欄位，
下一個人得自己判斷該填哪些。少一條路徑，設定就少兩項，錯誤訊息也能講得更明確。
手上是舊資源的人，請到 Azure 入口網站改用 v1 端點。

## 連帶修掉的缺陷

`AiChatEndpoint.Validate` 會呼叫 `settings.GetProvider()`，而 Provider 字串打錯時它丟
`InvalidOperationException`。先前碰不到，因為 `Enabled` 預設 false 會提前 return；
**拿掉 `Enabled` 之後這條路就通了**。而 `IsAvailable` 是在
`LogViewerView.OnInitializedAsync` 裡讀的，外面沒有 try-catch —— Provider 打一個字
就會炸掉整個日誌檢視頁，而不只是停用 AI 按鈕。

修法是在 `Validate` 裡接住並回傳中文訊息。`Validate` 的職責本來就是把壞掉的設定翻成
使用者看得懂的話，這裡接住最自然；`GetProvider()` 本身維持丟例外（`Create` 在
`Validate` 通過後才呼叫，安全）。有測試釘住。

## 補上的兩個守門測試

探索既有程式碼時發現兩處沒有保護的接縫，順手補上：

**`appsettings.json` 與設定類別的一致性。** 組態繫結會靜默忽略未知的鍵，所以移除
`Enabled` 之後，JSON 裡若殘留那一行不會有任何地方報錯，讀設定檔的人卻會以為它還有作用。
`AiSettingsTests.AppSettingsSection_ShouldOnlyContainKnownKeys` 讀檔斷言每個鍵都對得到
POCO 屬性。刻意只做單向（JSON 不得有未知鍵），不反過來要求每個屬性都出現在 JSON ——
`SystemSettings.Upload` 就是刻意不寫進範本的既有先例。

**`StartupSafetyValidator` 的 AI 區段。** 它讀的是**字串鍵**不經 POCO，改欄位名稱不會有
編譯錯誤，只會靜默失效；而既有的 `ProductionSafetyValidation_WithDevelopmentDefaults_ShouldFailFast`
餵進去的組態字典完全沒有 `AiSettings:*`。現在補了三支測試涵蓋「沒金鑰不該擋」、
「有金鑰但設定不全要擋」、「OpenAI 不需要 Endpoint」。

## 兩個容易踩的坑

**填錯端點欄位。** 入口網站上「專案端點」與「Azure OpenAI 端點」並排顯示，
前者形如 `https://xxx.services.ai.azure.com/api/projects/proj-default`，是給 Foundry
Agent SDK 用的，填進來會連不上。要用的是後者。文件已把這點標成 ⚠️。

**版本路徑後綴少一段或多一段。** 兩家都會踩：Azure 的舊習慣只貼到
`https://xxx.openai.azure.com`（少了 `/openai/v1`），OpenAI 則常照官方文件填
`https://api.openai.com/v1`（先前會被加成 `/v1/v1`）。兩種都是 404，而 404 的訊息
看不出是路徑問題。現在共用的 `EnsureSuffix` 兩邊都補齊，正規化規則有測試釘住，
包含大小寫與重複後綴的情況。

## 驗證

- `dotnet test`：434 支全綠（AI 相關從 159 增為 175）。
- `dotnet build`：0 警告。`dotnet format --verify-no-changes`：無差異。
- 文件編碼檢查零失敗。
- **守門測試做過反向驗證**：故意把 `"Enabled": false` 塞回 `appsettings.json`，
  確認 `AppSettingsSection_ShouldOnlyContainKnownKeys` 會紅並指名是哪個鍵，之後還原。
- 以實際端點形狀做過組裝驗證，兩家各三到四種貼法都組出正確網址：

| Provider | 輸入 | 組出的網址 |
|---|---|---|
| Azure | 入口網站原樣 / 多一斜線 / 只貼根網址 | `.../openai/v1/chat/completions`，標頭 `api-key` |
| OpenAI | 留空 / 只填網域 / `https://api.openai.com/v1` | `https://api.openai.com/v1/chat/completions`，標頭 `Authorization: Bearer` |

  兩家的部署名稱或模型 id 都出現在請求 body 的 `model` 欄位，網址不含 `api-version`。
- 設定不全時的訊息逐一確認過：缺金鑰、Azure 缺端點、缺模型、Provider 打錯字，
  四種都回中文訊息且不丟例外。
