## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) B-5。改動前只有兩個清理 worker（`LogRetentionWorker`、`AiCallLogRetentionWorker`），都是「啟動就跑一次、之後每 24 小時」：
沒有共用排程、沒有執行紀錄、IIS 每次回收都會再跑、重疊回收時兩個行程各跑一次；Token 用量紀錄完全不會自動清除。之後的備份（B-7）、報表、彙總都需要排程。

使用者決定：

- 排程以 **cron 運算式**描述，用 **Cronos** 套件解析（MIT、無相依、只負責算時間）。
- **拆成 B-5a／B-5b**：本次 B-5a = 框架＋管理頁＋遷入兩個既有清理＋補上 Token 用量清理；已軟刪除資料的自動永久刪除留給 B-5b。
- Token 用量預設保留 **365 天**（0 = 不清除）。
- 清理改為**每天固定時間（預設 03:00）＋啟動時若錯過就補跑一次**，回收不再額外觸發。

設計先由盤點代理整理現況，再由規劃代理對照程式碼審查，抓到六個照草案做會出錯的地方（見第二節）。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 跨行程只跑一次以**資料庫原子搶占**為權威（`LastScheduledForUtc < 時段` 才搶得到）| 只靠檔案鎖擋不住最常見的重疊回收情境：A 跑完釋放鎖、B 一毫秒後才拿到。搶占在 SQLite 的單寫者鎖內完成，而且單調（較新的時段被搶走後，較舊的也搶不到）|
| 另以**檔案鎖**防同一作業重疊執行 | 手動執行還沒結束時排程時間到了，記一筆「略過」而不是同時跑兩份；OS 會在行程死亡時釋放鎖，不會留下解不開的鎖 |
| ⚠️ 補跑錨點放在 `ScheduledJobState`，不放 `JobRun` | 執行紀錄會依保留天數清除；錨點跟著消失就會誤判「從沒跑過」而重跑 |
| ⚠️ 補跑錨點 = max(上次搶到的時段, 建立或最後切換啟用的時間) | 全新安裝、新加入或重新啟用的作業不會一啟動就補跑（避免整合測試與上班時段大量刪除），真正錯過的時段補跑一次 |
| ⚠️ 作業註冊為 singleton 描述＋ scoped 作業 | 排程器與設定驗證器都是 singleton；從根容器列舉作業會產生一個永遠不釋放的 DbContext |
| ⚠️ 作業回傳 `ScheduledJobResult` | 現有清理服務會吞掉例外回 null；只回字串的話會被記成成功，而丟例外會讓同一個錯誤在系統例外紀錄出現兩筆 |
| ⚠️ 資料庫讀回的時間一律 `SpecifyKind(Utc)` | Cronos 只接受 UTC；EF 從 SQLite 讀回的是 Unspecified，不處理的話第二次啟動就丟例外 |
| ⚠️ 執行中把設定改壞時沿用上一份合法設定 | `IOptionsMonitor.CurrentValue` 會丟驗證例外，沒接住的話排程器直接停掉 |
| ⚠️ 手動執行走佇列，由排程器啟動 | 在 Blazor 事件裡 `Task.Run` 會繼承畫面的 ExceptionContext 與追蹤碼，作業的錯誤會被記成畫面操作；關機時主機也不會等它 |
| ⚠️ Token 用量分批刪除 | 原本的寫法一次載入全部過期資料並在一個交易裡刪，第一次清兩年份的資料會長時間佔住寫入鎖 |
| 排程器註冊在例外寫入器之後 | 主機以相反順序停止，作業在關機時記的錯誤才還有人寫進系統例外紀錄 |
| 時區用伺服器本地時區 | 「每天 03:00」是給人看的時間；資料庫一律存 UTC |

## 三、驗證（2026/10/04 實跑）

**故意改壞 23 處，全部被測試抓到**，包括：搶占永遠成功、搶占條件 `<` 改成 `!=`、忽略鎖的結果、回收殘留不看鎖、例外不記錯誤、回報失敗記成成功、不建立新的追蹤碼、
拿掉 `SpecifyKind`、補跑回傳最早的時段、補跑不含剛好在時段上、錨點忽略啟用時間、下次時段用 UTC 解讀、不擋永不觸發與 6 欄位的 cron、排程用現在而不是時段、
設定改壞時不保留上一份、例外紀錄清理用 UTC 時鐘、稽核清理用本地時鐘、Token 清理只刪第一批／完全忽略取消／用 `<=` 門檻、AI 清理把失敗當成功、健康監控不把失敗算異常。

過程中修正了三個測試本身的問題：
- 「執行後 ExceptionContext 已清除」的斷言永遠成立 —— AsyncLocal 在被 await 的方法裡設定的值本來就不會流回呼叫端，所以拿掉這個測不到東西的斷言，保留「執行期間是背景作業」的檢查。
- 兩種改壞方式（`if (false)`）會觸發「執行不到的程式碼」警告而建置失敗，沒有真的跑到測試；改用執行期條件後確認都被抓到。
- 「忽略取消」第一版只拿掉了一處，token 仍傳給查詢，不算真正忽略；改成拿掉方法內所有用法後確認被抓到。

舊的 `LogRetentionWorkerTests` 抓不到「例外紀錄與稽核紀錄的時鐘用反」（資料離門檻好幾週）；新的測試把資料放在本地與 UTC 相差的 8 小時內，兩種用反都會失敗。

**真實環境**（Playwright 驅動本機 Edge；所有外部路徑與日誌都指向暫存目錄，`C:\temp\MyProject` 無任何新檔）：

- 管理頁列出四個作業與下次執行時間；「立即執行」Token 用量清理 → 背景執行，5 秒自動更新後顯示「成功、29 ms、刪除 0 筆…」；執行紀錄窗顯示「手動（support）」與追蹤碼。
- 停用 AI 對話紀錄清理 → 下次執行顯示「已停用」；再啟用；稽核頁看得到 `Job.Trigger`、`Job.Disable`、`Job.Enable`。
- 系統健康監控出現「排程作業 · 權重 5 · 正常：4 個作業，啟用 4 個；最近一次失敗 0 個；逾期 0 個」。
- **兩個行程**（不同連接埠）指向同一個暫存資料庫，把稽核清理設成每分鐘：連續四個時段，每個時段資料庫裡都**只有一筆**執行紀錄；日誌顯示 A 每分鐘搶到並執行，
  B 每分鐘都記「slot not claimed」。B 晚啟動時，A 在暖機後補跑了錯過的那一個時段（只補一次）。
- 資料庫檔旁建立了四個作業的 `*.job-<名稱>.lock`。日誌除了既有的 `JSDisconnectedException` 雜訊（整頁換頁時產生，與本次無關）外沒有錯誤。

**品質關卡**：`Invoke-QualityGate.ps1` 完整通過（1286 個測試，含弱點掃描）。
