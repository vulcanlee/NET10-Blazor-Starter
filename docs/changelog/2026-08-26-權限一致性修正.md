# 權限一致性修正與四方守門測試（0.4.33）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.42
- 首次實作版本：0.4.33
- 最後核對日期：2026/08/26

## 目的

宣告式選單重構（0.4.22）把「三方同步」做得很徹底：`Menu.json` 的 13 個 id 與
`SidebarMenuService.MenuPermissionMap` 一一對應、無錯位。

**但漏了第四方：頁面自己實際呼叫的 `CheckAccessPage(權限鍵)`。**
沒人驗證它與 `MenuPermissionMap` 是否一致，於是出現了三個對不上的地方。

## 問題與修正

### 一、`/projects` 用錯權限鍵（使用者看得到選單、點進去被踢）

| | 修正前 | 修正後 |
|---|---|---|
| 選單 id 21 → 權限鍵 | `角色_專案項目`（"專案項目"）| 不變 |
| `ProjectViewView.razor.cs:88` 實際檢查 | `角色_專案管理`（"專案管理功能"，**群組鍵**）| `角色_專案項目` |

只被授予「專案項目」的角色，選單看得到 `/projects`，點進去卻顯示「你沒有權限存取此頁面」。

### 二、「使用者管理」「角色管理」是死權限

`MenuPermissionMap` 宣告 id 31/32 受這兩個權限鍵控制，`RolePermissionService` 也把它們
上架到角色矩陣（管理員勾得到、會種出 `Permission` 資料列），
**但 `MyUserView` / `RoleViewView` 實際是以 `CheckIsAdmin()` 守門** —— 非管理員永遠進不去。
勾了等於沒勾。

**處置：改為管理員專屬**（比照「統計與分析」群組的現成做法）。
`RolePermissionService.GetRoleListPermissionAllName()` 移除整個「系統管理」群組，
權限鍵不再上架矩陣、不種資料列；頁面維持 `CheckIsAdmin()` 不變。
`MenuPermissionMap` 的 `[3]/[31]/[32]` 保留，靠 `CheckAccessPage` 的管理員短路顯示選單
（與 `[6]/[61]/[62]/[63]` 同一機制）。

> 為什麼不是反過來「讓權限鍵生效」：那會放寬權限（非管理員可被授予管理使用者與角色的能力）。
> 選擇保守的一邊。

### 三、兩個權限鍵常數帶尾隨空白

```
MagicObjectHelper.角色_角色管理 = "角色管理 "   ← 尾隨空白
MagicObjectHelper.角色_登出     = "登出 "       ← 尾隨空白
```

其餘 12 個常數都沒有。選單意外能運作（`SidebarMenuService` 同時比對 `Name` 與 `PermissionName`），
但這個髒字串會隨 RBAC 回填寫進 `Permission.Key` 與 `RoleView.TabViewJson`，
而權限判定是 **Ordinal 比對** —— 屬於隱形的資料污染。

**處置：常數去空白，並在 `RbacBackfillService` 新增冪等的資料正規化步驟。**

`Permission.Key` 有唯一索引，因此去空白後若與現有列撞鍵**必須合併而非直接改寫**：
把重複列的 `RolePermissionMap` 轉掛到保留列（保留列已有的對應則刪除，避免違反
`(RoleViewId, PermissionId)` 唯一索引），再刪掉重複列。
`RoleView.TabViewJson` 內的權限名稱一併 trim 並去重。

**無 schema 變更，不需要 migration。**

### 四、`ProjectViewView` 是唯一漏掉 `Clone()` 的檢視

`ProjectViewView.razor.cs:232` 編輯前未 `Clone()`，其餘四個檢視都有
（`CategoryViewView:187`、`TeamViewView:187`、`RoleViewView:197`、`MyUserView:199`）。
`MyUserView` 同樣走 `GetAsync` 路徑卻仍 `Clone()`，兩者直接矛盾。

實務上因為 `GetAsync` 回的是新 map 出來的 adapter model，目前不會污染表格列，
但它破壞了「所有檢視一律 `Clone()`」這條可審計的慣例；且該檢視修改後會直接
mutate `Files` 集合（`:545-555` `RemoveExistingFile`），更該補上。

## 新增守門測試

`MyProject.Tests/MenuPermissionConsistencyTests.cs`（5 個測試）：

| 測試 | 驗證 |
|------|------|
| `MenuJsonIds_ShouldExactlyMatch_MenuPermissionMapKeys` | Menu.json 的 id 集合 == `MenuPermissionMap` 的 key 集合 |
| `MenuPermissionMapValues_ShouldAllBe_MagicObjectHelperConstants` | 對應表的值都是 `MagicObjectHelper` 常數 |
| `PermissionKeyConstants_ShouldNotHaveSurroundingWhitespace` | 權限鍵常數不得帶前後空白 |
| `Views_CheckAccessPageKey_ShouldMatch_MenuPermissionMap` | **第四方**：檢視實際用的鍵 == 該路由在對應表的鍵 |
| `AdminOnlyViews_ShouldNotUse_CheckAccessPage` | 管理員專屬檢視只用 `CheckIsAdmin()` |

新增受控檢視時，於 `ViewToMenuId`（或 `AdminOnlyViews`）登錄一筆即可。

為此 `SidebarMenuService.MenuPermissionMap` 由 `private` 改為 `internal`，
並於 `MyProject.Web.csproj` 加上 `InternalsVisibleTo("MyProject.Tests")`。

`AdminOnlyPermissionTests` 的白名單擴充納入系統管理群組三個鍵。

`RbacBackfillServiceTests` 新增 3 個測試涵蓋正規化：舊髒鍵去空白且授權不遺失、
撞鍵合併且兩個角色的授權都保住、`TabViewJson` 去空白並去重。

## 影響與注意事項

- **既有部署首次啟動 0.4.33 時**，`RbacBackfillService` 會自動正規化權限鍵資料。
  此步驟冪等，且沿用既有「失敗只記 log、不中止啟動」的處理方式。
- 原本被授予「使用者管理」「角色管理」的非管理員角色，**行為沒有改變**
  （它們本來就進不去）；差別只在角色矩陣不再顯示這兩個可勾選項。
- 新增受控檢視時，除了既有三處（`MagicObjectHelper` 常數、`Menu.json` 項目、
  `MenuPermissionMap` 對應），請一併於 `MenuPermissionConsistencyTests` 登錄。
