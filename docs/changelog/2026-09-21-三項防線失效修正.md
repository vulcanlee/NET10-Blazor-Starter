# 修掉三項「防線存在但不生效」的缺陷（0.9.48）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.48
- 首次實作版本：0.9.48
- 最後核對日期：2026/09/21

## 起因

0.9.47 查出三項缺陷但只寫進文件，這次實際修掉。三項的**共通病灶是同一個**：
拿寫死的字面值做精確比對。只要那個字面值被改掉 —— 腳本改名、範本換預設值 ——
防線就靜默失效，沒有任何錯誤訊息。

## ① JWT 佔位金鑰偵測：改為樣式比對

`StartupSafetyValidator` 與 `SystemHealthService` 各自存了一份
`DevelopmentSigningKey = "DevelopmentOnly-ChangeThisJwtSigningKey-AtLeast32Chars"` 做精確比對。
`New-StarterProject.ps1` 會把前綴換成新專案代號，換完就不再相等 ——
衍生專案的 Production 啟動檢查與健康監控**兩道一起靜默失效**。

判準移到 `JwtSettings`，成為單一來源：

```csharp
public const string PlaceholderSigningKeyMarker = "ChangeThisJwtSigningKey";

public static bool IsPlaceholderSigningKey(string? signingKey) => ...
```

兩處的私有常數刪除，改呼叫它。前綴換成什麼都不影響判定。

**正面副作用**：那兩個常數消失後，腳本的殘留掃描不再命中它們 ——
警告從 8 條降到 **5 條**，而且消失的正是最危險的那兩條（看起來像漏改的舊字串、
改掉就等於拆掉偵測器）。指引 §2.4 已依實測重寫。

## ② 預設管理者密碼：擋留空，也擋範本出貨過的值

原本只比對字面 `"support"`，但範本實際出貨的是 `1qaz@WSX` —— 防線形同虛設很久。
`appsettings.Production.json` 出貨的空字串問題更隱晦：它同樣不等於 `"support"`，
而 `Program.cs` 的 seed 會把空字串直接雜湊成管理員密碼，且每次重啟重新套用。

改為兩段檢查：留空 → 擋；命中 `TemplateSupportPasswords`（`support`、`1qaz@WSX`）→ 擋。

⚠️ **這是部署行為變更**：Production 若沿用 `appsettings.Production.json` 出貨的空字串，
啟動會直接失敗。這是刻意的 fail-fast，與 `SigningKey` 留空的既有行為一致；
請用環境變數 `BootstrapSettings__SupportPassword` 提供真正的密碼。

腳本端則**移除**那條從未命中的 `"SupportPassword": "support"` → `"change-me"` 取代規則
（以及殘留掃描裡對應的樣式）。換成另一個固定佔位值並不會比較安全，只是把弱值換成另一個弱值；
真正的防線是啟動檢查 —— 本機開發仍可用文件記載的預設帳密登入，Production 則被擋下。

## ③ `LoginRateLimitTests` 順序相依：合併為單一測試

登入配額壓到 2，而限流分區鍵是 `login:` ＋ 使用者／IP／`anonymous`；
`WebApplicationFactory` 裡 `RemoteIpAddress` 是 null，所以同一個 factory 底下的
每個測試都落在**同一個分區**。原本兩個測試裡，
`GeneralApi_ShouldNotBeAffectedByLoginQuota` 會連打 5 次登入把配額吃光，
先跑的是誰，另一個就必定失敗。

而 xUnit 依測試案例 UniqueID 的雜湊排序，UniqueID **含組件名稱** ——
**衍生專案取什麼名字，就決定新專案第一天的測試是綠是紅。**

### 兩條走過的彎路，都寫進註解防止被「順手優化」回去

先試「每個測試各自 `new` 一個 factory」，結果撞上另一個限制：
`ApiTestApplicationFactory` 的 `Dispose` 會把它設定的環境變數清掉，
同一個處理程序裡先棄置再建立第二個，NLog 會在重新載入設定時丟
`Unrecognized value 'BasePath'`。

最後改為**合併成一個測試**，保留 `IClassFixture`（一個 factory）：
2 次 401 → 第 3 次 429 並驗證 ApiResult 信封 → 緊接著打一般 API 驗證它仍是 401
（證明登入配額沒有消耗一般 API 的配額）。原本兩個測試的意圖完整保留，
而且比原本更強 —— 一般 API 的驗證就發生在登入分區剛被打爆的當下。

## 守門測試：擋住同一類錯誤再發生

新增 `MyProject.Tests/StartupSafetyConventionTests.cs`，**直接讀 `appsettings.json`
實際出貨的值**去驗證它必須被 Production 拒絕，而不是把值再寫死一次 ——
否則只是把同一個錯誤複製到測試裡。日後有人換了範本預設值卻忘了同步比對清單，測試就會紅。

另在 `ApiIntegrationTests` 補三條情境測試：衍生專案形式的佔位金鑰、
`SupportPassword` 留空、`SupportPassword` 為 `1qaz@WSX`，三者都必須 fail-fast。
