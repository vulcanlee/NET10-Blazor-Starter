# 修正專案附件下載 404：補上缺少的端點（0.4.31）

- 文件版本：1.0
- 文件狀態：已實作

- 首次實作版本：0.4.31
- 最後核對日期：2026/08/25

## 目的

`ProjectViewView.razor` 的附件連結指向 `/api/project-files/{id}/download`，但**這個端點在整個方案中不存在** —— 每一次專案附件下載都會 404。這是 0.4.30 日誌補強過程中浮現的既有 bug，當時記錄為待另開議題處理。

稽核後確認這不是「功能沒做」，而是只差最後一段：

| 層 | 狀態 |
|---|---|
| `ProjectFile` 實體、migration、上傳、實體檔案存放 | 已完成 |
| `ProjectService.GetFileDownloadAsync`（含團隊權控守門、ContentType、原始檔名） | **已完整實作，但從未被呼叫** |
| UI 連結 | 已存在 |
| HTTP 端點 | **缺** |

`docs/prd/專案項目-prd.md` 早已標註「對外端點的實際註冊位置未在現行 Controllers 找到（未確認）」—— 文件察覺了，程式沒補。

## 變更範圍

### 一、新增 ProjectFileController

`MyProject.Web/Controllers/ProjectFileController.cs`，路由 `api/project-files` 與 `api/v1/project-files`，端點 `GET {id}/download`。

**這個端點只收 Cookie 驗證**，與其他走 JWT 的 Web API 不同：呼叫端是 Blazor 畫面上的一般連結（`<a href>`），由瀏覽器直接導覽，帶的是登入 Cookie 而不是 Bearer token。照抄現有 controller 的 `[Authorize(JwtBearer)]` 必定 401。

路由明確寫成 kebab-case 而非慣用的 `api/[controller]`，是為了維持 UI 既有的網址。

回應規則：
- 成功 → 原生 `File` stream（不包 `ApiResult`），`enableRangeProcessing: true` 讓 1GB 上限的附件可以續傳。這是 `docs/operations/正式部署與安全檢查清單.md` 既有的原則。
- 失敗 → `ApiResult` 404。

**查無紀錄、團隊越界、實體檔案不存在三種情況一律回 404。**統一回應才不會讓外部用狀態碼推斷哪些 `ProjectFileId` 真的存在；三者的差異已由 `ProjectService` 分別以 Warning 記錄，維運端仍分得出來。

例外處理必須關掉 stream：`GetFileDownloadAsync` 回傳的是**已開啟的** `FileStream`，若在取得之後、回傳之前拋例外，`File(...)` 不會接手關閉，檔案控制代碼會外洩。

### 二、修正 HasPermissionAttribute 的 claim 對應

補這個端點時撞到的陷阱：兩套驗證機制的 claim 對應是**相反的**。

| | UserId | Account | 姓名 |
|---|---|---|---|
| Cookie（Blazor／本端點）| `Sid` | `NameIdentifier` | `Name`（**個資**）|
| JWT（現有 API）| `NameIdentifier` | `Name` | `display_name` |

屬性裡原本寫的是 `int.TryParse(NameIdentifier)` —— 這只有 JWT 成立；Cookie 下拿到的是帳號字串，解析失敗回 401。而且 `account` 取的是 `ClaimTypes.Name`，在 Cookie 下那是**使用者姓名**，會寫進日誌與稽核表的 `ActorAccount`。

當時沒有實際外洩（屬性只掛在 JWT controller 上），但這正是下一個人踩的坑。改為以「`NameIdentifier` 是不是數字」判斷來源，並且 `ClaimTypes.Name` **只在確定是 JWT 的那一支取用** —— Cookie 這一支永遠不碰它。JWT 分支邏輯完全等價，既有的 401／403 契約測試就是這條路徑的回歸網。

### 三、成功下載寫稽核

`Project.FileDownload` 事件，記 UserId、帳號、`ProjectFileId` 與檔名。附件內容可能敏感，而日誌只保留 30 天、會被輪替刪除；稽核在資料庫裡才是長期軌跡，外洩事件回溯時需要的正是「誰在什麼時候把哪個附件拿走了」。

沿用專案既有的 fail-open 作法：稽核寫入失敗只記 Error，不害使用者拿不到檔案。

稽核寫在 controller 而非 Service，與 `HasPermissionAttribute` 一致（web 層從 claim 取行為者）：`ProjectService` 在 Blazor 與 HTTP 兩種情境下都會被用到，而 `CurrentUserService` 只在 Blazor circuit 內有值，Service 層拿不到 HTTP 情境的 actor。

### 四、附件路徑防護

`GetFileDownloadAsync` 在檢查檔案是否存在之前，先確認解析後的絕對路徑確實落在設定的 `ProjectFilePath` 之下。

`RelativePath` 一律由 `SavePhysicalFileAsync` 寫成「年/月/Guid.副檔名」，正常情況不可能逸出；守的是資料庫被直接改過的情況 —— 這個端點會把伺服器本機的檔案內容送出去，不該把「這個值一定安全」當成前提。

根目錄未設定時一律拒絕：`Path.Combine("", x)` 會退化成相對於工作目錄的路徑。

### 五、測試

`GetFileDownloadAsync` 先前是**零覆蓋率**。擴充 `ProjectServiceTeamAccessTests` 的 fixture（原本傳的 `ProjectFilePath` 是空字串，下載必定失敗），新增五條：成功下載、查無 Id、非管理員越界、實體檔案不存在、路徑逸出根目錄。

`ApiIntegrationTests` 加一條「未帶驗證打這個網址不會是 404」—— 直接擋住「端點根本沒註冊」這種回歸，正是這次的 bug。

兩條守門都已實測驗證有效：把路由改壞、把路徑防護拿掉，對應的測試確實變紅，還原後通過。**守門測試不會失敗就沒有價值。**

## 已知取捨

- **Cookie 過期時點附件會看到 JSON 而不是登入頁。**`HasPermissionAttribute` 會在 Cookie 驗證發出挑戰之前先短路，回 401 `ApiResult` JSON。實務上影響很小：使用者是從自己正在看的頁面點連結，Cookie 若已失效，Blazor circuit 也已經斷了。
- **不做 JWT 版的下載端點。**目前沒有呼叫端。
- **不改 UI。**連結網址與 `target="_blank"` 維持原樣。
