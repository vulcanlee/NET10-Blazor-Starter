- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.9.37
- 首次實作版本：0.9.37
- 最後核對日期：2026/09/19

## 為什麼

`腳手架開發指引.md` 的 RBAC 段落（§3.5）只有 **64 行**，講得完「這項技術是什麼」，
講不完「一個企業級權限系統該怎麼設計」。而新手最需要的恰恰是後者。

盤點既有文件後確認這是真實缺口：

- **權限主題的 FAQ 位置完全是空的** —— 全 `docs/` 沒有任何一份用問答體裁講權限。
- **沒有任何文件寫過端到端走查**（「某人＋某角色＋某團隊 → 他看到什麼、能按什麼、打 API 回什麼」）。
- 既有文件各自為政：`認證授權與權限機制.md` 講機制但**完全沒講團隊列級權控**；
  `紀錄分類與團隊權控-prd.md` 講團隊但不講操作；速查表 §5 只有紅線沒有範例。

### 二、缺陷 A：「可看不可改」在 UI 上根本失效 🔴

角色矩陣只勾「檢視」時產生的是 `專案項目:view`，**不含裸鍵**；
但 `AuthenticationStateHelper.CheckAccessPage` 只比對裸鍵 —— 於是唯讀角色
**連頁面都打不開、選單也不顯示**。動作級授權當時只有 API 端真正生效。

- `CheckAccessPage` 改為「管理員 ∨ 裸頁面鍵 ∨ `頁面鍵:view`」，
  是 `CheckAccessAction`「動作鍵不中則退回裸鍵」的鏡像。
- `CategoryViewView` 與 `TeamViewView` 的新增／修改／刪除鈕補上 `CheckAccessAction`
  （先前只有 `ProjectViewView` 有，三頁行為不一致）。
- ⚠️ 這是**放寬**：原本進不來的唯讀角色現在進得去（但按不到寫入鈕）。這正是動作級授權的原意。
- 新增兩條測試釘住上下界：`:view` 應通過、`:create` 應被拒。

### 三、缺陷 B：`export` 是死權限

矩陣勾得到 `專案項目:export` 等三個鍵，但**全系統沒有任何地方檢查它** ——
與 0.4.33 修掉的「使用者管理勾了等於沒勾」屬同一類。

- 自 `RolePermissionService.SupportedActions` 與 `RoleViewView` 的動作欄下架。
- `PermissionActions.Export` 常數因此無人引用，一併移除。
- 新增 `AdminOnlyPermissionTests.ExportAction_ShouldNotAppearInRolePermissionMatrix` 守門。
- ⚠️ **既有資料**：已授予的 `X:export` 會在該角色下次存檔時被 `RbacWriteService` 的差集同步刪除；
  殘留的 `Permission` 列無害。無需手動清理。
- 要重新上架，必須**先**有會檢查它的程式，順序不能反。

### 四、缺陷 C：團隊權控 PRD 漏了 Web API 的缺口

`紀錄分類與團隊權控-prd.md` 通篇把團隊權控寫成「資安不變量」，卻沒提
**Web API 走 Repository 路徑完全沒有列級過濾**這件事（該事實只記在部署檢查清單裡）。
這份是團隊權控的權威文件，漏了它會讓人誤判 API 是安全的 —— 已在 §五補上並互相連結。

## 沒有做什麼

**Web API 的列級過濾缺口本次刻意不補。** 它被三份文件明載為「刻意設計」，
補上去會讓現有整合方突然少拿到資料，屬行為變更而非順手修正。
已列為 §6.5 的第一項建議，並寫明前置條件（JWT 不帶 `ClaimTypes.Sid`，不補這個過濾會退化）。
