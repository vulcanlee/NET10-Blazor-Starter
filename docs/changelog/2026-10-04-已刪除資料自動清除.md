# 已刪除資料自動清除：刪除超過保留天數的專案、分類、團隊、使用者、角色由排程作業永久刪除（0.9.97）

## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) B-5b。A-4b／A-4c（0.9.94、0.9.95）把專案、分類、團隊、使用者、角色改成軟刪除，當時約定「依保留天數自動永久刪除留給排程」；
B-5a（0.9.96）建好了排程框架。改動前已刪除的資料（含專案附件檔、使用者個資）會無限期留著，只能在各頁「顯示已刪除」逐筆手動永久刪除。

使用者決定：

- 刪除後預設保留 **90 天**再自動永久刪除（`SoftDeleteSettings:PurgeAfterDays`，`0`＝不自動刪除）。
- **五種都清**：專案（含附件實體檔）、分類、團隊、使用者、角色。
- 稽核：**每種資料每次一筆彙總**（`X.AutoPurge`：筆數、天數、觸發方式、被刪的 `#Id 名稱` 清單，過長截斷）。

設計經盤點與一次對照程式碼的審查，抓到幾個照原草案會出錯的地方（第二節 ⚠️）。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| ⚠️ 系統層級清除，**不套團隊範圍**、不重用各服務的 `PurgeAsync` | 背景作業沒有登入者，`ProjectService.PurgeAsync` 會擋下所有有團隊的專案。速查表「刪除、還原、永久刪除都要檢查團隊範圍」補上這個明文例外 |
| 順序：專案 → 分類 → 團隊 → **使用者 → 角色** | `MyUser.RoleViewId` 是 Restrict 外鍵；使用者先刪，同一輪中它們引用的角色才刪得掉 |
| ⚠️ **每一筆用新的 DbContext**，並在載入時重新確認完整條件 | 共用 context 時，一筆存檔失敗的實體會留在追蹤裡，之後每一筆的 `SaveChanges` 都跟著失敗 |
| ⚠️ 追蹤中 `Remove`，**不用 `ExecuteDelete`** | DELETE 帶著版本號：候選之後被還原（還原會換新版本號）→ 並行衝突 → 略過。`ExecuteDelete` 不比對版本號，會刪掉剛被還原的資料；它也套用軟刪除過濾器 |
| 專案附件實體檔在**提交成功後**才經 `ProjectFileStore` 刪除；刪不掉只計數 | 先刪檔再存的話，存檔失敗會留下指向不存在檔案的資料列；反過來只會留下孤兒檔 |
| ⚠️ 角色仍被任何使用者（含已刪除、尚未到期的）當主要角色 → 留到下次；刪除當下被指派的外鍵錯誤也一樣 | 外鍵連已刪除的使用者都算；把外鍵錯誤當失敗的話，健康監控會因為正常的競態一直紅燈 |
| ⚠️ support 帳號（不分大小寫）與「預設角色」永遠不刪 | 它們若被其他途徑軟刪除，啟動時的種子資料會還原它們；先被永久刪除就救不回原本的設定 |
| ⚠️ 取消時**不丟例外**，回傳部分結果；作業先寫稽核再把取消交回框架 | 被永久刪除的業務資料不可以沒有任何紀錄 |
| 每種資料各自 try/catch，結果物件建在 try 之前 | 一種資料失敗不影響其他種；失敗前已刪的仍寫稽核，作業回 Failure |
| 略過、使用中、受保護、刪檔失敗都不算失敗 | 只在訊息列出數量；只有真正的錯誤才讓「上次執行」變紅 |
| 門檻用本地時鐘 | `DeletedAt` 由 `SoftDeleteHelper` 以本地時間寫入 |
| 不在「顯示已刪除」加「預計刪除日」欄 | 天數可調、作業可停用，畫面上的日期不可靠；說明頁改寫為「預設 90 天後自動永久刪除（依系統設定）」|

不在範圍：名稱字串參照（專案上的分類／團隊名稱、角色的預設團隊）不清理，維持既有行為。

## 三、驗證（2026/10/04 實跑）

**故意改壞 22 處，全部被測試抓到**：
- 清除服務：門檻方向反了、漏掉專案、不刪附件檔、提交前就刪檔、改用 `ExecuteDelete`、使用中檢查沒有 `IgnoreQueryFilters`、角色排在使用者之前、
  刪除當下被指派不處理、不保護 support、support 比對區分大小寫、一種資料失敗就整個中止、失敗時清掉已刪清單、不檢查取消。
- `ProjectFileStore` 不檢查根目錄；`ProjectService` 移除附件時先刪檔再存。
- 作業：拿掉天數 0 的保護、用 UTC 時鐘、沒刪到也寫稽核、不截斷 Detail、失敗時不寫稽核、把受保護當成失敗、取消時先丟出再寫稽核。

每一輪改壞後都從還原的原始碼重新建置，避免 B-5a 遇過的「舊編譯產物造成誤判」。
