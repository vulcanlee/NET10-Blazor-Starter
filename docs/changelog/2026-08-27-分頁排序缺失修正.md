# 修正分頁查詢缺少 OrderBy（0.4.46）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.46
- 首次實作版本：0.4.46
- 最後核對日期：2026/08/27

## 症狀

執行期日誌反覆出現 EF Core 警告：

```
WARN|Microsoft.EntityFrameworkCore.Query|The query uses a row limiting operator
('Skip'/'Take') without an 'OrderBy' operator. This may lead to unpredictable results.
```

這不是噪音。沒有 `ORDER BY` 時 SQLite 不保證回傳順序，分頁可能出現「同一筆資料在第 1 頁
和第 2 頁都看到」或「某筆資料翻遍所有頁都看不到」—— 只是資料量小的時候不容易察覺。

## 根因

Blazor 路徑五支 `*Service.GetAsync(DataRequest)` 的排序區塊有**三個各自獨立的漏洞**，
任何一個成立都會讓 `Skip`／`Take` 前面完全沒有 `OrderBy`：

| # | 漏洞 | 受影響 |
|---|---|---|
| ① | `if (!string.IsNullOrWhiteSpace(SortField))` 沒有 `else` 預設分支，**首次載入必然無排序** | `ProjectService`、`RoleViewService`、`MyUserService` |
| ② | 排序方向三元式尾巴寫成 `: dataSource`，`SortDescending == null` 時原樣回傳、不排序 | 五支全中 |
| ③ | `SortField` 有值但不在 `if / else if` 清單內（日後加欄位漏補即成立） | 五支全中 |

②的 `: dataSource` 是整組寫法的核心問題：它讓「沒排到」與「排好了」共用同一個變數，
從型別上看不出差別，因此 ①③ 這兩個缺口才會一直沒被發現。

**Web API 路徑不受影響**：`TeamRepository` / `CategoryRepository` / `ProjectRepository`
用 `switch` 運算式且有 `_ =>` 預設分支。CRUD 產生器 `scripts/New-CrudModule.ps1` 的樣板
也早已是「先無條件排序再分頁」的正確寫法。

## 修正

把「有沒有排到」變成型別看得出來的事：排序結果收在 `IOrderedQueryable<T>? sorted`，
未命中的分支留 `null`，最後在 `Skip` 之前用 `??` 一次收斂。

```csharp
IOrderedQueryable<Team>? sorted = null;

if (!string.IsNullOrWhiteSpace(dataRequest.SortField))
{
    if (dataRequest.SortField == nameof(TeamAdapterModel.Name))
    {
        sorted = dataRequest.SortDescending == true
            ? dataSource.OrderByDescending(x => x.Name).ThenByDescending(x => x.Id)
            : dataRequest.SortDescending == false
                ? dataSource.OrderBy(x => x.Name).ThenBy(x => x.Id)
                : null;                      // ← 原本是 : dataSource
    }
    // ...其餘分支同形...
}

// Skip/Take 一定要搭配 OrderBy，否則 SQLite 不保證回傳順序，分頁會重複或漏資料。
// 未指定欄位、欄位不認得、方向為 null —— 三種情況一律退回預設排序。
dataSource = sorted ?? dataSource.OrderByDescending(x => x.UpdatedAt).ThenByDescending(x => x.Id);
```

三個漏洞由同一行補完，且日後新增排序欄位忘了補分支，也只會退回預設排序，不會再變成「無排序」。

預設排序沿用 `TeamService` / `CategoryService` 原有的「更新時間新→舊 ＋ Id 遞減」，
使用者看到的畫面順序與修正前一致：

| 服務 | 預設排序 |
|---|---|
| `TeamService` / `CategoryService` / `ProjectService` | `UpdatedAt` 遞減 → `Id` 遞減 |
| `RoleViewService` / `MyUserService` | `UpdateAt` 遞減 → `Id` 遞減 |

`TeamService` / `CategoryService` 原有的 `else { ... }` 預設排序區塊一併移除，
避免同一個預設值寫在兩個地方。

## 守門機制

`MyProject.Tests/TestDbContextFactory.cs` 把這個警告在**測試環境**升級為例外：

```csharp
.ConfigureWarnings(w => w.Throw(CoreEventId.RowLimitingOperationWithoutOrderByWarning))
```

一行涵蓋所有走測試工廠的服務，不必逐支重複。正式環境**維持只記警告**，不改變執行期行為。

驗證過守門確實有效：把五支服務的修正暫時退掉後跑全套測試，8 個測例失敗
（4 個是本次新增的，4 個是 `ProjectServiceTeamAccessTests` 既有測例被警告擋下 —— 正是漏洞①）。

## 行為變化

`SortDescending` 為 null 或排序欄位不認得時，原本回傳「資料庫任意順序」，改後回傳預設排序。
這是修正而非回歸 —— 原本那個順序本來就不保證，只是碰巧看起來穩定。

## 取捨與排除的作法

- **不在正式環境把警告升級為例外**：真的漏了排序時，正式環境該記警告並照常出頁面，
  不該讓使用者看到 500。守門留在測試層就夠。
- **不改 Repository 與產生器樣板**：兩者已有正確的預設分支，符合「只動該動的」原則。
- **不改成「先無條件排序、再視情況覆寫」**：那會讓 EF 產出多餘的 `ORDER BY` 欄位
  （`OrderBy(a).OrderBy(b)` 在 LINQ 語意上是 `ORDER BY b, a`），SQL 變髒。

## 已知未覆蓋

`RoleViewService` 與 `MyUserService` 目前沒有 `GetAsync(DataRequest)` 的測例，
因此它們的漏洞①只靠程式碼修正保證，沒有測試直接涵蓋。五支的寫法完全同形，
日後任一支補上清單查詢測例時，`TestDbContextFactory` 的守門就會自動生效。
