## 目的

[路線圖](../planning/00-腳手架強化路線圖.md) A-4 的最後一項（A-4c）。A-4b（0.9.94）已讓專案、分類、團隊改為軟刪除；使用者與角色牽涉登入、權限判斷、Google 登入、種子資料，當時刻意拆出來。
兩個盤點代理加上一次對照程式碼的審查，列出照著 A-4b 的做法直接套用會出錯的地方，本次逐項處理。

使用者決定：

- 角色仍是某些**未刪除**使用者的主要角色時：**擋下**，訊息寫出人數與前幾個帳號。
- 已刪除的使用者用 Google 登入：**導回登入頁並顯示**「此帳號已被刪除，請洽系統管理員。」。
- Google 比對順序：**GoogleId 優先**（有效的 GoogleId → 已刪除的 GoogleId → 有效的 Email → 已刪除的 Email → 新建）。
- 兩個既有缺陷**併入本次修正**：審查找到的角色畫面模型 `Clone()` 漏了版本號；真實瀏覽器驗證找到的登出重新導向迴圈（見第四節）。

## 二、設計決定

| 決定 | 理由 |
|---|---|
| 權限判斷在 `GetKeysForRolesAsync` 過濾，而不是只過濾 `UserRole` 查詢 | legacy `MyUser.RoleViewId` 也是權限來源；只過濾一邊會留下漏洞（有測試釘住只有 legacy 欄位的情況） |
| 角色的額外角色連結、使用者的角色／團隊連結都保留 | 還原後要原樣回來；不在關聯表上加過濾器（會撞唯一索引） |
| 仍是主要角色時禁止刪除，並在**存檔後再複查一次** | 「刪除角色的檢查」與「使用者存檔時驗證角色」各在不同的 DbContext；任一方先完成都可能讓某人掛著已刪除的主要角色，每次換頁都被登出 |
| 事前檢查不能只靠事後複查取代 | 先寫入再還原會換掉版本號，正在編輯這個角色的人存檔時會被誤判為衝突（測試會檢查被拒絕的刪除不改版本號） |
| support 比對設定檔的 `SupportAccount`、不分大小寫 | 寫死的常數在 support 改名後會漏擋；多擋一個不會出事，少擋一個可能刪掉唯一的救援帳號 |
| 存檔驗證角色時，主要角色為 null 允許 | Google 自動建立的帳號在預設角色不存在時就是 null；很多既有資料與測試也是 |
| 永久刪除一律追蹤載入後 `Remove` | `ExecuteDelete` 也套用具名過濾器，對已刪除的列會刪 0 筆 |
| Google 已刪除時告知原因，密碼登入則不告知 | Google 已驗證本人身分，告知沒有洩漏疑慮；密碼登入維持「帳號或者密碼不正確」，不透露帳號曾存在 |
| `?sso=` 只認固定代碼 | 不把網址內容顯示到頁面上 |

## 四、真實瀏覽器驗證

Playwright 驅動本機 Edge；所有外部路徑與日誌都指向暫存目錄。

- 角色：新增 → **修改後存檔成功**（0.9.93～0.9.94 這一步會被誤判為並行衝突）。
- 刪除仍是 bob 主要角色的角色 → 擋下：「還有 1 位使用者以「Browser Role 2」為主要角色（bob），無法刪除。請先到使用者管理把他們的主要角色改成其他角色，再刪除。」
- 使用者頁 support 那一列只有「修改」，沒有「刪除」。
- bob 能登入 → 刪除（確認窗為新版文字）→ bob 已開著的瀏覽器換頁後回到登入頁 → 用 bob 登入得到「帳號或者密碼不正確」→「顯示已刪除」看到他（刪除時間、刪除者 support）
  → 還原 → bob 可以登入 → 再刪除 → 永久刪除（確認窗提醒角色與團隊設定一併刪除）。
- 角色沒人用之後：刪除 → 「顯示已刪除」→ 永久刪除。
- 登入頁 `?sso=deleted` 顯示「此帳號已被刪除，請洽系統管理員。」。Google 登入本身無法在本機實測，以服務與頁面測試涵蓋。

**驗證中找到的既有缺陷（已修正）**：第一輪驗證時，被刪除的使用者換頁後瀏覽器顯示「**重新導向太多次**」。
日誌顯示每次請求 `/Auths/Logout` 都記一次「User not found」，再 302 回 `/Auths/Logout`：登出頁沒有指定版面而套用 `MainLayout`，
`MainLayout` 先跑 `Check`，使用者無效時又導向 `/Auths/Logout`，這個導向發生在登出頁清掉 Cookie 之前。
**被停用的使用者完全一樣**（以停用帳號重現，日誌記「UserId=4 is disabled」），所以這是既有缺陷，至少從 0.9.41 起就存在；A-4c 只是讓「刪除」也會走到它。
使用者決定併入修正：登出頁指定 `EmptyLayout`。先寫整合測試（以網站自己的 `TicketDataFormat` 產生停用／已刪除者的有效 Cookie，請求 `/Auths/Logout` 必須導向 `/Auths/Login`），
修正前兩個案例都失敗、修正後通過；重跑瀏覽器驗證，被刪除與被停用的使用者換頁後都回到登入頁。
