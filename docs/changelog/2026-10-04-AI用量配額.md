## 二、設計決定

| 決定 | 理由 |
|---|---|
| 檢查放在 `AiChatCompletionClient` | 日誌分析與例外分析（含每一輪追問）共用；健康檢測的探針不經它，自然不會被擋 |
| 提醒放在 `TokenUsageLogService.RecordAsync` | 任何經用量記錄點的呼叫（含健康檢測、日後新增的 AI 功能）都會計入並觸發，不必每個呼叫點各寫一次 |
| 期間用本地時間 | `TokenUsageLog.OccurredAt` 本來就存本地時間；「今天」對使用者的意義是本地的今天 |
| 已用金額等於上限就擋 | 「上限 NT$ 100」的直覺是用到 100 就停 |
| 同時達到多個上限時回報最晚重置的 | 例如每人每日與全系統每月都達到時，說「明天重置」會讓人白等 |
| 讀不到用量時放行 | 配額是費用控管，不該讓 AI 分析因資料庫短暫錯誤整個停擺；錯誤會寫日誌 |
| 通知只發最高達到的門檻、去重鍵含期間 | 一次跳過 80% 直接到 100% 時只收一則；隔天、下個月重新計算 |
| 不做預先保留額度 | 送出前無法知道費用；並行時小幅超過上限是可接受的代價 |
| 管理員沒有豁免 | 費用不分身分；要緊急解除就調高上限，立即生效 |

## 四、實機驗證

Playwright＋Edge，所有外部路徑與日誌隔離到暫存目錄；AI 端點是暫存目錄裡的 Node 假端點（回固定的 100k 輸入＋20k 輸出 token，模型 `gpt-6-astra` 每次約 NT$ 63），不使用真的金鑰、不花錢：

- 在系統參數把「每人每日上限」改成 150（稽核 `SystemParameter.Update`）。
- 日誌檢視連續按 4 次「AI 分析」：前 3 次成功（已用 63 → 126 → 189）；第 4 次不送出（假端點收到的請求數不變），對話窗顯示「已達每人每日 AI 用量上限（NT$ 150，今日已用 NT$ 189），2026-10-05 00:00 重置。…」，稽核有 `Ai.QuotaBlocked`（`AiQuota#User:Daily`、`limit=150; used=189`）與失敗原因 `QuotaExceeded` 的 `LogViewer.AiAnalyze`。
- 鈴鐺：「AI 用量已達上限的 80%：每人每日（今日已用 NT$ 126）」與「AI 用量已達上限：每人每日（NT$ 189）」各一則。
- 已達上限時打開系統健康監控：AI 連線檢查照常送出（假端點多一個請求），費用計入（Token 用量頁全系統今日 NT$ 252 ＝ 4 × 63）。
- Token 用量頁上方顯示「全系統每日：今日 NT$ 252／不限制　…　每人每日上限：NT$ 150」。
- 把上限改成 1000 → 下一次 AI 分析立即成功。
- `C:\temp` 未被寫入；結束後停掉 `MyProject.Web` 與假端點。
