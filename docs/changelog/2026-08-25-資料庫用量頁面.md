## 目的

系統沒有任何地方能看出 SQLite 資料庫的實際磁碟占用。`/system-health` 只回報「可否連線」與「待套用 migration 數」，看不到檔案有多大、WAL 累積了多少、有多少空間可回收，也看不出哪張表最占空間 —— 要判斷這些只能登入伺服器翻檔案。

## 變更範圍

### 一、新增 /database-usage 頁面

放進既有的「統計與分析」子功能表（id 62，icon `data_usage`），成為「日誌檢視」的兄弟項目。

六張用量卡片（磁碟占用總計／主資料庫檔／預寫日誌／共享記憶體索引／已配置／可回收）、WAL 說明橫幅、估算免責說明，以及各資料表的筆數／資料量估算／索引數表格（四欄皆可排序）。

**本頁沒有任何操作按鈕**，純閱讀，不提供 VACUUM 或 WAL checkpoint 等會寫入資料庫的動作。

> icon 刻意選 `data_usage` 而非直覺的 `database`：後者是 Material Symbols 專有名稱，本專案載入的是 classic Material Icons，會渲染成破圖方塊 —— `MenuIconTests` 的註解正是拿 `database` 當反例。

### 二、資料庫用量服務

新增 `MyProject.Web/Diagnostics/DatabaseUsageService.cs`（與 `LogQueryService` 同資料夾）。

**這是本專案第一段正式環境的原生 SQL**：`PRAGMA` 無法參數化，而 `ExecuteSqlRaw` 只回傳受影響列數，因此改走 `Database.GetDbConnection()` + `DbCommand`。

幾個實作上的關鍵決定：

- **檔案路徑取自已開啟連線的 `DataSource`**（即 `sqlite3_db_filename` 解析出的絕對路徑），而非組態值。這樣量到的必定是 EF 實際在用的那個檔案，設定漂移不可能發生。（順帶一提：`SystemSettings:ConnectionStrings:SQLiteDefaultConnection` 是死設定，從未被任何程式碼讀取。）
- **走 EF 的 `OpenConnectionAsync`／`CloseConnectionAsync`** 而非直接對 `DbConnection` 開關。EF 內部有開啟計數，若連線已被其他查詢開著，這裡的開關只會增減計數而不會關掉別人的。本頁在 Blazor Server 上，scope 是整個 circuit 而非單一請求，同一個 DbContext 可能活很久，更該把連線狀態原樣還回去。
- **索引數以單一 `GROUP BY` 查詢一次取回**，而非每張表各跑一次。
- **筆數與位元組加總在同一次掃描取回**，分兩次查詢會掃兩遍。

### 三、抽出共用的位元組格式化

`FormatFileSize` 原本是 `ProjectViewView.razor.cs` 裡的 private static，新頁面在六張卡片與整欄表格都會用到。移到 `MyProject.Share/Helpers/SizeFormatHelper.cs`，`ProjectViewView` 的私有方法改為一行委派，razor 標記的兩處呼叫點不動。

## 兩個實作中驗證出來的技術陷阱

### LENGTH 回傳字元數而非位元組數

SQLite 的 `LENGTH(文字欄)` 回傳的是**字元數**。實測：

```
LENGTH('中文測試')                = 4   (字元)
LENGTH(CAST('中文測試' AS BLOB))  = 12  (位元組)
```

少了 `CAST(... AS BLOB)`，中文資料會被少算到三分之一 —— 而且是**靜默錯誤**，畫面照樣顯示一個看起來合理的數字。已由 `DatabaseUsageServiceTests.Estimate_ChineseText_ShouldCountBytesNotCharacters` 守住，並實測驗證：拿掉 `CAST` 後該測試確實失敗。

### NULL 欄位會毒化整列加總

`NULL + 任何值` 仍是 `NULL`，而 `SUM()` 會直接跳過 `NULL` 列。因此必須**逐欄** `COALESCE(..., 0)` 而非只在外層包一次，否則只要一欄為 NULL 就會「悄悄少算」而不是報錯。同樣有對應測試。

## 驗證：dbstat 確實不存在

截圖原文斷言「本專案綁的 SQLite 沒有編入 dbstat 虛擬表」。實作前實際探測確認：

```
sqlite_version = 3.49.1
dbstat → SQLite Error 1: 'no such table: dbstat'
```

因此免責說明的文字屬實，估算採欄位位元組加總。

## 已知取捨

- **位元組估算是每張表全表掃描**，成本與資料庫總大小成正比且無索引可用。目前資料庫僅 144 KB 故可忽略；服務記錄每次量測耗時，日後真的變慢才有數據可依據。未設上限是明確的決定，不是疏漏。
- **`Microsoft.Data.Sqlite` 的 async 是假的**：`ExecuteScalarAsync` 等是同步工作包在已完成的 Task 裡，`CancellationToken` 無法中止已在進行的掃描 —— 所以用逾時設限並不會真的生效，這也是不採用逾時方案的原因。
- **數值欄位估算不精確**：INTEGER／REAL 轉 BLOB 會先經過文字表示，量到的是位數而非實際儲存的 varint 長度。不應改用 `CASE typeof(...)` 硬套固定長度，那同樣是猜測。
- **已配置可能大於主檔大小**：`page_count` 包含仍只存在於 WAL、尚未 checkpoint 回主檔的頁。這正是副標「含尚未併回主檔的頁」的意思。
