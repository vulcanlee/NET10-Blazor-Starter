# 日誌可觀測性補強（0.4.30）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.30
- 首次實作版本：0.4.30
- 最後核對日期：2026/08/25

## 目的

讓系統不穩定或出 bug 時，能第一時間從日誌看出「發生了什麼」，甚至還原「使用者當時做了什麼操作」。日常只看 Information，特殊情況才降到 Debug 查細節。

**但這不是從零開始。** 事前完整稽核的實況：專案已有 **419 筆日誌呼叫**，慣例嚴格一致（英文句子 ＋ PascalCase 佔位 ＋ 例外放第一參數，419/419 皆為英文），五個 CRUD 檢視的使用者操作也已相當完整。因此本次的性質是**補洞與導正**，而非大規模新增。

稽核挖出四個真正的問題，以下逐一處理。

## 一、Blazor 側的例外沒有應用程式層級的痕跡

五個 CRUD 檢視的 `LogError` 數量是 **0** —— 所有按鈕處理方法都沒有 try/catch。例外會直接拆掉 Blazor circuit，使用者只看到畫面斷線。

> 補充查證：框架本身其實**有**記錄（`RemoteErrorBoundaryLogger`，Warning 等級，`Microsoft.*` 類別），但訊息裡沒有使用者、沒有頁面、沒有應用程式上下文。所以問題不是「完全沒記」，而是「記了也查不出是誰在哪一頁出事」，且 circuit 直接死掉。

處理方式：

1. **五個 CRUD 檢視的寫入操作加 try/catch**（`OnModalOKHandleAsync` 與 `OnDeleteAsync`）。採「重新命名 ＋ 包裝」的作法而非在長方法內插入 try 區塊 —— 呼叫端沿用原名，因此一併獲得錯誤處理。各檢視的 `LogError` 由 0 增為 2。
2. **新增 `LoggingErrorBoundary`** 掛在 `Routes.razor`（而非 MainLayout）。原因是 MainLayout 涵蓋不到走 `EmptyLayout` 的首頁與走 `NoFooterLayout` 的登入頁，**也接不住 MainLayout 自己拋出的例外** —— 而 `MainLayout.OnInitializedAsync` 呼叫的 `AuthenticationStateHelper.Check` 正是全專案最容易出事的一段。
3. **`Error.razor` 與 `NotFound.razor` 補上日誌**。`Error.razor` 記在 Warning 且**不帶例外物件** —— 真正的例外與堆疊已由請求 middleware 以 Error 記過，這裡只標記「使用者確實看到了錯誤畫面」，靠 `TraceId` 與那筆對上。

## 二、權限拒絕完全靜默

`HasPermissionAttribute` 擋下請求時不寫任何日誌 —— 有人被擋下來完全不會知道。

現在三個拒絕分支都記在 **Warning**，並額外寫入**稽核軌跡**（`Permission.Denied`）。

> 稽核會不會被灌爆？不會。匿名請求在更前面就回 401、**不會進到權限檢查**，因此稽核寫入只發生在已登入的使用者身上，匿名流量無法觸發。

## 三、Warning 被濫用（139 筆，與 Information 相當）

專案把「密碼未填」「前置檢查未通過」「重複名稱」這類**預期內的驗證拒絕**也記成 Warning，真正的異常因此被淹沒。

**而現行文件正是這樣寫的** —— `日誌與設定檔說明.md` 的等級表把「業務驗證未通過」列在 Warning。所以文件與程式碼必須一起改，否則兩者會互相矛盾。

判斷準則（已寫入文件）：

> **Warning 是給「維運人員應該看一眼」的事。使用者打錯字不是。**
>
> - 讀取查無資料 = Information；**寫入**查無資料 = Warning（畫面過期或有人在探測）
> - 欄位／重複名稱驗證失敗 = Information；**權限與身分驗證失敗 = Warning**

依此重新分類 **50 處**。保留 Warning 的包括：所有授權拒絕、所有身分驗證失敗、寫入時查無資料、憑證拒絕、設定與資料完整性異常。

## 四、Email 正在外洩

三處以 Information 等級記錄 Email，其中一處連 Google `subject`（穩定的外部識別碼）一起。與既有規範「日誌不應寫入密碼、token 或完整連線字串」的精神衝突，也與本次「只記 Account 與 UserId」的決定衝突。

全部改為記 `UserId` 或 `Provider`。

## 五、使用者操作追蹤

**畫面切換集中在 `ApplicationCircuitHandler`，不動任何頁面。** 選它而非 MainLayout 的理由同上：涵蓋所有版面。

circuit 的開啟／關閉／斷線日誌也補上 `Account` 與 `UserId`，讓斷線、導覽、操作三種日誌能用 `CircuitId` 串起來。

**身分取自 `AuthenticationStateProvider` 而非 `CurrentUserService`** —— 這是實作中修正的一個錯誤。`CurrentUserService` 要等 `AuthenticationStateHelper.Check` 在元件的 `OnInitializedAsync` 跑過才有值，而 circuit 開啟的時間點早於任何元件初始化，且首頁走 `EmptyLayout` 根本不會跑到。用它會導致大部分 circuit 都記成匿名。

## 六、補上高價值的 logger

`HasPermissionAttribute`（權限拒絕）、`PermissionChecker`（權限判定 → Debug）、三個 Repository（查詢條件與筆數 → Debug）、`DistributedCacheService`（命中／未命中 → Debug）、`EffectiveTeamResolver`、`RbacWriteService`（權限同步 → Information）。

**刻意不補**：`TotpService`（純密碼學運算，所有輸入輸出都是機密，加 logger 只會誘使人記錄它）、`CurrentUserService`（純狀態持有）、`RolePermissionService`（回傳靜態結構）、靜態擴充方法類別。這些都列入守門測試的豁免清單並註明理由。

## 七、降低雜訊（本次影響最大的單一改動）

HTTP 請求 middleware 原本把**每一筆**請求都記在 Information，包含靜態資產與健康探針。

`/health/live` 若每 10 秒輪詢一次，一天就是 **8,640 筆 Information** —— 比一位使用者一整天的操作紀錄還多。不處理的話，日誌會變得「更完整但更難讀」，正好違背本次的目的。

現在低價值路徑（靜態資產、`/_blazor`、`/health`、`/swagger` 等）記在 Debug；**但狀態碼 400 以上一律維持 Information 以上** —— 靜態資產的 404 往往正是「連結壞掉」最早的線索。

另外把「每次導覽都會出現但不帶使用者意圖」的 Information 降為 Debug：驗證狀態初始化、側邊選單載入、各檢視的初始化與清單重載。並刪掉 `MainLayout` 與 `NavMenu` 兩處重複的導覽 Debug —— 它們記的內容是緊接著那行的嚴格子集。

## 八、只引入 Critical，不引入 Trace

`Program.cs` 頂層的致命例外改用 `LogCritical` —— 應用程式因此終止，那正是 Critical 的定義，與「單一請求失敗」必須能區分開。全專案只有這一處。

**不引入 Trace**：使用者的心智模型是兩層（平常看 Info、出事看 Debug），第三層會讓每一行日誌都多一個決策成本。而且目前選 TRACE 與選 DEBUG 輸出完全相同，因為框架的 Trace 被 `nlog.config` 的 `final` 規則擋掉。文件已寫下「迴圈內／逐筆的日誌一律 Trace」的規則，等真正需要時再出現。

## 已知取捨

- **連線中斷記在 Warning**：正常關閉分頁也會觸發，因此 Warning 數量約等於工作階段數。訊息已改寫說明這點，避免維運人員白追。若 Warning 雜訊成為問題，這是第一個該降級的。
- **保留策略未調整**（維持單檔 100MB／保留 30 天）。粗估一位使用者活躍一小時約 150 筆 Information、約 33KB；因為 `archiveEvery="Day"` 每日切檔，要單日超過 100MB 需要約 380 位並行使用者，餘裕充足。先觀察實際量。
- **`nlog.config` 的 `overflowAction="Discard"`**：突發流量下（尤其執行期切到 Debug 時）NLog 會**靜默丟棄**事件。因此 Debug 應該限時使用，丟棄情形可在 `MyProject.Web-nlog-internal.log` 查到。
- **Google SSO 使用者的 Account 就是 Email**，因此對他們而言記 Account 等於記 Email。這是刻意接受的取捨（已與使用者確認），因為 Account 是追蹤「是誰做的」最直接的依據。
- **CRUD 加 try/catch 是行為變更**：原本例外會拆掉 circuit，現在捕捉後提示使用者並留下日誌。這正是「使用者遇到錯誤時要留下痕跡」的目的。
