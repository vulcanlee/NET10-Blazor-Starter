# API 安全基礎設施補強：限流分割、安全標頭、上傳白名單（0.4.35）

- 文件版本：1.0
- 文件狀態：已實作
- 現行系統版本：0.4.35
- 首次實作版本：0.4.35
- 最後核對日期：2026/08/26

## 目的

承接 0.4.34 的 API 安全缺陷修正，處理基礎設施層面的五項問題。

## 變更範圍

### 一、限流是全站共用的單一計數器

`AddConfiguredRateLimiting` 原本用 `options.AddFixedWindowLimiter("api", ...)` ——
那是**不分割的單一計數器**，120 次/分鐘是**所有使用者共用**的。
任一呼叫端（或掃描器）每分鐘打滿 120 次，其他所有人都會拿到 429。

**處置**：改用 `AddPolicy` + `RateLimitPartition.GetFixedWindowLimiter`，分割鍵為：

| 情境 | 分割鍵 |
|------|--------|
| 已驗證身分 | `user:{身分名稱}` —— 同一人換 IP 仍受同一份配額 |
| 未登入 | `ip:{來源 IP}` |
| 取不到 IP | `anonymous`（共用） |

另為 `/api/Auth/login` 立獨立且更嚴格的 `login` 政策（預設 10 次/分鐘）。
帳號鎖定（連續失敗 5 次）是第二道防線，但它擋不住「橫向」猜測多個帳號。

**配額改為可設定**（`RateLimit:ApiRequestsPerMinute` / `RateLimit:LoginRequestsPerMinute`）。
各案流量特性不同（內網管理系統 vs 對外開放 API），寫死在程式碼不合理；
整合測試也因此不再受正式配額牽制 —— 原本測試套件的登入次數已逼近 10 次上限，屬於一改設定就會紅的隱患。

### 二、缺少安全回應標頭

新增 `UseSecurityHeaders()`，設定 `X-Content-Type-Options: nosniff`、
`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`。

`nosniff` 對本專案特別重要：附件下載會回吐儲存時記下的 ContentType，
少了它，瀏覽器可能把附件當成 HTML 解析而造成同源 XSS。

> **CSP 刻意不納入本次範圍**：Blazor Server 有自己的 CSP 需求，且 `App.razor`
> 會從 fonts.googleapis.com 載入字型、AntDesign 會注入 inline style。
> 導入時請先以 `Content-Security-Policy-Report-Only` 觀察，確認無誤再轉為正式標頭。

### 三、`/UploadFiles` 匿名可讀

`UseConfiguredDownloadStaticFiles` 把 `ExternalFileSystem.DownloadPath` 掛在 `/UploadFiles`，
且**註冊於 `UseAuthentication()` / `UseAuthorization()` 之前**；`UseStaticFiles` 本身也不看授權
—— 等於整個下載目錄匿名可讀。

預設設定下 `ProjectFilePath`（`...\ProjectFile`）不在 `DownloadPath`（`...\Download`）底下，
所以**沒有直接外洩**；但交付到客戶端後只要有人把檔案放進該目錄就會裸奔，
與 `ProjectFileController` 的權限 + 團隊守門 + 稽核軌跡完全相反。

**處置**：移到授權中介軟體之後，並以 `UseWhen` 分支加上「必須已驗證身分」的閘門，未登入回 401。

### 四、上傳無副檔名白名單，且回吐呼叫端提供的 ContentType

`.html` / `.svg` / `.exe` 皆可上傳；`ContentType` 直接沿用呼叫端提供的值並在下載時原樣回吐。
配合當時缺少的 `nosniff`，構成同源 stored XSS。

**處置**：新增 `MyProject.Business/Helpers/UploadFileTypePolicy`：

- **副檔名白名單**（預設涵蓋文件、試算表、簡報、圖片、封存），
  刻意不含 `.html/.htm/.svg/.xhtml/.js/.exe/.bat/.cmd/.ps1/.sh`。
- **ContentType 一律依副檔名決定**，完全忽略呼叫端提供的值
  （攻擊者可以上傳 `.txt` 卻宣稱 `text/html`）。白名單外的副檔名回退 `application/octet-stream`。
- 各案可於 `SystemSettings.Upload.AllowedExtensions` 覆寫白名單；留空採用內建預設。

> 已經做對、未更動的部分：儲存檔名一律 `Guid.NewGuid():N`（原檔名只存 DB 不進路徑）、
> `IsUnderProjectFileRoot` 的正規化比對且 fail-close。**路徑穿越防護原本就是扎實的。**

### 五、其餘小項

- **移除死碼**：`Program.cs` 設定了 `CookiePolicyOptions`（含 `MinimumSameSitePolicy = None`），
  但 pipeline **從未呼叫 `UseCookiePolicy()`**。且 `SameSite=None` 本身會削弱 CSRF 姿態，不該啟用。
- **`UseForwardedHeaders` 可設定信任來源**：新增 `ForwardedHeaders:KnownProxies` /
  `KnownNetworks`。限流改為以 IP 分割之後這件事更重要 ——
  未設定信任來源時，呼叫端可自行偽造 `X-Forwarded-For` 繞過配額。
  沒設定就維持 ASP.NET Core 預設（僅信任 loopback）。

## 驗證

`dotnet test` 由 214 → **244 個全數通過**。新增：

| 測試 | 驗證 |
|------|------|
| `RateLimitPartitionTests`（4）| 不同 IP 得到不同分割；同 IP 相同；已驗證身分優先於 IP；無 IP 回退共用分割 |
| `UploadFileTypePolicyTests`（20+）| 危險副檔名一律擋下、自訂白名單可覆寫預設、ContentType 依副檔名對應、預設清單不含可執行 script 的類型 |
| `Responses_ShouldIncludeSecurityHeaders` | 三個安全標頭皆存在 |
| `UploadFilesStaticPath_WithoutLogin_ShouldNotBeAnonymouslyReadable` | `/UploadFiles/*` 未登入回 401 |

> 撰寫測試時抓到實作 bug：`UploadFileTypePolicy.Normalize` 回退預設清單時用集合運算式
> `[.. keys]` 建 `HashSet`，**會遺失 `OrdinalIgnoreCase` 比較器**，導致 `.PNG` 這種大寫寫法被誤擋。
> 已修正並保留該測試案例。

`TreatWarningsAsErrors`（0.4.32 導入）也在本次立即發揮作用：
`ForwardedHeadersOptions.KnownNetworks` 已過時，建置直接失敗，改用 `KnownIPNetworks`。

其餘關卡：0 warning、`dotnet format` 0 error、文件編碼檢查通過。

## 影響與注意事項

- **限流語意改變**：此前是全站共用配額，現在每個呼叫端各自計算。
  正式環境若走反向代理，**務必設定 `ForwardedHeaders:KnownProxies` 或 `KnownNetworks`**，
  否則所有請求的來源 IP 都會是代理伺服器（全部擠在同一個分割）。
- **`/UploadFiles` 需要登入**才能取用。若既有前端有匿名引用該路徑的資源，需一併調整。
- **上傳類型受限**：預設白名單外的檔案會被擋下並顯示「檔案 X 的類型不在允許清單中。」，
  各案可用 `SystemSettings.Upload.AllowedExtensions` 調整。
- **CSP 尚未導入**，仍列為後續項目。
