# 腳本警告訊息的判讀說明，以及最後一行的亂碼修正（0.9.47）

- 首次實作版本：0.9.47

## 起因

使用者實際跑 `New-StarterProject.ps1` 產生新專案後回報兩件事：

1. 最後印出**八條 `警告:`**，不知道要不要處理
2. 最後一行出現亂碼：`Next: see docs/guides/VS Code ??啣??撠?銝???.md`

## 八條警告：全部不用處理，但有兩條絕對不能改

殘留字串掃描（`New-StarterProject.ps1` 結尾）會命中五類東西：文件裡的範例值、腳本自己的
取代規則、整合測試自帶的金鑰，以及**兩個守門用的比對常數**。

`StartupSafetyValidator.cs:7` 與 `SystemHealthService.cs:24` 的
`DevelopmentSigningKey` 看起來像「漏改的舊專案字串」，其實是**偵測用的樣本**。
跟著改成新代號，等於把偵測器的比對基準一起改掉。

逐條說明已寫進 `docs/guides/腳手架開發指引.md` 新增的 §2.4。

## 更重要的是：真正危險的兩件事不在警告清單裡 🔴

### ① 換掉 JWT 金鑰的同時，兩道 Production 防線一起失效

腳本把 `appsettings.json` 的 `SigningKey` 換成 `<新代號>-ChangeThisJwtSigningKey-AtLeast32Chars`，
值仍是佔位符，但下列兩處都是**精確比對**原字串 `DevelopmentOnly-…`：

| 位置 | 原本擋什麼 | 換過之後 |
|------|-----------|---------|
| `StartupSafetyValidator.cs:18` | Production 仍用開發金鑰 → 中止啟動 | 不再相等，**不擋** |
| `SystemHealthService.cs:227` | 健康監控「身分驗證」標示不健康 | 不再相等，**顯示良好** |

唯一還擋得住的是 `appsettings.Production.json` 的 `"SigningKey": ""` 配上
`[MinLength(32)]` ＋ `ValidateOnStart()`，但那只在**有部署 Production 設定檔**時成立。
少了它，46 字元的佔位符兩道檢查都過得了，服務會帶著一把人人猜得到的金鑰正常啟動。

### ② 腳本宣稱會換掉 `SupportPassword`，但那條規則從未命中

取代規則寫的是 `"SupportPassword": "support"`，範本出貨的是 `appsettings.json:48` 的 `1qaz@WSX` ——
**取代從來沒有發生過**。`StartupSafetyValidator.cs:24` 檢查的同樣是 `"support"`，也不作響。

這是 §2.3「地雷一」與 §9 缺口 #13 記載的問題，只是多了一層：連腳手架腳本都以為自己處理掉了。

**兩者本次都只記錄、未修正**（使用者決定另案處理）。修正會動到守門的比對邏輯與既有測試，
適合當作獨立一次異動。

## 亂碼：腳本缺 UTF-8 BOM

關鍵線索是「警告訊息裡的中文**檔名正常**，只有最後那行**原始碼裡的中文字串**壞掉」——
執行期讀到的路徑沒問題，被錯誤解讀的是**原始檔本身**。

`scripts/New-StarterProject.ps1` 當時沒有 BOM，而 Windows PowerShell 5.1 對無 BOM 的檔案
套用系統 ANSI（本機是 Big5）。同目錄的 `New-CrudModule.ps1` 有 BOM ——
本專案既有慣例沒套到這支腳本上。

### 做了什麼

在 `scripts/New-StarterProject.ps1` 開頭補上 UTF-8 BOM（3 個位元組），**不動任何程式邏輯**。
複製時 `Test-Utf8Bom` 會逐檔保留 BOM 狀態，衍生專案的副本也會帶著 BOM。
