每一批都用同一套方法，並和**改動前在乾淨 main（`ba1686d`，0.10.42）取的基準**比對：

## B.6 獨立審查

審查代理只拿到 diff 與使用者的原則（行為不變，只有根目錄檢查是刻意的改變），逐段和原本的程式比對：

### 1. `UserApi` 誤用防呆

繼承 `CrudApi` 後多了 `UpdateAsync(int, object)`（只回成功與否，會丟掉「管理員改到自己帳號」時伺服器回的新 Token）與 `NameConflictAsync(object)`（只認 409，不回帳號格式不符）。
使用者頁一直正確呼叫 `UpdateAsync(UserDto)` 與 `AccountConflictAsync`。0.10.47 起 `UserApi` 以 `new`＋`[Obsolete(error: true)]` 遮蔽這兩個方法，經 `UserApi` 呼叫就編譯錯誤。
其他繼承 `CrudApi` 的（分類、團隊、專案）沒有這個問題：專案的 JSON 新增／修改端點真的存在（附件另走表單端點）。

### 2. 根目錄檢查的大小寫依作業系統

`RootedFiles.TryResolve`、`BackupStore.TryResolveFullPath`、`SystemSettingsValidator.IsSameOrInside` 原本一律 `OrdinalIgnoreCase`。在分大小寫的檔案系統（Linux）上，
`RootedFiles` 會把只差大小寫的同層資料夾（根目錄 `Files`、路徑走到 `files`）當成在根目錄底下。新增 `Share/Helpers/PathComparison`：
`Current` 在 Windows、macOS（預設檔案系統不分大小寫）是 `OrdinalIgnoreCase`，其他是 `Ordinal`，與 .NET 自己判斷路徑是否分大小寫的規則相同；三處改用它。
**Windows 上行為完全不變**。`VolumeResolver` 只在非 Windows 分支用 `Ordinal`，本來就正確，不動。
三處的風險不同：`RootedFiles` 是放寬方向（真的可能放行）；`BackupStore` 的檔名已被正規式限制成備份檔名格式、不含分隔符號，實際沒有風險，為一致一併改；
系統設定的目錄重疊檢查是保守方向，在 Linux 上只會把 `/data/Backup` 與 `/data/backup` 誤報為重疊，改後正確。
新增 2 個測試：`PathComparison.For` 兩種結果與 `Current` 在目前平台的值；只差大小寫的同層資料夾在不分大小寫的檔案系統上接受（鎖住 Windows 行為不變）、分大小寫的拒絕。
