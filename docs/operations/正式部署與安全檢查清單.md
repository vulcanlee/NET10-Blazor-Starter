## 前端部署方式（0.10.10 起）🔴

0.10.10 起（WASM 遷移 M11）前端 `MyProject.Web.Client` 是獨立的 Blazor WebAssembly 靜態網站（入口頁 `wwwroot/index.html`），`MyProject.Web` 只是 API 主機。兩種部署方式擇一，由 API 主機的 `ClientSettings:BaseUrl` 決定：

| | ① 同站台（預設） | ② 雙站台 |
|---|---|---|
| IIS 站台 | 一個（例如 `https://erp.公司.com`） | 兩個：前端靜態站（例如 `https://app.公司.com`）＋ API 主機（例如 `https://api.公司.com`） |
| `ClientSettings:BaseUrl` | 留空 | 前端的網址 |
| 前端 `wwwroot/appsettings.json` 的 `ApiBaseUrl` | 留空（與網頁同一個網址） | API 主機的網址（發佈參數 `-p:StaticSiteApiOrigin` 填入） |
| 誰提供前端檔案 | API 主機（`MapStaticAssets`＋SPA 回退） | 前端站台的 IIS（`web.config` 的 URL Rewrite 規則） |
| CORS | 不開放（同一個來源，不需要） | 自動允許 `ClientSettings:BaseUrl` 的來源 |

兩種方式都**不需要反向代理**：同站台由 API 主機直接提供前端；雙站台是兩個各自獨立的 IIS 站台。

### ① 同站台：API 主機直接提供前端

- [ ] 照以前一樣發佈 `MyProject.Web`（`dotnet publish src/MyProject/MyProject.Web -c Release`），輸出已經帶著前端的檔案（`wwwroot/index.html`、`_framework/`、樣式與圖檔），部署到一個 IIS 站台；IIS 需求與以前相同（ASP.NET Core Hosting Bundle），不需要 URL Rewrite 模組。
- [ ] 發佈 `MyProject.Web` 時會**另外發佈一次** `MyProject.Web.Client` 到中繼資料夾，拿它處理過的 `index.html`（import map、帶指紋的檔名）覆蓋過去，並逐一確認 `index.html` 引用的 `_framework` 檔案都在輸出裡，對不上就讓發佈失敗；所以發佈會比以前多花一點時間。
- [ ] `ClientSettings:BaseUrl` 留空、前端的 `wwwroot/appsettings.json` 的 `ApiBaseUrl` 也留空。⚠️ 同站台**不要在部署後改** `wwwroot/appsettings.json`：前端檔案由 `MapStaticAssets` 依發佈時產生的清單提供，部署後改內容可能對不上；同站台本來就該留空。
- [ ] 不是 API、也沒有對應檔案的 GET 一律回 `index.html`（由前端路由顯示對應頁面或「找不到頁面」）；`/_framework/` 底下找不到的檔案回 404；`/api/` 底下找不到回 404 的 `ApiResult`。
- [ ] 前端的回應帶 CSP（內容見「速率限制與安全標頭」一節）；`script-src` 要帶 `index.html` 裡 import map 的雜湊，主機在執行時從 `index.html` 算出來，不必手動設定。

### ② 雙站台：前端靜態站＋API 主機

**前端靜態站（例如 `app.公司.com`）**

- [ ] 發佈時帶 API 主機的來源（只要 scheme＋主機＋連接埠，不帶路徑）：`dotnet publish src/MyProject/MyProject.Web.Client -c Release -o <輸出資料夾> -p:StaticSiteApiOrigin=https://api.公司.com`。輸出根目錄是 `web.config`＋`wwwroot\`（網站檔案在 `wwwroot\` 底下）；IIS 站台的**實體路徑指向輸出根目錄**（不是 `wwwroot`），`web.config` 的規則會把網址對到 `wwwroot\`。
- [ ] IIS 要安裝 **URL Rewrite 模組**（SPA 回退、預先壓縮的 `.br` 檔與標頭改寫都靠它；沒裝時站台會回 500.19）。靜態站不需要 ASP.NET Core Hosting Bundle。
- [ ] 應用程式集區的「.NET CLR 版本」設為 **沒有受控碼**（純靜態檔，不跑 .NET）。
- [ ] `-p:StaticSiteApiOrigin` 在發佈時同時填好兩個地方，兩處一致：
      1. `wwwrootppsettings.json` 的 `ApiBaseUrl` → `https://api.公司.com/`（前端呼叫 API 的網址）。
      2. `web.config` 裡 `Content-Security-Policy` 的 `connect-src` → `connect-src 'self' https://api.公司.com`（沒有的話瀏覽器會擋下所有 API 呼叫，主控台出現 CSP 錯誤，系統無法使用）。
      兩處一律從專案裡的範本重寫：同一個輸出資料夾重新發佈也照樣填好；**不帶參數就回到空白**（同站台的設定），雙站台每次發佈都要帶。參數格式不對（帶路徑、`?`、`#`，或不是 http(s)）時發佈直接失敗。
      ⚠️ 不要在部署後手改輸出裡的這兩處：下次發佈會被蓋回去；0.10.11 起手改還會讓 Service Worker 安裝失敗、使用者卡在舊版（見「PWA 與離線」）。
- [ ] `web.config` 的 `script-src` 裡 `sha256-…` 是 `index.html` 裡 import map 的雜湊，**發佈時由 `MyProject.Web.Client.csproj` 自動填入**（每次建置的檔名指紋不同）——不要手改，也不要把舊的 `web.config` 整份蓋回新版（雜湊對不上時瀏覽器會擋下 import map，WebAssembly 載不起來）。
- [ ] `web.config` 已設定：MIME（`.wasm`、`.dll`、`.webcil`、`.dat`、`.blat`、`.pdb`、`.json`、`.woff(2)`，0.10.11 起加 `.webmanifest`）、瀏覽器接受 Brotli 時送預先壓縮的 `.br`（IIS 自己的靜態與動態壓縮關掉）、`_framework` 找不到的檔案回 404（不回 `index.html`）、其他網址回 `index.html`；快取 `index.html` 等一律 `no-cache`、`_framework` 底下帶指紋的檔案 `public, max-age=31536000, immutable`（只套用在 200 回應：部署途中新的 `index.html` 先上線、檔案還沒複製完時，404 不會被快取一年）；安全標頭與 API 主機相同（`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Strict-Transport-Security: max-age=2592000`〔與 API 主機的 `UseHsts` 一樣 30 天〕、CSP），`/Auths/ResetPassword` 另加 `Referrer-Policy: no-referrer` 與 `Cache-Control: no-store`。
- [ ] 靜態站要有 HTTPS 繫結：`web.config` 已加 HSTS（`max-age=2592000`，瀏覽器只在 https 回應採用；Token 存在前端網址的 storage，前端更需要只走 https）。
- [ ] ⚠️ **上線前在真的 IIS 驗證一次靜態站**：`web.config` 的 URL Rewrite 規則（SPA 回退、`.br` 與標頭改寫、快取、重設密碼頁）只有 IIS 才會執行，本機與自動化測試只能解析 XML（`StaticSiteWebConfigTests`）；M11 的雙站台實機是用照這些規則寫的 Node 模擬靜態站跑的。至少確認：深層網址（例如 `/projects`）重新整理拿到頁面、`_framework` 的 `.wasm` 回 `Content-Encoding: br` 與正確的 `Content-Type`、`index.html` 是 `no-cache`、回應帶 CSP 與 HSTS、登入後換幾頁主控台沒有 CORS 或 CSP 錯誤、附件能下載；0.10.11 起另確認 `manifest.webmanifest` 回 200 與 `application/manifest+json`、Service Worker 註冊成功（見「PWA 與離線」）。

**API 主機（例如 `api.公司.com`）**

- [ ] 發佈與部署 `MyProject.Web` 照舊（輸出一樣帶著前端檔案，雙站台時不會提供，不影響）。
- [ ] `ClientSettings:BaseUrl` 填前端的網址，例如 `https://app.公司.com/`：必須是完整的 http(s) 網址、不帶 `?` 或 `#`，**Production 必須是 https**，寫錯網站不會啟動（事件檢視器有說明）。
- [ ] 填了之後 API 主機的行為：
      - 只提供 API：不是 `/api` 的路徑一律 404（Swagger、健康檢查、Google 登入的端點照常）。
      - CORS 只允許 `ClientSettings:BaseUrl` 的來源，加上 `Cors:AllowedOrigins`（前端以外還有別的網站要呼叫 API 時才填）；只收 `Authorization`、`Content-Type` 兩個標頭與 GET／POST／PUT／DELETE，公開 `Content-Disposition`（下載檔名），不帶憑證（不用 Cookie）；預檢（OPTIONS）在驗證與限流之前回應，快取 10 分鐘。
      - Google 登入完成、被拒絕與錯誤頁一律導回 `ClientSettings:BaseUrl`（只用設定值，不採用請求的 Host）。
      - 所有信中連結（重設密碼、站內通知、巡檢報告、例外告警）一律以 `ClientSettings:BaseUrl` 開頭，蓋過 `EmailSettings:PublicBaseUrl`（Production 用 Smtp 時可以不填 `PublicBaseUrl`）。
- [ ] 有用 Google 登入時：Google Cloud Console 的「已授權的重新導向 URI」是 **API 主機**的 `https://api.公司.com/signin-google`（回呼在 API 主機，登入完成再導回前端的 `/Auths/Login#code=…`）；「已授權的 JavaScript 來源」不需要。
- [ ] 驗收：從前端網址登入、換幾頁，瀏覽器開發者工具的「網路」看得到 `/api` 請求都打到 API 主機、主控台沒有 CORS 或 CSP 錯誤；用「忘記密碼」寄一封信，確認信中連結是前端的網址。

> API 主機與前端靜態站是**兩份不同的 `web.config`**：API 主機的（`MyProject.Web/web.config`，含 aspNetCore 處理常式與 4 GB 上傳上限）與靜態站的（`MyProject.Web.Client/web.config`，只在發佈 Client 時放進輸出根目錄）。不要互相複製。

## PWA 與離線（0.10.11 起）🟡

前端是 PWA：Service Worker 把前端的程式檔快取在瀏覽器（**不快取 API、資料或 Token**），斷線時畫面不卡死、底部出現離線提示列，恢復連線後自動復原；可以安裝到桌面或手機主畫面。同站台與雙站台都適用。

- [ ] **前端網址必須是 HTTPS**：Service Worker 只在 HTTPS（或 localhost）生效。用 http 的內部網址部署時沒有離線、安裝與新版本提示（其他功能照常）。
- [ ] 雙站台的靜態站 `web.config` 要有 `.webmanifest` 的 MIME（`application/manifest+json`；0.10.11 起的範本已加，IIS 預設不認得、會回 404）。升級時用新版發佈輸出的 `web.config`，不要把舊的整份蓋回去。
- [ ] `service-worker.js`、`service-worker-assets.js`、`manifest.webmanifest` 必須是 `no-cache`（預設就是；不要替它們另設長效快取，否則瀏覽器查不到新版本）。這三個檔案與 `appsettings.json` 沒有 `.br`／`.gz` 副本是正常的（刻意不產生，清單在 `MyProject.Web.Client/FrontendCompression.props`，同站台與靜態站發佈都套用；有副本時伺服器會優先送出過期的版本）。
- [ ] **部署新版的行為**：使用者部署後第一次開頁仍是舊版（從快取），瀏覽器同時下載新版；下載完畫面底部出現「有新版本，按這裡重新整理」，**按下才換成新版**（或關掉這個網站的所有分頁再開）。不會強制重新載入（使用者可能正在編輯）。
      ⚠️ 換版前舊前端仍會呼叫新 API：API 的改版要相容上一版前端，不相容的改版請通知使用者按提示列或重新整理。
- [ ] 部署途中不要讓使用者看到半套檔案：先把整份發佈輸出放好再切換站台（Service Worker 安裝時以 integrity 驗證每個檔案，缺檔或內容不符時新版安裝失敗、使用者留在舊版，下次開頁再試）。
- [ ] 🔴 **部署後不可手改任何前端檔案**（`appsettings.json`、`theme.css`、圖片、`index.html`……），**一律改原始碼後重新發佈**（雙站台改 API 網址用 `-p:StaticSiteApiOrigin`，發佈時同步更新 Service Worker 資產清單上的雜湊與版本）。Service Worker 安裝時以資產清單的 integrity 驗證每個檔案：手改的檔案雜湊對不上，**新版 Service Worker 整個安裝失敗**，現有使用者一直停在舊版（不會出現「有新版本」提示列），而且**那個修改本身也不會生效**——Service Worker 一直回快取裡的舊檔。0.10.10 以前「`index.html` 與 `appsettings.json` 是 `no-cache`、改了立刻生效」的說法 0.10.11 起不再成立。新版安裝失敗時，前端會經瀏覽器錯誤回報記到伺服器：API 主機日誌與系統例外紀錄出現一筆來源「瀏覽器」、訊息以 `Service worker installation failed…` 開頭的錯誤（使用者登入後才送出）——部署後看到它，就是有檔案和資產清單對不上。
- [ ] **只改伺服器的安全標頭（CSP 等）時要重新發佈前端**：Service Worker 把入口頁 `index.html` 連同當時的回應標頭一起存進快取，之後導覽都回這一份。同站台的 CSP 由 API 主機執行時算、雙站台在靜態站的 `web.config`；只改了標頭、前端檔案沒變時，資產清單版本不變，使用者會一直沿用安裝當時的標頭。要讓新標頭生效，前端版本必須變動（重新發佈前端，有建置內容的異動本來就會升版）。
- [ ] **伺服器停機或部署中（IIS 回 502／503／504）時**：前端視同連不上伺服器，保留登入，畫面顯示「目前無法連線到伺服器，恢復連線後會自動重新載入。」或「目前無法連線到伺服器，請稍後再試。」；伺服器恢復後（探測拿到非 5xx 的回應）自動重新載入，不必請使用者重新登入；使用者操作到一半剛好遇到 Token 刷新也不會被登出（0.10.10 以前會）。
- [ ] 已安裝的 App 名稱與顏色來自 `MyProject.Web.Client/wwwroot/manifest.webmanifest`（固定值；系統參數頁改系統名稱不會改到它）。首次載入畫面的系統名稱同樣是固定值（`index.html`、`Commons/ClientLoadingScreen.razor`，0.10.13 起）。
- [ ] 驗收（瀏覽器開發者工具 →「應用程式」）：Service Worker 已啟用、「快取儲存空間」只有一個 `offline-cache-<範圍>:<版本>`（根目錄部署是 `offline-cache-%2F:…`）且裡面沒有 `/api/` 的項目、Manifest 沒有錯誤；「網路」切成離線後重新整理，畫面仍開得起來並出現離線提示列；切回線上後自動恢復。
- [ ] 已知：Material Icons 字型由 Google Fonts 載入、不快取，離線時圖示會顯示成文字；離線時資料畫面需要連線（不做離線資料快取與同步）。

## 退版／移除 Service Worker（0.10.11 起）🔴

0.10.11 起使用者的瀏覽器裝了 Service Worker，**導覽一律先回快取的前端**。下列情況，已裝過的使用者會卡在快取裡的舊前端，而且**沒有任何提示**：

- 退版到 0.10.10 以前（那些版本沒有 `service-worker.js`：瀏覽器檢查更新拿到 404，舊的 Service Worker 照樣留著，繼續提供 0.10.11 的前端去呼叫退版後的 API）。
- 決定拿掉 PWA（不再註冊 Service Worker）。
- 從同站台改成雙站台，而**原本的網址改當 API 主機**（API 主機不提供前端檔案，原網址上的 Service Worker 會一直提供舊前端）。若原網址改當前端靜態站、API 換新網址，新前端的 Service Worker 會照一般的新版本流程換上，不需要這一節。

處理方式：在**原網址**的 `/service-worker.js` 部署一支「自我註銷」的 Service Worker，取代已安裝的那一支。

```js
// 自我註銷的 Service Worker：清掉 PWA 的快取、註銷自己，並重新載入已開著的分頁，之後瀏覽器直接向伺服器取前端。
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', event => event.waitUntil((async () => {
    const keys = await caches.keys();
    // 只刪這個範圍的快取（名稱是 offline-cache-<encodeURIComponent(範圍路徑)>:<版本>），同一來源其他路徑的系統不受影響。
    const prefix = `offline-cache-${encodeURIComponent(new URL(self.registration.scope).pathname)}:`;
    await Promise.all(keys.filter(key => key.startsWith(prefix)).map(key => caches.delete(key)));
    await self.registration.unregister();
    const clients = await self.clients.matchAll({ type: 'window' });
    await Promise.all(clients.map(client => client.navigate(client.url)));
})()));
```

- [ ] **放在哪裡**：
      - 同站台：放在 API 主機提供的前端 `wwwroot/service-worker.js`。同站台的檔案由 `MapStaticAssets` 依**建置時**產生的清單提供（長度、ETag 都記在清單裡），直接覆蓋發佈輸出裡的檔案不可靠：請放進原始碼再發佈——退回 0.10.10 以前時新增 `MyProject.Web.Client/wwwroot/service-worker.js`；0.10.11 以後的版本要拿掉 PWA 時，把這段寫進 `service-worker.published.js`（發佈時它會取代 `service-worker.js`），並一併拿掉 `index.html` 的 `js/pwa.js` 與 manifest 連結，否則新前端又會再註冊一次。
      - 雙站台：放在靜態站根目錄的 `wwwroot/service-worker.js`（IIS 直接提供實體檔，可以直接放；維持 `no-cache`）。
      - 同站台改雙站台、原網址改當 API 主機：API 主機的雙站台模式不提供前端檔案，所以**先**以同站台部署一版帶自我註銷 `service-worker.js` 的版本，等使用者都換掉後再切成雙站台。
- [ ] **保留一段時間**：瀏覽器要等使用者下一次開這個網站時檢查更新才會抓到它；建議至少保留到所有使用者都開過一次（例如一到兩個月）。IIS 的存取記錄裡還有 `/service-worker.js` 的請求，就代表還有瀏覽器沒換掉。
- [ ] 它會在啟用時**直接重新載入**已開著的分頁（不會出現提示列），請避開使用者正在編輯的時段部署。
- [ ] 驗收：開發者工具「應用程式」裡 Service Worker 已註銷、「快取儲存空間」沒有這個範圍的 `offline-cache-…`；重新整理拿到的是伺服器上目前的前端。

## 網頁登入效期與純 Token 登入（0.10.8 起）🔴

0.10.8 起網頁不再發登入 Cookie：登入成功後瀏覽器只拿到 Token（勾「記住我」存在 localStorage、沒勾存在 sessionStorage），每個請求以 Bearer 帶上。效期設定從 `CookieSettings` 改名為 `SessionSettings`。

- [ ] 依公司規定檢視 `SessionSettings`：
      - `IdleTimeoutMinutes`（預設 480）：沒勾「記住我」時，多久沒使用就要重新登入；**關掉分頁也會登出**（Token 在 sessionStorage）。
      - `IdleTimeoutSliding`（預設 `true`）：`true` 每次使用重新起算；`false` 從登入起最多 `IdleTimeoutMinutes` 分鐘，一直使用也會到期。
      - `RememberMeDays`（預設 30）：勾了「記住我」時整個登入最長幾天（從登入那一刻算，不延長）。
      - `AccessTokenMinutes`（預設 15）：網頁的存取 Token 效期，到期前畫面自動換新；不建議調長。
      - `ValidationIntervalMinutes`（預設 5）：改密碼、停用、強制登出之後，**其他主機**最晚幾分鐘內看到（同一台主機是立即的）。
- [ ] **升級時**：設定檔、`appsettings.Production.json` 或環境變數裡若還有 `CookieSettings:ExpireMinutes`／`RememberMeDays`／`ValidationIntervalMinutes`／`SlidingExpiration`，仍然有效（蓋過 `SessionSettings`），啟動日誌會記一筆警告。確認數值後改成 `SessionSettings` 的鍵（`ExpireMinutes` → `IdleTimeoutMinutes`、`SlidingExpiration` → `IdleTimeoutSliding`），再把舊鍵刪掉。
- [ ] **升級到 0.10.8 後每個人都要重新登入一次**（原本的登入 Cookie 不再被讀取）；兩步驟驗證「記住這台裝置」也要重新勾一次（原本記在 Cookie）。安排在離峰時間升級並事先公告。
- [ ] 同一個瀏覽器只有一個身分（與以前的 Cookie 相同）：在其中一個分頁換人登入，其他分頁會改成那個人；要同時用兩個帳號請用不同的瀏覽器或無痕視窗。
- [ ] 沒有主要角色的帳號不能用網頁登入（網頁的 Token 一律回 403 `NO_PRIMARY_ROLE`，畫面會登出）；App 的 API 登入不受影響。
- [ ] 有用 Google 登入時：Google Cloud Console 的「授權重新導向 URI」維持 `https://<正式網域>/signin-google`（沒有改；0.10.10 起雙站台時是 API 主機的網域，見「前端部署方式」）。0.10.8 起回呼後不發 Cookie，而是產生 60 秒、只能用一次的代碼，導回 `/Auths/Login#code=…` 由登入頁換成 Token；代碼綁定發起登入的那個瀏覽器分頁。舊書籤直接打 `/Auths/Google/Login`（沒帶瀏覽器綁定值）會回登入頁，從登入頁按「使用 Google 登入」即可。
- [ ] 確認正式環境的 `Security:ReturnExceptionDetails` 為 `false`（`appsettings.Production.json` 出貨值；未設定時只有 Development 會在 `ApiResult.Exception` 回傳例外細節，由 `ExceptionDetailPolicy` 統一判斷）。設成 `true` 時，任何呼叫 API 的人（瀏覽器開發者工具、App）都會在 500 回應裡看到例外型別、訊息與堆疊。錯誤通知「複製」附完整例外則與此設定無關，只有管理員可以（`PagePermissions.MayCopyErrorDetail`；0.10.7 以前 Server 頁面才另依此設定對所有使用者放行）。

### 附件上傳與下載票證（0.10.3 起）🟡

- [ ] **部署後確認網站目錄的 `web.config` 含 `<requestLimits maxAllowedContentLength="4294967295" />`**（發佈時 SDK 會把 aspNetCore 處理常式合併進原始碼的 `web.config`，這一段應該保留；雙站台時指的是 **API 主機**的 `web.config`，前端靜態站的 `web.config` 是另一份，上傳不經過它）。少了它 IIS 只收約 28.6 MB 的請求，較大的附件在存檔時直接被 IIS 擋下（404.13），程式完全收不到、也沒有日誌。若部署流程會覆寫或另外產生 `web.config`，要把這一段加回去。
- [ ] **IIS 應用程式集區維持一個背景工作處理序**（「最大背景工作處理序數」= 1，預設值；不要開網頁花園）。一次性下載票證只存在發票證那個行程的記憶體，多個處理序時票證會被另一個處理序當成無效，下載回 404。集區回收（含重疊回收）只會讓還沒用的票證失效，使用者重按一次檔名即可。
- [ ] 匿名的 `GET /api/v1/downloads/{票證}` 是刻意開放的（票證本身就是憑證：60 秒、只能用一次，兌換時重新檢查使用者與權限）。若前面有反向代理或 WAF 會記錄完整網址，票證會出現在記錄裡；票證用過即失效，風險有限，但仍建議限制這類記錄的存取。
- [ ] 已知限制：公司若統一安裝會預先抓取網址的下載管理員或瀏覽器擴充功能（或代理伺服器會先掃描下載），票證會先被用掉，使用者下載得到 404「下載連結無效或已過期」，再點一次即可；頻繁發生時把這個網站排除在預先抓取之外。
- [ ] 雙站台（0.10.10 起）下載是跨來源：瀏覽器會忽略 `<a download>` 而整頁導過去，所以前端改以 `fetch` 取回整個檔案、在瀏覽器記憶體組成 blob 再存檔（不經過 WASM）。⚠️ 檔案先整個下載完才出現存檔，大檔（例如數百 MB 的備份）會佔用相同大小的瀏覽器記憶體，也看不到瀏覽器的下載進度；大型備份建議同站台部署或直接從伺服器的備份目錄取得。失敗（票證失效、權限已失去）時畫面顯示伺服器的訊息、留在原頁。

### AI 逐字顯示（NDJSON 串流，0.10.5 起）🟢

日誌檢視的 AI 分析、系統例外紀錄的 AI 例外分析改在 WebAssembly 頁面執行，AI 回覆經 `application/x-ndjson` 回應一行一行送到瀏覽器（程式已關閉回應緩衝，並送 `Cache-Control: no-cache, no-transform`、`X-Accel-Buffering: no`）。

- [ ] **IIS 不要壓縮或緩衝 `application/x-ndjson`**：它不在 IIS 動態壓縮的預設類型內，預設就沒問題；若主機的 `httpCompression` 把 `*/*` 或 `application/x-ndjson` 加進 `dynamicTypes`，請把它排除（`web.config` 有註解說明）。
- [ ] **前面有反向代理（ARR、nginx、負載平衡器、WAF）時，關閉這類回應的緩衝**：nginx 會看 `X-Accel-Buffering: no`；其他代理請依產品設定關閉回應緩衝，並確認不會因為長時間沒有新資料就切斷連線（AI 第一個字可能要等好幾分鐘）。
- [ ] 驗收：在日誌檢視頁按「AI 分析」，回覆應該一段一段出現。若等很久才一次整段出現，功能仍正常（稽核與用量紀錄不受影響），只是中間有壓縮或緩衝，照上兩點排除。
- [ ] `RateLimit:ApiRequestsPerMinute`（預設每人每分鐘 120 次）：WASM 頁面每次整頁載入要換 Token、讀外框與選單，連續快速換頁的人可能被限流；0.10.5 起被限流時畫面顯示「請求過於頻繁，請稍後再試。」與「重新整理」按鈕，不會被登出。使用者常遇到時再調高。

### Agent、工作流程與通知推播的長連線（0.10.7 起）🟡

Agent 測試台、系統管理助理、Agent 工作流程改在 WebAssembly 執行，對話與執行同樣走 NDJSON 串流；另外每個開著的分頁有一條**通知推播**長連線（`POST /api/v1/notifications/stream`），鈴鐺、公告與首頁「我的通知」因此幾乎即時更新。串流閒置時會送心跳（Agent 與工作流程每 15 秒、推播每 25 秒），推播連線最長 30 分鐘就由伺服器結束、瀏覽器自動重連。

- [ ] **IIS 與反向代理不可緩衝 `application/x-ndjson`**（同上一節）：被緩衝時推播的變動要等緩衝滿才送出，鈴鐺看起來就跟沒有推播一樣（仍有 60 秒輪詢，不會漏）。
- [ ] **閒置逾時要大於心跳間隔**：反向代理、負載平衡器、WAF 的「閒置連線逾時」（例如 Azure 負載平衡器預設 4 分鐘、AWS ALB 預設 60 秒、nginx `proxy_read_timeout` 預設 60 秒）至少要大於 **30 秒**（推播心跳 25 秒）；建議 120 秒以上。IIS ARR 的 `proxy timeout` 同理。太短時連線會被切斷再重連，功能仍正常但會多出許多重連。
- [ ] **建議用 HTTP/2**（IIS＋HTTPS 預設就是）：HTTP/1.1 下瀏覽器每個網域最多 6 條連線，每個分頁的推播長連線各佔一條。程式限制每位使用者最多 3 條推播連線（第 4 個分頁起只靠 60 秒輪詢），保留另外 3 條給一般 API；HTTP/2 沒有這個問題。只有本機以 http 開發時是 HTTP/1.1。
- [ ] **應用程式集區維持一個背景工作處理序**（同上方「附件上傳與下載票證」）：工作流程停在等人回覆時，執行留在**發起那個行程的記憶體**最多 30 分鐘，重新整理後才接得回來；Agent 對話的「每段對話一把鎖」與推播的連線數也只在單一行程內有效。集區回收或重新部署時，等人回覆的工作流程會變成「中斷」（紀錄留在最後一次存檔），推播連線會自動重連。
- [ ] 不想要推播（例如代理伺服器無法調整、或要減少長連線）：設 `NotificationSettings:PushEnabled=false`（預設 `true`），端點回 404、外框不連，鈴鐺與公告退回 60 秒輪詢；改了之後新的連線立即生效（已開著的分頁重新整理後生效）。
- [ ] 推播連線不記「慢請求」日誌；看到每 30 分鐘一次的重連屬正常。
- [ ] 驗收：開兩個分頁登入同一個管理員，在其中一個到「系統健康監控」按「發送測試通知」，另一個分頁的鈴鐺應在幾秒內出現數字。

- [ ] 上線後到「系統健康監控」確認「寄信服務」為綠燈，並用「寄出測試信」寄一封給自己。
- [ ] 啟用寄信即開放「忘記密碼」（0.9.60 起）：確認使用者的 Email 都登記正確；用一個測試帳號實際走一次
      忘記密碼 → 收信 → 重設 → 登入，並確認信中連結是 `PublicBaseUrl` 的網域（雙站台時是 `ClientSettings:BaseUrl` 的前端網域）。
- [ ] 評估 `PasswordResetSettings`（連結效期 30 分、同帳號冷卻 60 秒）；冷卻是唯一的濫用防線，不建議調成 0。
- [ ] 若 IIS 開了 W3C 日誌，注意它會記下重設連結的完整網址（含 token）：縮短日誌保存期或限制存取。

## 速率限制與安全標頭（0.4.35 起）
- [ ] 依本案流量特性檢視 `RateLimit:ApiRequestsPerMinute`（預設 120）與 `RateLimit:LoginRequestsPerMinute`（預設 10）。
- [x] 限流**依呼叫端分割**（已驗證身分優先，其次來源 IP），不再是全站共用單一計數器。0.10.8 起限流排在驗證之後，「已登入每人一份」才真的生效（之前全部依 IP 分區，同一個出口 IP 的所有人共用一份配額）。
- [x] 較嚴格的登入配額（`LoginRequestsPerMinute`，每 IP）算進：App 的 `/api/Auth/login`、兩步驟驗證（登入第二步與自己的設定）、Google 代碼兌換、忘記／重設／變更密碼、新分頁取得 Token（`session/fork`）。**網頁登入（`login/web`）與登入頁設定（`login-settings`）不算**：網頁登入照以前畫面登入的做法，防猜密碼靠帳號鎖定，並受一般 API 的每 IP 配額限制 —— 不然同一個出口 IP 的公司早上登入尖峰會被擋。
- [ ] **走反向代理時必須設定 `ForwardedHeaders:KnownProxies` 或 `KnownNetworks`**：
      未設定時所有請求的來源 IP 都會是代理伺服器（全部擠在同一個限流分割，
      0.9.117 起「稽核紀錄」的來源 IP 也會全部變成代理的 IP），且呼叫端可自行偽造 `X-Forwarded-For`。
      IIS in-process 或直接 Kestrel 不經代理，不需設定。
- [x] 回應含 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`（0.10.10 起雙站台的前端靜態站由它的 `web.config` 加上同樣的標頭）。
- [x] Host 標頭空白或組不成網址的請求直接回 400（0.9.115 起，`UseRejectInvalidHost`；`AllowedHosts` 擋不到空白 Host）。掃描器常送這種請求，日誌只會記一筆 Information，不會再連記多筆 ERROR。
- [x] **前端有 CSP**（0.10.10 起；0.10.9 以前沒有）：
      `default-src 'self'; script-src 'self' 'wasm-unsafe-eval' 'sha256-<import map 的雜湊>'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; object-src 'none'`。
      同站台由 API 主機加在前端的回應上（Swagger UI 不套用；import map 雜湊在執行時從 `index.html` 算）；雙站台由靜態站的 `web.config` 加（雜湊發佈時自動填入），內容兩邊一致（`StaticSiteWebConfigTests` 守門）。
      `'wasm-unsafe-eval'` 是 WebAssembly 編譯所需；`'unsafe-inline'` 只在 `style-src`（AntDesign 會注入行內樣式）；`img-src data:` 給兩步驟驗證的 QR Code。
      0.10.13 起**只有 Development** 的同站台主機在 `connect-src` 另外允許 `http(s)://localhost:*`、`ws(s)://localhost:*`（Visual Studio 瀏覽器連結與熱重載）；正式環境（`ASPNETCORE_ENVIRONMENT` 不是 Development）與靜態站 `web.config` 不含 localhost —— 上線前用瀏覽器開發者工具看一次回應標頭確認。
- [ ] 雙站台時靜態站 `web.config` 的 `connect-src` 要有 API 主機的來源：發佈前端時帶 `-p:StaticSiteApiOrigin=https://api.公司.com` 就會填入（見「前端部署方式」）。
- [ ] 要加外部資源（別的字型、圖片、分析工具的網址）時，要同時改 `MyProject.Web/Hosting/FrontendContentSecurityPolicy.cs` 與 `MyProject.Web.Client/web.config`，否則會被瀏覽器擋下。
- [x] 已知：AntDesign 頁籤在 HTML 上加了行內事件 `ondragover="event.preventDefault();"`，會被 CSP 擋下而在主控台出現一則違規訊息；本專案頁籤不開放拖曳、點選走 Blazor 事件，不影響功能，所以刻意不加 `'unsafe-hashes'`。

## Data Protection 金鑰（兩步驟驗證與記住裝置靠這一節）🔴

0.10.8 起網頁不發登入 Cookie，登入本身改用 JWT（簽章金鑰是 `JwtSettings:SigningKey`，不在金鑰環裡），但下列東西仍然用 Data Protection 的金鑰加密 ——
**金鑰換一批，它們全部失效**：

| 用金鑰環加密的 | 金鑰換一批的後果 |
|---|---|
| 兩步驟驗證的密鑰（0.9.104 起） | 所有開啟兩步驟驗證的人驗證碼一律不正確、登入不了（見下方最後一項） |
| 兩步驟驗證「記住這台裝置」的 Token（0.10.8 起） | 記住過的裝置下次登入要重新輸入驗證碼 |
| 登入第二步的待驗票證（5 分鐘）、兩步驟驗證設定票證（15 分鐘）（0.10.8 起） | 正在登入或設定到一半的人要重來 |
| Google 登入過程的暫存外部 Cookie（5 分鐘）、防偽 Cookie | 正在進行 Google 登入的人要重來 |

0.9.39 之前完全沒有設定，金鑰走框架預設位置；本節的檢查項就是為了不再重蹈覆轍。

- [ ] `SystemSettings:ExternalFileSystem:DataProtectionKeyPath` 已指向**應用程式重新部署後
      仍然存在**的目錄（不要放在會被發行流程清掉的位置），且執行身分對它有**讀寫**權限。
- [ ] 部署後確認該目錄底下**真的有產生 `key-*.xml`**。沒有就是設定沒生效。
- [ ] **IIS**：應用程式集區的**識別身分固定不變**。⚠️ Windows 上金鑰檔預設以 **DPAPI** 加密，
      換了識別身分即使檔案還在也**解不開**。
- [ ] **IIS**：建議把應用程式集區的 `loadUserProfile` 設為 `true`。
      ⚠️ 未載入使用者設定檔時，框架預設會退化成「金鑰只存在記憶體」——
      **每次回收就換一批**（IIS 預設 20 分鐘閒置關閉、29 小時定期回收）。
- [ ] **多機／多節點**：所有節點必須**共用同一個金鑰目錄**（或改用集中式金鑰儲存），
      否則票證與記住裝置 Token 在另一台解不開（登入第二步失敗、記住的裝置被要求重新驗證）。
      另外 Google 登入的一次性代碼與票證的「已用過」紀錄只在單一行程的記憶體：Google 回呼與兌換要落在同一台（要黏著工作階段），
      同一張待驗票證最多在每台各用一次（每次仍要通過驗證碼）。
- [ ] 確認 `MagicObjectHelper.DataProtectionApplicationName` 未被改動。
      ⚠️ 它是金鑰環的用途判別子，**改了等於讓上表的東西全部失效**；
      不固定它的話，連「換一個部署目錄」都會失效。
- [ ] 金鑰目錄納入備份，且**不可**納入版本控制或公開的檔案分享。
- [ ] 0.9.104 起金鑰環也加密兩步驟驗證的密鑰：⚠️ 金鑰換一批，**所有開啟兩步驟驗證的人都登入不了**（驗證碼一律不正確），只能由管理員逐一「重設兩步驟驗證」。support 不受強制，是這時的救援入口。

> 相關設定與行為說明見 [日誌與設定檔說明 §4.6](日誌與設定檔說明.md)
> 與 [腳手架開發指引 §3.4](../guides/腳手架開發指引.md)。

## 排程作業（0.9.96 起）🟡

**排程作業跑在網站行程裡：應用程式集區停了，排程就跟著停。** IIS 預設閒置 20 分鐘就關閉集區，
半夜沒有人使用時，03:00 的清除作業根本不會執行（下次有人連上時才補跑一次）。

- [ ] **IIS**：應用程式集區的「啟動模式」設為 **AlwaysRunning**，「閒置逾時（分鐘）」設為 **0**。
- [ ] **IIS**：站台的「預先載入已啟用」（`preloadEnabled`）設為 **true**，回收後不必等第一個請求就會啟動。
- [ ] 部署後到「排程作業」頁確認十四個作業（稽核紀錄、系統例外紀錄、AI 對話紀錄、Agent 對話、Token 用量紀錄、站內通知、寄信紀錄、巡檢報告、登入 Token 九個清理作業＋已刪除資料清理、系統備份、稽核紀錄完整性檢查、密碼到期提醒、系統管理助理巡檢）都有「下次執行」時間；隔天確認「上次執行」是成功。
      「系統健康監控」的「排程作業」項目若顯示逾期，通常就是上面兩項沒設好。
- [ ] 多台機器共用同一個資料庫時，同一時段只會有一個行程執行（資料庫搶占）；若只想讓特定一台跑排程，
      其他台設 `ScheduledJobSettings:Enabled = false`。
- [ ] 資料庫檔旁的 `*.job-<作業名稱>.lock` 是作業的檔案鎖，**停站時可以刪除**，網站執行中不要動它。
- [ ] 關機時正在執行的作業會被中斷並記為「中斷」；長時間的作業（例如系統備份、系統管理助理巡檢）要留意 IIS 的關機時限（`shutdownTimeLimit`）。

> 設定見 [日誌與設定檔說明 §4.11](日誌與設定檔說明.md) 的 `ScheduledJobSettings`；規則見 [排程作業 PRD](../prd/排程作業-prd.md)。

## 系統備份（0.9.99 起）🔴

- [ ] `SystemSettings:ExternalFileSystem:BackupPath` 改到資料碟上的獨立目錄（不可與其他資料目錄重疊、不可在網站目錄底下，啟動時會檢查）。
- [ ] `BackupPath` 的 NTFS 權限只給應用程式集區身分與系統管理員 —— ⚠️ 備份不加密且含金鑰環，拿到的人可以偽造登入。
- [ ] 部署後到「系統備份」頁按「立即備份」確認成功；隔天確認 02:00 的自動備份成功。
- [ ] 安排**異地保存**（至少每週把最新一份複製到另一台主機或檔案伺服器）與每季一次的**還原演練**（[備份與還原操作手冊](備份與還原操作手冊.md)）。
- [ ] IIS 應用程式集區的定期回收時間避開 02:00。
- [ ] 0.10.6 起「下載」走一次性票證（與附件相同，見上方「附件上傳與下載票證」）：**不能續傳**，大檔下載中斷要回頁面再按一次；異地保存建議直接從 `BackupPath` 以檔案複製，不要靠瀏覽器下載。票證只在發票證的那個行程有效，應用程式集區要維持一個背景工作處理序。
- [ ] `appsettings*.json` 與環境變數不在備份裡，另外保存一份。

## 稽核紀錄防竄改金鑰（0.9.175 起）🔴

每筆稽核紀錄都用 `AuditKeyPath` 裡的金鑰（`audit-hmac.key`，第一次寫稽核時自動產生）簽章，每天 03:30 的排程「稽核紀錄完整性檢查」會重算簽章，發現被改、被刪就通知全體管理員並寄信。金鑰**刻意不進系統備份**（金鑰和資料庫在一起，拿到備份的人就能重算簽章）。

- [ ] `SystemSettings:ExternalFileSystem:AuditKeyPath` 改到資料碟上的獨立目錄（必須是絕對路徑，不可與其他資料目錄或 `BackupPath` 重疊、不可在網站目錄底下，啟動時會檢查）。
- [ ] `AuditKeyPath` 的 NTFS 權限**只給應用程式集區身分與系統管理員**。⚠️ 同時拿到資料庫與金鑰檔的人可以改紀錄而不被發現。
- [ ] 部署並有人登入後，確認目錄底下產生了 `audit-hmac.key`；隔天確認還多了 `audit-chain-checkpoint.json`，且「稽核紀錄完整性檢查」是成功。
- [ ] 把 `audit-hmac.key` **另外離線保存一份**（例如公司的密碼保管庫），**不要和系統備份放在一起**。
- [ ] 換主機時，把金鑰檔複製到新主機**同樣的 `AuditKeyPath`** 再啟動網站；沒帶過去的話系統會自動產生新金鑰，之前的紀錄只能顯示「金鑰不同」、無法驗證內容，而且第一次檢查會回報「金鑰變更」。
- [ ] 從備份還原資料庫後，下一次檢查會回報一次「資料庫回退」並通知管理員，這是預期的（見[備份與還原操作手冊](備份與還原操作手冊.md)）。

## 系統參數（0.9.98 起）🟡

管理員可在「系統參數」頁（`/system-parameters`）覆寫保留天數、監控門檻、系統名稱、各功能的 AI 模型等 55 個非機密的值（0.9.166 時；以 `SystemParameterCatalog.All` 為準），存在資料庫、**蓋過 appsettings 與環境變數**。

- [ ] 上線前先在「系統參數」頁設定正式的系統名稱與簡介，並依規定確認各種紀錄的保留天數（稽核紀錄有保存年限時調大或設 0）。
- [ ] 部署人員改了設定檔或環境變數卻沒生效時，先到「系統參數」頁看那個鍵的來源是不是「系統參數」；要改回設定檔的值請按「還原為設定檔值」。
- [ ] 升級後打開「系統參數」頁，確認沒有「未套用」或「不認得的參數」提示（新版本若收窄了範圍，舊的覆寫會被略過並標示）。
- [ ] appsettings 本身仍要合法：啟動時只驗證設定檔，覆寫在資料庫初始化之後才套用。

- [ ] 系統參數存在 `BackendDB.db` 裡，備份資料庫時一併帶走；換機只搬設定檔的話，管理員改過的值會回到設定檔的值。
- [ ] 0.10.6 起系統參數頁在 WebAssembly 執行，存檔經 `POST /api/v1/system-parameters/save`（只限管理員），驗證全在伺服器；不在參數目錄的鍵（例如 `JwtSettings:SigningKey`）一律 404，不能經 API 寫進資料庫。

> 可覆寫的鍵與優先順序見 [日誌與設定檔說明 §4.15](日誌與設定檔說明.md)；規則見 [系統參數 PRD](../prd/系統參數-prd.md)。

## 工作階段失效（0.9.103 起）🟡

- [ ] **升級到 0.9.103 後每個人都要重新登入一次**（舊的 Cookie 與 API token 沒有工作階段版本），API 用戶端要重新以帳密取得 token。安排在離峰時間升級並事先公告。
- [ ] 確認 API 用戶端不是拿 refresh token 當 Bearer 呼叫 API —— 0.9.103 起只接受 access token。
- [ ] 懷疑帳號被盜用時：先改密碼或停用，再到使用者管理按「強制登出」。已發出的存取 Token 會比對工作階段版本：同一台主機立即失效，多台主機最晚 `SessionSettings:ValidationIntervalMinutes`（預設 5 分鐘）。

## 兩步驟驗證（0.9.104 起）🟡

- [ ] 決定政策：要強制的角色在「角色管理」勾「需要兩步驟驗證」；所有管理員都要時，在「系統參數」開「管理員必須使用兩步驟驗證」。⚠️ 開之前**你自己先設定好**，否則存檔後馬上被帶去設定頁。
- [ ] 不希望共用電腦被「記住」時，把「記住裝置天數」設 0。0.10.8 起「記住這台裝置」存在瀏覽器的 localStorage（以金鑰環加密、綁使用者與工作階段版本），改密碼、強制登出、重設兩步驟驗證之後就失效。
- [ ] 訂好「手機遺失」的處理流程：本人用備用碼登入後自行停用再重設；備用碼也沒有時，管理員**確認是本人**後在使用者管理按「重設兩步驟驗證」。
- [ ] 會用 Web API 的帳號若開啟或被要求使用兩步驟驗證，用戶端要在 `POST /api/Auth/login` 帶 `twoFactorCode`；被要求使用卻還沒設定的帳號，API 一律拒絕登入。這類整合帳號建議放在不強制的角色。
- [ ] 伺服器時間要正確（NTP）：驗證碼只接受前後各 30 秒的誤差。
- [ ] 還原備份時金鑰環要跟資料庫一起還原（見[備份與還原操作手冊](備份與還原操作手冊.md)），否則所有人的驗證碼都會不正確。

## AI 用量上限（0.9.109 起）🟡

- [ ] 決定要不要限制 AI 費用：預設四個上限都是 0（不限制）。要限制時在「系統參數」的「AI 用量」設定全系統與每人的每日、每月上限（新台幣）。
- [ ] 確認實際使用的模型都在 `AiPricingSettings` 有價格（Token 用量頁沒有「未定價」提示）—— 未定價的呼叫以 0 元計，上限對它無效。
- [ ] 全系統達上限時會寄信給管理員，確認管理員帳號有 Email、寄信已設定。

## 系統管理助理與定時巡檢（0.9.155／0.9.161 起）🟡

系統管理助理（`/admin-assistant`，左側選單「系統管理 › 管理助理 › 系統管理助理」）只有管理員能用，可以查詢，也可以經核准後代為修改，包括紅字核准＋輸入「確認」的不可復原操作。排程「系統管理助理巡檢」預設每天 07:30 以 AI 巡檢一次（只用查詢工具，每次約 NT$ 3）。

- [ ] 決定要不要每天巡檢：不要時到「排程作業」頁停用「系統管理助理巡檢」；執行時間改 `ScheduledJobSettings:Jobs:AdminPatrol:Cron`。AI 設定不完整時巡檢會略過（記為成功）。
- [ ] 巡檢結果有「注意」或「異常」時會通知全體啟用中的管理員並寄信：確認管理員帳號有 Email、寄信已設定，且 `EmailSettings:PublicBaseUrl` 已填（沒填時信裡沒有連結）。
- [ ] 巡檢報告存在 `AiAgentConversationPath\AdminPatrol`：目錄權限與備份照上方「檔案上傳與下載」的 `AiAgentConversationPath` 處理；保留期是 `AdminPatrolSettings:RetentionDays`。
- [ ] 系統管理助理的 AI 費用受「AI 用量」的全系統與每人上限約束；巡檢不屬於任何人，**只受全系統上限**（超過時作業失敗、管理員收到排程失敗通知；見上方「AI 用量上限」）。模型可在「系統參數」的「AI 模型」覆寫（`AiModelSettings:AdminAssistant`、`AiModelSettings:AdminAssistantRouter`），覆寫的模型也要在 `AiPricingSettings` 有價格。

> 功能說明見 [系統管理助理](../features/系統管理助理.md)。

## 同一主機名稱部署多個衍生系統

**瀏覽器的 Cookie 只看主機名稱、不看連接埠。** `http://server:8081` 與 `http://server:8082`
（或同一站台底下的兩個子應用程式）會共用同一批 Cookie；名稱相同就會互相覆蓋。
0.10.8 起登入改存在瀏覽器的 localStorage／sessionStorage（依「網址的通訊協定＋主機＋連接埠」區分，不同連接埠互不影響），
仍用到 Cookie 的只剩 Google 登入過程的暫存 Cookie（0.10.9 以前另有防偽 Cookie，0.10.10 起主機拿掉 Razor 元件與 `UseAntiforgery`，不再使用）；同一站台底下的兩個子應用程式（同一個網址來源）則會共用 storage，
存放 Token 的鍵依專案名稱區分（`proja.auth`），一樣不會互撞。

以 `New-StarterProject.ps1` 產生的專案，下列項目已經依專案名稱區分，**不需要**另外處理：

| 項目 | 值（以專案名 `ProjA` 為例）|
|------|------|
| 登入 Token 的 storage 鍵 | `proja.auth`（0.10.8 起；之前的登入 Cookie `.ProjA.Auth` 已不再發出）|
| 外部登入暫存 Cookie | `.ProjA.External` |
| 防偽 Cookie | `.AspNetCore.Antiforgery.<依應用程式名稱雜湊>`（0.10.9 以前；0.10.10 起不再使用）|
| Data Protection 應用程式名稱 | `ProjA` |
| 資料庫／上傳／金鑰等目錄 | `C:\temp\ProjA\...` |
| NLog 日誌 | `NLog:BasePath` 底下再分 `ProjA.Web\` 子目錄與檔名前綴 |

- [ ] 兩個系統的 `ExternalFileSystem` 各路徑**不要**指到同一個目錄（尤其是 `DatabasePath` 與 `DataProtectionKeyPath`）。
- [ ] 各自使用獨立的 IIS 應用程式集區。
- [ ] 0.10.11 起前端是 PWA：瀏覽器的快取儲存空間以來源區分，同一來源不同路徑的兩套系統（例如 `https://server/proja/` 與 `https://server/projb/`）共用同一個快取儲存空間；快取名稱帶範圍路徑（例如 `offline-cache-%2Fproja%2F:<版本>`），Service Worker 啟用時只刪自己範圍的舊快取，**彼此不互刪**，可以這樣部署。
- [ ] 0.9.64 之前產生的衍生專案、且還沒升級到 0.10.8：在 `Program.cs` 的 `AddCookie(MagicObjectHelper.CookieScheme, ...)` 補上
      `options.Cookie.Name = ".<專案名>.Auth";`（套用後既有登入會失效一次）。0.10.8 起登入 Cookie 已移除，這一項不再需要。


## 部署設定
- [ ] 設定 HTTPS、HSTS、反向代理 header 與正式網域（0.10.10 起先決定同站台或雙站台，見「前端部署方式」）。
