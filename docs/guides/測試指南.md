## 1. 測試框架與套件

`MyProject.Tests` 使用：

- **xUnit** — 測試框架（`[Fact]` / `[Theory]`）。
- **bUnit** — Blazor 元件測試：在測試裡渲染元件、找元素、觸發點擊（0.9.90 起，寫法見 §5.1）。
- **Microsoft.AspNetCore.Mvc.Testing** — 以 `WebApplicationFactory` 啟動整個 Web API 做整合測試。
- **Microsoft.NET.Test.Sdk** — 測試執行器。
- **coverlet.collector** — 程式碼覆蓋率蒐集。

實際版本以 `src/MyProject/MyProject.Tests/MyProject.Tests.csproj` 為準。

### 2.2 ⚠️ 元件測試才剛起步

0.9.87 之前，約 1100 個測試**沒有一個渲染 Blazor 元件**：UI 的保證全是「用正規表示式掃原始碼」
（上面那些 ⭐ 守門測試），加上 `PageAuthorizationTests`、`EmailPagesIntegrationTests` 檢查伺服器渲染出的 HTML（0.10.8 起頁面全在 WASM，這兩組改驗空外殼、API 與回應標頭）。
結果是**你可以把畫面改壞，而測試全綠** —— 0.9.30 那次全站視覺改版就是這樣通過測試的。

0.9.90 起加入 bUnit，建立了共用基底 `Components/ComponentTestBase` 與 4 個樣板測試類別，之後陸續增加，目前 13 個（0.10.9，刪除 Server 版鈴鐺與公告橫幅的 `NotificationComponentTests`；見 §2.1 的 `Components/*`），
涵蓋三種情境：純展示元件、含 AntDesign 元件與點擊事件、由 `ModalService` 開出的確認窗。寫法見 §5.1。

**仍未涵蓋的範圍（知道它們存在，才不會誤以為測試全綠就沒事）：**

- **頁面層**：CRUD 清單頁、使用者與角色管理頁都沒有元件測試（0.10.4 起這兩頁是 WASM 頁，改以 API 整合測試與實機情境 `scripts/e2e/m05-admin.mjs` 涵蓋；0.10.5 起日誌與 AI 管理六頁同樣以 API 整合測試與 `m06-ops.mjs`、`m06-ai.mjs` 涵蓋；0.10.6 起維運七頁與首頁以 API 整合測試與 `m07-ops.mjs` 涵蓋，首頁小工具另有 bUnit；0.10.7 起 Agent 測試台、Agent 工作流程、系統管理助理以 API 整合測試與呼叫真實模型的 `m08-agents.mjs` 涵蓋，巡檢報告窗另有 bUnit；0.10.8 起登入相關頁面、變更密碼、兩步驟驗證設定以 API 整合測試與 `m09-auth.mjs` 涵蓋，登入頁另有 bUnit）。頁面依賴外框的登入工作階段（`ClientSession`、`/api/v1/Auth/me`；0.10.8 以前是 `AuthenticationStateHelper.Check()`）與 Table 的遠端資料來源，要渲染整頁得準備大量測試替身。
- **視覺**：bUnit 不跑 CSS，色彩、排版、捲動、浮層位置仍然只能靠人眼。repo 根目錄的 `.playwright-cli/` 沒有接進品質關卡。

0.10.0 起有**實機驗證腳本**（不在品質關卡裡，每個 WASM 遷移里程碑完成前手動執行）：`scripts/Start-E2EHost.ps1` 以隔離資料夾啟動網站，

## 3. 在本機執行

```powershell
# 執行整個方案的所有測試
dotnet test src/MyProject/MyProject.slnx

# 只跑測試專案
dotnet test src/MyProject/MyProject.Tests/MyProject.Tests.csproj

# 以單一測試類別或方法過濾
dotnet test src/MyProject/MyProject.slnx --filter "FullyQualifiedName~ApiIntegrationTests"
dotnet test src/MyProject/MyProject.slnx --filter "Name=GetProvider_ShouldThrow_WhenUnknown"
```

本 repo 沒有 CI。提交前跑品質關卡（restore、Release 建置、format、test、文件編碼、CRUD 產生器錨點、弱點掃描，遇到失敗就停；
VS Code 對應任務為 `quality-gate`）：

```powershell
pwsh ./scripts/Invoke-QualityGate.ps1          # -Quick 略過弱點掃描
```

注意關卡的 Test 步驟用 **Release** 組態；開發時直接跑 `dotnet test` 用的是 Debug，兩者結果應該相同。

衍生專案若要自建 CI，可參考 [CI-CD 與品質檢查](../operations/CI-CD與品質檢查.md) 的參考設計。

## 5. 撰寫新測試的慣例

- 整合測試走 `WebApplicationFactory`，驗證對外 **`ApiResult` 合約**（狀態碼 + 信封結構），不依賴內部實作細節；需觸發 403／500 等情境時，透過測試專案的 probe controller 製造，**不新增正式 API contract**。
- ⚠️ **會啟動 host 的測試類別一律標 `[Collection(nameof(IntegrationHostCollection))]`**（0.9.60 起，`IntegrationHostCollection.cs`），整批循序執行、不與彼此平行。
  原因是兩個行程層級的共用狀態：`Program.cs` 結束時的 `LogManager.Shutdown()` 會清掉全行程的 NLog 設定（`Main` 在背景執行緒結束，時間點不受控），
  以及 `ApiTestApplicationFactory` 會寫入／清除行程環境變數。0.9.60 多了兩個 host 類別後，這個競態從偶發變成幾乎每次都發生。
  配套：`ApiTestApplicationFactory` 建構時若 NLog 設定已被清掉就重新載入 `nlog.config`；`Program.cs` 的 `UseNLog` 關掉「從 appsettings 載入 NLog 設定」。
  同一個競態的第二個症狀（0.9.90 修正）：`Program.cs` 曾「先檢查 `LogManager.Configuration` 不是 null、再讀一次」，前一個 host 的 `Shutdown()` 落在兩次讀取之間就丟 `NullReferenceException`。加入 bUnit 改變了組件載入時間後，這個失敗從幾乎不出現變成約四分之一。**讀全域 NLog 設定一律先存進區域變數**。
- 單元測試針對 Service / Helper 的純邏輯，必要時以 in-memory 或測試替身隔離資料庫。
- ⚠️ 測試要讀原始碼、設定檔、文件或腳本時，一律經 `SourceTree`（`Infrastructure/SourceTree.cs`，0.10.0 起），不要自己從 `AppContext.BaseDirectory` 往上找（`SourceTreeConventionTests` 守門）。
  畫面檔要用 `SourceTree.UiFile("Views/…")`（0.10.2 起）；要掃全部畫面檔用 `SourceTree.UiFiles("*.razor")`（0.10.9 起，不含 `bin`、`obj`），⚠️ 呼叫端仍要斷言結果不是空的（掃描路徑失效時守門測試不能變成永遠通過）。
  0.10.9 起 `SourceTree.UiRoots` 只剩 `MyProject.Web.Client`（0.10.1～0.10.8 遷移期間另含 Server 版的 `MyProject.Web/Components`）。0.10.10 起 `SourceTree.Components`（0.10.9 時只剩主機頁 `App.razor` 與外框 API 用的服務類別）刪除，改用 `SourceTree.ClientWebRoot`（前端的靜態檔根目錄 `MyProject.Web.Client/wwwroot`：`index.html`、`theme.css`、`app.css`、`js/`、`images/`、`lib/`、`appsettings.json`）。
  元件測試要權限判斷時用 `Components/TestPagePermissions.AddTo(Services)`（0.10.9 起取代 Server 版的 `ServerPagePermissions`，目前使用者取自測試登記的 `CurrentUserService`）。
- `TestDbContextFactory` 可傳入 EF 攔截器（0.10.0 起），例如要驗證 `SecurityStampInvalidationInterceptor` 時。
- 新增 / 修改 API 時，請補對應整合測試；新增 Entity 或密碼／權限邏輯時，補單元測試。對照 [維護規範](../operations/維護規範.md) 的 commit 前檢查清單。
- 新增 / 修改共用元件（`MyProject.Web.Client/Commons/`；0.10.2 起 `ViewNotification`、`RequirePermission`、`AuditHistoryDialog` 等都在這裡，命名空間不變）時，補元件測試（§5.1）。

### 5.1 怎麼寫元件測試（bUnit，0.9.90 起）

元件測試放在 `MyProject.Tests/Components/`，命名空間 `MyProject.Tests.Components`，一律寫成 `.cs`
（測試專案是 `Microsoft.NET.Sdk`，不是 Razor SDK，不能寫 `.razor` 測試）。四個樣板由簡到繁：
`StatusPillTests` → `FormSectionTests` → `CrudActionButtonTests` → `FormModalFlowTests`，照著抄最快。

**1. 繼承 `ComponentTestBase`。** 它繼承 bUnit 的 `BunitContext`，並做了三件事：

- `JSInterop.Mode = JSRuntimeMode.Loose`：AntDesign 的 Button、Tooltip、Modal 內部會呼叫 JS（量測位置、焦點、事件監聽），
  測試環境沒有瀏覽器。Loose 讓這些呼叫直接回傳預設值；預設的 Strict 模式會讓每一個沒設定的 JS 呼叫都變成測試失敗。
- `Services.AddAntDesign()`：註冊 `ModalService`、`MessageService`、`NotificationService` 等，與 `MyProject.Web.Client/Program.cs` 相同（0.10.9 起伺服器端的 `Program.cs` 不再註冊 AntDesign）。
- 實作 xUnit 的 `IAsyncLifetime`，在釋放測試環境之前先 `DisposeComponentsAsync()`（2026/11/08 起）。⚠️ 不要拿掉：
  AntDesign 的事件監聽（`IDomEventListener`）全部共用一個沒有鎖的訂閱清單，元件 Dispose 與服務 Dispose 若同時進行，
  會偶發「Collection was modified」（負載高時約每 25～30 次一次，`ExceptionAiAnalysisModalStreamingTests`、`FormModalFlowTests` 都中過）。
  自己另外寫測試基底時也要照做。

需要登入身分或其他服務時，在測試類別的建構子裡用 `Services.AddSingleton(...)` 補上；多個測試類別都要用時，再搬進基底。

**2. 渲染並傳參數**（bUnit 2.x 的 API；網路上很多範例還是 1.x 的 `TestContext`／`RenderComponent`）：

```csharp
var cut = Render<StatusPill>(parameters => parameters
    .Add(p => p.Text, "啟用")
    .Add(p => p.Tone, StatusTone.Positive));
```

`ChildContent` 用 `.AddChildContent("<input id=\"field\" />")`；`EventCallback` 直接傳 lambda：`.Add(p => p.OnClick, () => clicked++)`。

**3. 找元素、觸發事件**：`cut.Find("css 選擇器")`（找不到會丟例外）、`cut.FindAll(...)`（可以是空的）、
`element.Click()`。元素是 AngleSharp 的 DOM 物件，可用 `ClassList.Contains`、`GetAttribute`、`TextContent`、`QuerySelector`。

**4. 測 `ModalService` 開出來的確認窗**（見 `FormModalFlowTests`）：先 `Render<AntContainer>()` —— 正式環境它在版面裡，
確認窗就畫在它底下；接著呼叫會開窗的方法但**先不要 await**，用 `container.WaitForElement(".ant-modal-confirm ...")` 等窗出現，
點按鈕後再 `await` 方法的回傳值（加 `WaitAsync(TimeSpan)` 避免卡死）。破壞性確認（`ConfirmDialog.AskDestructiveAsync`）的確定鈕帶 `.ant-btn-dangerous`，可以用它區分兩顆按鈕。

**5. 斷言原則**：

- 斷言**本專案元件自己的行為**：class 名稱、文字、渲染成什麼元素、事件有沒有觸發、方法回傳值。
- **不要比對整段 HTML**（`MarkupMatches` 整段快照）：AntDesign 升版或無關的標記調整就會讓測試大量失敗，測試變成負擔。
- 不要斷言 AntDesign 內部的結構細節，只用到「找到我們的按鈕」所需的最少選擇器。

**6. 驗證測試真的有在測**：寫完後故意把元件改壞一次（例如改掉一個 class），確認測試會失敗再改回來。
注意改壞的方式要能通過編譯 —— 專案開了 `TreatWarningsAsErrors`，`if (true)` 這種寫法會先在建置階段失敗，那不算驗證到測試。
