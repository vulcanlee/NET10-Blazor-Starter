## 1. 目的與讀者

使用手冊的讀者是**使用系統的人**：一般使用者、管理員、維運人員。他們不寫程式，很多人第一次接觸這類系統。

所以手冊要做到三件事：

1. **先講為什麼，再講怎麼做**：每個畫面先說「沒有它之前大家怎麼受苦」「它解決什麼」，再說按鈕。
2. **完整可自學**：讀完就能自己操作，看得懂系統在做什麼，遇到問題知道去哪裡查。
3. **用白話**：專有名詞第一次出現時用生活比喻解釋，並收進「名詞速覽」。

手冊**不談程式**：不寫類別名稱、資料表、程式碼路徑。設定檔的鍵名只出現在「設定檔導讀」一節，而且要附白話說明。

## 2. 三份文件的分工

腳手架有三份描述畫面的文件，角度不同，不要互相取代：

| 文件 | 讀者 | 回答的問題 | 在哪裡 |
|---|---|---|---|
| **使用手冊**（《新手完整操作指南》） | 使用系統的人 | 「這套系統是什麼、我該怎麼用、為什麼要這樣用」：全貌、心智模型、設定順序、每個畫面的欄位與按鈕、FAQ | `docs/guides/新手完整操作指南.md` |
| **頁面操作說明** | 正在某一頁操作的人 | 「這一頁每個按鈕、每則訊息是什麼」：逐字的按鈕、提示與錯誤訊息 | 系統內按標題旁的「?」；檔案在 `MyProject.Web/Datas/Help/<路由>.md` |
| **畫面與欄位字典** | 開發者 | 「這個欄位在程式裡是什麼、有什麼限制與陷阱」 | `docs/guides/畫面與欄位字典.md` |

**手冊和操作說明的差別**：
- 操作說明是「這一頁的完整說明書」，逐字列出每一則訊息。
- 手冊是「整套系統的導覽與教學」，每個畫面也有欄位表與按鈕表，但重點是**為什麼、什麼時候用、跟其他畫面的關係、常見陷阱**。
- 手冊的每個畫面章節最後，都要連到該頁的操作說明，讓讀者查逐字細節。

## 3. 章節結構樣板

手冊的章節固定如下。**「共通」**的章，新系統複刻後大多可以沿用，只要核對；**「業務」**的章，新系統要改寫成自己的業務。

| 章 | 標題 | 性質 | 新系統要做的事 |
|---|---|---|---|
| 開頭 | 文件頭、定位說明、先選你的閱讀路線 | 共通 | 改系統名稱；閱讀路線依自己的角色調整 |
| 摘要 | 三分鐘搞懂這份文件與這套系統（五個痛點） | **業務** | 改寫成自己系統解決的痛點 |
| 索引目錄 | — | 共通 | 跟著章節更新 |
| 一 | 這套系統是什麼、解決什麼痛點 | **業務** | 改寫 |
| 二 | 五分鐘心智模型 | 共通＋業務 | 主軸「人 → 權限 → 資料 → AI → 維運」保留；第 4 站「資料」改成自己的業務流程 |
| 三 | 畫面地圖與彼此關係 | 共通＋業務 | 總覽表加上自己的業務畫面 |
| 四 | 前置：登入與帳號安全 | 共通 | 核對即可 |
| 五 | 基礎設定（依序完成） | 共通 | 核對即可；有新的主檔就加一節 |
| 六 | 業務資料 | **業務** | 腳手架寫的是範例模組「專案項目」。**新系統把這一章換成自己的業務畫面**，可以拆成多章（第六章之後依序編號，後面各章順延） |
| 七 | AI 功能 | 共通 | 刪掉的 AI 功能就刪掉那一節；新增的 AI 功能照樣板補 |
| 八 | 系統管理 | 共通 | 核對即可 |
| 九 | 監控與維運 | 共通 | 核對即可 |
| 十 | 首頁、站內通知與個人化 | 共通 | 核對即可 |
| 十一 | 資料維護與生命週期 | 共通＋業務 | 補上自己業務資料的刪除、還原與保留規則 |
| 十二 | 名詞速覽 | 共通＋業務 | 補業務名詞 |
| 十三 | FAQ 與問題排除 | 共通＋業務 | 補業務常見問題 |
| 十四 | 延伸閱讀 | 共通 | 跟著文件清單更新 |

**刻意不寫的內容**：端到端走查（用一個虛構情境串起所有畫面）。腳手架沒有主要業務流程，走查章由新系統視需要自行加寫，放在「資料維護與生命週期」之後。

## 4. 每節開頭的四行

每一個「章」和每一個「節」（`##` 與 `###`）開頭，都要先寫這四行引言，再寫內文：

```markdown
> **本節目的**：（一句話：這一節要讓讀者完成什麼）
> **適用對象**：（誰該讀：一般使用者、管理員、維運人員…）
> **學完會知道**：（讀完能回答哪些問題、能做哪些事）
> **特別注意**：（最容易誤會或做錯的一件事）
```

寫法要點：
- **本節目的**寫「讓讀者能做什麼」，不寫「本節介紹 XX」。
- **特別注意**只寫一件最重要的事；沒有特別要注意的，就寫最常見的誤解。
- `####` 以下的小節不用寫四行。

## 5. 畫面章節樣板

每個畫面一節，可以直接複製下面的樣板改寫。**標題一定要含路由**，守門測試靠它檢查（見第 9 節）。

````markdown
### 5.6 使用者管理 `/myusers`

> **本節目的**：…
> **適用對象**：…
> **學完會知道**：…
> **特別注意**：…

**一句話摘要**：（這一頁做什麼）
**從哪裡進入**：左側選單「系統管理 › 帳號與權限 › 使用者管理」。
**哪種人要用**：（角色與時機）
**需要的權限**：（管理員專用，或角色權限「XX」的檢視／新增／編輯／刪除）

**為什麼需要它？**（沒有它之前大家怎麼受苦、它解決什麼）

**準備資料的建議**：（開始前要先想好或先建好什麼）

**欄位表**：

| 欄位 | 意義 | 怎麼輸入 | 必填 | 白話舉例 |
|---|---|---|---|---|
| … | … | … | ✅ | … |

**按鈕表**：

| 按鈕 | 按下後會怎樣 | 會看到的提示 | 注意事項 |
|---|---|---|---|
| … | … | … | … |

**清單怎麼看**：（每一列代表什麼、狀態標籤的意思、預設排序）

**常見陷阱**：
- …

> 逐字的按鈕與訊息說明：系統內本頁標題旁的「?」（操作說明）。
````

規則：
- **欄位表與按鈕表裡的名稱，一律用畫面上的原文**（按鈕文字、欄位標籤、提示訊息），不要自己換說法。
- 一個畫面有多個視窗（例如新增視窗、複製視窗）時，每個視窗各一張欄位表，用粗體小標題分開。
- 只有清單、沒有編輯視窗的畫面（例如監控頁），欄位表改成「畫面上的區塊與指標」表，欄位一樣是「名稱／意義／怎麼看／白話舉例」。
- 「需要的權限」寫使用者看得懂的說法，例如「角色權限『專案項目』的檢視」，不寫權限鍵。

## 6. 表格欄位的定義

| 表格 | 欄位 | 怎麼寫 |
|---|---|---|
| 欄位表 | 欄位 | 畫面上的欄位標籤原文 |
|  | 意義 | 這個欄位代表什麼，一句話 |
|  | 怎麼輸入 | 格式、長度、可選值、預設值 |
|  | 必填 | 必填寫 ✅，選填寫 —，有條件的寫條件（例如「新增時必填」） |
|  | 白話舉例 | 一個具體例子，或最容易誤會的地方 |
| 按鈕表 | 按鈕 | 畫面上的按鈕文字原文 |
|  | 按下後會怎樣 | 結果，以及中間會不會先跳確認窗 |
|  | 會看到的提示 | 右下角或確認窗的提示原文；沒有寫「無」 |
|  | 注意事項 | 什麼時候不會出現、不能按、會留下什麼紀錄、能不能復原 |
| 全畫面總覽表（第三章） | 畫面、路由、選單位置、誰會用、需要的權限、一句話用途 | — |
| FAQ 速查表 | 問題、解答 | 解答先給結論，再給「去哪一節看」 |

## 7. 文風

1. **先講為什麼**：每個畫面都要回答「沒有它之前怎麼受苦」。用具體情境，例如「新同事到職，要找三個人才開得好帳號」。
2. **生活比喻**：抽象概念用比喻，例如「團隊像是資料夾的門禁卡」「軟刪除像資源回收筒」。
3. **短句、一段一件事**：一句話不超過兩個逗號；一段只講一件事。
4. **術語第一次出現要解釋**，並收進「名詞速覽」。
5. **用使用者看得到的名稱**：選單名稱、按鈕名稱照畫面原文；不寫程式名稱。
6. **不誇大、不猜測**：手冊寫的每一件事都要能在畫面或操作說明上找到依據；不確定就不寫。
7. **一律繁體中文**，UTF-8 含 BOM。
8. 不使用表情符號；警示用「⚠️」，必讀用粗體。

## 9. 同步規則與守門測試

**改了一個頁面的按鈕、欄位或訊息，三份文件要一起改**：

1. 該頁的操作說明 `Datas/Help/<路由>.md`（第三段「畫面上有哪些按鈕」）。
2. 使用手冊的該頁章節（欄位表與按鈕表）。
3. 畫面與欄位字典（改到欄位定義或限制時）。

**新增一個登入後的頁面**：
- 照既有規定登記 `Datas/HelpTopics.json` 並寫操作說明（見《開發慣例與限制速查》§6.14）。
- **同時在手冊加一個畫面章節，標題要含路由**，例如 `` ### 6.2 訂單管理 `/orders` ``。
- 用 `scripts/New-CrudModule.ps1` 產生的頁面，產生器會自動在第六章最後加一節初稿（0.9.165 起，樣板 `scripts/crud-manual-section.md.tmpl`，插在第七章前的分隔線之前）。初稿的欄位表與按鈕表是通用寫法，補上實際欄位後要一起改。

**守門測試** `UserManualCoverageTests`（在品質關卡的測試步驟裡執行）：
- `Datas/HelpTopics.json` 登記的每一個路由，在手冊裡都要有一個標題（`##`～`####`）含有 `` `/路由` ``（不分大小寫），漏寫就失敗。
- 手冊與本規範都必須存在。
- 測試只檢查「有沒有章節」，**不檢查內容對不對**；內容正確性靠第 12 節的檢查清單。

## 10. 新系統的做法

複刻出新系統後，依序：

1. **改系統名稱**：手冊開頭、摘要、第一章的系統名稱改成新系統的名字。
2. **改寫業務章**：摘要（五個痛點）、第一章、第二章的第 4 站、第六章（業務資料）。第六章可以拆成多章，後面的章順延編號。
3. **刪掉沒用的範例**：刪除「專案項目」範例模組時，第六章的範例內容一併刪除或改寫。
4. **核對共通章**：新系統改過的共通功能（例如拿掉 AI 功能、改了登入方式），對應章節一起改。
5. **補 FAQ 與名詞**：把業務的常見問題與名詞加進第十二、十三章。
6. **跑品質關卡**：守門測試會指出哪些頁面還沒有章節。

## 11. 給 AI 的提示詞範本

把下面的提示詞貼給 Claude Code、Codex 等 AI 助手，再補上方括號裡的內容。

**新增一個畫面的章節**：

```text
請依 docs/guides/使用手冊寫作規範.md，在 docs/guides/新手完整操作指南.md 的第 [章] 章新增
[畫面名稱] `/[路由]` 這一節。

資料來源（以這些為準，不要猜）：
- 頁面程式：src/[專案]/[專案].Web/Components/Views/[…].razor 與 .razor.cs
- 操作說明：src/[專案]/[專案].Web/Datas/Help/[路由].md
- PRD：docs/prd/[…].md

要求：
- 照第 5 節的畫面章節樣板，開頭四行、欄位表、按鈕表、清單怎麼看、常見陷阱都要有。
- 欄位與按鈕名稱用畫面原文。
- 更新第三章的全畫面總覽表與索引目錄。
- 不確定的地方列出來問我，不要自己補。
- 完成後跑 pwsh ./scripts/Invoke-QualityGate.ps1。
```

**複刻後改寫業務章節**：

```text
這個專案是從 NET10-Blazor-Starter 腳手架複刻出來的「[系統名稱]」，業務是 [一兩句話描述]。
請依 docs/guides/使用手冊寫作規範.md 第 10 節，改寫 docs/guides/新手完整操作指南.md：
1. 系統名稱改成「[系統名稱]」。
2. 摘要的五個痛點、第一章、第二章第 4 站，改寫成這個系統的業務。
3. 第六章換成這些業務畫面：[列出路由]，每個畫面依第 5 節樣板寫。
4. 第十二、十三章補上業務名詞與常見問題。
開始前先列出你的理解與要問我的問題，確認後再寫。
```

**頁面改版後同步**：

```text
我改了 `/[路由]` 這一頁：[改了什麼]。
請依 docs/guides/使用手冊寫作規範.md 第 9 節，同步更新操作說明、使用手冊與畫面與欄位字典，
按鈕與訊息用畫面原文，完成後跑品質關卡。
```

## 12. 交付前的檢查清單

- [ ] 每個 `##`、`###` 都有開頭四行。
- [ ] 每個畫面章節的標題都含路由，並有欄位表、按鈕表、清單怎麼看、常見陷阱與操作說明連結。
- [ ] 欄位與按鈕名稱和畫面一致（至少啟動網站抽查新增或改過的畫面）。
- [ ] 第三章的全畫面總覽表涵蓋所有畫面。
- [ ] 索引目錄的連結都能點到。
- [ ] 每張 Mermaid 圖都有純文字版。
- [ ] 沒有「TODO」「待補」之類的未完成標記。
- [ ] 檔案是 UTF-8 含 BOM。
- [ ] 品質關卡全部通過（含守門測試）。
