## 1. 這個腳手架是什麼

一套已經可以直接上線的 **.NET 10 + Blazor Server 後台系統底座**。
它不是「範例專案」，是「把每個內部系統都會重寫一次的東西先寫好」。

### 適合

- 企業內部管理後台、營運系統、專案追蹤平台。
- 使用者數十到數百人、以**部門／團隊**切分資料可見範圍。
- 需要「一開始就有」帳號權限、日誌、稽核、健康監控的專案。

### 不適合

| 情境 | 為什麼 |
|------|-------|
| 公開網站、高流量 C 端 | Blazor Server 每個使用者一條 SignalR 連線，狀態在伺服器 |
| 需要離線／弱網路 | 連線斷了畫面就不能操作，不是漸進式降級 |
| 多租戶 SaaS | 沒有租戶隔離，只有團隊分權（§9）|
| 高併發寫入 | 只支援 SQLite，單寫入者（§3.3）|
| 需要多國語言介面 | 多語系是空殼，零個 `.resx`（§3.14、§8）|

### 核心設計取向

**用慣例與守門測試把品質固定住。** 這個 repo 有 18 條「慣例測試」——
它們不測功能，專門擋「照著做會出錯但不會報錯」的寫法。
你會覺得某些規矩很囉唆，那些規矩幾乎都是踩過坑之後加的，`docs/changelog/` 有紀錄。

## 2. 從複製到跑起來

完整逐步操作在 [VS Code 開發環境與新專案上手指南](VS%20Code%20開發環境與新專案上手指南.md)（732 行）。
這裡只講**順序與最容易出事的點**。

### 2.1 建議順序

```
1. 跑 scripts/New-StarterProject.ps1 複製並改名
2. 檢查高風險字串（上手指南 §8.3 的 12 項）
3. 換掉 appsettings.json 的預設值        ← 見 §2.3，有兩個地雷
4. 設定 User Secrets
5. dotnet build → dotnet test → 跑起來登入
6. 換品牌（名稱、Logo、favicon）→ 見上手指南 §7
7. 換顏色 → 見本文 §7
```

```powershell
./scripts/New-StarterProject.ps1 -ProjectName YourApp -DestinationPath D:\Work\YourApp
```

腳本會：遞迴複製（排除 `.git`／`bin`／`obj`）、全檔文字取代 `MyProject` → `YourApp`、
深層優先改資料夾與檔名、**產生新的 `<UserSecretsId>`**、
把 `appsettings.json` 的開發用 JWT 金鑰與 `SupportPassword` 換掉，最後掃描殘留字串。

### 2.2 `<UserSecretsId>` ⚠️

`src/YourApp/YourApp.Web/YourApp.Web.csproj` 第 6 行：

```xml
<UserSecretsId>83f6d54f-9f33-4cd9-a626-d4c05c996e5d</UserSecretsId>
```

**這個值一定要換掉。** 它是「這個專案的機密存在硬碟哪個資料夾」的鍵：

```
%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json
```

兩個專案共用同一個 Id，機密就會互相污染，而且 `dotnet user-secrets clear`
會一次清掉所有共用專案的機密。

- 用腳本複製：**已經自動換好**（除非你用 `-UserSecretsId` 指定）。
- 手動複製：自己產一個 `[guid]::NewGuid()` 貼上去。

> ⚠️ 只有 `*.Web.csproj` 有這個設定，其他專案沒有，也不需要加。
> ⚠️ User Secrets **只在 Development 環境載入**（`Program.cs:42` 用的是預設設定來源鏈，
> 全案沒有任何明確的 `AddUserSecrets(...)`）。正式環境用環境變數或密鑰保管庫。

### 2.3 一定要換掉的值，以及兩個地雷 ⚠️

| 位置 | 值 | 不換的後果 |
|------|----|-----------|
| `JwtSettings:SigningKey` | 開發預設字串 | **Production 啟動會被擋下** |
| `BootstrapSettings:SupportPassword` | `1qaz@WSX` | **⚠️ 見下方地雷一 —— 自動檢查擋不住它** |
| `Swagger:EnabledInProduction` | 必須**明確**寫 true 或 false | 沒寫也會被擋下（不是預設 false，是強迫你表態）|
| `SystemSettings:ExternalFileSystem:*` | `C:\temp\MyProject\…` | 資料庫與附件會存在暫存目錄 |
| `SystemSettings:SystemInformation:SystemName` / `SystemDescription` | 樣板文字 | 登入頁、側邊欄、首頁都會顯示它 |

應該移到 User Secrets 的：`JwtSettings:SigningKey`、`GoogleOAuthSettings` 兩個、
`CacheSettings:RedisConnection`、`AutoMapper:LicenseKey`。

> ⚠️ `BootstrapSettings:SupportPassword` **不要**放 User Secrets ——
> 它每次啟動會反向覆寫資料庫裡的密碼，行為與一般機密不同。

#### 地雷一：預設密碼的自動檢查擋不住預設密碼 🔴

`StartupSafetyValidator.cs:24` 只比對字面字串 `"support"`：

```csharp
if (string.Equals(supportPassword, "support", StringComparison.Ordinal))
```

但範本實際出貨的是 `appsettings.json:43` 的 `"1qaz@WSX"`。
**兩者不相等，所以原封不動的腳手架部署到 Production 會通過檢查** ——
帶著一組公開在原始碼裡的管理員密碼上線。

更糟的是 `appsettings.Production.json:15` 出貨的是**空字串**，它同樣不等於 `"support"`，
也會通過。而 `Program.cs:343` 的 seed 沒有防呆：

```csharp
support.Password = SecurePasswordHasher.HashPassword(bootstrapSettings.SupportPassword);
```

空字串會被雜湊起來 —— **support 管理員帳號變成空密碼**，
而且因為 `else` 分支每次啟動都比對一次，**每次重啟都會重新套用**。

**所以這一項必須人工確認，不能依賴啟動檢查。** 上線前：

```powershell
# 確認實際生效的值不是 1qaz@WSX、不是 support、也不是空字串
$env:BootstrapSettings__SupportPassword
```

（這是目前唯一一個「防線存在但不生效」的地方，已列在 §9 缺口清單。）

#### 地雷二：Production 的 `SigningKey` 出貨是空字串，會讓服務起不來

`appsettings.Production.json:12` 是 `"SigningKey": ""`，而 `JwtSettings` 是全案
**唯一**有 `ValidateOnStart()` 的設定類別（`Program.cs:142-145`），
`SigningKey` 帶著 `[Required]` 與 `[MinLength(32)]`（`JwtSettings.cs:15-17`）。

**不用環境變數覆寫就直接啟動失敗。** 這是刻意的 fail-fast，不是 bug ——
但第一次部署的人會以為系統壞了。設定方式：

```
JwtSettings__SigningKey = <至少 32 字元的隨機字串>
```

### 3.1 Blazor Server

**它在解決什麼問題**

用 C# 寫互動式網頁。按鈕點下去、表格排序、對話窗開關這些互動，
全部在**伺服器**執行，瀏覽器只負責顯示畫面與傳送事件。
你寫的是 `.razor` 檔，裡面 HTML 與 C# 混在一起，不需要寫 JavaScript。

**不用它會怎樣**

後台系統的典型做法是「ASP.NET Core Web API ＋ React/Vue 前端」。
那代表你要：養第二個專案、第二套建置流程（npm、打包）、
第二種語言的人力，而且**驗證規則要寫兩次**（前端擋一次、後端再擋一次）。
本專案的驗證只寫一次（`DataAnnotations` 掛在 AdapterModel 上），兩邊共用。

**為什麼選它** ⭐

| 選項 | 取捨 |
|---|---|
| **Blazor Server**（本專案）| 一種語言、一個專案、驗證只寫一次。代價：每個使用者一條常駐連線，狀態在伺服器 |
| Blazor WebAssembly | 狀態在瀏覽器、可離線。代價：首次載入要下載整個 .NET runtime（數 MB），且資料存取一定要透過 API，等於還是要寫兩層 |
| MVC / Razor Pages | 最輕、最傳統。代價：任何互動都要整頁重新整理，做不出本專案的對話窗體驗 |
| API + React/Vue | 前端生態最成熟、人才最多。代價：兩個專案、兩套流程、驗證寫兩次 |

判準是「**內部後台、使用者數十到數百人、要快**」。這個前提下 Server 模式的
「狀態在伺服器」不是缺點，因為使用者本來就在內網、連線穩定。
前提一變（公開網站、上千併發、要離線），這個選擇就要重新評估。

**渲染模式**

.NET 8 起 Blazor 有多種渲染模式。本專案的設定（`Components/Routes.razor`、`App.razor`）：

| 模式 | 說明 | 本專案 |
|---|---|---|
| 靜態 SSR | 伺服器產生 HTML 後送出，沒有互動 | 登入頁等 `[ExcludeFromInteractiveRouting]` 的頁面 |
| **Interactive Server** | 透過 SignalR 連線互動，狀態在伺服器 | **絕大多數頁面** |
| Interactive WebAssembly | 在瀏覽器執行 | 未使用 |
| Interactive Auto | 先 Server、下載完再切 WASM | 未使用 |

登入頁刻意走靜態 SSR —— 它是傳統表單 POST，不需要 circuit，
而且在還沒登入時建立 SignalR 連線沒有意義。

**circuit 是什麼，為什麼重要**

一個使用者打開一個分頁 ＝ 一個 **circuit**（一條 SignalR 連線 ＋ 伺服器上的一份狀態）。
這件事有兩個非常實際的後果：

1. **DI 的 Scoped 生命週期 ＝ circuit 的生命週期**，不是「一次 HTTP 請求」。
   一個使用者開著分頁幾小時，Scoped 服務就活幾小時。
   這就是為什麼資料服務**一律注入 `IDbContextFactory` 而不是 `DbContext`**（見 §3.3）。
2. **連線斷了畫面就不能操作** —— 會跳出重連提示（`ReconnectModal.razor`）。這不是離線模式。

circuit 的生命週期事件由 `Components/ApplicationCircuitHandler.cs` 記錄，
它同時負責提供「誰、在哪一頁」給例外紀錄管線。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `Program.cs:82-88` | `AddRazorComponents().AddInteractiveServerComponents()` ＋ SignalR 設定 |
| `Program.cs:441` | `MapRazorComponents<App>().AddInteractiveServerRenderMode()` |
| `Components/App.razor` | HTML 外殼、樣式表載入順序 |
| `Components/Routes.razor` | 路由、`AntContainer`、`OverlayStyles` |
| `Components/ApplicationCircuitHandler.cs` | circuit 生命週期日誌 |

**可以調什麼**

| 參數 | 位置 | 預設 | 改了會怎樣 |
|---|---|---|---|
| `MaximumReceiveMessageSize` | `Program.cs:86` | **10MB**（框架預設 32KB） | 調小會讓長文輸入斷線；調大會增加單一訊息的記憶體占用 |
| `BlazorDisableThrowNavigationException` | `MyProject.Web.csproj` | `true` | 設 false 會讓靜態 SSR 期間的 `NavigateTo` 丟出 `NavigationException`（.NET 9+ 的新行為） |
| 渲染模式 | `App.razor` 的 `RenderModeForPage()` | 依頁面 | 改成 WASM 需要整個資料存取層改走 API |

**常見情境食譜**

*我想讓某個頁面不要建立 SignalR 連線（純靜態）*
在該頁面加上 `[ExcludeFromInteractiveRouting]`，參考 `Components/Auths/Login.razor`。
注意：加了之後頁面上的 `@onclick` 就不會有反應，表單要改成傳統 POST。

*使用者反映「輸入長文之後畫面就沒反應了」*
十之八九是 SignalR 訊息超過上限。確認 `Program.cs:86` 的值，
瀏覽器 Console 會看到 connection closed。這正是本專案把它調到 10MB 的原因。

*我想知道某個使用者的 circuit 什麼時候斷的*
看日誌裡 `ApplicationCircuitHandler` 的紀錄。

**踩過的坑**

| 坑 | 症狀 | 出處 |
|---|---|---|
| 用 Scoped `DbContext` | 追蹤實體只增不減、讀到過期資料、「A second operation was started」| 速查表 §3，由 `DataAccessServiceLifetimeTests` 守門 |
| 在 `<EditForm>` 掛 `@onkeydown` | 對話窗裡按 Enter 就存檔關窗，輸入還沒完成 | 速查表 §6.3，由 `ModalKeyboardConventionTests` 守門 |
| 沒調 `MaximumReceiveMessageSize` | 輸入長文後連線無聲斷掉 | `Program.cs:83-86` 的註解 |

**何時該換掉／深入閱讀**

使用者數上千、需要離線、或要做公開網站時重新評估。
架構細節見 [架構總覽](../architecture/架構總覽.md) §2、§4.1。

### 3.2 AntDesign Blazor

**它在解決什麼問題**

提供現成的表格、對話窗、表單元件、下拉、日期選擇器。
特別是「可排序、可分頁、資料從伺服器來」的表格 —— 那是後台系統最常見也最花時間的東西。

**不用它會怎樣**

光是一個遠端分頁表格（排序、換頁、載入中狀態、空資料狀態、固定欄）
就要寫上千行，而且每個專案重寫一次。

**為什麼選它** ⭐

| 選項 | 取捨 |
|---|---|
| **AntDesign Blazor**（本專案）| 元件最齊全、表格功能最完整、企業後台風格。代價：套件較重，樣式覆寫要照它的 DOM 結構來 |
| MudBlazor | Material 風格、文件好、社群活躍。表格功能較 AntDesign 弱一些 |
| Radzen Blazor | 元件多、有商業支援。部分進階功能要付費 |
| Fluent UI Blazor | 微軟官方、與 Windows 風格一致。元件數量最少 |
| 自己刻 | 完全可控。代價：這個腳手架大概要多花三個月 |

**本專案用在哪**：10 張 `<Table>`、所有對話窗、表單元件、側邊選單。

**可以調什麼**

樣式全部走 token，不要直接改元件。**判準是 DOM 位置，不是元件名稱**：

| 元件渲染在哪 | 樣式寫在哪 |
|---|---|
| `AntContainer` 底下（Modal／Confirm／Notification／Message）| `Components/Commons/OverlayStyles.razor` |
| 頁面 DOM 內（Table／Pagination／Input／Select／Tag）| `wwwroot/theme.css` |

⚠️ `App.razor` 的 AntDesign CSS **載在最後**，所以 `theme.css` 的 `<link>` 必須排在它**之後**，
由 `ThemeConventionTests` 守門。順序錯了，十個清單頁的樣式會**同時靜默失效**。

**常見情境食譜**

*我想換全站顏色* → 見 §7.1，只改 `wwwroot/theme.css` 的 `:root`。

*我想改表格的某個視覺* → 改 `theme.css` 的全域 `.ant-table-*` 規則，
十張表一起生效。**不要**寫在單一檢視的 `.razor.css` 裡。

*我要加一個新對話窗* → 只寫尺寸，果凍視覺由共用基底提供。見對話窗規範 §2.1。

**踩過的坑**

| 坑 | 症狀 |
|---|---|
| 列底色寫在 `tr` 而非 `> td` | 固定的「操作」欄在 hover 時留一塊白 |
| 在檢視的 `.razor.css` 寫 `.ant-*` | 只對你正在改的那一頁生效，然後被複製到其他九頁 |
| 逐窗複製果凍樣式 | 沒被點名的窗自動落空（0.9.28 修） |
| 用 `<Modal Width>` 設尺寸 | 尺寸有兩個來源，下一個人必定改錯地方 |

**何時該換掉／深入閱讀**

幾乎不要換 —— 全站樣式已經跟它的 DOM 結構綁定。
完整規範見 [介面視覺設計規範](../architecture/介面視覺設計規範.md)（常駐介面）與
[對話窗 UI 設計規範](../architecture/對話窗%20UI%20設計規範.md)（浮層），
以及[速查表](../architecture/開發慣例與限制速查.md) §6.1～§6.9。

### 3.3 EF Core + SQLite

**它在解決什麼問題**

用 C# 類別操作資料庫，不用寫 SQL；資料表結構的變更用 **Migration** 做版本控管
（像 git 之於程式碼）。SQLite 則讓整個資料庫就是一個檔案，不需要另外安裝資料庫伺服器。

**不用它會怎樣**

手寫 SQL 與手動管理 schema 演進 —— 「這個欄位是哪一版加的」「測試機的 schema 跟正式機一樣嗎」
這類問題會長期消耗時間。

**為什麼選它** ⭐

EF Core 的選擇沒什麼爭議（.NET 生態的預設）。**真正的取捨在 SQLite**：

| 選項 | 取捨 |
|---|---|
| **SQLite**（本專案）| 零安裝、整個資料庫一個檔、備份就是複製檔案。**代價：單寫入者、無法多機共用** |
| SQL Server | 併發強、工具成熟、企業常見。代價：要授權、要安裝、要 DBA |
| PostgreSQL | 免費、功能強、跨平台。代價：要安裝與維運 |

本專案選 SQLite 是因為腳手架要**能立刻跑起來**，不該要求使用者先裝資料庫。
SQL Server 軌道曾經存在，0.4.24 移除（決策見 `changelog/2026-08-17-移除工作項目會議記錄與MSSQL支援.md`）。

> ⚠️ **這裡有一個要正視的矛盾**：本專案的快取支援 Redis（那是為了多台機器共用），
> 但 SQLite 是本機檔案，**兩台機器不能共用同一個 `.db`**。
> 如果你真的要橫向擴充，資料庫必須先換掉 —— 快取支援 Redis 並不代表這個系統可以多機部署。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `MyProject.AccessDatas/BackendDBContext.cs` | DbContext 與 13 個 Entity |
| `MyProject.AccessDatas/Migrations/` | 全部 migration |
| `ServiceCollectionExtensions.cs:166-190` | **雙註冊**（見下） |
| `Program.cs:285-294` | 啟動時自動 `Migrate()`（沒有 migration 就 `EnsureCreated()`）|

**⚠️ 雙註冊：為什麼有兩種取得 DbContext 的方式**

```
AddDbContextFactory<BackendDBContext>()   → Blazor 路徑用，每個方法建一個、用完即棄
AddScoped(從工廠取一個)                    → Web API 路徑用（scope ＝ 一次 HTTP 請求，本來就正確）
```

理由見 §3.1 的 circuit 說明。**不要改回單純的 `AddDbContext`** ——
`DataAccessServiceLifetimeTests` 會擋。

**可以調什麼**

| 參數 | 位置 | 預設 | 改了會怎樣 |
|---|---|---|---|
| 資料庫檔位置 | `appsettings.json` → `SystemSettings:ExternalFileSystem:DatabasePath` | `C:\temp\MyProject\DB` | 改完要重啟；舊檔不會自動搬過去 |
| 連線字串 | **不可直接設定** | 由 `MagicObjectHelper.GetSQLiteConnectionString(DatabasePath)` 組出來 | `SystemSettings:ConnectionStrings:SQLiteDefaultConnection` 是**死設定**，從未被讀取 |
| 資料庫檔名 | `MagicObjectHelper.cs:7` | `BackendDB.db` | 寫死，不是設定 |

**常見情境食譜**

*我要加一個欄位*
改 Entity → 產 migration → 啟動時自動套用：
```powershell
cd src/YourApp
dotnet ef migrations add AddInvoiceNote --project YourApp.AccessDatas --startup-project YourApp.Web
```
⚠️ **任何 Entity／欄位變更都要產 migration**，否則程式與資料庫 schema 會不一致。

*我要把資料庫搬到別的路徑*
改 `DatabasePath` → 停掉服務 → 把 `.db`、`.db-wal`、`.db-shm` **三個檔一起**搬過去 → 重啟。
只搬 `.db` 會遺失尚未寫回的交易。

*我要換成 PostgreSQL / SQL Server*
這不是改設定，是改程式：換 NuGet provider、改 `AddConfiguredDatabase` 的 `UseSqlite`、
**重新產生整套 migration**（provider 之間不通用）、檢查所有 `collation` 與字串比較行為。
評估成本見 §10。

**踩過的坑**

| 坑 | 症狀 | 出處 |
|---|---|---|
| `Skip`/`Take` 之前沒有 `OrderBy` | 同一筆在第 1、2 頁都看到，或翻遍所有頁都看不到 | 速查表 §3.1（0.4.46 修）|
| 加唯一索引的 migration 沒先清理既有資料 | migration 回滾、**每次重啟都再失敗一次** | 速查表 §4.2 |
| SQLite 的 `lower()` 只折疊 ASCII | `ÉCOLE`／`école` 不視為重複 | 速查表 §4.2 已知限制 |
| 字串尾隨空白 | 「技術文件 」與「技術文件」同時存在 | 速查表 §4.2（0.4.41 修）|

**何時該換掉／深入閱讀**

併發寫入變多、或需要多機部署時。
資料模型見 [資料模型與資料庫](../architecture/資料模型與資料庫.md)，
指令見 [EFCore 指令備忘](EFCore.md)。

### 3.4 Cookie 驗證 ＋ JWT Bearer（雙軌）

**它在解決什麼問題**

兩種使用者要用兩種方式證明身分：

- **瀏覽器上的人** → Cookie。登入後瀏覽器自動帶著，不用寫任何程式。
- **程式呼叫 API** → JWT。放在 HTTP 標頭裡，可跨網域、可設定短效期。

**不用它會怎樣**

只用 Cookie，外部系統呼叫 API 會很彆扭（要處理 cookie jar、CSRF）。
只用 JWT，瀏覽器端要自己存 token、自己續期，還有 XSS 竊取的風險。

**為什麼選它** ⭐

雙軌的代價是「兩套設定、兩套 claim」，但換來的是兩種情境都自然。
替代方案是引入完整的 Identity Provider（IdentityServer／Keycloak／Entra ID），
那對「內部後台」來說是殺雞用牛刀 —— 除非你本來就要做單一登入。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `Program.cs:152-160` | Cookie scheme，`LoginPath` `/Auths/Login` |
| `Program.cs:161-199` | JWT Bearer，自訂 `OnChallenge`／`OnForbidden` 讓 401／403 也回 `ApiResult` |
| `Program.cs:201-216` | Google OAuth2（**只有設定完成時才註冊**）|
| `MyProject.Web/Auth/JwtTokenService.cs` | 簽發與驗證 |

**⚠️ 兩套的 claim 對應是相反的**

| Claim | Cookie | JWT |
|---|---|---|
| `Sid` | UserId | — |
| `NameIdentifier` | **帳號** | **UserId** |
| `Name` | **姓名（個資）** | **帳號** |

`HasPermissionAttribute.ResolveActor` 用「`NameIdentifier` 是不是數字」判斷來源。
**寫任何從 claim 取身分的程式時，不要假設只有一套。**

**⚠️ 滑動續期不是「每次使用都續」**

`SlidingExpiration` 同樣沒有設定，框架預設是 **`true`** —— 但它的規則比直覺複雜：
**已經用掉超過一半效期時的那一次請求才會續期，而且是從那一刻起重新算滿。**

假設效期設 3 天（中點 1.5 天），最後一次使用的時間決定一切：

| 最後一次使用 | 已過／剩餘 | 會不會續期 | 實際失效 |
|---|---|---|---|
| 第 1 天 | 1 天／2 天，剩餘較多 | 不續 | 第 3 天（原訂）|
| 第 2 天 | 2 天／1 天，剩餘較少 | **會續** | **第 5 天**（第 2 天 ＋ 3 天）|

所以答案既不是「第 3 天」也不是「第 4 天」，而是「**觸發續期的那一刻 ＋ 完整效期**」。

套回現況（0.9.39 起可設定）：沒勾記住我是 **8 小時**（中點 4 小時）、
勾了是 **30 天**（中點 15 天）。0.9.39 之前吃的是框架隱藏預設 14 天。

⚠️ **Blazor Server 專屬陷阱**：續期只發生在**真正的 HTTP 請求**上。頁面載入之後，
Blazor 的換頁走的是 SignalR circuit，**不經過 cookie 中介軟體**。所以「使用者開著分頁
操作一整天」並不保證會續到 cookie —— 要等到重新整理、開新分頁或檔案下載那類真正的
HTTP 往返。這代表**實際被登出的時機可能比你預期的早**。

**可以調什麼**

| 參數 | 位置 | 預設 | 範圍 | 改了會怎樣 |
|---|---|---|---|---|
| `JwtSettings:AccessTokenMinutes` | appsettings | `60` | 1–1440 | 越短越安全，但呼叫端要更常換 token |
| `JwtSettings:RefreshTokenDays` | appsettings | `7` | 1–365 | ⚠️ refresh token **無法個別撤銷**，只能靠短效期或換金鑰 |
| `JwtSettings:ClockSkewMinutes` | appsettings | `2` | 0–60 | 容忍伺服器之間的時鐘誤差 |
| `JwtSettings:SigningKey` | appsettings／環境變數 | 開發預設值 | ≥32 字元 | **改了之後所有既有 token 立刻失效**（這就是「換金鑰」撤銷法）|
| `CookieSettings:ExpireMinutes` | appsettings | `480`（8 小時）| 1–43200 | **沒勾**記住我時的票證效期 |
| `CookieSettings:RememberMeDays` | appsettings | `30` | 1–365 | **勾了**記住我時的票證效期（登入時以 `ExpiresUtc` 覆蓋）|
| `CookieSettings:SlidingExpiration` | appsettings | `true` | — | 過半效期才續、從當下重新算滿（見上）。設 `false` 則到期就是到期 |
| `SystemSettings:ExternalFileSystem:DataProtectionKeyPath` | appsettings | `C:	emp\MyProject\Keys` | — | 🔴 **金鑰環目錄。換掉＝全站立刻登出**（見「踩過的坑」）|
| 「記住我」 | `Login.razor.cs:139` | `IsPersistent` ＝勾選值 | — | 只影響**瀏覽器端**：不勾＝關瀏覽器即失效的 session cookie。⚠️ **票證效期兩者相同**，沒有「記住我比較久」這回事 |
| Google 登入的持久性 | `ExternalAuthController.cs:111-113` | **永遠 session cookie** | — | 🔴 沒傳 `AuthenticationProperties`，等同永遠沒勾記住我（見「踩過的坑」）|
| 外部 OAuth cookie | `Program.cs:206-208` | 5 分鐘 | — | 只在 OAuth 往返期間使用，不需要長 |

**常見情境食譜**

*我要讓登入 session 短一點*
改 `appsettings.json` 的 `CookieSettings:ExpireMinutes`（0.9.39 起，之前要動程式碼）。
⚠️ **只改這一個鍵不夠**：滑動續期預設開著，8 小時會在使用者每 4 小時進站一次時無限延長。
真的要「上班時間到就重新登入」，得同時把 `CookieSettings:SlidingExpiration` 設成 `false`。

*使用者在第 2 天用過系統，第幾天才會被登出？*
不是第 3 天也不是第 4 天 —— 是**觸發續期的那一刻再加一個完整效期**。
規則與走查表見上面的「⚠️ 滑動續期不是『每次使用都續』」。

*這個效期應該搬到 `appsettings.json` 嗎？*
**已經搬了**（0.9.39）—— 見上面的 `CookieSettings`。當初判斷要搬的三個理由值得記下來，
因為它們就是 §5 那條判準的實例：(1) 它會因環境而異（內部工具 30 天，對外系統可能要 8 小時，
而且常被客戶的資安政策直接規定）；(2) API 那一軌早就外部化了
（`JwtSettings:AccessTokenMinutes`／`RefreshTokenDays`），UI 這一軌卻連 hard-code 都沒有；
(3) 改它不該需要重新編譯部署。
⚠️ **但不是每個旋鈕都該外部化** —— 隔壁那個 OAuth 往返的 5 分鐘就**刻意沒有**跟著搬，
它不因環境而異，抽出來只是多一個沒人會調的鍵。

*我要讓某個外部系統呼叫 API*
在 `/Profile` 幫他設一組 API 密碼 → 他用 Email ＋ 該密碼打 `/api/v1/auth/login` 換 JWT。
注意這與登入密碼是**兩組不同的密碼**。

*我要立刻讓所有 token 失效*
換掉 `JwtSettings:SigningKey`。這是目前唯一的撤銷手段。

**踩過的坑**

🔴 **沒有設定 Data Protection，登入就存不住**（0.9.39 修正）。登入 Cookie 是用
Data Protection 的金鑰加密的。0.9.39 之前完全沒有 `AddDataProtection()`，金鑰落在
使用者設定檔下 —— **IIS 的應用程式集區若未載入使用者設定檔，會退化成「只存在記憶體」**，
每次回收（IIS 預設 20 分鐘閒置關閉、29 小時定期回收）就換一批，全站所有人被登出。
現在固定寫到 `DataProtectionKeyPath`，並以 `SetApplicationName` 固定判別子
（不固定的話，**換部署路徑也會失效**）。
⚠️ Windows 上金鑰檔以 DPAPI 加密，**應用程式集區識別身分換掉一樣會解不開**；多機要共用目錄。

🔴 **而且它還會被放大**：`AuthenticationStateHelper` 在「未認證」時原本導向
`/Auths/Logout`，而那一頁會無條件 `SignOutAsync` **刪掉 Cookie**。於是 Cookie 只要有
**任何一次**讀不到，原本還有效的「記住我」就被永久毀掉，症狀還會自我延續。
0.9.39 起該分支改導向 `/Auths/Login`（其餘五個分支維持導向登出），
由 `AuthenticationStateHelperTests` 釘住。


🔴 **Google 登入的 `SignInAsync` 沒有傳 `AuthenticationProperties`**
（`ExternalAuthController.cs:111-113`，用的是三參數多載）。後果是 Google 使用者的
`IsPersistent` 永遠是 `false` —— 等同永遠沒勾「記住我」，關掉瀏覽器就要重新登入，
而 Google 登入那條路上也沒有「記住我」可以勾。**這是未預期的不一致，不是設計決定。**
帳密登入那一支（`Login.razor.cs:137-141`）是有傳的。

`.MyProject.External` 這個 cookie 名稱裡有專案名 —— 改名時要一起改，
否則兩個衍生專案在同一台機器上會互相干擾（上手指南 §8.3 的高風險清單）。

**何時該換掉／深入閱讀**

要做單一登入（SSO／OIDC）時。
[認證授權與權限機制](../security/認證授權與權限機制.md)、
[記住我登入原理說明](../security/記住我登入原理說明.md)（這份寫得像教材，推薦給新人）、
[Google OAuth2 第三方登入](../security/Google%20OAuth2%20第三方登入.md)。

### 3.5 RBAC 動作級授權

**它在解決什麼問題**

不只控制「能不能進這一頁」，而是「能看但不能改」「能改但不能刪」。

**不用它會怎樣**

只能做到頁面層級的開關。實務上客戶第一個要求就是「這個角色只能看」。

**為什麼選它** ⭐

本專案是自己實作的 RBAC，不是用 ASP.NET Core Identity。理由：
Identity 帶來的是「使用者與密碼管理」，而本專案真正需要的是
「**權限鍵 ＋ 角色 ＋ 團隊行級過濾**」三層模型，Identity 對後兩層沒有幫助。
代價是密碼雜湊、鎖定這些要自己寫（`SecurePasswordHasher`、`MyUserServiceLogin`）。

**模型**

```
使用者 ──┬─ 主要角色（RoleViewId）──┐
         └─ 額外角色（UserRole）────┴─→ 權限取聯集 → RolePermissionMap → Permission
         └─ 直綁團隊（UserTeam）───┬─→ 有效團隊 → 決定看得到哪些「資料列」
                角色預設團隊 ──────┘
         └─ IsAdmin ────────────────→ 短路所有動作級檢查，且不受團隊過濾
```

**本專案用在哪**：`[HasPermission("resource:action")]`（API）、
`CheckAccessPage`／`CheckAccessAction`（UI），兩邊共用 `IPermissionChecker`。

**可以調什麼**

權限鍵不是設定，是程式常數。新增一個受權限控管的頁面要**同步四處**：

1. `MagicObjectHelper.cs` 新增權限鍵常數
2. `Datas/Menu.json` 新增項目（唯一 `id`）
3. `SidebarMenuService.MenuPermissionMap` 加 `id → 權限鍵`
4. 頁面的 `CheckAccessPage(權限鍵)` 用**同一個鍵**

⚠️ 四方一致由 `MenuPermissionConsistencyTests` 守門。第四方用錯鍵的症狀是
「使用者看得到選單、點進去被踢出」。

**常見情境食譜**

*我要新增一個只有某些角色能看的頁面* → 照上面四處同步，然後去角色管理勾選。

*我要一個「只能看不能改」的角色* → 角色管理裡只勾 `view`，不勾 `create/edit/delete`。

*為什麼我勾不到「使用者管理」的權限？*
系統管理與統計分析各頁的權限鍵**刻意不上架角色矩陣** —— 它們只靠 `IsAdmin` 放行。
由 `AdminOnlyPermissionTests` 守門，**請勿補上**。

**踩過的坑**

`RoleView.TabViewJson` 是舊的權限彙總字串，現在只剩「角色編輯畫面回填」的用途，
**不參與權限判定**（判定讀 RBAC 關聯表）。不要手改它。

**何時該換掉／深入閱讀**

⭐ **完整的權限設計教學在 [§6](#6-權限控管設計指南)** —— 通用觀念、六層防線、
五個人物走查、操作步驟與 FAQ。這一節只講「這項技術是什麼」。

需要「資料列層級」的細緻權限時（目前只有團隊層級）。
[認證授權與權限機制](../security/認證授權與權限機制.md)、
[權限授權現況評估與改善路線](../security/權限授權現況評估與改善路線.md)（含決策紀錄）、
[速查表 §5](../architecture/開發慣例與限制速查.md)。

### 3.6 AutoMapper

**它在解決什麼問題**

同一筆資料在系統裡有三種形狀：資料庫的 Entity、API 對外的 DTO、畫面用的 AdapterModel。
AutoMapper 負責在它們之間搬欄位，不用手寫幾十行賦值。

**不用它會怎樣**

每個模組要手寫三組轉換，而且**加欄位時很容易漏掉其中一組** ——
症狀是「新欄位在畫面上填了，存進去卻是空的」。

**為什麼選它** ⭐

| 選項 | 取捨 |
|---|---|
| **AutoMapper**（本專案）| .NET 生態最通用、寫法最省。**代價：16.x 是商業授權版本** |
| Mapperly | 原始碼產生器，編譯期產生轉換程式碼、零反射、免費。代價：語法不同，要重寫 Profile |
| 手寫轉換 | 零相依、完全可控、編譯期就能發現漏欄位。代價：程式碼量大 |

> ⚠️ **授權風險（複製腳手架時最容易忽略的法務問題）**
>
> 目前版本是 `AutoMapper 16.1.1`（`Directory.Packages.props`）。
> 未設定 `AutoMapper:LicenseKey` 時，**應用程式啟動會在日誌印出**：
>
> ```
> You do not have a valid license key for the Lucky Penny software AutoMapper.
> This is allowed for development and testing scenarios. If you are running in
> production you are required to have a licensed version.
> ```
>
> 這段是實際執行時捕獲的訊息，不是推測。**正式商用前請確認授權狀態。**
> 若不打算購買，最實際的替代是改用 Mapperly（見 §10）。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `MyProject.Business/Models/AutoMapping.cs` | 唯一的 Profile，所有映射都在這裡 |
| `Program.cs:225-234` | 註冊，並在有 `LicenseKey` 時套用 |

**可以調什麼**

| 參數 | 位置 | 預設 | 說明 |
|---|---|---|---|
| `AutoMapper:LicenseKey` | appsettings（建議放 User Secrets）| `""` | 留空會印出上面那段警告 |

**常見情境食譜**

*我加了一個新模組，要設定映射*
在 `AutoMapping.cs` 加 `CreateMap<Entity, Dto>()` 等三組。
名稱相同的屬性會自動對應，不同的用 `ForMember`。

*我加的欄位存不進去*
檢查 `AutoMapping.cs` 有沒有那個欄位的映射。這是最常見的原因。

*多值標籤（List ↔ 換行分隔字串）怎麼處理*
已經有現成寫法，用 `TagStringHelper`，掛在 `ForMember` 上。參考 `Categories`／`Teams`。

**踩過的坑**

| 坑 | 說明 |
|---|---|
| 正規化寫在檢查而非映射上 | `NameNormalizer` 必須掛在「→ Entity」的映射上，這樣 Blazor 與 API 兩條路徑才都涵蓋到。速查表 §4.2 |
| `Clone()` 是淺複製 | List 欄位改多選會連帶改到表格那一列。一律「指派新清單」 |

**何時該換掉／深入閱讀**

授權成本不可接受時 → Mapperly。
[DTO 與模型邊界規範](../architecture/DTO%20與模型邊界規範.md)。

### 3.7 NLog

**它在解決什麼問題**

把系統發生的事寫成檔案，分等級（Trace/Debug/Info/Warn/Error/Fatal），
自動按日輪替、自動刪掉太舊的。出事時這是唯一的現場。

**不用它會怎樣**

`Console.WriteLine` 在正式環境看不到；用 .NET 內建的 logging 則沒有檔案輪替與保留策略。

**為什麼選它** ⭐

| 選項 | 取捨 |
|---|---|
| **NLog**（本專案）| 設定檔驅動、支援執行期 `autoReload`、target 種類多。代價：XML 設定 |
| Serilog | 結構化日誌（每筆是一個物件）、生態最活躍。若你要送到 Seq／Elastic，Serilog 比較順 |
| 內建 `ILogger` ＋ 檔案 provider | 最少相依。代價：輪替與保留要自己處理 |

本專案選 NLog 主要是因為 **`autoReload` ＋ 執行期調整等級**這個組合 ——
`/log-level-setting` 頁就是靠它做到「不重啟就改等級」。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `src/MyProject/MyProject.Web/nlog.config` | 64 行：4 個 target、8 條 rule |
| `Program.cs:51-75` | 讀 `NLog:BasePath`、`ClearProviders()`、`UseNLog()`、注入變數 |
| `Diagnostics/LogLevelRuntimeState.cs` | 執行期等級覆寫，並在 autoReload 後重新注入變數 |

**`nlog.config` 的結構**

```
根屬性     autoReload="true"  throwConfigExceptions="true"  internalLogLevel="Info"
targets    file_async (AsyncWrapper) → file     ← 寫檔，有輪替與保留
           console_async (AsyncWrapper) → console
rules      1. Microsoft.Hosting.Lifetime*        Info   final
           -  Microsoft.AspNetCore.Hosting.*     Info   final   ← 預設註解掉
           2. Microsoft.EntityFrameworkCore.*    Warn   final
           3. Microsoft.*                        Warn   final
           4. System.*                           Warn   final
           5. Microsoft.*                        (全部丟棄)      final
           6. System.*                           (全部丟棄)      final
           7. *                                  info           ← 應用程式自己的日誌
```

**可以調什麼**

| 目標 | 改哪裡 | 目前值 |
|---|---|---|
| 日誌存放位置 | **`appsettings.json` 的 `NLog:BasePath`**（不是 nlog.config）| `C:\temp\Logs` |
| **保留天數** | `nlog.config` 的 `maxArchiveDays` | `30` |
| 單檔大小上限 | `archiveAboveSize` | `104857600`（100MB）|
| 輪替頻率 | `archiveEvery` | `Day` |
| 看得到 EF Core 的 SQL | 把 rule 2 的 `minlevel` 由 `Warn` 改成 `Debug` | — |
| 看完整 HTTP 診斷 | 取消註解那條 `Microsoft.AspNetCore.Hosting.Diagnostics*` rule | — |
| 應用程式日誌等級 | rule 7，或用 `/log-level-setting` 頁（不用重啟）| `info` |

**常見情境食譜**

*我要把日誌改成保留 90 天*
`nlog.config` 的 `maxArchiveDays="30"` 改成 `"90"`。`autoReload` 會自動生效，不用重啟。
⚠️ 硬碟空間要一起評估：每天一個檔、單檔上限 100MB。

*我要把日誌搬到別的磁碟*
改 `appsettings.json` 的 `NLog:BasePath`，**不是** nlog.config ——
nlog.config 裡用的是 `${var:BasePath}`，那個變數由 `Program.cs:68` 注入。
改完要**重啟**（這個值只在啟動時讀一次）。

*我只想讓某個 namespace 出 Debug*
在 rule 5、6（那兩條 `final="true"` 的丟棄規則）**之前**插入你的 rule：
```xml
<logger name="YourApp.Business.Services.Invoice*" minlevel="Debug" writeTo="file_async,console_async" final="true" />
```
⚠️ 插在後面永遠不會被執行到 —— 前面的 `final="true"` 已經把它攔走了。

*我要臨時看 Debug，但不想改檔案*
用 `/log-level-setting` 頁。⚠️ 它**只存在記憶體，重啟就回到 nlog.config 的設定**。

*我要加一個新 target（寫到資料庫／寄信／送 Seq）*
在 `<targets>` 加一個，然後把它的名字加進相關 rule 的 `writeTo`。
**用 `AsyncWrapper` 包起來**，並設定有界佇列與 `overflowAction="Discard"` ——
與既有兩個 target 一致，也與本專案例外管線的取捨一致（寧可丟日誌，不可拖垮請求）。

**踩過的坑** ⚠️

| 坑 | 說明 |
|---|---|
| **改 layout 會讓 `/logs` 靜默壞掉** | `LogQueryService.cs:22,24,27` 寫死了 `TimestampLength=24`、`FieldCount=7`。改 layout 之後日誌檢視頁查不到任何東西，**而且不會報錯**。由 `DocumentationConventionTests.NLogLayout_ShouldMatchLogQueryServiceFieldCount` 守門 |
| `autoReload` 會清掉變數 | reload 之後 `BasePath` 會消失、日誌寫到磁碟根目錄。`LogLevelRuntimeState` 在 `ConfigurationChanged` 時重新注入，**不要移除那段** |
| `appsettings.json` 的 `Logging:LogLevel` 是死設定 | `ClearProviders()` 之後它完全無效，改它不會有任何反應 |
| 記錄了不該記的東西 | **絕不記錄密碼／token／金鑰／驗證碼／Email／姓名**。由 `LoggingConventionTests` 擋 |

**何時該換掉／深入閱讀**

要做結構化日誌並送到 Seq／Elastic 時考慮 Serilog（見 §10）。
[日誌與設定檔說明](../operations/日誌與設定檔說明.md) §1–§3 是日誌內容規範的權威來源。

### 3.8 分散式快取（Memory／Redis）

**它在解決什麼問題**

把算過或讀過的東西暫存起來，下次直接拿。換成 Redis 之後，多台機器可以共用同一份快取。

**不用它會怎樣**

側邊選單每次換頁都要重讀 `Menu.json` 並重算權限過濾。

**為什麼選它** ⭐

用的是 .NET 內建的 `IDistributedCache` 抽象，外面再包一層 `ICacheService`。
好處是**切換 provider 不用改任何呼叫端**，只改一個設定值。
替代方案是直接用 `IMemoryCache`（更簡單，但永遠無法多機共用）。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `MyProject.Web/Caching/DistributedCacheService.cs` | `ICacheService` 實作 |
| `ServiceCollectionExtensions.cs:195-222` | 依設定註冊 Memory 或 Redis |
| `Components/Layout/SidebarMenuService.cs:10` | 目前唯一的使用者，快取鍵 `sidebar:menu:raw` |

**可以調什麼**

| 參數 | 預設 | 說明 |
|---|---|---|
| `CacheSettings:Provider` | `Memory` | `Memory` 或 `Redis`；**填別的字串會在啟動時丟例外** |
| `CacheSettings:RedisConnection` | `""` | Provider=Redis 時必填，否則啟動失敗 |
| `CacheSettings:InstanceName` | `MyProject:` | Redis 鍵的前綴。改名時要一起改，否則兩個專案會共用快取 |
| `CacheSettings:DefaultExpirationMinutes` | `30` | 絕對過期（不是滑動）。程式有 1 分鐘的下限保護 |

**常見情境食譜**

*我改了 `Menu.json` 但選單沒變*
快取還沒過期。重啟，或等 30 分鐘。這是最常見的困惑。

*我要換成 Redis*
`Provider` 改 `Redis`、填 `RedisConnection`（建議放 User Secrets）。呼叫端一行都不用改。

*我要快取自己的查詢*
注入 `ICacheService`。⚠️ 注意它的 `null` 語意 —— 快取值為 `null` 與「沒有快取」無法區分。

**何時該換掉／深入閱讀**

要多機部署時 —— 但先讀 §3.3 的矛盾，資料庫才是真正的瓶頸。
[分散式快取機制](../features/分散式快取機制.md)（93 行，含四個程式範例）。

### 3.9 速率限制

**它在解決什麼問題**

擋住「同一個人在一分鐘內打了五千次 API」。最常見的用途是防暴力破解密碼。

**不用它會怎樣**

登入端點會被字典攻擊；一個寫壞的呼叫端迴圈就能拖垮整個服務。

**為什麼選它** ⭐

用的是 .NET 7 起內建的 `RateLimiter`，不是 AspNetCoreRateLimit 之類的套件 ——
內建的夠用，少一個相依。代價是功能較陽春（例如沒有分散式計數，多機部署時每台各算各的）。

**本專案用在哪**：`ServiceCollectionExtensions.cs:248-340`，
`Program.cs:439` 的 `MapControllers().RequireRateLimiting("api")`。

**設計重點：只有一個政策，裡面分兩種配額**

```
政策 "api"
 ├─ 登入路徑（/api/Auth/login、/api/v1/Auth/login）→ LoginRequestsPerMinute
 └─ 其餘                                          → ApiRequestsPerMinute
分區鍵：user:{帳號} → 沒登入就 ip:{位址} → 都沒有就 "anonymous"
```

⚠️ 兩組配額**寫在同一個政策裡**是刻意的 —— 用 `[EnableRateLimiting("login")]` 另外掛一個政策
會被端點慣例蓋掉，不會生效。

**可以調什麼**

| 參數 | 位置 | 預設 | 可否熱更新 |
|---|---|---|---|
| `RateLimit:ApiRequestsPerMinute` | appsettings | `120` | ✅ 用 `IOptionsMonitor`，改檔即生效 |
| `RateLimit:LoginRequestsPerMinute` | appsettings | `10` | ✅ 同上 |
| **時間視窗** | `ServiceCollectionExtensions.cs:295` | **1 分鐘，寫死** | ❌ 要改程式 |
| **佇列長度** | 同上 `:296` | **`0`（不排隊，超過直接 429）** | ❌ 要改程式 |
| 登入路徑判斷 | 同上 `:312-313` | 兩個路徑寫死 | ❌ 新增登入端點要一起改 |

**常見情境食譜**

*客戶反映 API 常常 429*
先看是不是同一個帳號在跑批次。`ApiRequestsPerMinute` 是**每個呼叫端各自計算**的，
不是全站總量。調大這個值即可，改檔就生效不用重啟。

*我要讓某個端點不受限流*
在該 Controller／Action 掛 `[DisableRateLimiting]`。

*走了反向代理之後，所有人都被算成同一個 IP*
設定 `ForwardedHeaders:KnownProxies` 或 `KnownNetworks`。
⚠️ **不設定的話來源 IP 全部變成代理伺服器，限流形同虛設**，
而且 `X-Forwarded-For` 可以被偽造。這兩個鍵**不在 appsettings.json 裡**，要自己加。

**何時該換掉／深入閱讀**

多機部署時（內建的是單機計數，四台機器等於配額變四倍）→ 考慮 Redis 版的分散式限流。
[日誌與設定檔說明 §4.3.0](../operations/日誌與設定檔說明.md)、
[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)。

### 3.10 健康檢查

**它在解決什麼問題**

兩件不同的事：
1. **給機器看**：負載平衡器／容器編排要知道「這台能不能收流量」。
2. **給人看**：值班的人要一眼看出「現在是不是有東西壞了」。

**不用它會怎樣**

服務掛了要等使用者回報；重新部署時流量會打到還沒準備好的機器。

**為什麼選它** ⭐

`/health/live` 與 `/health/ready` 用的是 .NET 內建的 Health Checks（標準做法）。
但**人看的那一頁是自己寫的**（`/system-health`）—— 內建的健康檢查只回傳
Healthy/Unhealthy，本專案需要「百分比 ＋ 燈號 ＋ 佐證數值」，所以自己做了一層計分。

**本專案用在哪**

| 位置 | 內容 |
|---|---|
| `Program.cs:433-437` | `/health/live`（tag `live`）、`/health/ready`（tag `ready`）|
| `MyProject.Web/Health/SystemHealthService.cs` | 11 項檢查 |
| `MyProject.Web/Health/SystemHealthScoreCalculator.cs` | 計分與燈號 |

**計分方式**

```
每一項：正常 = 拿滿權重，警示 = 拿一半，異常 = 0
分數 = 得分 ÷ 總權重 × 100
燈號：≥90 綠，≥70 黃，其餘紅
```

⚠️ **總權重是 125 不是 100**（由 `SystemHealthTests.CheckWeights_ShouldSumTo125` 釘住）。
權重高不代表比較嚴重，只代表比較影響分數。

| 檢查項 | 權重 | 檢查項 | 權重 |
|---|---|---|---|
| 資料庫 | 25 | 網站／應用程式 | 10 |
| 日誌 | 15 | API | 10 |
| 身分驗證 | 15 | 檔案系統 | 10 |
| 安全設定 | 10 | LLM API | 10 |
| 快取服務 | 10 | 主機資源 | 5 |
| AI 計費表 | 5 | | |

**可以調什麼**

權重、檢查項、燈號門檻**全部寫死在程式裡**，不是設定。要改就是改
`SystemHealthService.cs` 與 `SystemHealthScoreCalculator.cs:23-33`。

⚠️ 新增或移除檢查項會改變總權重，`SystemHealthTests` 會紅 —— 記得同步測試裡的數字與文件。

**常見情境食譜**

*我要加一項自己的檢查（例如外部 API 通不通）*
在 `SystemHealthService` 加一個回傳 `SystemHealthItem` 的方法，給它一個權重，
更新 `SystemHealthTests.CheckWeights_ShouldSumTo125` 的期望值與
[系統健康監控](../features/系統健康監控.md) 的權重表。

*為什麼開這一頁會產生 AI 費用？*
⚠️ 「LLM API」那一項**每次開頁都真的呼叫一次 API**，會計費，
並以作業名稱「系統健康檢測」出現在 Token 用量頁。不想要的話拿掉那一項檢查。

*負載平衡器該打哪個端點？*
`/health/ready`。`/health/live` 只代表行程還活著。

**何時該換掉／深入閱讀**

要接 Prometheus／Grafana 時 → 見 §10 的 OpenTelemetry。
[系統健康監控](../features/系統健康監控.md)。

### 3.11 AI 整合與 Token 計費

**它在解決什麼問題**

兩件事：把一大堆日誌丟給 LLM 整理成人看得懂的報告；以及**記錄每一次呼叫花了多少錢**。

**不用它會怎樣**

出事時要人工翻幾千行日誌；用了 LLM 卻不知道每個月會被扣多少。

**為什麼選它** ⭐

刻意**不用 Semantic Kernel 或 LangChain** —— 那些是為了 agent、RAG、工具呼叫設計的，
而本專案只需要「送一次 chat completion、拿回一段 Markdown」。
直接用 `HttpClient` 打 REST，相依最少、行為最可預測。
代價：如果你之後要做 RAG 或多輪對話，要自己補。

**本專案用在哪**：`MyProject.Web/Ai/`（14 個檔）。
兩個呼叫點：日誌檢視頁的「AI 分析」、健康監控頁的 LLM 探測。

**可以調什麼**

| 參數 | 預設 | 在 appsettings？ | 說明 |
|---|---|---|---|
| `AiSettings:ApiKey` | `""` | ✅ | **有沒有填就是開關**，沒有獨立的 Enabled |
| `AiSettings:Provider` | `AzureOpenAI` | ✅ | 或 `OpenAI` |
| `AiSettings:Endpoint` | `""` | ✅ | Azure 必填；OpenAI 留空 |
| `AiSettings:Model` | `""` | ✅ | Azure 填**部署名稱**，OpenAI 填模型 id |
| `AiSettings:TimeoutSeconds` | `600` | ✅ | ≤0 時程式退回 120 秒 |
| `AiSettings:SystemPrompt` | 程式預設 | ❌ | 不寫就用 `AiPromptDefaults.SystemPrompt` |
| `AiSettings:MaxEntries` | `100` | ❌ | 一次送幾筆日誌 |
| `AiSettings:MaxOutputTokens` | `null` | ❌ | `null` 代表不送這個參數 |
| `AiSettings:Temperature` | `null` | ❌ | 同上 |
| `AiPricingSettings:UsdToTwd` | `31.5` | ✅ | 匯率 |
| `AiPricingSettings:Models` | 8 個模型 | ✅ | 費率表 |

**⚠️ 新增自己的 LLM 呼叫點：三件事，一件都不能少**

1. 注入 `ITokenUsageRecorder`（**不要**直接相依 `TokenUsageLogService`）
2. 在 `TokenUsageOperations`／`TokenUsageCallKinds` 登記常數
3. 拿到回應後呼叫一次 `RecordAsync`

做完這三件事，該次呼叫會自動出現在 `/token-usage` 與五個統計頁籤，**不需要改畫面**。
**漏記的那一筆，通常正是花掉最多錢的那一筆。**

還要記得在 `AiPricingSettings:Models` 補上該模型的費率，否則會全部記成「未定價」。

**常見情境食譜**

*我要接自己的 Azure OpenAI*
`Provider=AzureOpenAI`、`Endpoint` 貼入口網站給的端點（程式會自動補 `/openai/v1`）、
`Model` 填**部署名稱**不是模型名稱、`ApiKey` 放 User Secrets。

*我要控制花費*
本專案**刻意不做應用層限流** —— 請在 Azure OpenAI 資源的配額層設 TPM/RPM。
另外注意健康監控頁每次開啟都會呼叫一次。

*費用顯示「未定價」*
`AiPricingSettings:Models` 裡沒有那個模型的費率。費率是**前綴比對**的
（`gpt-4o-2024-08-06` 會套 `gpt-4o`），加一組對應的 key 即可。
⚠️ 已經記錄的歷史資料**不會回頭補算** —— 費用是呼叫當下的快照。

**踩過的坑**

| 坑 | 說明 |
|---|---|
| 把模型回應直接丟進 `MarkupString` | 日誌含使用者輸入，模型輸出是**攻擊者可部分控制的**。一律走 `AiMarkdownRenderer.ToSafeHtml` |
| 回吐上游錯誤 body | body 可能夾帶整份提示詞（＝日誌內容）。錯誤訊息只能由固定字串 ＋ `error.code` 組成 |
| 健康檢查沿用 600 秒逾時 | 自動載入的頁面端點一失聯就卡十分鐘。健康探測自帶 30 秒 |

**何時該換掉／深入閱讀**

要做 RAG、多輪對話或工具呼叫時 → 考慮 Semantic Kernel。
[AI 日誌分析](../features/AI日誌分析.md)（428 行，最詳盡的一份）、
[速查表 §6.7](../architecture/開發慣例與限制速查.md)（新增呼叫點的紅線）。

### 3.13 檔案上傳

**它在解決什麼問題**

讓使用者把檔案掛在一筆紀錄上，並且安全地存起來、再讓人下載。

**為什麼這樣做** ⭐

**存在本機磁碟，沒有抽象層。** 三個地方各自處理檔案：
專案附件（`ProjectService`）、例外堆疊檔（`ExceptionStackFileStore`）、
Token 原始 JSON（`TokenUsageRawStore`）。
這是刻意的簡化 —— 腳手架不預設你會用雲端儲存。
代價是要換 S3／Azure Blob 時得改三處（見 §9 缺口 7、§10）。

**可以調什麼**

| 參數 | 位置 | 預設 |
|---|---|---|
| 附件根目錄 | `SystemSettings:ExternalFileSystem:ProjectFilePath` | `C:\temp\MyProject\ProjectFile` |
| 允許的副檔名 | `SystemSettings:Upload:AllowedExtensions`（**不在 appsettings，要自己加**）| 留空 ＝ 用內建的 18 種 |
| **單檔大小上限** | `ProjectService.cs:17`（**寫死**）| **1GB** |
| 下載掛載路徑 | `ApplicationBuilderExtensions.cs:251`（寫死）| `/UploadFiles` |

內建白名單（`UploadFileTypePolicy.cs:26-47`）：
`.pdf .txt .csv .doc .docx .xls .xlsx .ppt .pptx .jpg .jpeg .png .gif .bmp .webp .zip .7z .rar`
**刻意不含** `.html .htm .svg .xhtml`（可執行 script，同源 XSS）與
`.exe .dll .bat .cmd .ps1 .sh .js`。

**常見情境食譜**

*我要允許上傳 `.svg`*
⚠️ 先想清楚：SVG 可以內嵌 script，下載時若回吐 ContentType 就是同源 XSS。
真的要開就在 `SystemSettings:Upload:AllowedExtensions` 自己列一份完整白名單。

*我要把上限從 1GB 改成 100MB*
`ProjectService.cs:17` 的常數，**三處都要對齊**：伺服器端檢查、
`ProjectViewView.razor.cs:319` 的前端檢查、`OpenReadStream` 的參數。

**⚠️ 已知限制**：`DownloadPath` 底下的檔案，**任何已登入使用者**都讀得到
（那條靜態檔路由沒有逐筆權限檢查）。專案附件走的是有權限檢查的 Controller，不受影響。

**深入閱讀**：[檔案上傳機制](../features/檔案上傳機制.md)。

### 3.14 多語系

**它在解決什麼問題**

讓同一套系統顯示不同語言。

**⚠️ 現況：這是一個空殼**

必須講清楚，否則會誤導：

| 項目 | 狀態 |
|---|---|
| `AddLocalization()` 與 zh-TW／en-US 文化 | ✅ 有註冊 |

| **`IStringLocalizer` 的使用** | ❌ **零處** |
| **語言切換器** | ❌ 沒有。`RequestCultureProviders` 刻意只留 `Accept-Language` |

**要真的做多語系需要**：把所有硬編字串抽到 `.resx`、加語言切換器與 Cookie provider、
處理 `MagicObjectHelper.預設角色` 這類中文識別字。這是一項大工程，見 §10。

**深入閱讀**：[多語系與本地化](../features/多語系與本地化.md)。

### 3.15 測試與守門測試文化

**它在解決什麼問題**

一般測試驗證「功能對不對」。本專案還有另一種測試：**擋住「照著做會出錯但不會報錯」的寫法**。

**為什麼有這種東西** ⭐

這個腳手架踩過的坑有一個共同特徵 —— **不會壞、不會紅、CI 全綠，只有實際點開那一頁才看得出來**：

- 對話窗少寫 `MaskClosable="false"` → 誤點遮罩，整份輸入無聲蒸發
- 用 `EditContext.IsModified()` → **恆為 false**，未儲存提示永遠不跳
- 匯出用 `new UTF8Encoding(true)` → 沒有 BOM，Excel 開啟整片亂碼
- 色票寫死在檢視裡 → 半年後換品牌色翻五個檔都翻不完

文件擋不住這些（沒人會每次都讀），所以把它們變成**會紅的測試**。
這是本專案最重要的品質機制，也是複製腳手架時最該保留的東西。

**目前的規模**

| 類別 | 數量 | 說明 |
|---|---|---|
| 測試總數 | 約 602 | `[Fact]` ＋ `[Theory]` 展開 |
| **守門測試檔** | **18** | 見下 |
| 行為測試檔 | 約 42 | API 契約、RBAC、領域服務、AI 與計費 |

守門測試包括：`MenuPermissionConsistencyTests`（四方一致）、`AdminOnlyPermissionTests`、
`DataAccessServiceLifetimeTests`、`LoggingConventionTests`、`ButtonIconConventionTests`、
`MenuIconTests`、`ExportEncodingConventionTests`、`FormModalConventionTests`、
`ModalKeyboardConventionTests`、`AiModalStyleConventionTests`、`ThemeConventionTests`、
`LogoutConfirmationConventionTests`、`DocumentationConventionTests` 等。

**⚠️ 最大的缺口：零個元件測試**

602 個測試裡**沒有一個渲染 Blazor 元件**。所有 UI 保證都是「用正規表示式掃原始碼」。
這代表：你可以把畫面改壞而 CI 全綠。對「用腳手架約束品質」這個目標，這是最大的漏洞（見 §9、§10）。

**常見情境食譜**

*守門測試紅了，我該改測試還是改程式？*
**先假設是你的改法有問題。** 讀失敗訊息 —— 那裡通常寫著當初為什麼要加這條。
確定是規範本身要變，才連同測試一起改，並在 changelog 說明。

*我要加一條自己的守門測試*
比照 `ThemeConventionTests`：掃描檔案、比對、失敗訊息要說明**為什麼這件事會靜默出錯**。
⚠️ 記得 `Assert.NotEmpty` 保護掃描路徑 —— 路徑失效時測試會空跑綠燈，等於沒有守門。

*我只想跑某一個測試*
```powershell
dotnet test src/YourApp/YourApp.slnx --filter "FullyQualifiedName~ThemeConventionTests"
```

**深入閱讀**：[測試指南](測試指南.md)（含完整涵蓋矩陣）。

### 3.16 建置品質關卡

**它在解決什麼問題**

讓「品質」不依賴人的自律。

**為什麼這樣設計** ⭐

| 機制 | 擋住什麼 | 不用它會怎樣 |
|---|---|---|
| `TreatWarningsAsErrors=true` | 任何新警告 | 警告會累積到幾百條，然後沒有人看 |
| CPM（`Directory.Packages.props`）| 版本分歧 | 七個專案各自寫版本，升級時漏掉一個 |
| `.editorconfig` ＋ `dotnet format` | 格式爭論 | code review 花在空白與括號上 |
| `global.json` | SDK 版本漂移 | 「在我的機器上可以」 |
| `Test-DocsEncoding.ps1` | 文件缺 BOM | 中文在某些編輯器變亂碼 |

**可以調什麼**

| 檔案 | 你會改什麼 |
|---|---|
| `Directory.Packages.props` | **所有套件版本的唯一來源**。升級一律改這裡，`.csproj` 不寫版本 |
| `Directory.Build.props` | 要豁免某個警告時加 `NoWarn`（**針對單一規則碼**，並註明原因與解除條件），不要整包關掉 |
| `.editorconfig` | 要新增一條強制規則時。注意所有 `dotnet_style_*` 目前都是 `:silent` |
| `global.json` | 換 SDK 版本band 時 |
| `.github/workflows/dotnet-ci.yml` | CI 的五道關卡 |

⚠️ `Directory.Build.props` 有一條 `NuGetAuditSuppress`（SQLitePCLRaw 的 CVE-2025-6965），
上游釋出修補版後要**同時**移除它與 CI 弱點掃描的允許清單。

**常見情境食譜**

*建置失敗，說某個警告是錯誤*
這是刻意的。修掉那個警告，不要關掉 `TreatWarningsAsErrors`。

*我要升級 AntDesign*
只改 `Directory.Packages.props` 的版本號。改完跑完整測試 ——
`.ant-*` 的 DOM 結構可能變，而本專案有大量樣式覆寫。

*CI 的格式檢查紅了*
本機跑 `dotnet format src/YourApp/YourApp.slnx` 再提交。

**深入閱讀**：[CI-CD 與品質檢查](../operations/CI-CD與品質檢查.md)、
[維護規範](../operations/維護規範.md)。

## 4. 設定檔完全指南

這一章列出**每一個可以在設定檔裡改的東西**。找不到你要的？先看 [§5](#5-沒有寫在設定檔裡的旋鈕)。

> 本章與 [日誌與設定檔說明](../operations/日誌與設定檔說明.md) §4 **刻意重複** ——

### 4.0 先理解三件事

**① 設定的來源與優先順序**（後面覆蓋前面）

```
appsettings.json
  → appsettings.{Environment}.json      （Development / Production）
    → User Secrets                       ⚠️ 只在 Development 載入
      → 環境變數                          巢狀用雙底線：JwtSettings__SigningKey
        → 命令列參數
```

**② 只有一個設定類別會在啟動時驗證**

全案只有 `JwtSettings` 用了 `ValidateDataAnnotations().ValidateOnStart()`（`Program.cs:142-145`）。
其餘 8 個 `Configure<T>` **完全沒有驗證** —— 填錯型別或超出合理範圍不會有人告訴你，
系統會帶著錯誤的值跑。

**③ `StartupSafetyValidator` 的五道檢查（只在 Production）**

| # | 檢查 | 有效嗎 |
|---|---|---|
| 1 | `JwtSettings:SigningKey` 不是開發預設值 | ✅ |
| 2 | `BootstrapSettings:SupportPassword` 不是 `"support"` | 🔴 **形同虛設**，見 §2.3 地雷一 |
| 3 | `Swagger:EnabledInProduction` 有被明確設定 | ✅ |
| 4 | 用 Redis 時 `RedisConnection` 不為空 | ✅ |
| 5 | 填了 AI 金鑰時 `Endpoint`（Azure）與 `Model` 不為空 | ✅ |

任一不過就丟例外中止啟動。

### 4.1 `appsettings.json` 逐區段

#### `Logging` ☠️ 死設定

| 鍵 | 值 |
|---|---|
| `Logging:LogLevel:Default` | `Information` |
| `Logging:LogLevel:Microsoft.AspNetCore` | `Warning` |

⚠️ **改它不會有任何效果。** `Program.cs:73` 呼叫 `ClearProviders()` 之後由 NLog 完全接管，
日誌等級只看 `nlog.config`（見 §4.4）。留著是因為它是 .NET 範本的一部分。

#### `AllowedHosts`

| 鍵 | 預設 | 說明 |
|---|---|---|
| `AllowedHosts` | `*` | 允許的 Host 標頭白名單。框架層處理，本專案沒有程式讀它。防 Host header 注入時可以收緊 |

#### `Swagger`

| 鍵 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `Swagger:EnabledInProduction` | bool | `false` | ⚠️ Production **必須明確寫出來**，沒寫會被擋下啟動 |

#### `Security`

| 鍵 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `Security:ReturnExceptionDetails` | bool? | `null` | `null` ＝ 依環境決定（只有 Development 回傳細節）。Production 設 `true` 會把堆疊追蹤回給呼叫端 |

#### `Cors`

| 鍵 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `Cors:AllowedOrigins` | string[] | `[]` | 空陣列 ＝ **完全不允許跨來源**。要開放就列出完整來源（含 scheme 與 port）|

#### `RateLimit`

| 鍵 | 型別 | 預設 | 熱更新 | 說明 |
|---|---|---|---|---|
| `RateLimit:ApiRequestsPerMinute` | int | `120` | ✅ | **每個呼叫端各自計算**，不是全站總量 |
| `RateLimit:LoginRequestsPerMinute` | int | `10` | ✅ | 登入端點專用，比一般嚴格 |

時間視窗與佇列長度**不可設定**，見 §5。

#### `ForwardedHeaders` ⚠️ 不在檔案裡，但很重要

| 鍵 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `ForwardedHeaders:KnownProxies` | string[] | `[]` | 信任的反向代理 IP |
| `ForwardedHeaders:KnownNetworks` | string[] | `[]` | 信任的網段（CIDR）|

⚠️ 這兩個鍵**沒有出現在任何 appsettings 檔裡**，要自己加。
走 Nginx／IIS ARR／雲端 LB 時**必設** —— 不設的話所有請求的來源 IP 都會變成代理伺服器，
速率限制與日誌裡的 IP 全部失真，而且 `X-Forwarded-For` 可以被偽造。
無法解析的項目會被**靜默忽略**。

#### `CacheSettings`

| 鍵 | 型別 | 預設 | 說明 |
|---|---|---|---|
| `CacheSettings:Provider` | string | `Memory` | 只接受 `Memory` 或 `Redis`；**其他值會在啟動時丟例外** |

#### `BootstrapSettings` 🔴 最需要小心的一段

| 鍵 | 型別 | JSON 值 | 說明 |
|---|---|---|---|
| `BootstrapSettings:SupportAccount` | string | `support` | 預設管理員帳號 |

（`Program.cs:270-272`）。行為是**冪等 seed**：

- 帳號不存在 → 建立，密碼取自這裡
- 帳號存在但密碼對不上 → **用這裡的值覆寫回去**（每次啟動都檢查）

🔴 **三個必須知道的事實**：

1. 自動檢查只擋字面 `"support"`，擋不住出貨的 `1qaz@WSX`（§2.3 地雷一）。
2. `appsettings.Production.json:15` 出貨的是**空字串**，同樣會通過檢查，
   而 `Program.cs:343` 沒有防呆 → **管理員帳號變成空密碼**。
3. 因為是每次啟動覆寫，**在畫面上改密碼是沒用的** —— 重啟就被打回去。
   要改就改這個設定值（或用環境變數 `BootstrapSettings__SupportPassword`）。

⚠️ **不要**把它放 User Secrets —— 它的行為與一般機密不同（會反向覆寫資料庫）。

### 6.1 先搞懂五個問題

權限系統做壞的原因，幾乎都不是技術不夠，而是**一開始沒想清楚這五件事**。

#### 一、你到底在防誰？

四種威脅，防法完全不同。把它們混為一談，就會做出「防了最不可能的、漏了最常發生的」系統。

| 威脅 | 長什麼樣 | 本系統靠什麼擋 |
|---|---|---|
| **外部匿名者** | 沒登入就打 API、猜網址 | 認證（第 1 層）＋ 端點預設拒絕（第 2 層）|
| **內部越權**（最常發生）| 有帳號，但去做不該做的事、看不該看的資料 | 動作級授權（第 3 層）＋ 團隊列級（第 5 層）|
| **誤操作** | 手滑刪掉別人的東西 | 動作級授權 ＋ UI 不顯示按鈕（體貼，不是防線）|
| **離職未清權** | 帳號還在、權限還在 | 停用帳號；⚠️ 已簽發的 JWT 仍會活到過期（見 §6.3 案例五）|

⚠️ **實務上 90% 的資安事件是第二種**，但多數人花 90% 的力氣在第一種。
原因是第一種有現成套件可以裝，第二種必須自己想清楚業務規則。

#### 二、三種模型，你要哪一種

| 模型 | 怎麼判定 | 適合 | 代價 |
|---|---|---|---|
| **ACL**（存取控制清單）| 每筆資料掛一份「誰可以做什麼」 | 檔案系統、共享文件 | 資料一多就爆炸，無法回答「小王能做什麼」 |
| **RBAC**（角色）⭐ | 使用者 → 角色 → 權限 | **絕大多數企業內部系統** | 角色數量會隨組織複雜度成長 |
| **ABAC**（屬性）| 用規則運算（部門＝X 且 金額<Y 且 時間在上班時段）| 規則多變、條件組合複雜 | 很難除錯，「他為什麼不能進去」要跑一次規則引擎才知道 |

**本系統選 RBAC，並在上面加一層「團隊」做資料範圍**，這是企業系統最常見的組合：
角色回答「能做什麼」，團隊回答「能看到哪些」。

⭐ **給新手的建議：先用 RBAC，不要一開始就上 ABAC。**
ABAC 的彈性在前三個月很爽，之後每一次「他為什麼看得到／看不到」都要花半天追規則。
等到 RBAC 真的表達不了需求（例如「只能看金額 10 萬以下的案子」）再考慮混進屬性判斷。

#### 三、「能做什麼」與「能看到哪些資料」是兩件事 ⚠️

這是新手最常搞混的一點，也是本系統用**兩套不同機制**處理的原因。

```
能做什麼（動作權限）          能看到哪些（資料範圍）
──────────────────          ──────────────────
角色 → 權限鍵                 團隊 → 查詢述詞
專案項目:view / create        Teams 欄位是否有交集
在「進入端點」時判定            在「組 SQL」時判定
不通過 → 403                  不通過 → 那筆資料根本不出現
```

舉例最快：

- 小王有 `專案項目:view`，但不屬於任何團隊 → **進得去頁面，但清單是空的**（除了公開紀錄）。
- 阿美屬於研發部，但沒有 `專案項目:view` → **連頁面都進不去**，談不上看到幾筆。

兩者**互不取代**。只做角色不做範圍，結果是「業務部看得到研發部所有案子」；
只做範圍不做角色，結果是「每個人都能刪除自己看得到的東西」。

#### 四、最小權限原則，以及它的帳單

原則很簡單：**預設不給，要用才給，用完收回。**
但它有帳單，而且帳單是管理成本：

- **權限爆炸**：頁面 × 動作 = 權限鍵數量。本系統 3 個受控頁 × 4 個動作 = 12 個動作鍵，
  還算好管；20 個頁面就是 80 個，矩陣會變成一面牆。
- **角色爆炸**：為了「差一個權限」而複製出「業務主管A」「業務主管B」，半年後沒人知道差在哪。
- **申請流程成本**：權限切太細，使用者每天都在「我少了一個權限」。

⭐ **實務取捨**：先切到「頁面 × 動作」這一層就好（本系統的選擇），
不要一開始就做欄位級。真的需要再往下切 —— 往下切容易，收回來很難。

#### 五、防線只能放在伺服器端 🔴

**UI 隱藏按鈕不是授權，它只是體貼。**

任何人都可以：改網址直接進頁面、用開發者工具把 `disabled` 拿掉、
或者根本不開瀏覽器，直接用 `curl` 打你的 API。

所以本系統的規則是：

- UI 的 `CheckAccessPage` / `CheckAccessAction` → **只負責不要讓使用者看到做不到的事**。
- API 的 `[HasPermission]` 與服務層的查詢述詞 → **才是真正的邊界**。

⚠️ 這條規則反過來也成立：**不要因為「UI 上按不到」就省略伺服器端檢查**。
本系統 3 個業務頁的每一個寫入動作，在 Controller 上都有對應的 `[HasPermission]`，
即使 UI 早就把按鈕藏起來了。

### 6.2 本系統的六層防線

一個請求要拿到資料，必須通過六層。**每一層擋的東西都不一樣，而且都有它擋不到的**。

| # | 防線 | 擋什麼 | **擋不到**什麼 | 程式在哪 |
|---|---|---|---|---|
| 1 | 認證 | 匿名者 | 已登入者想做什麼 | `Program.cs:153-221` |
| 2 | 端點預設拒絕 | 忘了標授權的 Controller | 有權限者的越權查詢 | `Program.cs:430-432` |
| 3 | 動作級授權 | 可看不可改 | 看得到**哪幾筆** | `HasPermissionAttribute.cs`、`PermissionChecker.cs` |
| 4 | 頁面／選單可見性 | 誤入與畫面雜訊 | **直接打 API** ⚠️ | `AuthenticationStateHelper.cs:188-206` |
| 5 | 資料列範圍（團隊）| 跨團隊偷看（**僅 Blazor**）| **Web API 路徑** 🔴 | `TagStringHelper.cs:110-161` |
| 6 | 管理員短路 | —— | 它本身就是最大的風險面 | 散在 10 處，見下 |

#### 第 1 層：認證 —— 你是誰

兩條路徑，**claim 對應是相反的**（§3.4 已詳述，這裡只提結論）：
Cookie 走 UI，`Sid` 放 UserId；JWT 走 API，`NameIdentifier` 放 UserId。

⚠️ **JWT 不帶角色、不帶權限鍵、不帶團隊**（`Auth/JwtTokenService.cs:79-93` 只放
`Sub`／`NameIdentifier`／`Name`／`display_name`／`is_admin`／`token_type`）。
這是刻意的：權限每次請求現查資料庫，所以**改了權限不需要重新發 token**。
代價是每個請求多一次查詢。

#### 第 2 層：端點預設拒絕 —— 忘記標授權也不會漏

```csharp
app.MapControllers().RequireRateLimiting("api").RequireAuthorization();   // Program.cs:430-432
```

新增的 Controller **預設就是要登入**，要開放匿名必須自己標 `[AllowAnonymous]`。
這叫「安全預設值」：漏掉的後果是「太嚴」而不是「太鬆」。

⚠️ 刻意**不用** `AuthorizationOptions.FallbackPolicy`（`Program.cs` 的 `MapControllers` 上方有註解）。
Blazor 頁面走同樣「安全預設值」的另一條路（0.9.41 起）：`Components/Pages/_Imports.razor` 對整個
`Pages/` 標 `[Authorize]`，未登入的整頁請求直接 302 到登入頁；匿名頁面自己標 `[AllowAnonymous]`
並列入 `PageAuthorizationTests` 的白名單。見 [開發慣例與限制速查 §5.1](../architecture/開發慣例與限制速查.md)。

#### 第 3 層：動作級授權 —— 可看不可改

權限鍵格式是 `頁面:動作`（`PermissionKeys.cs:20-23`），動作有四個：
`view` / `create` / `edit` / `delete`。

判定邏輯只有三行，但每一行都有理由（`PermissionChecker.cs:33-49`）：

1. **管理員短路** → 直接 true。
2. **多角色聯集**：`UserRole` ∪ legacy `RoleViewId` → `RolePermissionMap` → `Permission.Key`。
3. **裸鍵退路**：有裸鍵 `專案項目` 就視同擁有該頁全部動作（舊制相容）。
   ⚠️ 反向不成立 —— 有 `專案項目:view` **不等於**有裸鍵（`PermissionCheckerTests.cs:56`）。

被拒時回 **403 ＋ `ApiResult`**，並寫一筆 `Permission.Denied` 稽核
（`HasPermissionAttribute.cs:67-82`）。匿名請求在更前面就被擋成 401，**不寫稽核** ——
否則匿名流量可以灌爆稽核表。

#### 第 4 層：頁面與選單可見性 —— 體貼，不是邊界

三個方法，用途不同，**不要用錯**：

| 方法 | 用在哪 | 通過條件 |
|---|---|---|
| `CheckIsAdmin()` | 8 個管理員專屬頁 | `IsAdmin` |
| `CheckAccessPage(頁面鍵)` | 4 個業務頁 ＋ 側邊選單過濾 | 管理員、裸鍵、或 `頁面:view` |
| `CheckAccessAction(頁面鍵, 動作)` | 按鈕顯隱 | 管理員、`頁面:動作`、或裸鍵 |

⚠️ **`CheckAccessPage` 接受 `頁面:view` 是 0.9.37 才修的**。
在那之前它只認裸鍵，於是「只勾檢視」的角色**連頁面都打不開**——
動作級授權只有 API 端真正生效。修正後唯讀角色才真的可用。

⚠️ 這一層**完全不是安全邊界**。選單過濾只是不讓人看到點不進去的東西；
使用者照樣可以直接在網址列輸入 `/categories`，這時擋他的是頁面自己的
`CheckAccessPage`；而如果他改打 API，擋他的是第 3 層。

#### 第 5 層：資料列範圍 —— 團隊

**有效團隊 = 使用者直接綁的團隊（`UserTeam`）∪ 他每個角色的預設團隊（`DefaultTeamsJson`）**，
聯集去重（`EffectiveTeamResolver.cs:19-77`）。

⚠️ **系統沒有「目前團隊／切換團隊」的概念** —— 永遠是所有團隊的聯集。

過濾規則（`TagStringHelper.cs:110-137` 的 `BuildTeamAccessPredicate`）：

```
紀錄的 Teams 為空       → 公開，所有人看得到
紀錄的 Teams 有值       → 必須與使用者的有效團隊有交集
使用者是管理員           → 完全不套這個述詞
```

🔴 **這一層有一個必須知道的缺口**：團隊過濾只寫在 **Blazor 服務層**
（`ProjectService.cs:78-82`）。**Web API 走的是 `ProjectRepository`，完全沒有列級過濾** ——
同一位非管理員在畫面上看不到別團隊的紀錄，持 JWT 打 `POST /api/Project/search`
卻拿得到全部。

這是**刻意的現況**而非疏漏，但交付前必須讓客戶知道。
完整說明與檢查項見 [正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)
的「已知限制」段落；要補的話見 [§6.5](#65-還可以加什麼含實作點)第一項。

⚠️ **分類（Category）的規則與紀錄相反**，而且是刻意的：

| 使用者的團隊 | 看得到的**紀錄** | 看得到的**分類** |
|---|---|---|
| 沒有任何團隊 | 只有公開紀錄（最嚴）| **全部分類**（最寬）|
| 有團隊 | 公開 ＋ 有交集 | 公用 ＋ 有交集 |

理由寫在 `CategoryService.cs:34-41`：分類可見性只是**下拉清單的便利性過濾**
（避免塞滿用不到的項目），**不是安全邊界** —— 安全邊界由第 3 層負責。
⚠️ 修改時不要順手把兩者「改成一致」，有測試守門。

#### 第 6 層：管理員短路 —— 方便，也是最大風險

`IsAdmin` 在 **10 個地方**短路：API 動作授權、`CheckAccessPage`、`CheckAccessAction`、
`CheckIsAdmin`、單筆團隊判定、專案清單查詢、分類清單查詢，以及三處 UI 提醒的略過。

**但它沒有短路這三件事**：

1. 登入時的**帳號停用**與**鎖定**檢查（`MyUserServiceLogin.cs:74-86`）。
2. 每次導覽的 `Status`／`RoleView == null`／**強制改密碼**檢查
   （`AuthenticationStateHelper.cs:79-107`）—— 管理員若沒有角色，一樣被踢去登出。
3. **速率限制**。

⚠️ **管理員不是一種角色**，是 `MyUser.IsAdmin` 這個布林欄位。
你在角色矩陣裡找不到「管理員」，也無法把它授予給某個角色。

⚠️ 有 **11 個權限鍵刻意不上架角色矩陣**（系統管理與統計分析兩群組的所有頁面），
它們只靠 `IsAdmin` 放行。由 `AdminOnlyPermissionTests` 守門，**請勿補上** ——
補上去會放寬權限（非管理員可被授予管理使用者與角色的能力）。

### 6.3 五個人，五種走查

抽象規則看十遍不如走一次。以下五個人物**都用同一組設定**：
兩個團隊（研發部、業務部）、三筆專案紀錄（A 掛研發部、B 掛業務部、C 沒掛團隊）。

每個案例固定四段：**他是誰 → 他看到什麼 → 他按得到什麼 → 打 API 會怎樣**，
並標出是第幾層防線在作用。

#### 案例一：小王，稽核員（只能看，不能改）

**他是誰**：角色「稽核員」，在角色矩陣的「專案項目」列只勾了**檢視**。
存檔後他拿到的權限鍵是 `專案項目:view` ——⚠️ **不含**裸鍵 `專案項目`。
團隊：研發部。

**他看到什麼**
- 側邊選單出現「專案項目」。第 4 層：`CheckAccessPage("專案項目")` 用 `專案項目:view` 通過。
- 點進去看到 **A（研發部）與 C（無團隊，公開）**，看不到 B。第 5 層。

**他按得到什麼**
- 「新增」鈕**不顯示**（第 4 層 `CheckAccessAction(..., create)` 為 false）。
- 每一列的「修改」「刪除」鈕**不顯示**。

**打 API 會怎樣**
- `POST /api/Project/search` → **200**（有 `專案項目:view`）。
  ⚠️ 但因為第 5 層的缺口，這裡會回 **A、B、C 全部三筆** —— 比他在畫面上看到的多。
- `POST /api/Project`（新增）→ **403**，訊息「目前使用者沒有『專案項目:create』權限。」
  並寫一筆 `Permission.Denied` 稽核。第 3 層。

> 🔴 這個案例同時示範了本系統最重要的一個不對稱：
> **第 3 層（能做什麼）在 UI 與 API 上都生效；第 5 層（能看到哪些）只在 UI 上生效。**

#### 案例二：阿美，研發部的專案人員

**她是誰**：角色「專案人員」勾了「專案項目（全部）」→ 拿到**裸鍵** `專案項目`。
團隊：研發部。

**她看到什麼**：A ＋ C，一樣看不到 B。第 5 層對她和小王一視同仁 ——
**團隊與角色無關**，給再大的動作權限也不會多看到一筆。

**她按得到什麼**：全部按鈕都在（裸鍵 ⇒ 全動作，第 3 層的退路規則）。

**打 API 會怎樣**：四個動作全部 200。

⚠️ **她可以編輯 C（公開紀錄）**，而 C 是全公司都看得到的。
「公開」指的是**可見性**，不是唯讀 —— 想要「大家看得到、只有我能改」，
本系統目前做不到，需要資源擁有者機制（見 [§6.5](#65-還可以加什麼含實作點)）。

#### 案例三：老陳，跨兩個團隊、兩個角色

**他是誰**：主要角色「專案人員」（裸鍵 `專案項目`），
額外角色「分類維護」（`分類清單:view`＋`分類清單:edit`）。
直接綁定團隊：業務部；而「專案人員」這個角色的**預設團隊**是研發部。

**他的有效權限**：兩個角色的**聯集** ——
`專案項目`、`分類清單:view`、`分類清單:edit`。

**他的有效團隊**：`UserTeam`（業務部）∪ 角色預設團隊（研發部）= **兩個都有**。

**他看到什麼**：A、B、C **三筆全都看得到**（與兩個團隊都有交集，加上公開的 C）。

**他按得到什麼**：專案頁全部按鈕；分類頁有「修改」但**沒有「新增」與「刪除」**。

⚠️ **陷阱**：使用者管理的清單頁「角色」欄**只顯示主要角色**。
老陳實際擁有的是兩個角色的聯集，但清單上看起來只有「專案人員」——
要查他真正有什麼，得點進編輯視窗看「額外角色」。

#### 案例四：小林，系統管理員

**他是誰**：`IsAdmin = true`。⚠️ 他**不需要任何角色權限**，也不需要任何團隊。

**他看到什麼**：所有選單、所有頁面、所有紀錄（A、B、C）。第 6 層在 10 處短路。

**他按得到什麼**：全部。

**打 API 會怎樣**：全部通過（`PermissionChecker.cs:33-39` 對**任何**權限鍵都回 true，
包括根本不存在的鍵 —— `PermissionCheckerTests.cs:14` 就是用 `"任何權限"` 驗這件事）。

**但他不是萬能的**：
- 帳號被停用 → 登入就被擋。
- `RoleView` 為 null → 每次導覽的檢查會把他踢去登出（⚠️ 建管理員帳號時別忘了給角色）。
- 速率限制照算。

⚠️ **管理員帳號應該越少越好**。本系統沒有「管理員做了什麼」的專用畫面
（`AuditLog` 有寫但沒有 UI，見 §10.2），所以管理員的行為實務上很難事後追。

#### 案例五：小張離職了

**處置**：管理員把他的帳號**停用**（不是刪除 —— 刪除會讓稽核紀錄失去對應）。

**UI 這條路**：下一次他點任何頁面，`AuthenticationStateHelper.Check` 讀到
`Status == false` 就回 `InvalidUser` 並導向登出（`:79-85`）。**立即生效。**

**API 這條路** ⚠️：
- 新的 `/api/Auth/login` → 擋掉。
- `/api/Auth/refresh` → 擋掉。`AuthController.cs:60-63` 刻意**回查資料庫**而不是直接拿
  claim 重簽，就是為了這個情境。
- 🔴 **但他手上那張還沒過期的 access token 仍然有效**，直到 `AccessTokenMinutes` 到期。
  `PermissionChecker` 不檢查 `MyUser.Status`。

**所以離職流程要寫成**：停用帳號 → **等過 `AccessTokenMinutes`** → 才算真的斷。
要立刻斷只有一招：換掉 `JwtSettings:SigningKey`（會讓**所有人**的 token 失效）。

### 6.4 要改權限，步驟是什麼

五個最常見的任務。每一個都附「**怎麼驗證你改對了**」——
權限改錯不會編譯失敗、不會紅燈，只有實際用那個角色登入才看得出來。

#### 任務一：新增一個受權限控管的頁面

**四處必須同步**（`Menu.json` → `MenuPermissionMap` → `MagicObjectHelper` → 頁面的
`CheckAccessPage`），細節**不在這裡重述**，看
[速查表 §5](../architecture/開發慣例與限制速查.md) 與
[維護規範 §2](../operations/維護規範.md)。

⚠️ 第四處最容易漏，症狀是「**使用者看得到選單、點進去被踢出**」。
`MenuPermissionConsistencyTests` 會擋，但它是靠掃描原始碼比對的，
新檢視要記得登記進那份對照表。

**怎麼驗證**：`dotnet test --filter "FullyQualifiedName~MenuPermissionConsistencyTests"`。

#### 任務二：做一個「只能看不能改」的角色

1. 角色管理 → 新增角色 → 在目標頁面那一列**只勾「檢視」**。
2. ⚠️ **不要勾「（全部）」** —— 那會存成裸鍵，等於全動作。勾了「全部」之後，
   四個動作的核取方塊會變成 disabled，這就是提示。
3. 使用者管理 → 把角色指派給人。

**怎麼驗證**：用該使用者登入 →
選單看得到、頁面進得去、**新增／修改／刪除鈕都不顯示**；
再用他的 JWT 打 `POST /api/<資源>` 應得 **403**（不是 200，也不是 401）。

#### 任務三：讓某個團隊只看到自己的資料

1. 團隊清單 → 建立團隊。
2. 在紀錄（專案項目）上指定「團隊」。⚠️ **留空 = 公開給所有人**，不是「沒人看得到」。
3. 把使用者綁到團隊：使用者管理的「團隊」欄（直接綁），
   或角色管理的「預設團隊」（該角色的人都繼承）。

**怎麼驗證**：用該使用者登入，清單應只剩「自己團隊的」＋「沒掛團隊的」。
⚠️ 別用管理員帳號測 —— 管理員不受團隊過濾，你會以為沒生效。

#### 任務四：把一頁改成「只有管理員能用」

比照既有的 8 個管理員專屬頁：頁面守門改用 `CheckIsAdmin()`，
**並且把該權限鍵從 `RolePermissionService.GetRoleListPermissionAllName()` 拿掉**。

⚠️ 只改頁面、不從矩陣下架，就會做出「**勾得到卻永遠無效**」的死權限 ——
0.4.33 的「使用者管理／角色管理」與 0.9.37 的 `export` 都踩過這個坑。
`AdminOnlyPermissionTests` 就是為此而存在。

**怎麼驗證**：以非管理員登入 → 選單不出現該項、直接輸入網址會看到紅字提示；
再到角色管理確認矩陣裡**找不到**那個權限鍵。

#### 任務五：收回某個人的權限

- **收回一項動作** → 角色管理取消勾選。**下一次換頁就生效**，不必重新登入
  （`AuthenticationStateHelper.Check` 每次導覽都重查資料庫）。
- **收回全部** → 使用者管理停用帳號。UI 立即生效；
  ⚠️ API 端已簽發的 access token 仍活到過期（見案例五）。

**怎麼驗證**：請對方重新整理頁面 —— 按鈕應該當場消失。

### 6.5 還可以加什麼（含實作點）

> ⚠️ 以下**全部尚未實作**，是給「這個腳手架不夠用了」時的方向，不是現況說明。
> 依投報率排序。刻意只寫「要動哪裡」，不附程式碼 —— 理由同 §10 開頭那段。

#### 一、Web API 補上團隊列級過濾 🔴 最該先做

- **解決什麼**：目前 API 與 UI 的資料可見範圍不一致（§6.2 第 5 層的缺口）。
  只要把 API 開放給終端使用者，這就從「已知限制」變成「資料外洩」。
- **什麼時候一定要做**：API 給**人**用（而不是只給內部系統整合）的那一刻。
- **接在哪**：兩條路二選一 ——
  讓 `ProjectController` 改用已經有 scope 的 `ProjectService`（改動小、行為立刻一致），
  或在 `ProjectRepository` 注入 `IRecordAccessScopeProvider` 並套
  `TagStringHelper.BuildTeamAccessPredicate`（維持分層、但要逐個 Repository 補）。
- **代價**：**現有整合方會突然少拿到資料**。這是行為變更，要先盤點呼叫方。
- ⚠️ 另有一個前置問題要一起解：`JwtTokenService` 發的 token **不帶 `ClaimTypes.Sid`**，
  而 `RecordAccessScopeProvider` 的第二段 fallback 正是靠 `Sid` 取得使用者
  （`RecordAccessScopeProvider.cs:45-46`）。不補這個，過濾會退化成「只看得到公開紀錄」。

#### 二、稽核紀錄畫面 ✅ 已於 0.9.42 實作

- 入口 `/audit-logs`（系統管理 → 權限管理 → 稽核紀錄），管理員專屬。
  查詢服務為 `AuditLogQueryService`，見 [稽核紀錄 PRD](../prd/稽核紀錄-prd.md)。
- ⚠️ 留下的經驗：`AuditLog.OccurredAt` 是全專案唯一以 UTC 寫入的時間欄位，
  照抄例外紀錄頁（存本地時間、全程不換算）會讓整條時間軸偏掉一個時區。

#### 三、權限判定結果快取

- **解決什麼**：`CheckAccessPage` 是同步比對記憶體沒問題，但
  `AuthenticationStateHelper.Check` **每次導覽**都重查資料庫，`HasPermissionAttribute`
  **每個 API 請求**也查一次。使用者一多會看得到。
- **什麼時候才值得**：上百人同時在線，或權限查詢出現在慢查詢清單裡之前，**都不值得**。
- **接在哪**：`PermissionChecker` 外面包一層 `ICacheService`（已有 Memory／Redis 兩種實作）。
- ⚠️ **代價是失效問題**：一加快取，「改了權限下次換頁就生效」這個目前的好性質就沒了，
  必須在 `RbacWriteService` 的三個 `Sync*Async` 都做主動失效。**這是最容易做錯的一項。**

#### 四、資源擁有者（Owner）

- **解決什麼**：目前無法表達「大家看得到，但只有建立者能改」（見案例二的阿美）。
- **接在哪**：紀錄上加 `OwnerUserId`，在 `ProjectService` 的
  `UpdateAsync`／`DeleteAsync` 加判斷。⚠️ 這兩個方法**目前完全沒有列級檢查**，
  是自然的接入點。
- **代價**：要處理「擁有者離職了怎麼辦」，通常會連帶需要「轉移擁有者」的功能。

#### 五、欄位級權限

- **解決什麼**：「業務可以看案子，但看不到金額」。
- **接在哪**：DTO 層（依權限決定是否填入欄位），**不要在 UI 層做**（見 §6.1 第五點）。
- **代價**：很高。每個 DTO 都要分版本，AutoMapper 的對應會複雜好幾倍。
  ⭐ **先問清楚是不是真的需要** —— 多數時候「拆成兩個頁面」就解決了。

#### 六、臨時授權與代理

- **解決什麼**：「主管請假三天，請代理人暫時有他的權限」。
- **接在哪**：`UserRole` 加 `ExpiresAt`，`PermissionChecker.GetRoleIdsAsync` 加時間條件。
- **代價**：需要一個定期清理的背景工作，以及「代理期間做的事要記在誰頭上」的稽核設計。

#### 七、職責分離（SoD）

- **解決什麼**：「同一個人不可以同時有『請款』與『核准』兩個權限」。金融與稽核場景常見硬需求。
- **接在哪**：角色存檔與使用者指派兩處都要檢查互斥規則（`RbacWriteService`）。
- **代價**：規則要有地方維護；⚠️ 還要處理「規則新增之前就已經違規的既有使用者」。

#### 八、多租戶

- **解決什麼**：本系統只有**團隊分權**（單一租戶內的部門模型），**不是租戶隔離**。
- ⚠️ 這不是加一層權限，是**重新設計資料模型**（每張表加 `TenantId` ＋ 全域查詢篩選）。
  詳見 §10.5。真的要做 SaaS，建議從頭設計而不是改這個腳手架。

### 6.6 FAQ

問句體裁與 §3 的「常見情境食譜」一致（*斜體提問* → 回答）。

**設定與生效**

*我改了角色權限，使用者要重新登出再登入嗎？*
**不用。** `AuthenticationStateHelper.Check` 每次導覽都重查資料庫並覆寫 `RoleList`，
請對方重新整理頁面就會生效。⚠️ 但這個好性質在你加上權限快取之後就沒了（§6.5 第三項）。

*為什麼我在角色矩陣裡勾不到「使用者管理」？*
那 11 個管理員專屬權限鍵**刻意不上架矩陣**，它們只靠 `IsAdmin` 放行。
由 `AdminOnlyPermissionTests` 守門，**請勿補上** —— 補了等於放寬權限。

*「匯出」那一欄跑去哪了？*
0.9.37 移除。它勾得到卻**沒有任何地方檢查它**，屬於「勾了等於沒勾」的死權限。
要重新上架，必須**先**寫出真正會檢查它的程式。

*我可以直接改 `RoleView.TabViewJson` 嗎？*
**不行。** 它已退為「角色編輯畫面的回填欄位」，**不參與權限判定** ——
判定讀的是 `RolePermissionMap`。手改它只會讓畫面與實際權限不一致。

**看得到 / 看不到**

*選單裡沒看到，和點進去被擋，是同一件事嗎？*
不是。選單沒出現＝第 4 層過濾掉了；點進去看到紅字提示＝頁面自己的守門擋的。
⚠️ 兩者**都不會**導到錯誤頁，檢視會留在原地顯示提示。

*為什麼同一個人在畫面上看不到那筆，用 API 卻查得到？*
第 5 層的已知缺口：團隊過濾只寫在 Blazor 服務層，Web API 走 Repository 沒有過濾。
見 §6.2 第 5 層與 §6.5 第一項。

*團隊留空到底是最寬鬆還是最嚴格？*
**看是哪個欄位**，這是全系統最容易搞錯的一點：

| 欄位 | 留空的意思 |
|---|---|
| 專案項目的「團隊」 | **公開給所有人**（最寬）|
| 分類的「適用團隊」 | 所有團隊都能用（最寬）|
| 角色的「預設團隊」 | **只看得到公開紀錄**（最嚴）|
| 使用者的「團隊」 | 沿用其角色的預設團隊（**不等於沒有團隊**）|

*為什麼分類和紀錄的規則是相反的？*
刻意的。分類可見性只是下拉清單的便利性過濾，**不是安全邊界**；
紀錄可見性才是。改時不要順手「統一」，`CategoryServiceTeamVisibilityTests` 會擋。

*使用者可以切換「目前團隊」嗎？*
**沒有這個概念。** 永遠是他所有團隊的聯集。

*我把團隊改名了，既有紀錄會跟著改嗎？*
**不會。** 紀錄上存的是**團隊名稱字串**，不是 Id。改名等於讓舊紀錄指向一個不存在的團隊，
可見性會靜默出錯。這也是團隊名稱有唯一索引與正規化的原因。

**角色與管理員**

*管理員是一種角色嗎？*
**不是**，是 `MyUser.IsAdmin` 布林欄位。矩陣裡找不到它，也無法授予給角色。

*一個人可以有多個角色嗎？權限是聯集還是覆蓋？*
可以，**聯集**。主要角色（`RoleViewId`）＋ 額外角色（`UserRole`）。
⚠️ 使用者清單的「角色」欄只顯示主要角色，要看全部得點進編輯視窗。

*勾了「（全部）」和四個動作全勾，有差嗎？*
有。「全部」存成**裸鍵**（`專案項目`），四個動作全勾存成**四個動作鍵**。
判定結果目前一樣，但裸鍵的語意是「這一頁的所有動作，包含以後新增的動作」。
要嚴格控管就別用裸鍵。

*我給了 `專案項目:view`，他為什麼進不去頁面？*
0.9.37 之前會這樣 —— `CheckAccessPage` 當時只認裸鍵。**升級後已修正**。
若你在舊版本上遇到，權宜解是改勾「（全部）」，但那會給到全部動作。

**權限鍵**

*權限鍵可以用英文嗎？*
可以，但**本系統現況是中文**（`專案項目:view`）。⚠️ 要換必須連同既有資料一起搬 ——
`Permission.Key` 有唯一索引，`RoleView.TabViewJson` 裡也存著同樣的字串。

*權限鍵可以隨便改名嗎？*
⚠️ **不建議。** 改名等於「舊鍵消失、新鍵出現」，所有角色的既有授權都會失效。
真要改，`RbacBackfillService` 的正規化／合併邏輯是可以參考的樣板。

*權限鍵前後可以有空白嗎？*
**不行**，判定是 Ordinal 比對，一個尾隨空白就會靜默對不上。
`MenuPermissionConsistencyTests` 有一條專門擋這個（0.4.32 真的踩過）。

**安全邊界**

*UI 已經把按鈕藏起來了，API 還需要檢查嗎？*
**需要，而且那才是真正的檢查。** UI 只是體貼，任何人都能繞過它直接打 API。

*我停用了一個人的帳號，他馬上就用不了嗎？*
UI 立即生效；**API 端他手上那張 access token 仍活到過期**。
要立刻全斷只有換 `JwtSettings:SigningKey`（所有人一起失效）。

*API 回 401 和 403 差在哪？*
401 ＝「我不知道你是誰」（沒登入／token 無效）；403 ＝「我知道你是誰，但你沒這個權限」。
**只有 403 會寫稽核** —— 匿名流量不應該能灌爆稽核表。

*上傳的檔案有做權限檢查嗎？*
專案附件走的是有檢查的 Controller（查無／越界／檔案不存在一律回 404，不以狀態碼洩漏存在與否）。
⚠️ 但 `DownloadPath` 底下的靜態檔案路由**沒有逐筆檢查**，任何已登入者都讀得到。

主按鈕漸層的亮端是給深色文字用的，白字放上去會低到約 2:1。

### 7.2 換登入頁主題（例如冬景 → 秋景）

登入頁的視覺**不吃 `theme.css` 的版面規則**，它有自己的 `Login.razor.css`（415 行）與三張素材。

#### 要換的素材

| 檔案 | 用途 | 要求 |
|------|------|------|
| `wwwroot/images/login-winter-desktop.png` | 桌面背景 | 約 1774×887，**不要有文字、Logo、表單** —— 中段要留白給真的 UI |
| `wwwroot/images/login-winter-mobile.png` | 手機背景 | 約 853×1844，中央低對比留白 |
| `wwwroot/images/login-snow.png` | 飄落粒子，會重複鋪排 | **必須有真正的透明背景**（alpha），不是白底 |

換成秋景時：背景改成楓紅／琥珀色調的落葉場景，`login-snow.png` 換成稀疏的落葉顆粒。
檔名可以沿用（改名要一併改 `Login.razor` 的 `Assets` 參照與 `New-StarterProject.ps1` 的掃描）。

#### `Login.razor.css` 哪些是主題、哪些不要動

| 區段 | 行為 | 換主題時 |
|------|------|---------|
| `.login-container` 的 `--login-*` | 色票別名層 | **不要改**，它們指向 `theme.css`。改 §7.1 就好 |
| `.winter-scene` / `.winter-scene img` | 背景圖容器 | 只有換圖，CSS 不用動 |
| `.snow-layer` / `.snow-layer-far` | 兩層飄落動畫，18 秒與 28 秒 | **要調**：落葉比雪重，速度放慢、幅度加大會更自然 |
| `--snow-image` | 粒子圖來源（寫在 `Login.razor` 的行內樣式）| 換檔名時改這裡 |
| `.login-card` 與 `@supports` 毛玻璃 | 面板材質 | 不用動，顏色來自 token |
| `@media` 各斷點 | RWD（1024／768／359px）| **不要動**，已通過五種寬度驗收 |
| `@media (prefers-reduced-motion: reduce)` | 無障礙降級 | **不要動** |

> ⚠️ 飄落動畫只用 `transform`，不要改成動 `filter` 或 `box-shadow` —— 那會讓整頁持續重繪。

## 10. 未來可以加什麼

§8 講「缺什麼」，這一章講「**要補的話怎麼補、值不值得**」。
每一項四段：解決什麼 → 何時需要 → **接在哪** → 成本。

> ⚠️ 這裡**刻意不附安裝與註冊的程式碼片段**。那些程式碼沒有人編譯、沒有人測試，
> 套件一升版就過期，而且看起來像是官方建議的做法。只寫「接在哪個檔案的哪一段」，
> 實際寫法請看該套件當下的官方文件。

### 10.1 測試與品質

#### bUnit（Blazor 元件測試）⭐ 最推薦先做

- **解決什麼**：在測試裡真的渲染一個 Blazor 元件，斷言畫面內容與互動結果。
- **何時需要**：**現在。** 602 個測試沒有一個渲染元件，UI 保證全靠 regex 掃原始碼。
- **接在哪**：`MyProject.Tests` 加套件即可，不用動產品程式。從最有價值的開始 ——
  例如「`StatusPill` 給定 Tone 會輸出正確的 class」「表單對話窗取消時會跳未儲存確認」。
- **成本**：小。一個套件、不動架構。第一個測試大概半天，之後每個十分鐘。

#### Playwright（端對端測試）

- **解決什麼**：開真的瀏覽器點真的畫面，涵蓋 bUnit 測不到的東西
  （CSS 是否生效、固定欄 hover、側邊欄飛出、跨頁流程）。
- **何時需要**：改過視覺之後想要有回歸保護時。本專案的視覺規範全靠人眼驗收。
- **接在哪**：新增一個測試專案；CI 要多一個步驟啟動應用程式。
  repo 根目錄已經有 `.playwright-cli/` 目錄但沒有接進 CI。
- **成本**：中。要處理測試資料庫、登入流程、CI 的瀏覽器安裝與執行時間。

### 10.2 使用者會馬上要的功能

#### 寄信（MailKit 或 SMTP）＋ 忘記密碼

- **解決什麼**：系統目前**完全沒有對外通知能力**，連帶沒有自助重設密碼。
- **何時需要**：使用者不是全部坐在你隔壁的時候。
- **接在哪**：加一個 `IEmailSender` 抽象與設定區段（比照 `CacheSettings` 的 provider 切換寫法）；
  忘記密碼要加：重設 token 資料表、兩個頁面、`MyUserService` 的重設方法。
- **成本**：中。寄信本身小，但「忘記密碼」要處理 token 效期、單次使用、防列舉帳號。

#### 稽核紀錄畫面 ✅ 已於 0.9.42 實作

- 入口 `/audit-logs`，管理員專屬；支援時間區間／操作者／動作／成敗／關鍵字查詢、
  CSV 匯出、清除 365 天前與清空全部（兩者本身也會留下一筆稽核紀錄）。
- 詳見 [稽核紀錄 PRD](../prd/稽核紀錄-prd.md) 與
  [changelog](../changelog/2026-09-20-稽核紀錄查詢頁.md)。

#### TOTP 兩階段驗證接線

- **解決什麼**：`MyUser.TwoFactorEnabled`／`Secret` 欄位、`ITotpService`、6 個測試都在，
  但 **`ITotpService` 沒有任何地方注入** —— 等於沒有這個功能。
- **何時需要**：客戶有資安稽核要求時。
- **接在哪**：個人設定頁加 QR 註冊（需要一個 QR 產生套件）；
  `MyUserServiceLogin` 的登入流程加第二步；`AuthController` 的 API 登入同理。
- **成本**：中。核心演算法已經寫好且有測試，缺的是 UI 與流程。

#### 業務頁面的匯出與匯入

- **解決什麼**：目前只有三個診斷頁有匯出，專案／分類／團隊／使用者／角色都沒有。匯入完全沒有。
- **接在哪**：匯出比照 `ExceptionLogView.razor.cs:326`，
  位元組一律走 `TextDownloadPayload.Utf8WithBom`（有守門測試）。
  匯入要新增：檔案解析、逐列驗證、錯誤回報畫面、交易處理。
- **成本**：匯出小；**匯入不小** —— 難的不是讀檔，是「第 37 列錯了要怎麼告訴使用者」。
- ⚠️ **要受權限控管的話，得把 `export` 動作放回矩陣**（0.9.37 因為是死權限而下架，見 §6.6）。
  順序不能反：**先**有會檢查它的程式，**才**把它加回 `RolePermissionService.SupportedActions`
  與 `RoleViewView` 的動作欄，否則 `AdminOnlyPermissionTests` 會擋下來 —— 那正是它的用意。

### 10.3 維運與部署

#### 背景排程（Hangfire 或 Quartz.NET，或自己寫 `BackgroundService`）

- **解決什麼**：目前**沒有任何週期性工作**。唯一的 `IHostedService` 是例外寫入器。
  沒人清理日誌檔以外的東西、孤兒附件不會回收、Token 用量不會彙總。
- **何時需要**：第一次發現硬碟滿了的時候。
- **接在哪**：最輕的做法是加一個 `BackgroundService` ＋ `PeriodicTimer`，
  在 `AddApplicationServices` 註冊，就跟 `ExceptionLogWriter` 一樣。
  需要儀表板與重試才考慮 Hangfire（它會自帶資料表）。
- **成本**：自己寫很小；Hangfire 中（多一組資料表、一個管理頁面、與 SQLite 的相容性要測）。

#### `IFileStorage` 抽象 ＋ 雲端儲存

- **解決什麼**：三個類別各自 `Path.Combine` ＋ `FileStream`，換 S3／Azure Blob 要改三處。
- **何時需要**：要部署到容器、多機、或雲端的時候（本機路徑在那些環境沒有意義）。
- **接在哪**：抽 `IFileStorage`（`SaveAsync`／`OpenReadAsync`／`DeleteAsync`），
  三個現有使用者改成注入它：`ProjectService`、`ExceptionStackFileStore`、`TokenUsageRawStore`。
  比照 `ICacheService` 的 provider 切換寫法。
- **成本**：中。介面小，但要處理既有檔案的搬遷。

#### Dockerfile 與容器化

- **解決什麼**：目前綁 Windows ＋ `C:\temp\` 絕對路徑，CI 也跑 windows-latest。
- **何時需要**：要上 Kubernetes、或要跟其他容器一起部署時。
- **接在哪**：Dockerfile 只是第一步。真正要處理的是：
  所有絕對路徑改成容器內路徑並掛 volume（見上一項）、
  **SQLite 的資料庫檔要放在持久化 volume 上**、
  中文字型（PDF 用的已經內嵌，這點沒問題）。
- **成本**：中。`/health/live`、`/health/ready` 已經有了，這部分省下不少。

#### OpenTelemetry（追蹤與指標）

- **解決什麼**：目前的可觀測性是「NLog 檔案 ＋ 四個頁面」，
  沒有分散式追蹤、沒有可以畫圖的指標。
- **何時需要**：服務變多、要跨服務追一個請求的時候。
- **接在哪**：`Program.cs` 的服務註冊段加 tracing／metrics，pipeline 加 middleware。
  日誌已經有 `TraceId`（`${aspnet-TraceIdentifier}` 在 layout 裡），可以對接。
- **成本**：中。還要決定後端（Jaeger／Grafana／Application Insights）。

### 10.4 程式面的強化

#### FluentValidation

- **解決什麼**：複雜的跨欄位驗證。目前用 `DataAnnotations` ＋ `IValidatableObject`
  （例如 `ProjectAdapterModel.Validate()` 檢查結束日期不早於開始日期）。
- **何時需要**：驗證規則變複雜、或需要條件式驗證時。
- **接在哪**：與現有的 `DataAnnotations` 可以並存，逐模組導入。
  ⚠️ 但對話窗的驗證流程綁在 `EditContext.Validate()` 上，要確認整合方式。
- **成本**：中。**不建議在沒有痛點時導入** —— 兩套驗證機制並存本身就是負擔。

#### Polly（重試與斷路器）

- **解決什麼**：外部呼叫失敗時的重試、逾時、斷路。
- **何時需要**：接了會不穩的外部服務時。
- **接在哪**：掛在具名 `HttpClient` 上（目前只有一個 `AiChatCompletions`）。
  ⚠️ 注意：AI 呼叫**刻意不重試** —— 重試一次就多付一次錢，而且使用者已經在等了。
  要加重試前先想清楚這件事。
- **成本**：小。

#### 軟刪除

- **解決什麼**：目前全部是硬刪除，誤刪就沒了，沒有還原。
- **接在哪**：Entity 加 `IsDeleted`／`DeletedAt`，`BackendDBContext.OnModelCreating`
  加全域查詢篩選（`HasQueryFilter`），刪除改成標記。
- **成本**：中，而且**有連鎖效應**：唯一索引要考慮被軟刪的資料（同名重建會撞索引）、
  附件的實體檔要不要一起保留、統計數字要不要含已刪除。

#### Mapperly（取代 AutoMapper）

- **解決什麼**：AutoMapper 16.x 的商業授權問題（見 §3.6）。
- **何時需要**：不打算購買授權、而且要商用時。
- **接在哪**：`MyProject.Business/Models/AutoMapping.cs` 是唯一的 Profile，改寫集中在這一個檔。
  Mapperly 是原始碼產生器，編譯期就會告訴你哪些欄位沒對應到 —— 這其實是優點。
- **成本**：中。要重寫全部映射，但只有一個檔，而且改完編譯器會幫你抓漏。

#### Serilog（取代 NLog）

- **解決什麼**：結構化日誌 —— 每一筆是一個有欄位的物件，不是一行字串。
- **何時需要**：要把日誌送進 Seq／Elasticsearch 做查詢與儀表板時。
- **接在哪**：⚠️ **牽連很廣**。`/logs` 頁面靠解析固定格式的文字行運作
  （`LogQueryService` 的七欄位），換成結構化日誌等於那一頁要重寫。
  `/log-level-setting` 的執行期調整也要重做。
- **成本**：**大**。除非真的要接日誌平台，否則不划算。

### 10.5 資料層

#### 換成 PostgreSQL 或 SQL Server

- **解決什麼**：SQLite 的單寫入者限制、無法多機共用（§3.3）。
- **何時需要**：併發寫入變多、或要橫向擴充時。**這是本腳手架最可能需要換掉的一項。**
- **接在哪**：換 NuGet provider、改 `AddConfiguredDatabase` 的 `UseSqlite`、
  **整套 migration 重新產生**（provider 之間不通用）、
  檢查字串比較與 collation 行為（SQLite 的 `lower()` 只折疊 ASCII，別的資料庫不一樣，
  既有的唯一性測試可能會有不同結果）。
- **成本**：中到大。SQL Server 軌道曾經存在但 0.4.24 移除，可以參考當時的 changelog。

#### 全文檢索

- **解決什麼**：目前的搜尋是 `LIKE`，資料量大會慢。
- **接在哪**：SQLite 有 FTS5 擴充；換資料庫的話各家都有原生方案。
- **成本**：中。

#### 多租戶

- **解決什麼**：目前只有團隊分權，那是**單一租戶內的部門模型**，不是租戶隔離。
- **何時需要**：要做 SaaS 時。
- **接在哪**：⚠️ **這不是加功能，是改架構**。要決定隔離層級（共用資料庫加 TenantId／
  各自資料庫／各自 schema），然後每一個查詢都要帶租戶條件。
- **成本**：**大**。建議在專案開始時就決定，不要事後加。

### 10.6 真正的多語系

- **解決什麼**：§3.14 說的空殼。
- **接在哪**：把所有硬編中文抽到 `.resx`、加語言切換器與 Cookie provider
  （目前 `RequestCultureProviders` 刻意只留 `Accept-Language`）、
  處理 `MagicObjectHelper.預設角色` 這類**中文識別字**（那是資料庫裡的值，不只是顯示文字）。
- **成本**：**大**。介面文字很多，而且中文識別字散在程式與資料裡。

- `appsettings.json:43` 出貨的是 **`1qaz@WSX`** → 不相等，**通過檢查**
- `appsettings.Production.json:15` 出貨的是**空字串** → 也不相等，**也通過檢查**，
  而 `Program.cs:343` 沒有防呆，空字串會被雜湊 → **管理員變成空密碼**，
  而且每次重啟都重新套用

**所以要人工確認實際生效的值**：

```powershell
# 三個都不行：1qaz@WSX、support、空字串
$env:BootstrapSettings__SupportPassword
```

上線後再用 `support` 帳號登入一次，確認密碼確實是你設定的那一組。

#### 其餘四項由 `StartupSafetyValidator` 自動擋（沒過就啟動失敗，這是刻意的）

| 檢查 | 說明 |
|---|---|
| `JwtSettings:SigningKey` 不是開發預設值 | ⚠️ `appsettings.Production.json:12` 出貨是**空字串**，不覆寫就**啟動失敗** —— 那是 fail-fast 不是 bug。用 `JwtSettings__SigningKey` 環境變數設一組 ≥32 字元的隨機字串 |
| `Swagger:EnabledInProduction` 有被**明確設定** | true 或 false 都可以，就是不能沒寫 |
| 用 Redis 時連線字串不為空 | |
| 填了 AI 金鑰時 `Endpoint`（Azure）與 `Model` 不為空 | |

#### 它擋不到、你也要檢查的

- CORS 白名單（`Cors:AllowedOrigins`，空陣列 ＝ 完全不開放）
- **走反向代理時的 `ForwardedHeaders:KnownProxies`／`KnownNetworks`** ——
  這兩個鍵不在任何 appsettings 檔裡，要自己加。不設的話速率限制形同虛設
- 外部目錄路徑（六個，預設都在 `C:\temp\`）
- 附件副檔名白名單
- 是否要加 CSP（目前沒有）

### 11.2 環境

- Windows ＋ IIS 或 Kestrel。**沒有 Dockerfile**（§8 缺口 8、§9.3）。
- 走反向代理時**必須**設 `ForwardedHeaders:KnownProxies`／`KnownNetworks`，
  否則來源 IP 會全部變成代理伺服器，而且 `X-Forwarded-For` 可被偽造 —— 速率限制會失效。
- 健康檢查端點：`/health/live`（存活）、`/health/ready`（可收流量）。

### 11.3 已知限制要告知客戶

- **Web API 不做團隊列級過濾**（只有 Blazor 畫面有）。開放 API 給外部系統前務必說明。
- `DownloadPath` 底下的檔案，**任何已登入使用者**都讀得到（沒有逐筆權限檢查）。

## 12. 維運、監控與備份

### 12.1 每天看什麼

| 畫面 | 看什麼 |
|------|-------|
| `/system-health` | 健康百分比與紅黃綠燈。⚠️ 開這一頁會呼叫一次 LLM API（會計費）|
| `/system-exceptions` | 有沒有新的例外簽章、次數是否在爬 |
| `/database-usage` | 磁碟占用；「可回收」偏大時考慮 VACUUM |
| `/token-usage` | AI 花費 |

### 12.2 日誌

檔案在 `NLog:BasePath` 底下。`/logs` 可以查詢與匯出，`/log-level-setting` 可以在**執行期**調整等級。

⚠️ 執行期調整**只存在記憶體，重啟就回到 `nlog.config` 的預設**。要永久改請改設定檔。
⚠️ **沒有自動排程清理**（§8 缺口 6），日誌檔會一直長大，請自行安排排程。

### 12.3 備份

至少要備份三樣，**它們不在同一個地方**：

1. SQLite 資料庫檔（`ExternalFileSystem:DatabasePath`）—— 連同 `-wal`／`-shm` 一起
2. 專案附件（`ProjectFilePath`）
3. 例外堆疊檔與 Token 原始 JSON（`ExceptionPath`／`TokenUsagePath`）

只備份資料庫的話，附件與堆疊檔會遺失，而資料庫裡只剩指向它們的路徑。

### 12.4 改了東西要同步哪些文件

看 [維護規範 §2](../operations/維護規範.md) 的對照表。**每一次異動都要**：
`SystemVersion` Patch +1、新增一篇 changelog、同步索引。

### 13.3 完工驗收清單

**四道指令**（全部要綠）：

```
dotnet build   src/YourApp/YourApp.slnx        # 必須 0 warning（TreatWarningsAsErrors）
dotnet test    src/YourApp/YourApp.slnx
dotnet format  src/YourApp/YourApp.slnx --verify-no-changes
pwsh scripts/Test-DocsEncoding.ps1
```

⚠️ **這四道對「視覺是否正確」幾乎完全無感。** CSS 的失敗模式全是靜默的，
所以下面的人工檢查不是選配：

- [ ] 新增／修改的對話窗：接近滿版、欄位 2 欄、標題列與按鈕列固定、中間捲動
- [ ] 有改動的表格：滑過整列時，**固定的「操作」欄不可留下一塊白**
- [ ] 排序中的那一欄，底色要跟著整列走，不可還是灰的
- [ ] 側邊欄收合後，**兩層飛出**滑鼠平移不斷開；點完子項後飛出要收起來
- [ ] 捲動讓固定欄位於頂欄下方，再開右上角使用者選單 —— 不可被蓋住
- [ ] 開啟 `prefers-reduced-motion` 後無彈跳，顏色回饋仍在
- [ ] 四個寬度：640 / 768 / 1024 / 1800px

**文件同步**（`CLAUDE.md` 的硬性要求）：

- [ ] `SystemVersion` Patch +1
- [ ] 新增一篇 `docs/changelog/`，UTF-8 **含 BOM**
- [ ] 依 [維護規範 §2](../operations/維護規範.md) 對照表更新受影響的文件
- [ ] 新增／移除文件時，**三處索引**缺一不可
- [ ] **不要自動 commit**

### 13.4 為什麼慣例這麼多

幾乎每一條都對應一次實際踩過的坑，而且那些坑的共同特徵是
**不會壞、不會紅、CI 全綠，只有實際點開那一頁才看得出來**：

- 對話窗少寫 `MaskClosable="false"` → 誤點遮罩，整份輸入無聲蒸發
- 用 `EditContext.IsModified()` → **恆為 false**，未儲存提示永遠不跳
- 匯出用 `new UTF8Encoding(true)` → 沒有 BOM，Excel 開啟整片亂碼
- 列底色寫在 `tr` 而非 `> td` → 固定欄留白塊
- 色票寫死在檢視裡 → 半年後換品牌色翻五個檔都翻不完

守門測試就是把這些坑變成「會紅」。**看到守門測試擋你，先讀它的失敗訊息** ——
那裡通常寫著當初為什麼要加這一條。
